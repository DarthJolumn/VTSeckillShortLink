# 高并发秒杀全链路改造方案

## 一、订单ID：雪花算法

### 为什么是前置条件

分库分表后订单ID必须满足：
- 全局唯一（分表后不冲突）
- 趋势递增（避免B+树索引频繁分裂）
- 可解析出时间/业务信息

### 改良雪花算法

```
41bit 毫秒时间戳 + 5bit 数据中心 + 5bit 机器ID + 12bit 序列号
```

**注意**：不用数据库自增（分表后无法全局唯一），不用UUID（无序导致随机IO）。

## 二、分库分表

### 分片键选择

| 分片键 | 优点 | 缺点 | 适用场景 |
|--------|------|------|----------|
| `user_id` | 同一用户订单在同一分片，C端查询快 | 热点用户导致单分片瓶颈 | C端订单列表为主 |
| `order_id` | 写入均匀分散，无热点 | 按用户查需扫描所有分片 | 秒杀写入优先 ✅ |
| `activity_id` | 同一活动数据集中，便于统计 | 爆款活动单分片被打爆 | 后台运营分析为主 |

### 推荐方案

- **主表**：按 `order_id` 取模分64张表（2的幂次方便扩容）
- **辅助表/ES索引**：`user_id → order_id` 映射，解决C端查询
- **分表数量**：32/64/128，方便一致性哈希或翻倍扩容

## 三、核心联动：分表后参数重新校准

### 动态对齐公式

```
目标吞吐量 = 业务峰值QPS × 1.5（安全系数）
SEM大小 = ceil(目标吞吐量 × DB写入P99)
max-poll-records = SEM大小
max-poll-interval-ms = SEM × DB写入P99 × 5
```

### 实操步骤

1. 分表上线后，压测获取新的 DB写入 P99
2. 计算新参数：
   - 假设峰值 3000 QPS，P99 从 50ms 降到 20ms
   - `SEM = ceil(3000 × 0.02) = 60`
   - `max-poll-records = 60`
   - `max-poll-interval-ms = 60 × 20ms × 5 = 6s`（仍设5min留余量）

### ⚠️ 重要提醒

分表后**必须重新压测**！ShardingSphere 等中间件的SQL解析、路由、结果合并有开销，P99可能不降反升。一切参数以压测数据为准。

---

## 四、面试话术

> 我们的优化是全链路的。首先在ID生成上，采用改良雪花算法替代自增ID，既保证全局唯一又维持趋势递增，避免分表后索引分裂。其次在存储层，订单主表按 order_id 取模分64张表，写入压力均匀分散；用户维度查询通过映射表解决。最关键的是，分表后我们重新校准了消费端的背压参数。因为分表改变了DB写入P99，我们通过压测拿到新延迟值，再用"目标QPS × P99"公式动态调整 Semaphore 大小，并将 max-poll-records 与之严格对齐。这样既保证了消费速率始终匹配DB的真实处理能力，又避免了拉取过多消息造成的内存浪费。整个链路从ID生成、存储分片到消费背压是一体化设计的。
