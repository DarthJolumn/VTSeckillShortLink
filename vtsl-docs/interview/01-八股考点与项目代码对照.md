## JUC / 并发（重点，项目素材最丰富）

### 🔥🔥🔥 ConcurrentHashMap
**项目用法（4 处，选 2 个讲）**：
| 位置 | 场景 | 为什么用 |
|---|---|---|
| `vtsl-common/.../util/HmacUtil.java:15-16` | 网关签名密钥**多版本轮换**（`SECRETS` / `PREV_SECRETS`） | 读多写少，轮换时写入，无锁读 |
| `vtsl-websocket/.../manager/WsSessionManager.java:18-42` | 直播会话**三级索引**（sessions / roomSessions / userSessions / deviceSessions），并发连接/断开/踢人 | `computeIfAbsent` + `newKeySet()` 原子建桶，无 check-then-act 竞态 |
| `vtsl-seckill/.../consumer/SeckillOrderConsumer.java:29,101` | Kafka 消息重试计数 `ConcurrentHashMap<String, AtomicInteger>` | 每条消息独立计数，并发消费互不干扰 |
| `vtsl-user/.../service/UserService.java:50-51` | **Token 并发刷新合并** `ConcurrentHashMap<String, CompletableFuture<LoginResponse>>` | 同一时刻多个 401 只发一个 refresh，后续请求复用同一 future（**面试亮点**） |

**话术**：JDK8 起 CHM = CAS + synchronized 锁桶（链表头节点），读无锁；`computeIfAbsent` 提供原子"有则取、无则建"；比 `Hashtable`（全表锁）粒度细。项目里 4 个场景全是"并发读写共享索引"。

### 🔥🔥🔥 synchronized vs ReentrantLock
**项目用法**：
- `vtsl-common/.../util/SnowflakeIdGenerator.java:23` — `ReentrantLock lock` 保护雪花 ID 毫秒回拨 + 序列自增
- 类注释（`:10`）：JDK 25 **JEP 491 已修复 synchronized 在虚拟线程下的 pinning**，ReentrantLock 保留为最佳实践

**话术**：项目选 ReentrantLock 而非 synchronized 的三个理由——① 可中断（`lockInterruptibly`）② 可超时（`tryLock(timeout)`）③ 公平锁可选；AQS 实现。升级 JDK 25 后能展开讲 JEP 491：synchronized 在 VT 上不再 pinning 载体线程，但 RL 语义更丰富所以保留。

### 🔥🔥🔥 线程池（7 参数 / 流程 / 拒绝策略）
**项目用法**：`vtsl-shortlink-api/.../config/AsyncConfig.java:16-29`
```
ThreadPoolTaskExecutor：core=8, max=32, queue=2000, 前缀 shortly-async-
拒绝策略 = CallerRunsPolicy
```
用于 `AnalyticsAsyncService.record()` 的 `@Async("shortlyAsyncExecutor")` 点击统计异步落库。

**话术**：7 参数背全（core/max/keepAlive/queue/threadFactory/handler）；工作流程：core 满 → 进队列 → 队列满 → 扩到 max → 再满 → 拒绝；**为什么选 CallerRunsPolicy**：统计链路可降速——提交线程自己执行，天然背压，不丢数据（面试加分点：拒绝策略不是越"激进"越好，要配合业务容忍度）。

### 🔥🔥 CAS / 乐观锁 / AQS
**项目用法**：
- 乐观锁：`vtsl-seckill/.../entity/SeckillActivity.java:26`、`SeckillOrder.java:43` — `@Version` 字段，JPA 自动生成 `UPDATE ... SET version=version+1 WHERE version=?`，用于取消订单防并发（DB 先 → Redis 后的一致性基础）
- CAS 条件更新：`vtsl-shortlink-keygenerator/.../service/KeyService.java` — `updateFirst(where key=? AND status=available)` 防脏 key 重复发放
- AQS 三件套：Semaphore（见下）+ ReentrantLock（雪花 ID）+ 无自定义同步器

**话术**：乐观锁适用"读多写少 + 冲突可重试"；`@Version` 让 JPA 生成 CAS 式 UPDATE；KGS 的"条件更新"是手写 CAS——两个 CAS 场景可以对比讲。

### 🔥🔥 ThreadLocal → 项目用 ScopedValue（升级亮点）
**项目用法**：`vtsl-common/.../context/UserContext.java:5-7` + `filter/UserContextFilter.java:45`
```java
ScopedValue<Long> USER_ID = ScopedValue.newInstance();
ScopedValue.where(USER_ID, userId).run(...)   // 绑定作用域 = 整个请求
```
用户上下文（userId/role/deviceId）跨 Filter → Interceptor → Controller 传递。

**话术（面试高级答法）**：项目**刻意不用 ThreadLocal**，用 JDK 21+ 的 ScopedValue——① 虚拟线程下 ThreadLocal 曾导致 pinning（JEP 491 修复）② 线程池复用会让 ThreadLocal 串上下文（必须 finally remove，易漏 → 内存泄漏：弱引用 key + 强引用 value）③ ScopedValue 不可变 + 结构化并发，值随 `run()` 作用域自动清理。**主动抛出 ThreadLocal 内存泄漏知识点**（key 弱引用被回收、value 强引用链不释放），然后说"所以新项目直接上了 ScopedValue"。

### 🔥🔥 AQS 之 Semaphore（背压设计，独特点）
**项目用法（2 处）**：
- `SeckillOrderConsumer.java:30,46` — `Semaphore(30)` 对齐 HikariCP 池大小：信号量耗尽 → 阻塞 Kafka listener 线程 → poll 暂停 → **Broker 感知消费慢自动降速**
- `WsPushServiceImpl.java:21` — `Semaphore(200)` 推送限流

**话术**：这是"消费端背压"而不是"丢弃/堆积"——从根源杜绝虚拟线程无限堆积导致连接耗尽。面试官问"Kafka 消费不过来怎么办"，标准答案之外给这个项目解法。

### 🔥 线程创建方式（虚拟线程，项目最大亮点）
**项目用法**：
- `spring.threads.virtual.enabled: true`（所有模块 yml）— HTTP 请求跑 VT
- `Thread.startVirtualThread(...)`：`SeckillOrderConsumer.java:58`、`TimeoutCancelScheduler.java:54`、`LiveWebSocket.java:184`、`WsPushServiceImpl.java:48,90`

**话术**：4 种线程创建方式（Thread/Runnable/ExecutorService/VT）→ 项目用 VT 承载 IO 密集（Redis/Kafka/DB 调用都在 IO 上 park，VT 几乎零成本）；对比平台线程 1MB 栈 vs VT 几 KB；压测数据见 `vtsl-docs/performance/01-vt-vs-platform.md`。

## JVM

### 🔥🔥🔥 JVM 内存模型 + GC 算法
**项目用法**：无代码，有压测 `vtsl-docs/performance/02-g1-vs-zgc.md`
**话术**：项目 JVM 用 **ZGC**（`-XX:+UseZGC`）；同口径 450 并发对比：G1 GC 耗时 856ms → ZGC 3ms，P99 降 32%。展开：ZGC 染色指针 + 读屏障 + 并发整理，STW 与堆大小无关；G1 是分代 + Region + 并发标记，默认停顿目标 200ms。

### 🔥🔥🔥 类加载 + 双亲委派
**项目用法**：无自定义 ClassLoader。可讲**踩坑**：Boot 4.1 配置迁移（`spring.data.mongodb.*` → `spring.mongodb.*`）导致属性不绑定——本质是自动配置/配置绑定链路（`AutoConfiguration.imports` → `@ConfigurationProperties`）。另外 Dubbo 用 SPI 加载扩展。
**话术**：诚实说"项目没写类加载器，但理解双亲委派——为什么 JDK 类不能被应用覆盖（核心类安全）；打破方式：SPI（JDBC 驱动，Thread.contextClassLoader）、Tomcat 隔离、OSGi。项目里 Spring Boot 自动配置就是 SPI 思想的体现，我还踩过配置前缀不匹配的坑"。

## 集合

### 🔥 ArrayList vs HashMap
**项目用法**：`ShortLinkCache` 用 `HashMap` 组装 L2 字段；`List.of()` / `stream().toList()` 遍布各 Service。
**话术**：HashMap get/put 流程（hash → 桶 → 链表 → 红黑树）、扩容 2 倍（16→32 重 hash）、树化阈值 8/退化 6、负载因子 0.75（时空权衡）；ArrayList 动态扩容 1.5 倍（`grow` → 右移 1 位 + 原容量）；项目里集合用于组装返回 DTO，无并发场景用 HashMap 足够。

## MySQL

### 🔥🔥 索引底层（B+树）
**项目用法（真实索引设计）**：
- `vtsl-shortlink-api/.../resources/schema.sql` — `UNIQUE INDEX uk_short_key (short_key)`、`idx_user_id`、`idx_deleted_at`；`t_analytics` 的 `idx_url_id`、`idx_clicked_at`
- 秒杀订单 `order_no` 唯一索引 → `DuplicateKeyException` 幂等兜底（`SeckillOrderConsumer.java:85-87`）

**话术**：唯一索引 = 数据库层防重（短码防重复、订单幂等）；普通索引 = 查询加速（按 userId 查我的短链、按 urlId 查统计）。B+ 树三层可存千万级（16KB 页 × 约 1000 指针/层），叶子链表支撑范围扫描；对比 B 树（非叶子也存数据）、红黑树（深度大，磁盘 IO 多）。

### 🔥🔥 ACID / 事务隔离
**项目用法**：
- `@Transactional`：`SeckillService.java:42,66,126,147`（创建活动/上下架/创建订单/取消）、`UrlService.java:54,99,122`（创建/更新/删除短链）、`UserService.java` 注册登录
- **秒杀事务纪律**（`VtslSeckillApplication.java:24-27` javadoc）：抢购链路**全程无 @Transactional**（Caffeine → Redis Lua → Kafka，无 DB 写）；只有落库/取消/退款才开事务

**话术**：@Transactional 默认传播 REQUIRED；项目最关键的取舍——**抢购热路径不加事务**（事务 = 连接占用 + 锁），异步落库才开；取消订单"DB 先（@Version CAS）→ Redis 后"，DB 失败事务回滚、Redis 由对账补偿（`ReconciliationScheduler`），这是分布式事务的一致性方案。可重复读是 MySQL 默认隔离级别，靠 MVCC（undo log 快照）。

### 🔥🔥 MyBatis（#{} vs ${}）
**项目用法**：`vtsl-user` 用 **MyBatis-Plus**（`mybatis-plus-spring-boot4-starter`），其余新模块用 **JPA**（`spring-boot-starter-data-jpa`）——两种 ORM 并存是刻意对比点。
**话术**：`#{}` → PreparedStatement 占位符（预编译防 SQL 注入）；`${}` → 字符串拼接（仅限表名/排序字段等无法占位的场景，白名单校验）。项目里 user 模块保留 MP（老代码迁移成本），新模块统一 JPA——能讲"技术选型不是越新越好，要看团队/迁移成本"。

## Redis

### 🔥🔥🔥 缓存穿透 / 击穿 / 雪崩（项目三件套齐全）
| 问题 | 项目解法 | 位置 |
|---|---|---|
| **穿透**（查不存在） | 短链空值缓存（不存在的短码也缓存 30s） | `ShortLinkCache.java`（`isWrongType`/空值分支） |
| **击穿**（热点失效） | L1 Caffeine + L2 Redis + **DCL 防击穿**（回源加锁） | `ShortLinkCache.java`；秒杀 `ActivityCacheService` 用 Caffeine `LoadingCache`：`refreshAfterWrite(5s)` **过期返回旧值 + 后台异步刷新**（比互斥锁更优雅） |
| **雪崩**（批量失效） | TTL **随机抖动 ±10%**（`ThreadLocalRandom`） | `ShortLinkCache.java:157`（`TTL_JITTER`） |

**话术**：三问三答背熟；强调秒杀的 `refreshAfterWrite`（Caffeine 异步刷新 = 缓存击穿的最优解之一：请求拿旧值不等待，后台刷新新值）和 TTL 抖动（规避同时过期）。

### 🔥 Redis 数据类型（每种都有真实场景）
| 类型 | 项目场景 | 位置 |
|---|---|---|
| String | 库存 `stock:{id}`、一人一单 `ordered:`、幂等 `setIfAbsent`、网关 Nonce 防重放、**分布式锁** `setIfAbsent(lock:reconciliation, TTL 300s)` | `StockService.java:39,54`、`IdempotencyService.java:30`、`SignVerifyGlobalFilter.java:68`、`ReconciliationScheduler.java:119-120` |
| List | **KGS 预生成短码队列**（LPUSH/RPOP 原子发号） | `KeyGenerator.java:43`、`KeyService.java` |
| ZSet | 排行榜 `incrementScore / reverseRangeWithScores / reverseRank`（TopN、个人排名） | `LeaderboardServiceImpl.java:37,46,66,69` |
| Hash | 短链 L2 多字段（url/productId/expireAt/clickCount/status）`opsForHash().get` | `ShortLinkCache.java`（`HASH_PREFIX`） |
| Pub/Sub | **秒杀结果推送** `convertAndSend("ws:push:seckill-result")` → WS 广播 | `SeckillOrderConsumer.java:90` |
| Lua | `deduct_stock.lua` / `refund_stock.lua` 原子扣减/回补 | `StockService.java:28-34,54` |

**话术**：八大数据类型不用背八股，直接报项目场景；每个都能展开（如 ZSet 跳表 + 分数排序、Lua 原子性 vs 事务）。

### 补充：Redis 分布式锁（可主动提）
`ReconciliationScheduler` 对账任务多实例互斥：`SETNX lock:... TTL 300s`。
**话术**：简易版分布式锁（SETNX + TTL）；与 Redisson 对比——可重入、看门狗续期、红锁争议；项目选简易版因为对账任务"重复执行无害"（幂等），容忍极端情况下的锁过期。

## Spring

### 🔥 Bean 生命周期 / IOC / AOP
**项目用法**：
- `@PostConstruct`：`KeyGenerator.java:32`（打印 Mongo 连接库探针）、`ActivityBloomFilter.java:29`（布隆过滤器重建）
- `@PreDestroy`：`GrpcClientConfig.java:38`（`channel.shutdown()` 优雅关闭 gRPC）、`GrpcServerConfig.java:40`
- AOP 声明式：`@Transactional`、`@Async`（`AnalyticsAsyncService.java:33`）

**话术**：生命周期背一遍（实例化 → 属性填充 → Aware → BeanPostProcessor → init → 使用 → destroy）；AOP 讲 JDK 动态代理 vs CGLIB——`@Transactional` 失效三场景（同类自调用、非 public、异常被吞），项目里 SeckillService 内部方法调用是真实风险点，所以事务都开在 public 入口。

### 🔥 异常体系
**项目用法**：`BizException`（继承 RuntimeException 的业务异常，code+message）+ `GlobalExceptionHandler`（`@RestControllerAdvice` 统一转 `Result<T>`）；api 模块另有 `ApiGlobalExceptionHandler`。
**话术**：Error（不可恢复，OOM/StackOverflow）vs Exception（可处理）；unchecked（RuntimeException）业务异常不强制 try-catch，由全局处理器兜底——项目所有接口返回 `Result{code,message,data}`，业务错误码（1010 重复参与、1009 库存不足）可面试展开。

### 偶尔：事务传播行为
**项目用法**：全项目默认 `REQUIRED`，无特殊传播。
**话术**：背 REQUIRED/REQUIRES_NEW/NESTED/SUPPORTS 区别；说"项目主要用默认 REQUIRED，唯一要注意的是 Kafka Consumer 落库方法必须开事务且 MANUAL ACK（事务成功才 ack）"——把事务和消息确认绑一起讲。

## 一句话总结（面试开头可用）

> 这个项目把八股全串起来了：**ConcurrentHashMap** 管会话/重试/刷新合并，**Semaphore** 做 Kafka 背压，**ReentrantLock** 保护雪花 ID，**ScopedValue** 替代 ThreadLocal 传用户上下文，**虚拟线程**承载全链路 IO；**乐观锁 @Version** + **Lua** 双 CAS 防超卖，**唯一索引**做幂等，**Caffeine + Redis 双级缓存 + TTL 抖动**防穿透击穿雪崩，**6 种 Redis 类型**各有场景，**@Transactional + 对账调度器**解决分布式一致性。
