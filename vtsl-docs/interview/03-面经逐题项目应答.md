## 一、Java 基础

### 1. ArrayList vs LinkedList
**项目会问**："你项目里 List 用得多么？什么时候用 ArrayList？"
**答**：
- 项目里 List 几乎全是"查询结果组装/遍历"，如 `urlRepository.findByUserId...stream().toList()`（`UrlService.java:83-87`）、订单列表 `findByUserIdOrderByCreatedAtDesc`
- 全是**顺序访问 + 末尾追加**场景 → ArrayList（随机访问 O(1)、内存连续、CPU 缓存友好）
- LinkedList 的唯一优势（头部/中间插入 O(1)）在项目里没有需求；且 LinkedList 每个节点有额外指针开销
- 加分：Java 9+ 的 `List.of()` 返回不可变列表、`stream().toList()` 不可变——**面试官问"你注意过返回的 List 能不能改吗"** → "我们返回 `toList()` 是不可变的，防外部误改"

### 2. ConcurrentModificationException
**项目会问**："多线程遍历集合时怎么防 ConcurrentModificationException？"
**答（真实场景）**：
- 直播间广播/踢人要**遍历在线 session 集合**（`WsSessionManager.java:81,113` 的 `room.values()` / `sessions.values()`），连接和断开是高频并发操作
- 方案：session 容器用 **ConcurrentHashMap**——迭代器是**弱一致性**的（遍历时看到的是某个时间点的快照视图，不抛 CME）
- 对比：普通 HashMap 在遍历时被其他线程 put/remove → `modCount` 变化 → fail-fast 抛 CME
- 补充原理：CHM 弱一致性来自"分段遍历不检查 modCount + 迭代基于链表节点游标"；`computeIfAbsent` 原子建桶避免"先查后放"竞态
- 一句话："项目里所有会被并发读写的集合（会话索引/重试计数/刷新合并）都选 CHM，既无锁读又规避 CME"

### 3. synchronized vs ReentrantLock
**项目会问**："项目里哪里用了锁？为什么选 ReentrantLock？"
**答**：`SnowflakeIdGenerator.java:23` 用 `ReentrantLock` 保护雪花 ID 的毫秒回拨 + 序列自增。三个理由：
1. 可中断/可超时（`tryLock`）——生成器在极端时钟回拨时能优雅降级而不是死等
2. 公平锁可选
3. 项目 JDK 25：**JEP 491 已修复 synchronized 在虚拟线程上的 pinning**，但 RL 语义更丰富所以保留
- 面试延伸：synchronized 是 JVM 内置（monitorenter/exit，锁升级：无锁→偏向→轻量级 CAS 自旋→重量级），Java 8 后性能与 RL 差异缩小；RL 是 AQS 实现，需 try-finally 释放
- **可以主动提**：项目真正的高频"锁"其实在 Redis（分布式锁 `lock:reconciliation:cancelled`）和数据库（`@Version` 乐观锁）——JVM 锁只用在雪花 ID 这种单机临界区

## 二、并发编程

### 4. API 响应慢的优化方案（项目素材最强的题）
**项目会问**："你项目接口响应慢过吗？怎么定位、怎么优化？"
**答（真实链路：秒杀下单 3342ms → P99 92ms）**：
1. **定位**：SkyWalking 链路追踪发现尾延迟异常，最长 **3342ms**（`vtsl-docs/performance/03-async-shave.md`）
2. **四阶段控制变量法**定位根因：
   | 阶段 | 变更 | P99 | 结论 |
   |---|---|---|---|
   | 原状 | Kafka 同步 + 远端 Redis | 3342ms max | 慢 |
   | 仅 Kafka 异步 | `kafkaTemplate.send(msg)` 替代 `send().get(3s)` | 87ms | **Kafka 同步阻塞是主因** |
   | 组合优化 | 异步 Kafka + 本地 Redis | 305ms max | 跨 VM 网络是尾延迟次因 |
3. **优化手段对应面经三点**：
   - 超时控制：gRPC 客户端 `withDeadlineAfter(2s)`（`KeyServiceClient.java:26`）；GeoIpService 外部调用 timeout 2s
   - 异步化：`@Async("shortlyAsyncExecutor")`（AnalyticsAsyncService）、Kafka 异步削峰
   - 缓存：Caffeine L1(3s) + Redis L2(24h) 拦截热点
4. 数据结论：异步削峰后 300 并发 TPS 1513 / P99 92ms（AGENTS.md 记录）

### 5. 线程池参数设计
**项目会问**："你的线程池参数怎么定的？"
**答（不背公式，讲业务推导）**：
- `AsyncConfig.java:16-29`：core=8 / max=32 / queue=2000 / `CallerRunsPolicy`
- **为什么不是"CPU 核数 × 2"**：这是 IO 密集型线程池（点击统计要查 DB + 调外部 GeoIP，大部分时间在 IO 等待），线程数由**并发 IO 数**决定而不是核数；8/32 的经验值是"给足 IO 并发度，但用**有界队列 2000 + CallerRunsPolicy** 兜底"——队列满时提交线程自己执行（降速不丢数据）
- **背压设计**（更高级）：Kafka 消费端 `Semaphore(30)` 对齐 HikariCP 池（`SeckillOrderConsumer.java:30,46`）——信号量耗尽 → 阻塞 poll → **Broker 降速**，从根源杜绝线程堆积，而不是靠队列无限缓冲
- 面试官若追问"CPU 密集怎么配"：核心数 + 1，公式 `Ncpu × (1 + wait/compute)`

## 三、数据库

### 6. 索引设计（面经的"会议室表"→ 项目类比）
**项目会问**："你的订单表/短链表怎么建索引？为什么？"
**答（项目真实索引）**：
| 表 | 索引 | 设计理由 |
|---|---|---|
| `t_seckill_order` | `order_no` **唯一索引** | 幂等兜底：Kafka 重复消费时 `DuplicateKeyException`（`SeckillOrderConsumer.java:85-87`） |
| `t_url` | `uk_short_key` 唯一 + `idx_user_id` | 短码防重（等值）+ 我的短链列表（等值 userId） |
| `t_analytics` | `idx_url_id` + `idx_clicked_at` | urlId 等值 + 点击时间范围统计 |
- **面经"room_id → start_time → end_time"复合索引的最左前缀原理**可以套：如果订单要"按 userId + 时间范围"查，建 `(user_id, created_at)` 复合索引（等值在前、范围在后），避免回表；项目里 `idx_user_id` 是单列因为查询模式简单
- 加分：软删除表（`t_url.deleted_at`）加了 `idx_deleted_at`，因为"查未删除"是过滤高频条件

### 7. 时间范围查询优化
**项目会问**："按时间范围扫数据怎么防止拖垮 DB？"
**答（真实场景：超时取消 + 对账）**：
- `TimeoutCancelScheduler.java:50-51`：`findByStatusAndCreatedAtBeforeOrderByCreatedAtAsc(0, deadline, PageRequest.of(0, batchSize))`——**分页 500 批量扫描**（这是审计 P1-3 修复：原来无 LIMIT 全表加载会 OOM）
- `ReconciliationScheduler` 同理：`findByStatusAndCancelledAtAfter(...)` 60 分钟窗口 + 分页
- 范围查询走 `created_at` 索引；窗口参数可配（`reconciliation-window-minutes`）
- 面经里"无 room_id 时复合索引失效"的答法可平移：项目里如果"全量按状态扫"（status=2），单列 status 索引 + 时间过滤，必要时用 ES——项目目前量级用"分批扫 + 定时"足够

### 8. 事务隔离级别
**项目会问**："你项目事务隔离级别是什么？秒杀超卖怎么防？"
**答**：
- MySQL 默认 **可重复读（RR）**；项目未改，靠两点解决并发：
  1. **秒杀扣库存不走 DB**——Redis Lua 原子（`deduct_stock.lua`），根本不依赖 DB 事务隔离
  2. DB 层用**乐观锁 `@Version`**（`SeckillActivity.java:26`、`SeckillOrder.java:43`）——取消订单 CAS 式 UPDATE，冲突即重试/放弃
- 面试延伸：RR 解决不可重复读靠 **MVCC**（undo log 快照），幻读靠间隙锁（next-key lock）；项目"DB 先 → Redis 后"的取消订单用 `@Version` 防并发回补——把隔离级别和乐观锁串成一条链路讲

### 10. 大 value 优化
**项目会问**："Redis 里 value 越来越大怎么办？"
**答（项目对应手段）**：
1. **字段级更新避免整串覆盖**：短链点击计数用 `opsForHash().increment(FIELD_CLICK_COUNT, 1)`（`ShortLinkCache.java:121`）——Hash 单字段自增，不会反复读写大字符串
2. **数据分层，Redis 只放热数据**：点击统计走 `Kafka → StatisticsConsumer → MySQL 按天聚合`（`StatisticsConsumer.java:30-32`：`LocalDate` + `incrementClickCount`）——Redis 不积累历史，过期/聚合后落库
3. **有界队列**：KGS 队列只在 getKey 低于阈值时补货（`KeyService.java:36-39`），无人取号不会无限膨胀；List 上限由业务水位控制
4. 面试延伸：超大 value（>1MB）拆分/压缩（面经的"截断历史对话"思路）——项目用"聚合落库"替代，更符合业务

## 五、框架与工具

### 11. Spring Boot 自动装配原理
**项目会问**："你踩过自动装配/组件扫描的坑吗？"（送分题，项目有真实事故）
**答**：
- 原理：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（Boot 2.7+/3，旧版 `spring.factories`）声明候选配置 → `@ConditionalOnClass/@ConditionalOnMissingBean` 过滤 → 注册 Bean
- **项目事故 1（组件扫描）**：新版短链 api 模块 `@SpringBootApplication` 没写 `scanBasePackages`，默认只扫自己包 → `com.jolumn.vtslcommon.filter.UserContextFilter`（`@Component`）不注册 → `UserContext.currentUserId()` 恒为 null → **所有需登录接口 401**。修复：显式补扫描（`VtslShortlinkApiApplication.java:21-30`）——证明"自动装配不是黑盒，Bean 不生效要会查扫描范围"
- **项目事故 2（配置绑定迁移）**：Boot 4.1 把 mongo 连接属性前缀 `spring.data.mongodb.*` 改到 `spring.mongodb.*`（deprecated 不生效）→ KGS 数据落到默认 `test` 库。反编译 `@ConfigurationProperties(value="spring.mongodb")` 定位——**会看 jar 字节码/配置元数据排障**
- 这两件事合起来就是"自动装配 + 配置绑定 + 排障方法论"的完整故事

### 13. HTTPS 加密流程
**项目会问**："你的接口怎么保证安全？"（项目没有 HTTPS，但 gateway 有应用层签名——**更好的答案**）
**答**：
- HTTPS 解决"传输层"：TLS 握手（证书验证 → 客户端生成预主密钥用服务端公钥加密 → 双方派生会话密钥 → 对称加密通信）
- **项目在应用层补了一层**（gateway `SignVerifyGlobalFilter.java:49-60`）：`X-Timestamp + X-Nonce + X-Sign`（HMAC-SHA256）三头校验——**防篡改（HMAC）+ 防重放（Nonce 60s TTL + 时间窗 ±5min）**，密钥多版本轮换（`HmacUtil` CHM）
- 分层讲：HTTPS 防窃听，应用签名防"请求被改/被重放"（HTTPS 管不了已登录用户伪造请求）——两个层次都有实践

### 14. JVM 内存区域
**项目会问**："你 JVM 怎么调优的？"
**答（结合项目压测）**：
- 区域划分：线程私有（程序计数器/虚拟机栈/本地方法栈）+ 共享（堆：新生代 Eden/S0/S1 + 老年代；方法区 JDK8 后 = 元空间，本地内存）
- **项目实战**：G1 → **ZGC** 对比压测（`vtsl-docs/performance/02-g1-vs-zgc.md`）：450 并发，G1 GC 耗时 856ms → ZGC 3ms，P99 降 32%
- 原理展开：ZGC 染色指针 + 读屏障 + 并发整理，STW 与堆大小无关；元空间默认无上限（-XX:MaxMetaspaceSize 可限）——项目类不多，重点是 GC 停顿优化
