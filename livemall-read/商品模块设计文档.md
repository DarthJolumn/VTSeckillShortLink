# LiveMall 商品模块设计文档（V1.0 秒杀服务内嵌版）

## 一、设计背景与边界

### 1.1 当前阶段

商品服务暂不拆分微服务，作为 `livemall-seckill` 服务内的独立包 `product` 存在。

### 1.2 核心目标

- 支撑**商家发布商品** + **秒杀活动关联商品**
- 解决测试期单表数据增长过快问题（16 表分片）
- 为未来商品服务独立拆分预留无损迁移路径

### 1.3 非目标

- ❌ 复杂 SKU/SPU 模型
- ❌ B 端复杂检索（后续接 ES）
- ❌ 跨域事务
- ❌ 商品图片上传（URL 字段可为空）

### 1.4 演进承诺

包结构、ID 策略、分片键均按独立微服务标准设计，未来拆分时**零代码重构**。

## 二、数据库设计

### 2.1 数据库名称

`livemall_product_1`（独立数据库，与秒杀库 `livemall` 分离）

### 2.2 分表策略

| 维度 | 决策 |
|------|------|
| 物理拓扑 | 单库 16 张表：`t_product_0` ~ `t_product_15` |
| 分片键 | `id`（雪花 ID） |
| 分片算法 | `HASH_MOD(id, 16)` |

**为什么是 16 表？**
- 测试期 10w 数据已感压力，按日增 5w 商品估算，16 表单表 ≤ 3w 行，远低于 MySQL 单表 2000w 上限
- 16 是 2 的幂次，未来升级 4 库 × 4 表时仅需改配置，数据零迁移
- 与订单表 16 表对齐，运维认知一致

### 2.3 建表 DDL（分表就绪版）

```sql
CREATE DATABASE IF NOT EXISTS livemall_product_1 
DEFAULT CHARACTER SET utf8mb4 
DEFAULT COLLATE utf8mb4_general_ci;

USE livemall_product_1;

-- 分表模板（实际通过 ShardingSphere 路由，手动建表脚本见下方）
CREATE TABLE IF NOT EXISTS t_product_0 (
    id              BIGINT NOT NULL COMMENT '雪花 ID，全局唯一主键',
    user_id         BIGINT NOT NULL COMMENT '发布者用户 ID（关联用户服务）',
    title           VARCHAR(200) NOT NULL COMMENT '商品标题',
    subtitle        VARCHAR(500) DEFAULT NULL COMMENT '副标题/卖点',
    main_image      VARCHAR(500) DEFAULT NULL COMMENT '主图 URL（可为空）',
    detail_images   VARCHAR(2000) DEFAULT NULL COMMENT '详情图 URL（JSON 数组，可为空）',
    price           DECIMAL(10,2) NOT NULL COMMENT '原价',
    stock           INT NOT NULL DEFAULT 0 COMMENT '总库存',
    status          TINYINT NOT NULL DEFAULT 0 COMMENT '0:下架 1:上架 2:审核中',
    category_id     BIGINT DEFAULT NULL COMMENT '类目 ID（预留）',
    is_deleted      TINYINT NOT NULL DEFAULT 0 COMMENT '0:正常 1:已删除（软删除）',
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    INDEX idx_user_status (user_id, status, is_deleted),
    INDEX idx_status_created (status, is_deleted, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品表 0（分表就绪版）';

-- t_product_1 ~ t_product_15 结构完全相同，仅表名后缀不同
-- 完整建表脚本见：docker/product-init-tables.sql
```

### 2.4 关键设计决策

| 设计点 | 决策 | 理由 |
|--------|------|------|
| **主键** | `id BIGINT` 雪花 ID | 与订单表、活动表 ID 策略统一；天然哈希均匀，直接作分片键 |
| **用户关联** | `user_id` 替代 `merchant_id` | 与现有用户服务对齐，后续通过 `role` 字段扩展商家/管理员角色 |
| **图片字段** | `main_image` 等可为 `NULL` | V1 不强制要求图片上传，降低测试门槛 |
| **软删除** | `is_deleted` 字段（0/1） | 行业标准方案，支持数据恢复与审计；所有查询必须加 `is_deleted = 0` |
| **唯一约束** | 无 DB 层唯一索引 | 商品标题/用户组合唯一性由 Redis 前置校验，避免分布式唯一索引性能瓶颈 |
| **冗余字段** | 无 SKU/规格/详情 | V1 仅支持单品发布，复杂属性存 JSON 扩展字段或后续迭代 |
| **状态枚举** | 0/1/2 三态 | 满足上下架 + 审核基础流程；秒杀可用 = "上架且库存 > 0"，无需额外标记 |

## 三、分片策略（ShardingSphere-JDBC）

### 3.1 配置示例

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds_0
      ds_0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/livemall_product_1
        username: root
        password: root123
    rules:
      sharding:
        tables:
          t_product:
            actual-data-nodes: ds_0.t_product_{0..15}
            table-strategy:
              standard:
                sharding-column: id
                sharding-algorithm-name: hash-mod-16
            key-generate-strategy:
              column: id
              key-generator-name: snowflake
        sharding-algorithms:
          hash-mod-16:
            type: HASH_MOD
            props:
              sharding-count: 16
        key-generators:
          snowflake:
            type: SNOWFLAKE
            props:
              worker-id: ${WORKER_ID:1}
```

### 3.2 分片路由示例

| 雪花 ID | HASH_MOD(id, 16) | 路由表 |
|---------|------------------|--------|
| 1876543210987654321 | 1 | `t_product_1` |
| 1876543210987654322 | 2 | `t_product_2` |
| 1876543210987654328 | 8 | `t_product_8` |

**C 端查询**：传 `productId` → 直接命中分片（100% 路由率）  
**B 端查询**：按 `user_id` 查询 → V1 全表扫描（后续接 ES）

## 四、包结构与接口隔离

### 4.1 目录结构

```
com.jolumn.livemallseckill
├── product/                     ← 商品独立包（未来拆分边界）
│   ├── entity/Product.java
│   ├── repository/ProductRepository.java
│   ├── service/ProductFacade.java         ← 对外唯一入口
│   ├── service/ProductServiceImpl.java
│   ├── dto/ProductPublishCmd.java         ← 发布命令对象
│   ├── dto/ProductDTO.java
│   └── config/ProductShardingConfig.java
├── entity/SeckillActivity.java            ← 秒杀活动（依赖 ProductFacade）
├── entity/SeckillOrder.java               ← 秒杀订单（禁止直接引用 product.repository）
└── ...
```

### 4.2 强制约束

`activity` / `order` 包只能通过 `ProductFacade` 访问商品数据，**严禁注入 `ProductRepository`**。

### 4.3 Facade 接口

```java
public interface ProductFacade {
    /**
     * 商家发布商品
     * @return 商品 ID（雪花 ID）
     */
    Long publish(ProductPublishCmd cmd);
    
    /**
     * C 端查商品详情
     */
    ProductDTO getById(Long productId);
    
    /**
     * 秒杀扣减库存（Redis Lua 原子扣减）
     * @return true:扣减成功 false:库存不足
     */
    boolean checkAndDecrStock(Long productId, int quantity);
    
    /**
     * 校验商品是否存在且上架
     */
    boolean checkAvailable(Long productId);
}
```

## 五、核心业务流程（简化版）

### 5.1 商家发布商品

```
1. 接收 ProductPublishCmd（userId, title, price, stock, ...）
2. Redis 去重：SETNX product:dedup:{userId}:{md5(title)} TTL=24h
   - 已存在 → 返回错误"24h 内已发布同名商品"
3. ShardingSphere 自动生成雪花 ID
4. INSERT INTO t_product（分片路由自动生效）
5. 返回 productId
```

**简化点**：
- 无图片上传（URL 可为空）
- 无 SKU/规格
- 无 ES 同步（B 端查询走 DB）
- 无审核流程（直接上架）

### 5.2 秒杀关联商品

```
1. 创建秒杀活动：调用 ProductFacade.getById(productId)
2. 校验商品存在且 status=1 且 is_deleted=0
3. 禁止 JOIN：活动表冗余 product_id + seckill_price
4. 下单时快照冗余到订单表（product_id, title, price）
```

### 5.3 库存扣减（秒杀核心）

```
Redis Lua 原子扣减（与现有 SeckillService 复用）：
- KEYS[1] = stock:{productId}
- ARGV[1] = quantity
- 返回 0:成功 -1:库存不足
```

**注意**：V1 直接复用现有 `StockService`，仅需将 `activityId` 改为 `productId`（见待办列表中的重构任务）。

## 六、软删除实现

### 6.1 字段设计

```java
@Column(name = "is_deleted", nullable = false)
private Integer isDeleted = 0;  // 0:正常 1:已删除
```

### 6.2 查询约束

所有 Repository 方法必须加 `is_deleted = 0` 条件：

```java
@Query("SELECT p FROM Product p WHERE p.id = :id AND p.isDeleted = 0")
Optional<Product> findById(@Param("id") Long id);

@Query("SELECT p FROM Product p WHERE p.userId = :userId AND p.status = :status AND p.isDeleted = 0")
List<Product> findByUserIdAndStatus(@Param("userId") Long userId, @Param("status") Integer status);
```

### 6.3 删除操作

```java
@Transactional
public void softDelete(Long productId, Long userId) {
    Product product = productRepository.findById(productId)
        .orElseThrow(() -> new BizException(404, "商品不存在"));
    if (!product.getUserId().equals(userId)) {
        throw new BizException(403, "无权删除该商品");
    }
    product.setIsDeleted(1);
    productRepository.save(product);
}
```

## 七、与现有系统的对齐

### 7.1 ID 策略统一

| 模块 | ID 生成 | 用途 |
|------|---------|------|
| 秒杀订单 | `SnowflakeIdGenerator.nextOrderNo()` | 订单号 |
| 短链 | Redis INCR + Base62 | 短码 |
| **商品** | ShardingSphere 雪花 ID | 商品主键 |

### 7.2 用户关联

```
商品表 user_id → 用户服务 user.id
↓
未来扩展：user.role = 1 (商家) / 2 (管理员)
```

### 7.3 秒杀库存复用

现有 `StockService` 的 Redis key：
- `stock:{activityId}` → 改为 `stock:{productId}`
- `ordered:{activityId}:{userId}` → 改为 `ordered:{productId}:{userId}`

**注意**：此改动在"秒杀模块重构"任务中完成，不在本设计文档范围内。

## 八、风险与应对

| 风险 | 应对 |
|------|------|
| B 端按商家/标题查询触发全表扫描 | V1 后台管理仅支持 ID 精确查询；复杂检索后续接 ES |
| 分片不均 | 雪花 ID 高位含时间戳 + 机器号，低位序列号递增，Hash 后分布均匀；上线后监控各表行数 |
| 未来分库数据迁移 | 16 表 Hash 取模结果稳定，升级 4 库 × 4 表时用 ShardingSphere DistSQL 在线迁移 |
| 秒杀扣减超卖 | `checkAndDecrStock` 内部用 Redis Lua 原子扣减，DB 仅做最终一致性校准 |

## 九、面试话术

> "商品模块采用渐进式分片：在秒杀服务内独立封装商品包，采用雪花 ID 作主键兼分片键（单库 16 表 Hash 取模），支撑商家发布与秒杀关联。移除 DB 唯一索引改由 Redis SETNX 前置去重，Facade 接口隔离核心链路，为未来商品服务拆分预留无损迁移路径。软删除通过 `is_deleted` 字段实现，所有查询强制加 `is_deleted = 0` 条件，支持数据恢复与审计。"
