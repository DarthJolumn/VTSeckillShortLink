# 短链系统设计文档

## 一、系统目标

### 1.1 核心指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 日读量 | 100 万 | 短链跳转查询 |
| 日写量 | 10 万 | 短链生成（商品关联） |
| P99 延迟 | < 50ms | 读请求端到端延迟 |
| 可用性 | 99.9% | 核心跳转服务 |
| 读写比 | 10:1 | 典型读多写少场景 |

### 1.2 业务场景

```
商品上线事件 → 短链服务监听 → 自动生成短链（如: https://s.livemall.com/aB3xYz）
                                         ↓
                                  存储映射关系（短链 → 商品详情页 URL）
                                         ↓
用户点击短链 → 跳转到商品详情页
```

**核心职责**：
- **监听商品上线事件** → 自动生成短链
- **存储映射关系** → 短链码 ↔ 商品详情页 URL
- **提供跳转服务** → 用户点击短链 → 查询并跳转到对应商品详情页

**边界说明**：
- 不考虑商品管理逻辑（商品服务负责）
- 只关注短链的生成、存储、查询
- 短链与商品是 1:1 关系

## 二、架构总览

### 2.1 技术选型

| 组件 | 选择 | 理由 |
|------|------|------|
| **本地缓存** | Caffeine (W-TinyLFU) | 挡热点、防穿透、O(1) 性能 |
| **主存储** | Redis Master-Slave | 读写分离，Master 写、Slave 读 |
| **高可用** | Redis Sentinel | 自动故障转移，Master 挂了秒级切换 |
| **限流** | Sentinel | 应用层限流，保护 Redis 不被打爆 |
| **持久化** | MySQL | 冷备份 + 缓存 Miss 兜底 |
| **ID 生成** | Snowflake + Base62 | 无碰撞、有序、高性能 |

### 2.2 架构设计原则

**核心认知**：
- **写入方**：商品服务（商品上线事件触发短链生成），日写 10 万，~1 QPS，低频
- **读取方**：用户端（点击短链跳转），日读 100 万，~12 QPS（峰值 1000+），高频

**读写分离策略**：
- Redis Master：只负责写入（公司端，低频）
- Redis Slave：只负责读取（用户端，高频，多副本分摊压力）
- Sentinel：监控 Master/Slave，Master 挂了自动将 Slave 提升为 Master

## 三、写入链路：商品上线生成短链

### 3.1 完整时序

```
1. 商品上线事件触发
   ├─ 输入: 商品 ID, 商品详情页 URL, 过期时间
   
2. ID 生成
   ├─ Snowflake 生成 64 位 Long
   ├─ Base62 编码为 6-8 位短码 (如: aB3xYz)
   └─ 细节: 剔除易混淆字符 (0/O, 1/I/l)

3. 核心映射写入 (Redis)
   ├─ SET s:aB3xYz {"product_id":1001,"url":"...","status":1} EX {ttl}
   └─ HSET stats:aB3xYz pv 0 uv 0 (无 TTL)

4. DB 持久化 (异步)
   └─ Kafka 消息 → 消费者写入 MySQL

5. 写后读一致性保障
   ├─ 将新短码加入本地 Caffeine (TTL=3s)
   └─ 3 秒内的读请求直接命中本地缓存

6. 返回短码给商品服务
```

### 3.2 深度权衡：写后读一致性

**问题**：业务方拿到短码后立刻测试点击，若读请求打到 Redis 从库，主从延迟可能导致 404。

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| **A: 所有读写主库** | 强一致 | 主库读压力翻倍 | ❌ |
| **B: 接受短暂 404** | 简单 | 用户体验差，大 V 转发场景致命 | ❌ |
| **C: 本地缓存预热 3s** | 消除 404，内存成本低 | 多节点 3s 内不一致 | ✅ |

**选定方案 C**：写入成功后，将该短码加入本地 Caffeine 缓存（TTL=3s）。

- 3 秒内的读请求命中本地缓存直接返回
- 3 秒后走 Redis 从库，此时主从同步已完成
- **代价**：多节点间 3 秒内数据不一致
- **接受理由**：短码刚创建的 3 秒是"测试窗口"而非"流量窗口"，用极低的内存成本换取 99.9% 场景的完美体验

### 3.3 ID 生成策略

```java
// Snowflake → Base62 编码
public String generateShortCode() {
    long id = snowflakeIdGenerator.nextId();
    return Base62.encode(id);  // 6-8 位字符
}

// Base62 字符集（剔除易混淆字符）
private static final String ALPHABET = 
    "23456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghjkmnpqrstuvwxyz";
// 剔除: 0, 1, I, O, l (易混淆)
```

**时钟回拨处理**：
- 回拨 < 5ms → 自旋等待
- 回拨 > 5ms → 抛出异常拒绝写入 + 告警
- **代价**：极端情况下写入短暂不可用
- **接受理由**：短链创建是低频操作（日 10 万），回拨概率极低，用"偶尔拒绝"换取"绝不重复"

## 四、读取链路：从用户点击到返回商品详情

### 4.1 完整时序

```
1. 网关层解析短码
   └─ 从 URL 路径提取短码: /aB3xYz → code="aB3xYz"

2. L1 缓存 (Caffeine)
   ├─ 命中有效值 → 直接返回 (P99 < 1ms)
   ├─ 命中空值标记 → 直接返回 404 (拦截穿透)
   └─ Miss → 进入 L2

3. L2 缓存 (Redis)
   ├─ GET s:aB3xYz
   ├─ 命中 → 反序列化 JSON，回填 L1 缓存，返回
   └─ Miss → 进入 DB 兜底

4. DB 兜底 (MySQL)
   ├─ 查询 t_short_link 表
   ├─ 存在 → 回填 L1+L2，返回
   └─ 不存在 → 写入 L1 空值标记 (TTL=30s)，返回 404

5. 异步统计
   └─ Kafka 异步发送点击事件 → 消费者批量 HINCRBY stats:{code} pv 1
```

### 4.2 三级防护策略

| 防护层级 | 解决什么问题 | 代价 | 为什么值得 |
|---------|------------|------|----------|
| **L1 Caffeine** | 热点 Key 打爆 Redis | 占用 JVM 堆内存，GC 压力 | 单 Key QPS > 1 万时才触发，内存换 CPU |
| **L2 Redis String** | 海量长尾 Key 查询 | 网络 IO + 序列化开销 | P99 稳定 < 5ms，支撑百万级 QPS |
| **DB + 空值缓存** | 恶意穿透 / 脏数据 | DB 查询慢（~20ms） | 兜底安全网，30s 空值 TTL 平衡安全与恢复速度 |

### 4.3 为什么不加布隆过滤器？

**问题**：短链支持"逻辑删除"（商品下架）。

**布隆过滤器的局限**：
- 无法删除标记，会导致已删除短链永远被误判为存在
- 进而穿透到 DB 查出"已下架"状态，浪费 DB 资源

**更优方案**：本地空值缓存（30s TTL）
- 天然支持"删除后自动恢复"
- 30 秒后重新查 DB，符合业务逻辑

## 五、缓存策略详解

### 5.1 Caffeine 配置

```java
Cache<String, ShortLinkVO> localCache = Caffeine.newBuilder()
    .maximumSize(10_000)              // 最多缓存 1 万个短链
    .expireAfterWrite(
        new Expiry<String, ShortLinkVO>() {
            @Override
            public long expireAfterCreate(String key, ShortLinkVO value, long currentTime) {
                // 空值标记 TTL=30s，有效值 TTL=3s
                return value == null 
                    ? TimeUnit.SECONDS.toNanos(30)
                    : TimeUnit.SECONDS.toNanos(3);
            }
            // ... other methods
        })
    .recordStats()                    // 开启统计
    .build();
```

**关键设计**：
- **有效值 TTL=3s**：挡热点流量，3 秒后走 Redis 从库
- **空值标记 TTL=30s**：防穿透，30 秒后重新查 DB
- **W-TinyLFU 淘汰策略**：基于访问频率自动保留热点 Key

### 5.2 防击穿方案

**问题**：如果链接突然过期且有大量请求，要防击穿。

**方案**：Redisson 互斥锁（单 Key 粒度）

```java
public ShortLinkVO getShortLink(String code) {
    // 1. 查 L1
    ShortLinkVO cached = localCache.getIfPresent(code);
    if (cached != null) return cached;
    
    // 2. 查 L2
    String key = "s:" + code;
    String json = redisTemplate.opsForValue().get(key);
    if (json != null) {
        ShortLinkVO vo = JSON.parseObject(json, ShortLinkVO.class);
        localCache.put(code, vo);
        return vo;
    }
    
    // 3. 互斥锁回源 DB
    RLock lock = redissonClient.getLock("lock:s:" + code);
    try {
        if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
            // 双重检查
            json = redisTemplate.opsForValue().get(key);
            if (json != null) {
                ShortLinkVO vo = JSON.parseObject(json, ShortLinkVO.class);
                localCache.put(code, vo);
                return vo;
            }
            
            // 查 DB
            ShortLinkEntity entity = shortLinkMapper.selectByCode(code);
            if (entity != null) {
                ShortLinkVO vo = convert(entity);
                redisTemplate.opsForValue().set(key, JSON.toJSONString(vo), 
                    entity.getExpireTime(), TimeUnit.SECONDS);
                localCache.put(code, vo);
                return vo;
            } else {
                // 空值标记
                localCache.put(code, null);
                return null;
            }
        } else {
            // 锁竞争失败，返回默认值或旧值
            return getFallbackValue(code);
        }
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

**为什么用互斥锁而非逻辑过期**：
- 日读 100 万（平均 QPS ≈ 12），峰值预估 500 QPS
- 单 Key 并发不会太高，互斥锁开销可忽略
- 逻辑过期适合极端热点但容忍短暂脏读的场景

## 六、高可用设计

### 6.1 Redis 读写分离 + Sentinel 自动故障转移

**架构**：
```
Redis Master (写入) ← Sentinel 监控 → Redis Slave (读取)
     ↑                                        ↑
   公司端写入                              用户端读取
   (~1 QPS)                              (~120 QPS)
```

**配置**：
```yaml
spring:
  data:
    redis:
      cluster:
        nodes:
          - 192.168.1.1:6379  # Master 1
          - 192.168.1.2:6379  # Master 2
          - 192.168.1.3:6379  # Master 3
          - 192.168.1.4:6379  # Replica 1
          - 192.168.1.5:6379  # Replica 2
          - 192.168.1.6:6379  # Replica 3
        max-redirects: 3
      read-from: REPLICA  # 读写分离，读请求走 Slave
      lettuce:
        pool:
          max-active: 50
          max-idle: 20
```

**故障转移流程**：
1. Sentinel 每秒 ping Master，检测心跳
2. Master 无响应 → Sentinel 标记为主观下线
3. 多个 Sentinel 确认 → 标记为客观下线
4. Sentinel 选举 leader，选择最佳 Slave 提升为 Master
5. 应用层 Lettuce 客户端自动发现新 Master，切换连接
6. 整个过程 ~10 秒，业务无感知

### 6.2 Sentinel 应用层限流

**作用**：保护 Redis 不被突发流量打爆

```java
@RestController
public class ShortLinkController {
    
    @GetMapping("/{code}")
    @SentinelResource(
        value = "getShortLink",
        blockHandler = "handleBlock",
        fallback = "handleFallback"
    )
    public Result<ShortLinkVO> getShortLink(
        @PathVariable String code,
        @SentinelParam String shortCode  // 按短链参数限流
    ) {
        return shortLinkService.get(code);
    }
    
    // 限流处理
    public Result<ShortLinkVO> handleBlock(String code, String shortCode, BlockException ex) {
        log.warn("短链访问限流: code={}", shortCode);
        return Result.fail(429, "访问过于频繁，请稍后重试");
    }
    
    // 异常降级
    public Result<ShortLinkVO> handleFallback(String code, String shortCode, Throwable ex) {
        log.error("短链查询异常，降级处理: code={}", shortCode, ex);
        // 降级：返回缓存中的旧值或默认页面
        return shortLinkService.getFallback(code);
    }
}

// Sentinel 规则配置
@Configuration
public class SentinelConfig {
    @PostConstruct
    public void initRules() {
        // 热点参数限流：单 Key QPS 上限 5000
        ParamFlowRule rule = new ParamFlowRule("getShortLink")
            .setParamIdx(1)  // 第二个参数（shortCode）
            .setCount(5000); // QPS 上限
        
        ParamFlowRuleManager.loadRules(Collections.singletonList(rule));
    }
}
```

**限流策略**：
- 按短链参数限流（ParamFlowRule），防止单 Key 突发流量
- 单 Key QPS 上限 5000，超限快速失败
- 降级策略：返回缓存旧值或默认页面

### 6.3 Redis 集群故障降级

**问题**：Redis 集群选举期间（~10s）写入失败

**方案**：降级到 MySQL 同步写入

```java
public String createShortLink(CreateRequest req) {
    String code = generateShortCode();
    String json = buildJson(req);
    
    try {
        // 尝试写 Redis Master
        redisTemplate.opsForValue().set("s:" + code, json, req.getTtl(), TimeUnit.SECONDS);
    } catch (Exception e) {
        // Redis 故障，降级写 MySQL
        log.warn("Redis 不可用，降级写 MySQL", e);
        shortLinkMapper.insert(buildEntity(code, req));
    }
    
    // 本地缓存预热（解决写后读一致性）
    localCache.put(code, new ShortLinkVO(req));
    
    // 异步写 DB（无论是否降级，作为持久化备份）
    kafkaTemplate.send("short-link-create", buildMessage(code, req));
    
    return code;
}
```

**代价**：降级期间 P99 升至 ~50ms（MySQL 水平）
**接受理由**：可用性 > 性能，10 秒降级换全年 99.99% 可用

## 七、数据模型

### 7.1 Redis 数据结构


## 八、性能预估

### 8.1 读取性能

| 场景 | QPS | P99 | 说明 |
|------|-----|-----|------|
| L1 命中 | ~8000 | < 1ms | Caffeine 本地缓存，挡热点 |
| Sentinel 通过 | ~200 | < 5ms | 限流后进入 Redis |
| Redis Slave 命中 | ~200 | < 5ms | 读写分离，多副本分摊 |
| DB 兜底 | < 10 | < 20ms | 穿透率 < 1% |
| **加权平均** | **10000** | **< 2ms** | 满足 P99 < 50ms |

### 8.2 写入性能

| 环节 | 耗时 | 说明 |
|------|------|------|
| ID 生成 | < 1ms | Snowflake |
| Redis Master 写入 | < 2ms | SET + EX |
| 本地缓存预热 | < 0.1ms | Caffeine put |
| **总耗时** | **< 3ms** | 满足日 10 万写入 |

### 8.3 为什么不需要热 Key 自动发现？

**过度设计的场景**：
- 日读 1 亿+，峰值 10 万+ QPS
- 单 Key 热点打爆单个 Redis 节点
- 需要实时检测热 Key 并动态复制

**你的场景**：
- 日读 100 万，峰值 ~1000 QPS
- 本地 Caffeine 挡掉 90% 热点（命中率 ~90%）
- 剩下 10% 分摊到 Redis 集群（3 主 3 从），单节点压力很小

**结论**：本地缓存 + Redis 读写分离 + Sentinel 限流 = 足够应对，无需热 Key 自动发现

### 8.4 容量规划

| 资源 | 规格 | 数量 | 说明 |
|------|------|------|------|
| Redis Cluster | 3 主 3 从 + Sentinel | 6 节点 | 读写分离，高可用 |
| MySQL | 8C16G | 1 主 1 从 | 冷备份 + 兜底查询 |
| 应用服务 | 4C8G | 3 实例 | 支撑 5000 QPS |

**关键配置**：
- Redis 读写分离：Master 写（公司端），Slave 读（用户端）
- Sentinel 自动故障转移：Master 挂了 ~10 秒恢复
- Sentinel 应用层限流：单 Key QPS 上限 5000，保护 Redis

## 九、演进路径

### 9.1 V1.0 - 当前阶段（日读 100 万）

**架构**：
- 本地 Caffeine + Redis 读写分离 + Sentinel 限流
- Redis 3 主 3 从 + Sentinel 自动故障转移
- 单机房部署

**性能**：
- 日读 100 万，峰值 ~1000 QPS
- P99 < 5ms
- 本地缓存命中率 ~90%

### 9.2 V2.0 - 日读 1000 万（10 倍增长）

**瓶颈**：Redis Slave 读压力增大

**演进方案**：
1. **Redis 读写分离扩容**：1 主 3 从 → 1 主 6 从，读请求分摊到更多副本
2. **Caffeine 容量调整**：1 万 → 5 万，提升本地缓存命中率
3. **Sentinel 限流优化**：动态调整 QPS 上限

### 9.3 V3.0 - 日读 1 亿（100 倍增长）

**瓶颈**：单机房带宽和连接数

**演进方案**：
1. **多 IDC 双活部署**：短链按地域分片，就近访问
2. **CDN 边缘缓存**：热点短链推送到 CDN，减少回源
3. **Redis Cluster 扩容**：3 主 3 从 → 10 主 10 从

### 9.4 为什么不在 V1.0 就做热 Key 自动发现？

**过度设计的代价**：
- 开发复杂度增加（热 Key 检测、广播、动态复制）
- 运维复杂度增加（多套系统联动）
- 实际收益低（当前场景本地缓存 + 读写分离足够）

**演进原则**：
- 先用简单方案解决问题
- 监控发现瓶颈后再针对性优化
- 避免"未来可能用到"的提前设计

## 十、面试话术模板

**Q: 短链系统的架构设计？**

> "我的短链系统目标是日读 100 万、日写 10 万，P99 小于 50ms。核心设计是：本地 Caffeine 挡热点（命中率 ~90%），Redis 读写分离（Master 写、Slave 读），Sentinel 应用层限流保护 Redis，MySQL 作为持久化底座。
>
> 写入链路：商品上线事件触发，Snowflake 生成 ID，Base62 编码为短码，写入 Redis Master，本地缓存预热 3 秒解决写后读一致性。
>
> 读取链路：用户点击短链，先查 Caffeine（<1ms），Miss 后 Sentinel 限流，再查 Redis Slave（<5ms），再 Miss 查 DB 回填。防穿透用本地空值缓存（TTL=30s），防击穿用 Redisson 互斥锁。
>
> 高可用：Redis 3 主 3 从 + Sentinel 自动故障转移，Master 挂了 ~10 秒切换，业务无感知。Redis 故障降级写 MySQL，保证可用性。
>
> 为什么不过度设计？当前日读 100 万，本地缓存 + 读写分离足够应对，不需要热 Key 自动发现。等流量涨到 1 亿再演进到多 IDC 双活。"

**Q: 如果流量涨 100 倍怎么办？**

> "日读 1 亿时，单机房带宽和连接数会成为瓶颈。演进路径：
> 1. 先 Redis 读写分离扩容（1 主 6 从），Caffeine 容量动态调整
> 2. 引入 CDN 缓存热点短链，减少回源
> 3. 最终多 IDC 双活部署，短链按地域分片，就近访问
>
> 关键原则：先监控发现瓶颈，再针对性优化，不提前过度设计。"

**Q: 为什么不加布隆过滤器？**

> "因为短链支持逻辑删除（商品下架），布隆过滤器无法删除标记，会导致已删除短链永远被误判为存在，浪费 DB 资源。本地空值缓存（30s TTL）天然支持'删除后自动恢复'，更适合短链场景。"

**Q: 为什么不需要热 Key 自动发现？**

> "热 Key 自动发现适合日读 1 亿+、峰值 10 万+ QPS 的场景，单 Key 热点会打爆 Redis 节点。
>
> 但我的场景是日读 100 万，峰值 ~1000 QPS：
> - 本地 Caffeine 挡掉 90% 热点（命中率 ~90%）
> - 剩下 10% 分摊到 Redis 集群（3 主 3 从），单节点压力很小
> - 加上 Sentinel 限流保护，完全够用
>
> 提前引入热 Key 自动发现会增加开发和运维复杂度，但实际收益低。我的原则是：先用简单方案解决问题，监控发现瓶颈后再针对性优化。"

**Q: Redis 读写分离如何保证一致性？**

> "写入走 Redis Master，读取走 Redis Slave，主从同步有延迟（~1ms）。
>
> 解决方案：写入成功后，本地 Caffeine 缓存预热 3 秒。3 秒内的读请求命中本地缓存，不依赖 Redis 主从同步。3 秒后主从同步已完成，走 Redis Slave 读取。
>
> 这样既保证了写后读的强一致性，又实现了读写分离的高性能。"

## 十一、四层架构详解

### 11.1 接入层：流量治理与安全防线

**核心目标**：保护后端不被打垮、不被滥用。

| 防护层 | 实现方式 | 作用 |
|--------|---------|------|
| **全局限流** | Nginx/Gateway `limit_req`，全局 QPS 上限 800 | 拦截 CC 攻击和突发流量尖峰 |
| **热点参数防护** | Sentinel 热点熔断，按短码限流 | 单短链被刷量时自动降级，避免击穿缓存 |
| **安全校验** | 生成接口调用 URL 安全 API；跳转接口检查封禁标记 | 拦截恶意链接，O(1) 检查 `s:ban:{code}` |

### 11.2 缓存层：三级防御保障 P99<50ms

```
用户请求 → L1 Caffeine (热点尖峰, P99<0.1ms)
              ↓ Miss
         → Sentinel 限流检查
              ↓ 通过
         → L2 Redis Master (全量读, P99<2ms)
              ↓ Miss
         → 布隆过滤器检查（不存在直接 404）
              ↓ 可能存在
         → 互斥锁回源 DB
              ↓
         → 回填 L1+L2，返回
```

**L1 本地缓存（Caffeine）**：
- 定位：专抗热点尖峰，吸收超级热键的重复访问
- 策略：W-TinyLFU 淘汰算法，TTL=3s，容量 10 万条
- 效果：热点请求 P99 < 0.1ms，完全不出进程内存

**L2 分布式缓存（Redis Master）**：
- 定位：承接全量跳转读请求，保证强一致性
- **关键约束**：跳转读**绝不走 Slave**，避免主从延迟导致新创建的短链 404
- 当前峰值读 QPS ≈ 500，Master 单机性能余量充足
- 数据结构：`GET s:code:{shortCode}` → 原始长链，P99 < 2ms

**防穿透 & 防击穿**：
- **布隆过滤器**：跳转前先查布隆，不存在则直接返回 404，拦截 99% 的非法短码查询
- **空值缓存**：布隆误判时，DB 查无结果则缓存空值（TTL=30s），防止同一非法短码反复打 DB
- **互斥锁**：缓存 Miss 且非空值时，用 Redisson 单 Key 粒度加锁，保证仅一个线程回源 DB

### 11.3 ID 生成：Redis INCR + Base62

**核心变更**：短码生成**不使用雪花算法**，而是复用 Redis Master 的 `INCR short_url:seq` 命令。

| 特性 | 说明 |
|------|------|
| **原子自增** | 返回全局唯一递增 ID，天然无冲突 |
| **Base62 编码** | 将 10 进制 ID 转为 6 位 `[0-9a-zA-Z]` 字符串，长度固定、可读性好 |
| **性能匹配** | 日写 10 万 = 平均 1.2 QPS，Redis INCR 单线程可支撑 10 万+ QPS，性能余量超 8 万倍 |
| **无时钟风险** | 规避了雪花算法的机器码管理与时钟回拨风险 |

**去重前置**：生成前先查反向缓存 `GET s:hash:{md5(longUrl)}`，命中则直接返回已有短码，避免重复生成。

### 11.4 存储层：持久化底座与异步统计

**严格分离"映射数据"与"统计数据"**，避免高频写拖垮跳转读。

**MySQL 映射表（强一致）**：
```sql
CREATE TABLE short_url_mapping (
    id          BIGINT PRIMARY KEY,
    short_code  VARCHAR(10) NOT NULL UNIQUE,
    long_url    VARCHAR(2000) NOT NULL,
    url_hash    CHAR(32) NOT NULL COMMENT 'MD5(long_url)，用于去重',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    expire_at   DATETIME,
    status      TINYINT DEFAULT 1 COMMENT '1:正常 2:已删除',
    INDEX idx_url_hash (url_hash),
    INDEX idx_expire (expire_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**异步统计流水线（最终一致）**：
- **绝不实时 UPDATE 计数**：跳转时将 `{shortCode, timestamp, ua, ip}` 写入 Kafka
- **批量聚合**：消费端每 5 秒或每 100 条批量写入 ClickHouse，将百万级随机写转化为数百级顺序写
- **实时粗计数**：`Redis INCR s:stat:{code}:today`（TTL=48h）供后台即时预览，不影响主链路

### 11.5 高可用层：故障自愈与降级预案

**核心原则**：Redis 主从用于 **HA 热备**，而非分担跳转读。

**Redis HA**：
- 架构：1 主 2 从 + 3 哨兵
- Master 宕机时 10~30s 自动切换
- **Slave 平时仅作热备**，不承担跳转读流量，仅用于后台统计查询、备份、运维测试

**应用层降级**：
- Redis 不可用时，跳转降级为直接查 DB（带限流保护），或返回静态兜底页面
- 生成接口降级为拒绝服务并提示"系统繁忙"，避免脏数据写入

**监控告警**：
- 核心 SLI：跳转 P99 > 30ms、生成错误率 > 1%、Redis 主从延迟 > 1s
- 热点感知：Top10 热点 Key 实时看板，动态调整本地缓存策略

## 十三、与秒杀系统的对比

| 维度 | 秒杀系统 | 短链系统 |
|------|---------|---------|
| **核心矛盾** | 瞬时高并发扣库存 | 持续高并发跳转读 |
| **写入特点** | 突发峰值（秒杀开始瞬间） | 平稳低峰（日 10 万 = 1.2 QPS） |
| **读取特点** | 查询活动信息（量级小） | 跳转查询（量级大，日 100 万） |
| **Redis 角色** | 库存扣减（Lua 原子操作） | 主存储（承接全量读） |
| **一致性要求** | 最终一致（Kafka 异步下单） | 强一致（写后立即读，不走 Slave） |
| **ID 生成** | 雪花算法（分布式、高并发） | Redis INCR（简单、无时钟风险） |
| **缓存策略** | Caffeine + Redis（读写分离） | Caffeine + Redis Master（只读 Master） |

## 十四、总结

这套短链系统设计的核心思想：

1. **指标先行**：明确日读 100 万、P99 < 50ms 的硬约束
2. **简单可靠**：Caffeine → Redis Master → MySQL，不过度设计
3. **强一致保障**：跳转读只走 Master，彻底消除主从延迟导致的 404
4. **ID 生成极简**：Redis INCR + Base62，无时钟风险，性能余量充足
5. **统计异步化**：Kafka + ClickHouse，百万级写转化为数百级顺序写
6. **高可用热备**：Redis 主从仅作 HA，Slave 不承担读，降级预案兜底

**为什么不过度设计？**
- 当前日读 100 万，本地缓存 + Redis Master 足够应对
- 不需要读写分离（读取只走 Master，Slave 仅热备）
- 不需要热 Key 自动发现（Caffeine 挡热点足够）
- 所有组件直接服务于核心目标，简单可靠

这是一个**务实、可靠、可演进**的工程系统，而非纸上谈兵的完美架构图。
