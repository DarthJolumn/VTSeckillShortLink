# 面试答辩 — 性能调优与高并发消费

## 一、性能调优与容量治理

### 1. JVM 延迟治理

**简历描述：**
> 同口径压测（450 并发/扣减 10w 库存/90s/堆峰值 4GB）下 G1 因同步 Evacuation 产生 856ms STW；切换分代 ZGC 后 GC 耗时降至 3ms（均为 Proactive 主动触发），彻底排除 GC 抖动对延迟的干扰。

**数据支撑：**

| 指标 | G1 | ZGC | G1 是 ZGC 的倍数 |
|------|-----|-----|----------------|
| YGCT（Young GC 总耗时） | 0.652s | 0.001s | 652 倍 |
| CGCT（并发 GC 总耗时） | 0.205s | 0.001s | 205 倍 |
| 总 GC 耗时 | 0.856s | 0.003s | 285 倍 |
| Young GC 次数 | 170 次 | 9 次 | 19 倍 |
| Full GC | 0 | 0 | 持平 |
| GC 触发原因 | Evacuation Pause（STW） | Proactive / High Usage（并发） | ZGC 无强制 STW |

**必须能回答的问题：**

| 问题 | 答案 |
|------|------|
| G1 的 STW 从哪来？ | Evacuation Pause — 对象从 Eden/Survivor 复制到 Old 区时必须停应用线程 |
| ZGC 为什么不用停？ | 并发整理，用 load barrier（染色指针+读屏障）实现对象 relocate 不停应用 |
| 为什么选分代 ZGC？ | 非分代适合大堆（TB 级），分代在小堆（4GB）下吞吐更高、GC 频率更低 |
| Proactive 触发是什么？ | ZGC 主动 GC（不等到内存紧张就提前回收），避免 High Usage 被动触发时的突发暂停 |

**必须能回答的问题：**

### 3. 高并发消费与稳定性保障

**简历描述：**
> Kafka 消费端在载体线程层前置 Semaphore 背压（上限对齐 HikariCP 池大小），信号量耗尽主动阻塞 poll 循环，迫使 Broker 降速，从根源杜绝虚拟线程堆积引发的连接耗尽与 heap OOM。配合手动 ACK + 幂等去重 + 内存分级重试，压测验证订单入库成功率 100%，消息零丢失。

**必须能回答的问题：**

| 问题 | 答案 |
|------|------|
| 为什么 Semaphore 上限 = HikariCP 池大小？ | 每个消费 VT 占一个 DB 连接，Semaphore(30) = HikariCP(30)，保证不会 VT 多过连接 → 不会排队等连接 |
| 手动 ACK 和自动 ACK 区别？ | 自动 ACK：poll 到消息就提交 offset，处理失败消息丢了；手动 ACK：处理完才 ack，失败不 ack → 消息重投 |
| 幂等去重怎么实现的？ | DB 唯一约束 `(activity_id, user_id)`，重复订单抛 DuplicateKeyException，捕获后 ack 跳过 |
| 内存分级重试是什么？ | TransactionException 内存重试 3 次（不 ack，等 Kafka 重投），超过 3 次 ack 放弃（幂等兜底） |
| 如果 Semaphore 设成 60 会怎样？ | VT 堆积超过 HikariCP 池，线程排队等连接 → 延迟飙升，背压失效 |

**快速自检：**

1. 「G1 的 856ms 具体是什么操作导致的？」 — Evacuation Pause，对象从 Eden/Survivor 复制到 Old 区时必须 STW
2. 「300 并发是甜点，你是怎么判断的？」 — 阶梯加压发现 300→500 TPS 从 1513 涨到 1649 后不再增长，P99 从 92ms 翻倍到 169ms。300 线程延迟最优、吞吐够用，超 400 后边际收益为负
3. 「如果 Semaphore 设成 60 会怎样？」 — VT 堆积超过 HikariCP 池，线程排队等连接 → 延迟飙升，背压失效

## 二、数据一致性五道防线

### 防线 1：扣减原子性

> Redis Lua 查重-扣减-标记，Hash Tag `{activityId}` 同槽。

**实现：**
- `deduct_stock.lua` / `deduct_stock_single.lua` 原子执行：
  1. `EXISTS ordered:{activityId}:{userId}` — 判重
  2. `INCR stock:shard:{activityId}:shard` — 扣减（库存不足返回 -2）
  3. `SETEX ordered:{activityId}:{userId} 86400 1` — 标记已下单
- 所有 key 带 `{activityId}` hash tag → Redis Cluster 同 slot → 无 CROSSSLOT

**面试回答：**
> Lua 脚本内三步操作原子完成。Hash Tag `{activityId}` 保证同一个活动的库存 key 和订单标记 key 落在同一个 slot，Cluster 下不会 CROSSSLOT。

### 防线 2：超时精确取消

> ⚠️ **原描述有误**，实际实现如下：

**实际实现（非 Kafka 延迟消息）：**
- `TimeoutCancelScheduler` 每 15 秒扫描 status=0 且 created_at < now - 15min 的订单

**修正后的面试回答：**

### 防线 3：DB 最终兜底

> `uk_activity_user` 唯一索引，DuplicateKeyException 幂等 ack。

**实现：**
```java
@Entity
@Table(name = "t_seckill_order",
       uniqueConstraints = @UniqueConstraint(columnNames = {"activity_id", "user_id"}))
```

**消费端处理：**
```java
catch (DuplicateKeyException e) {
    log.warn("重复订单（幂等兜底）: orderNo={}", e.getMessage());
    ack.acknowledge();  // 重复消息，ack 跳过
}
```

**面试回答：**
> DB 层 `(activity_id, user_id)` 唯一约束兜底。Kafka 重复投递时 DuplicateKeyException 被捕获，ack 跳过，不会重复入库。

### 防线 4：Redis 故障安全

> 扣减强制走 Master，禁读写分离，杜绝主从异步复制超卖。

**实现：**
```yaml
# application.yml
spring:
  data:
    redis:
      cluster:
        read-from: MASTER  # 强制读主节点
```

**StockService.deduct() 故障处理：**
```java
Long result = redisTemplate.execute(deductScript, keys, args);
if (result == null) {
    throw new BizException(503, "系统繁忙，请稍后重试");  // Redis 故障 → 503
}
```

**面试回答：**
> Redis Cluster 配置 `read-from: MASTER`，扣减 Lua 强制走主节点，避免主从异步复制延迟导致超卖。Redis 返回 null 时抛 503 而非误导"库存不足"。

### 防线 5：退款幂等

> Lua EXISTS 前置校验 + 原子回补。

**实现：** `refund_stock.lua`
```lua
if redis.call("EXISTS", KEYS[2]) == 1 then  -- ordered key 存在才回补
    redis.call("INCR", KEYS[1])               -- 库存 +1
    redis.call("DEL", KEYS[2])                 -- 删除 ordered 标记
end
return 1
```

**面试回答：**
> refund Lua 脚本先 EXISTS 检查 ordered key，存在才 INCR 库存 + DEL 标记，原子完成。多次调用 refund 只有第一次生效，后续 ordered key 已删除，EXISTS 通不过，不会重复回补。

## 三、面试高频问题速查

### Q: 秒杀系统怎么保证不超卖？

> Redis Lua 原子扣减（扣库存+判重+设标记），Lua 脚本内完成，无并发问题。Lua 返回 -2 表示库存不足。

### Q: 下单链路是怎样的？

> 前端 → Gateway 限流 → SeckillService.placeOrder()（Caffeine 判存 + Redis Lua 扣减）→ Kafka → Consumer（Semaphore 背压 + 手动 ACK）→ DB 入库 → Redis Pub/Sub → WebSocket 推送结果

### Q: Kafka 消费失败怎么办？

> 手动 ACK：消费成功才 ack。TransactionException 内存重试 3 次，超过后 ack 放弃（幂等兜底，DuplicateKey 不会重复入库）。

### Q: 如何防止虚拟线程堆积？

> Semaphore(30) 上限对齐 HikariCP 池大小。信号量耗尽 → 阻塞 listener 线程 → poll 暂停 → Broker 感知消费慢 → 降速。从根源杜绝 VT 堆积。

### Q: 限流用的什么算法？

> 令牌桶（Token Bucket）：固定速率放令牌，请求取令牌，桶空则拒绝。允许突发流量（攒令牌后短时间放行一批），适合秒杀场景。漏桶（Leaky Bucket）强制匀速输出，不适合突发。

### Q: 分布式事务怎么处理的？

> 取消订单：DB 先（@Version CAS 防并发）、Redis 后（Lua EXISTS 幂等回补）。如果 Redis 回补失败，ReconciliationScheduler 每 5 分钟扫描 status=2 的订单，检查 ordered key 是否还在 Redis，在则补偿回补。

### Q: 为什么不直接用 Redis BF（布隆过滤器）？

> 活动量级小（几十到几百个），Caffeine 精确判存就够了。BF 在多实例间不一致（各自独立维护），反而会导致误杀 404。Caffeine 精确判存零误判、零同步开销。

### Q: soldOutCache 为什么删了？

> 1s TTL 的本地售罄缓存，其他实例 1s 内不知道已售罄 → 多笔无效 Redis deduct。活动量级小，删除后直接走 Redis Lua deduct 返回 -2 判断售罄，零延迟、零不一致。
