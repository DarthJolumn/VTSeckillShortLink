## 逐项详解

### ✅ 1. 业务架构

**文章要点：** 秒杀业务 = 商户暴露秒杀 + 用户抢购。前端控制按钮状态，后端保障数据一致性。

**项目实现：**
```
用户点击 → Gateway（HMAC + JWT + Sentinel）
        → SeckillService（Caffeine 判存 + Redis Lua 扣减）
        → Kafka 异步 → Consumer → DB 入库
        → Redis Pub/Sub → WebSocket 推送结果
```

**面试话术：**
> 秒杀链路独立模块，前端只拿 orderNo，结果通过 WebSocket 异步推送。活动管理、库存扣减、订单创建分层清晰。

---

### ⚠️ 2. 流量架构

**文章要点：** 瞬时凸峰 + 漏斗模型 + QPS 预估 + 性能压测

**项目实现：**
- Sentinel Dashboard 配置了规则
- 规则数据源注释掉了（未持久化到 Nacos）
- 阶梯压测 10→450 并发，定位 300 并发为甜点

**面试话术：**
> Gateway 层 Sentinel 令牌桶限流，阶梯加压定位单机安全阈值 300 并发 / 1500 QPS。

**不要说的：** 规则没持久化到 Nacos。

### ✅ 3. 异步架构

**文章要点：** 同步下单不可取，必须两阶段/三阶段异步。引入 MQ 解耦。

**项目实现：**
```java
// 第一阶段：同步扣减 Redis 库存 + 发 Kafka
kafkaTemplate.send("seckill-order", msg).get(3, TimeUnit.SECONDS);
return Result.ok(Map.of("result", "ok", "orderNo", orderNo));

// 第二阶段：Consumer 异步入库
@KafkaListener(topics = "seckill-order")
public void onMessage(...) {
    Thread.startVirtualThread(() -> {
        seckillService.createOrder(activity, userId, orderNo);
        ack.acknowledge();
    });
}
```

**面试话术：**
> Kafka 解耦下单和入库，前端同步返回 orderNo，异步等 WS 推送。虚拟线程处理高并发消费。

### ✅ 4. 分层架构

**文章要点：** 接入层（认证+限流）→ 服务层（业务逻辑）→ 持久层（缓存+DB）

**项目实现：**
```
Gateway (路由 + 鉴权 + 限流) :8080
    ↓
Service 层 (seckill / user / websocket / leaderboard)
    ↓
Repository 层 (JPA + Redis)
    ↓
Common 层 (共享工具类、DTO、异常定义)
```

**面试话术：**
> 微服务拆分，职责清晰。Gateway 统一鉴权限流，业务模块独立部署，Common 提供公共组件。

### ✅ 6. 缓存架构

**文章要点：** 多级缓存、缓存穿透/击穿/雪崩、布隆过滤器

**项目实现：**
```java
// L1: Caffeine 本地缓存（活动信息）
activityCache = Caffeine.newBuilder()
    .refreshAfterWrite(Duration.ofSeconds(5))
    .expireAfterAccess(Duration.ofSeconds(30))
    .build(id -> activityRepo.findById(id).orElse(null));

// L2: Redis Cluster（库存、去重标记）
// Lua 脚本原子操作
```

**审计修复记录：**
- 删除了 BF（活动量级小，Caffeine 精确判存替代，零误判）
- 删除了 soldOutCache（1s TTL 多实例不一致，Lua -2 兜底）

**面试话术：**
> Caffeine L1 + Redis Cluster L2 多级缓存。活动信息 5s 自动刷新。活动量级小（几十到几百），Caffeine 精确判存替代 BF，零误判零同步开销。

**追问：为什么不用 BF？**
> BF 多实例各自维护，新活动上架后其他实例 BF 不含该活动 → 误杀 404。活动量级小，Caffeine 精确判存就够了。

### ✅ 7. 数据一致性

**文章要点：** Redis 预扣减 → MQ → DB 最终扣减 → 超时回退

**项目实现（五道防线）：**

| 防线 | 实现 |
|------|------|
| 扣减原子性 | Lua 脚本"查重-扣减-标记"原子完成，Hash Tag 同槽 |
| DB 兜底 | `uk_activity_user` 唯一索引 + DuplicateKeyException 幂等 ack |
| Redis 故障安全 | read-from: MASTER，null → 503 |
| 退款幂等 | Lua EXISTS 前置校验 + 原子回补 |
| 分布式事务 | DB 先 @Version CAS → Redis 后 Lua 幂等回补 + 对账 |

**审计修复：**
- P0-2: cancelOrder 分布式事务 — 从"Redis 先→DB 后"改为"DB 先→Redis 后"
- 新增 ReconciliationScheduler 每 5 分钟对账

**面试话术：**
> 数据一致性五道防线：Lua 原子扣减 + 唯一索引幂等 + Master 读写 + 退款 EXISTS 校验 + 分布式事务对账。

### ✅ 8. MQ 异步

**文章要点：** Kafka 异步下单，手动 ACK，幂等去重

**项目实现：**
```yaml
consumer:
  enable-auto-commit: false
  ack-mode: manual
```
```java
// 手动 ACK
ack.acknowledge();

// 幂等去重
catch (DuplicateKeyException e) {
    ack.acknowledge();  // 重复消息，跳过
}

// 分级重试
catch (TransactionException e) {
    if (retried < MAX_RETRIES) { /* 不 ack，等重投 */ }
    else { ack.acknowledge(); }  // 超过 3 次，放弃
}
```

**面试话术：**
> 手动 ACK 保证消息不丢。DuplicateKeyException 幂等兜底。TransactionException 内存重试 3 次，超过后 ack 放弃。压测验证 100% 入库、消息零丢失。

### ⚠️ 9. 高可用

**文章要点：** 多副本、故障转移、优雅停机

**项目实现：**
- Redis Cluster 3 主 3 从
- 优雅停机 @PreDestroy 关闭 gRPC channel
- Semaphore 背压防 VT 堆积
- 缺：熔断器（Sentinel/Hystrix 未启用）、健康检查

**面试话术：**
> Redis Cluster 高可用，优雅停机，Semaphore 背压防 VT 堆积。

**不要说的：** 没有熔断器。

### ⚠️ 10. 限流

**文章要点：** 接口级 QPS 限制、用户级限流

**项目实现：**
- 消费端 Semaphore(30) 背压，对齐 HikariCP 池大小
- Gateway Sentinel 规则未持久化

**面试话术：**
> Kafka 消费端 Semaphore 背压，信号量耗尽阻塞 poll 循环迫使 Broker 降速，上限对齐 HikariCP 池大小（30），杜绝 VT 堆积。

---

### ⚠️ 11. 熔断

**文章要点：** 慢调用熔断、异常比例熔断

**项目实现：**
- Kafka 失败 Fail Fast → 回补库存 → 返回 503
- gRPC 推送失败仅 log.warn
- 无自动熔断降级

**面试话术：**
> Kafka 不可用时 Fail Fast，立即回补 Redis 库存，返回 503。

---

### ✅ 12. 降级架构

**文章要点：** 多层拦截、快速拒绝、降级兜底

**项目实现：**
- Caffeine 精确判存（替代 BF）→ 无效 activityId 直接 404
- Redis Lua deduct 返回 -2 → 库存不足直接拒绝
- Redis Pub/Sub 替代 gRPC 单点推送

**面试话术：**
> Caffeine 精确判存快速拒绝无效请求，Lua -2 兜底售罄判断，Redis Pub/Sub 多实例推送替代 gRPC 单点。

### ✅ 13. 存储高可用

**项目实现：**
```yaml
spring.data.redis:
  cluster:
    read-from: MASTER  # 避免主从延迟读到过期库存
```

**面试话术：**
> Redis Cluster 3 主 3 从，强制读 Master 避免主从异步复制超卖。HikariCP 连接池保护 MySQL。

## 面试核心话术总结

### 一句话版
> 秒杀系统覆盖 16 大架构中的 12 项：多级拦截漏斗（Gateway→Caffeine→Redis Lua）、Kafka 异步下单、Semaphore 背压、五道数据一致性防线、G1→ZGC 性能调优、Redis Cluster 高可用。

### 展开版

**Q: 秒杀系统怎么保证不超卖？**
> Lua 原子扣减 + Hash Tag 同槽 + read-from: MASTER + 唯一索引幂等 + 对账补偿。

**Q: 分布式事务怎么处理的？**
> DB 先 @Version CAS → Redis 后 Lua 幂等回补 → ReconciliationScheduler 每 5 分钟对账。

**Q: 如何防止虚拟线程堆积？**
> Semaphore(30) 对齐 HikariCP(30)。信号量耗尽 → 阻塞 listener → poll 暂停 → Broker 降速。

**Q: 为什么不用布隆过滤器？**
> 活动量级小，Caffeine 精确判存零误判。BF 多实例不一致会导致误杀 404。

**Q: 性能调优做了什么？**
> G1→ZGC（GC 856ms→3ms），SkyWalking 定位 Kafka Producer 同步发送 3342ms 为瓶颈，异步削峰后 300 并发 TPS 1513 / P99 92ms，快斜坡峰值 2065 TPS。

**Q: Kafka 消费失败怎么办？**
> 手动 ACK + 幂等去重 + 内存重试 3 次。100% 入库，消息零丢失。
