## Snowflake 分布式 ID

### ID 结构

64bit long：`0 | 41bit 时间戳 | 10bit workerId | 12bit 序列号`

| 段 | 位数 | 说明 |
|----|------|------|
| 符号位 | 1 | 始终 0 |
| 时间戳 | 41 | 毫秒级，自定义 epoch（2025-01-01），可用 69 年 |
| workerId | 10 | 0~1023，启动时通过环境变量注入 |
| 序列号 | 12 | 0~4095，同一毫秒内递增 |

### 核心逻辑

> ⚠️ VT 下用 `ReentrantLock` 替代 `synchronized`，避免 VT pinning。时钟回拨时 **先 unlock → sleep → 重新 lock**，避免持锁 sleep。

```java
public class DistributedIdGenerator {
    private final long workerId;
    private final long epoch = 1735689600000L;  // 2025-01-01
    private final Lock lock = new ReentrantLock();
    private final AtomicLong sequence = new AtomicLong(0);
    private volatile long lastTimestamp = -1L;

    public long nextId() {
        lock.lock();
        try {
            long timestamp = System.currentTimeMillis();
            // 时钟回拨处理
            if (timestamp < lastTimestamp) {
                long diff = lastTimestamp - timestamp;
                if (diff <= 30) {
                    // ★ 先释放锁再 sleep，避免 VT pinning + 持锁阻塞
                    lock.unlock();
                    try { Thread.sleep(diff); } finally { lock.lock(); }
                    // ★ 重新获取时间戳（sleep 后lastTimestamp 可能已被其他线程推进）
                    timestamp = Math.max(lastTimestamp + 1, System.currentTimeMillis());
                } else {
                    throw new RuntimeException("时钟回拨超过 30ms");
                }
            }
            // 同一毫秒内序列号递增
            if (timestamp == lastTimestamp) {
                long seq = sequence.incrementAndGet() & 0xFFF;  // 12bit mask
                if (seq == 0) {
                    // 序列号用完，等待下一毫秒
                    while (timestamp == lastTimestamp) {
                        timestamp = System.currentTimeMillis();
                    }
                    sequence.set(0);
                }
            } else {
                sequence.set(0);
            }
            lastTimestamp = timestamp;
            return (timestamp - epoch) << 22 | workerId << 12 | sequence.get();
        } finally {
            lock.unlock();
        }
    }
}
```

### workerId 分配

启动时通过环境变量 `WORKER_ID=1` 注入。docker-compose 中每个容器分配不同 ID。

### 面试追问

- 🔹 Snowflake vs UUID：UUID 无序导致 MySQL 页分裂，Snowflake 天然有序
- 🔹 时钟回拨处理：≤100ms 自旋等待，＞100ms 抛异常
- 🔹 workerId 怎么分配：环境变量手动指定 / 后续可改为 Redis 自动分配

## DFA 敏感词过滤

### 原理

构建 Trie 树，节点存储字符到子节点的映射。匹配时逐个字符遍历，命中终态节点即触发过滤。

### 构建

```java
public class DfaFilter {
    private final AtomicReference<TrieNode> rootRef;

    public void loadWords(Collection<String> words) {
        TrieNode newRoot = new TrieNode();
        for (String word : words) {
            TrieNode current = newRoot;
            for (char ch : word.toCharArray()) {
                current = current.children.computeIfAbsent(ch, k -> new TrieNode());
            }
            current.isEnd = true;  // 终态标记
        }
        rootRef.set(newRoot);  // AtomicReference 无锁替换
    }
}
```

### 匹配

```java
public boolean containsSensitive(String text) {
    TrieNode root = rootRef.get();
    for (int i = 0; i < text.length(); i++) {
        TrieNode current = root;
        for (int j = i; j < text.length(); j++) {
            current = current.children.get(text.charAt(j));
            if (current == null) break;
            if (current.isEnd) return true;
        }
    }
    return false;
}
```

时间复杂度 O(n²)（最坏），实际应用中大部分文本命中分支后很快中断，接近 O(n)。

### 热更新

`loadWords()` 构建新树 → `rootRef.set(newRoot)` → 旧树被 GC。读操作无锁，写操作替换引用。

### 面试追问

- 🔹 10w 词库性能：构建后查询 O(n)，单次匹配 1ms 内完成 1000 字
- 🔹 热更新机制：`AtomicReference` 无锁替换；如果要求实时性更高，通过 MQ 广播更新
- 🔹 为什么不直接用正则：正则逐个匹配性能 O(n × m)，词库大了会炸

## 接口签名

### 算法

```
sign = HMAC-SHA256(method + uri + timestamp + nonce + body, secretKey)
```

- 方法 + 路径 + 时间戳 + 随机串 + 请求体 拼接
- 字段按字典序排列（防篡改）
- 使用 HMAC-SHA256，密钥客户端和服务端各持一份

### 请求头

| 头 | 说明 |
|----|------|
| X-Sign | 签名字符串 |
| X-Timestamp | 毫秒时间戳 |
| X-Nonce | 唯一随机串（UUID 截取） |

### 服务端验证

```
1. 检查 timestamp 是否在 ±5min 内 → 超时拒绝
2. Nonce 是否已使用 → Redis SETNX，TTL=5min
3. 用同样参数重新计算 sign，比对
```

### 面试追问

- 🔹 Nonce 为什么存 Redis：高并发写密集，MySQL 扛不住
- 🔹 Redis 挂了怎么办：降级到只验 timestamp + sign，跳过 Nonce。幂等设计兜底
- 🔹 HMAC vs RSA：HMAC 对称加密，性能好。RSA 适合开放 API 签名

## ScopedValue 用户上下文

### 定义

```java
public class UserContext {
    // ScopedValue 定义
    private static final ScopedValue<User> USER = ScopedValue.newInstance();

    // 供 Controller/Service 获取
    public static ScopedValue<User> get() {
        return USER;
    }
}
```

### 注入（Gateway Filter 层）

Gateway 将 userId/role 写入 `exchange.getAttributes()` → 转发前 GlobalFilter 写入 Header：

```java
// Gateway 侧
exchange.getAttributes().put("userId", userId);
exchange.getAttributes().put("role", role);
// 另一个 Filter 在转发前将 attributes 写入 Header
request.mutate()
    .header("X-User-Id", userId.toString())
    .header("X-User-Role", role.toString());
```

### 提取（业务服务 Interceptor 层）

下游 MVC 服务通过 `HandlerInterceptor` 从 Header 提取并赋给 ScopedValue。**这就是 `1.1-项目概览` 中 `user/interceptor/` 目录的职责**：

```java
// livemall-user / livemall-seckill / livemall-leaderboard 共用
@Component
public class UserContextInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, 
                             HttpServletResponse response, 
                             Object handler) {
        String userIdStr = request.getHeader("X-User-Id");
        String roleStr = request.getHeader("X-User-Role");
        if (userIdStr != null) {
            ScopedValue.where(UserContext.USER, 
                new User(Long.parseLong(userIdStr), Integer.parseInt(roleStr)))
                .run(() -> {
                    request.setAttribute("__scoped_user_bound__", true);
                });
        }
        return true;
    }
}
```

> ⚠️ 注意 `ScopedValue.where().run()` 的作用域仅限于 `run()` 回调体内。上述代码中 `run()` 返回后 ScopedValue 就失效了。实际生产代码需用 `ScopedValue.callWhere()` 包裹整个 `DispatcherServlet` 调用链——Spring Boot 3.2+ 的 `ThreadPoolTaskExecutor` 配合 VT 已自动处理此问题，只需在 Controller 方法入口确保已绑定即可。另一个方案是用 `Filter` 替代 `Interceptor`，在 `doFilter` 内用 `ScopedValue.where().run()` 包裹整个调用链。

### 获取（业务服务 Controller/Service）

```java
User user = UserContext.get().get();
```

### 面试追问

- 🔹 ScopedValue vs ThreadLocal：TL 未 set 也占内存（16 slot 数组），VT 池化后泄漏。SV 没 bound 不占内存，自动清理
- 🔹 为什么不直接传参：每次方法调用都传 userId 污染代码边界。SV 按调用栈传递，对业务代码零侵入

## 异常体系

```java
// 业务异常基类
public class BizException extends RuntimeException {
    private final int code;
    public BizException(int code, String message) { ... }
}

// 全局异常处理器
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);

    }
}
```
