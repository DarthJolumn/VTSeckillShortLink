# 用户服务与认证机制（livemall-user）

> 内容来源：双 Token 设计 + t_user DDL + t_device_session DDL

## 认证架构

双 Token：

- **Access Token**（JWT，15min）→ 无状态，HMAC-SHA256 验签，零 IO
- **Refresh Token**（有状态，Redis 7天）→ 可撤销，仅刷新时查

性能对比 Session：10w QPS ≈ 11 QPS Redis 查询 vs 10w QPS，差 900 倍。

## 注册

```
客户端 → POST /auth/register
  → 参数校验（用户名 4~20 字符、密码 >8 位）
  → username 唯一检查（MySQL UNIQUE INDEX）
  → BCrypt.hashpw 加密 → INSERT t_user
  → 返回 Result.success()
```

## 登录流程

```
客户端 → POST /auth/login
  Gateway 验签 → 幂等检查（X-Idempotency-Key，Redis SETNX 5min）
  → UserService 查密码（BCrypt verify）
  → 签发 Access JWT + Refresh Token（存 Redis）
  → 缓存结果 → 返回双 Token
```

> 幂等保证：X-Idempotency-Key 可选的请求头，5min 内相同 key 返回已有结果。详见 `3.1.2-登录.md`。

## Token 刷新

```
客户端 → POST /auth/refresh
  → 校验 Refresh Token（Redis GET）
  → 签发新 Access Token（15min）
  → 返回新 Access Token
```

### 并发刷新防护

同一 Refresh Token 可能同时被多个过期请求触发刷新（比如 Access 刚过期，前端的 3 个 API 调用同时返回 401 并触发刷新）。解决方案：

```
1. 分布式锁：Redis SETNX refresh:lock:{refreshToken}，TTL 3s
2. 获取锁失败 → 等待 100ms → 重新 GET Redis → 如果已有新 Token 直接返回
3. 请求合并：ConcurrentHashMap 缓存进行中的刷新 CompletableFuture
   同一 Refresh Token 的后续请求复用同一个 Future，等它完成拿结果
4. 锁超时 3s → 自动释放，防止死锁
```

### Rotation vs Reuse

刷新时**生成新 Refresh Token，旧 Token 作废**（Rotation 模式）。如果旧 Refresh Token 泄露且已被刷新过，用户会发现自己的 Token 失效，触发重新登录——等于变相检测泄露。Reuse 模式（刷新后仍用同一个 Refresh）没有这个安全特性。

## 退出登录

```
客户端 → POST /auth/logout
  → 删除 Refresh Token（Redis DEL）
  → t_device_session 记录作废
```

## 修改用户信息

```
客户端 → PUT /user/profile
  → 参数校验（头像 URL 格式、昵称长度）
  → 更新 MySQL t_user
  → 返回新信息
```

密码修改需验证旧密码，走独立接口 `PUT /user/password`。

## 封禁/解禁

```
管理员 → PUT /user/ban/{userId}
  → 更新 MySQL t_user.status = 0/1
  → 删除该用户所有 Refresh Token（Redis SCAN + DEL）
  → WebSocket 推送封禁消息（详见 2.4）
```

封禁用户登录时拦截：`UserService.login` 查 status，为 0 返回"账号已封禁"。

## 设备管理

- 每设备独立 Refresh Token
- Redis：`device_sessions:{userId}` → Set<deviceId>
- 踢设备：删 Refresh Token + 通过 WebSocket 发 KICK（详见 `2.4-WebSocket长连接.md`）

> ⚠️ **P0-2 fixed**：原 `t_device_session` 表 DDL 存在但整个项目无任何代码读写——是无效设计。设备会话用 Redis TTL 7 天自动过期足矣。Redis 挂了用户重新登录即可，不需要 MySQL 做持久化。表 DDL 已从 `2.7-数据库设计.md` 移除。

## 数据库

```sql
CREATE TABLE t_user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    phone VARCHAR(20),
    avatar VARCHAR(255),
    role TINYINT DEFAULT 1,
    status TINYINT DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_phone (phone)
);
```

> ⚠️ `t_device_session` 表已移除——设备会话只在 Redis 中维护（`device_sessions:{userId}` Set + Refresh Token String），TTL 7 天自动过期，无需 MySQL 持久化。

```

## 安全策略

### 登录保护

| 措施 | 实现 |
|------|------|
| 失败限流 | Sentinel 热点参数限流：每 IP 10 QPS（Gateway 层，详见 2.6） |
| IP 获取 | 优先取 `X-Forwarded-For` 第一个 IP（Nginx/ Gateway 代理场景），兜底 `X-Real-IP` |
| 密码加密 | BCrypt（work factor=10），不可逆 |
| 异地检测 | 暂不实现，面试时作为可优化点（对比登录 IP 与历史 IP 地理位置） |

### CORS 注意

Knife4j 调试时 `allowedOrigin` 设为 `http://localhost:8080`，不可与 `allowCredentials(true)` 同时使用 `*` 通配符——浏览器 CORS 规范会拒绝。
