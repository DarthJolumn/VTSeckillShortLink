# WebSocket 长连接（livemall-websocket）

## 技术模型

@ServerEndpoint + 虚拟线程，一个连接一个 VT。连接不共享线程，长时间 idle 也不占线程池。

### VT 配置

> ⚠️ Tomcat/Jetty 默认不会用 VT 处理 @ServerEndpoint。必须显式设置 Executor。

```java
@Bean
public ServletServerContainerFactoryBean websocketContainer() {
    ServletServerContainerFactoryBean container = new ServletServerContainerFactoryBean();
    container.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
    return container;
}
```

不设此配置则 @OnOpen/@OnMessage/@OnClose 跑在 Tomcat 线程池（默认 ForkJoinPool），不享受 VT 优势。

### 实现骨架

```java
@ServerEndpoint("/ws/live/{roomId}")
public class LiveWebSocket {
    @OnOpen
    public void onOpen(Session session, @PathParam("roomId") Long roomId, 
                       @QueryParam("token") String token) {
        // 跑在 VT 上（由 ServletServerContainerFactoryBean 保证）
        Long userId = JwtUtil.verify(token);
    }
}
```

## 连接认证

客户端在 query 中传 Access Token：

```
ws://localhost:8083/ws/live/{roomId}?token=<AccessToken>
```

`@OnOpen` 中验签 + 提取 userId，失败则关闭连接发送 4001 状态码。不依赖 Gateway 转发——WebSocket 握手后直接长连接，Gateway 只做路由。

## 连接管理

```java
public class WsSessionManager {
    private static final ConcurrentHashMap<String, Session> liveSessions = new ConcurrentHashMap<>();
    
    public static void add(String sessionId, Session session) { ... }
    public static void remove(String sessionId) { ... }
    public static Session get(String sessionId) { ... }
}
```

`sessions` 存所有活跃连接。关播 / 踢人 / 服务下线时需要遍历清理。

## 房间管理

Redis：`room:{roomId}` → Set<userId>

```java
// 进房间
redisTemplate.opsForSet().add("room:" + roomId, userId.toString());
// 出房间
redisTemplate.opsForSet().remove("room:" + roomId, userId.toString());
// 在线人数
Long online = redisTemplate.opsForSet().size("room:" + roomId);
```

本地也缓存一份 `RoomManager`：`ConcurrentHashMap<Long, Set<String>>`（roomId → Set<sessionId>），用于广播时避免循环查 Redis。

## 开播 / 关播

开播（主播调用）：

```
主播 → PUT /live/room/{roomId}/start
  → 验证主播身份
  → 更新 MySQL t_live_room.status = 1, start_time = now()
  → Redis 创建 room:{roomId} 空 Set
  → 返回成功
```

关播（主播调用）：

```
主播 → PUT /live/room/{roomId}/stop
  → 验证主播身份
  → 广播 KICK 消息给房间所有用户（type=ROOM_CLOSED）
  → 等待 5s 让客户端断开
  → 强制关闭所有该房间 session
  → 更新 MySQL t_live_room.status = 0, end_time = now()
  → DEL room:{roomId}
```

## 心跳

```
客户端 → 服务端: {"type": "PING"}
服务端 → 客户端: {"type": "PONG"}
```

客户端每 30s 发 PING。服务端 `@OnMessage` 收到 PING 时回复 PONG，并更新该 session 的最后活跃时间。

服务端定时任务（@Scheduled 每 10s）扫描所有 session，最后活跃时间超过 60s 的主动关闭。防止客户端直接断开导致 onClose 未触发的"幽灵连接"。

## 在线人数同步

Redis SCARD 实时计数，本地缓存也有 count。定时任务每 30s 将在线人数写入 MySQL：

```sql
UPDATE t_live_room SET online_count = ? WHERE id = ? AND status = 1;
```

面试追问：为什么不同步更频繁？答：SCARD O(1)，30s 足够实时。在线人数不需要秒级精确。

## 断线重连

客户端指数退避：1s → 2s → 4s → 8s → 16s → max 30s，重试 10 次后停止。

服务端为每个连接维护离线消息：

```
Redis List: offline:{userId}
TTL: 5min（5min 不重连则丢弃）
```

每次推送消息前，判断 session 是否存活：
- 存活 → 直接发
- 已断开 → 追加到 `offline:{userId}`

客户端重连成功后拉取离线消息：

```java
List<String> msgs = redisTemplate.opsForList().range("offline:" + userId, 0, -1);
session.getAsyncRemote().sendText(String.join("\n", msgs));
redisTemplate.delete("offline:" + userId);
```

## 跨节点路由

多节点部署时，需要知道目标 userId 在哪台机器上。

```
Redis: ws:route:{userId} → {nodeId}:{sessionId}
TTL: 30min（随心跳续期）
```

消息转发：查 Redis 路由 → 判断 nodeId 是否本节点
- 本节点 → 直接发
- 非本节点 → Dubbo RPC 调用 `WsPushService.push(userId, message)`

Dubbo 接口定义（在 common 模块）：

```java
public interface WsPushService {
    boolean push(Long userId, String message);
    boolean pushToRoom(Long roomId, String message);
    boolean kickDevice(Long userId, String sessionId);
}
```

## 消息协议

```json
{
  "type": "BARRAGE" | "GIFT" | "KICK" | "SEC_KILL_RESULT" | "BAN" | "ROOM_CLOSED" | "ONLINE_COUNT" | "PING" | "PONG",
  "data": {},
  "messageId": "uuid（客户端生成，服务端用于去重）",
  "timestamp": 1719360000000
}
```

统一序列化为 JSON，Gateway 不解析内容，只做透传。

## 消息广播

房间内广播流程：

```
广播消息给 room:{roomId} 所有用户
  → 查本地 RoomManager 获取该房间所有 sessionId
  → 逐个发送（同步发送，VT 不会阻塞）
  → 如果 session 已断开，从本地移除
  → 查 Redis `ws:route:{userId}` 检查是否跨节点
  → 跨节点走 WsPushService.push
```

大批量广播的优化：遍历 session 列表，每个 session 开一个 VT 发送，避免一个慢连接拖慢所有人。

## 弹幕

```
客户端 → {"type": "BARRAGE", "data": {"messageId": "uuid", "content": "666"}}
  → WsMessageHandler 解析
  → 幂等去重：Redis SETNX barrage:{messageId} 1 EX 300（防断网重连重发）
  → DFA 过滤（调用 common 模块 SensitiveFilter）
    → 命中敏感词 → 替换为 *** 或直接丢弃
  → 广播到房间所有用户
  → 异步写入 MySQL t_barrage（用于历史回放）
```

服务器过滤，客户端无感。messageId 由客户端生成 UUID，服务端 5min 内相同 messageId 只处理一次。面试追问：为什么不客户端过滤？答：客户端可被篡改，服务器过滤是安全底线。

## 踢人

新连接建立时：

```
@OnOpen
  → 查 Redis `ws:route:{userId}`
  → 如果已有 sessionId：
    → 发 KICK 消息给旧 session
    → 等待 3s 让旧连接主动关闭
    → 旧连接未关闭则强制 close
  → 更新 Redis ws:route:{userId} = {nodeId}:{newSessionId}
```

## 秒杀结果推送

秒杀服务消费 Kafka 订单结果后，通过 Dubbo 调用 `WsPushService.push`：

```java
// SeckillOrderConsumer 中
WsPushService pushService = ...;
String msg = JsonUtil.toJson(new WsMessage("SEC_KILL_RESULT", result));
pushService.push(order.getUserId(), msg);
```

WebSocket 服务收到 push 请求 → 查 `ws:route:{userId}` → 本节点直接发 / 跨节点转发。

## 封禁推送

管理员封禁用户 → user 服务 → Dubbo 调用 `WsPushService.push`：

```
WsMessage type=BAN, data={}
```

WebSocket 收到 BAN 消息 → 关闭该用户所有 session。

## 降级方案

| 故障场景 | 降级动作 | 用户感知 |
|---------|---------|---------|
| Redis 挂了 | 路由失效 → 跨节点推送全断，单节点内广播仍工作 | 跨节点消息丢失 |
| Redis 挂了 | 房间管理切本地 Map，关播后房间丢失 | 在线人数不准 |
| 本节点宕机 | Nacos 摘除，客户端重连到其他节点 | 短暂断线，重连恢复 |
| 离线消息 Redis 满 | LRU 淘汰旧消息 | 旧消息丢失 |

## 面试追问要点

- WebSocket 和 HTTP 长轮询的区别（全双工 vs 半双工，头部开销）
- @ServerEndpoint 线程安全吗（每个连接一个实例，安全的）
- VT 在这里的优势（一个连接一个 VT，百万连接 = 百万轻量线程）
- 百万连接的内存占用（每个连接约 1-2KB，百万约 1-2GB，主要在 TCP 缓冲区）
- 为什么不用 Netty（Spring WebSocket 封装好了，VT 屏蔽了 IO 模型差异）
- 跨节点转发延迟（一次 Dubbo RPC < 5ms，用户无感知）
