# 排行榜服务（livemall-leaderboard）

## 接口暴露

排行榜**查询接口**（TopN、个人排名、历史）对外暴露 HTTP 接口，走 Gateway → MVC Controller。

**加分接口**（内部事件）走 Dubbo 调用，不直接对外——送礼/观看/点赞由 WebSocket 服务通过 Dubbo RPC 触发加分，保证实时性（RPC < 5ms vs Kafka 几百 ms）。

## 事件监听

排行榜加分通过 Dubbo 接收事件。

```java
public interface LeaderboardService {
    boolean addScore(Long activityId, Long userId, String eventType);
    List<RankEntry> getTopN(Long activityId, int n);
    RankEntry getRank(Long activityId, Long userId);
    List<RankEntry> getHistory(Long activityId, LocalDateTime time);
}
```

加分请求来源：
- 送礼 → WebSocket 服务接收送礼请求后 Dubbo 调 leaderboard
- 观看/点赞/评论/分享 → WebSocket 服务收到后 Dubbo 调 leaderboard

为什么不直接 Kafka 解耦？Leaderboard 需要**实时性**（用户送礼后排名立即变化），Kafka 有几百 ms 延迟。Dubbo RPC < 5ms。

## ZSet Key 设计

```
leaderboard:{activityId}
```

每个活动一个 ZSet key。活动结束后设置 TTL 7 天（保留排行榜供查询，到期 Redis 自动清理）。

### 热 Key 分析

单 Redis ZSet 的 ZINCRBY / ZREVRANGE 操作 QPS 上限约 8~10w（官方 benchmark）。本项目目标 10w QPS 是全站总量，不是单 ZSet 的操作量。一个直播间送礼/点赞/评论的加分频率不会超过每秒几百次，单 ZSet 绰绰有余。

对于超大规模活动（10w+ 在线用户同时疯狂互动），单个 ZSet 可能成为热点 key。分片方案（可优化点）：

```
leaderboard:{activityId}:{shard}   // shard = userId % shardCount
```

查询 TopN 时合并各分片结果（类似多路归并）：取各分片 TopN，合并排序后取最终 TopN。代价是排行榜分数跨分片不可直接比较（需归一化），查询复杂度 O(shardCount × N × log(shardCount × N))。本项目初期不分片。

## 互动加分

```java
@DubboService
public class LeaderboardServiceImpl implements LeaderboardService {
    
    private static final Map<String, Double> WEIGHT_MAP = Map.of(
        "WATCH", 0.3,
        "LIKE", 0.5,
        "COMMENT", 1.0,
        "SHARE", 2.0,
        "GIFT", 5.0  // 基础权重，实际金额 × 单价 × 数量
    );

    public boolean addScore(Long activityId, Long userId, String eventType) {
        double weight = WEIGHT_MAP.getOrDefault(eventType, 0.0);
        if (eventType.equals("GIFT")) {
            // 礼物需要从 data 中取实际金额
            // weight = giftPrice * quantity * 1.0
        }
        String key = "leaderboard:" + activityId;
        redisTemplate.opsForZSet().incrementScore(key, userId.toString(), weight);
        return true;
    }
}
```

权重配置表（可配置，Nacos 动态下发）：

| 事件 | 权重 | 说明 |
|------|------|------|
| WATCH | +0.3 | 每分钟 |
| LIKE | +0.5 | 每次 |
| COMMENT | +1.0 | 每次 |
| SHARE | +2.0 | 每次 |
| GIFT | 金额 × 1.0 | 按礼物价值 |

## Top N 查询

```java
public List<RankEntry> getTopN(Long activityId, int n) {
    String key = "leaderboard:" + activityId;
    Set<ZSetOperations.TypedTuple<String>> set = redisTemplate
        .opsForZSet()
        .reverseRangeWithScores(key, 0, n - 1);
    // 转成 RankEntry 返回
}
```

Caffeine 本地缓存 1s，QPS > 1000 时防止打爆 Redis：

```java
Cache<Long, List<RankEntry>> topNCache = Caffeine.newBuilder()
    .expireAfterWrite(1, TimeUnit.SECONDS)
    .maximumSize(1000)
    .build();
```

**缓存决策依据（P1-4 补充）：**

| 场景 | 预期 QPS | 需要缓存？ |
|------|---------|-----------|
| 主播/运营看大屏 | 1 QPS | ❌ 不需要 |
| 观众页 TopN 轮询 | 100 QPS | ❌ 不需要 |
| 弹幕/礼物后自动刷新 | 1000 QPS | ⚠️ 可能不需要 |
| 10w 用户同时刷首页 | 1w QPS | ✅ 需要 |

> 本项目以 10w QPS 为目标，1s 过期窗口内 Caffeine 命中率 >90%，大幅削减 Redis ZREVRANGE 压力。如果实际 TopN QPS < 1000，可去掉此缓存——直接查 Redis。

## 个人排名

```java
public RankEntry getRank(Long activityId, Long userId) {
    String key = "leaderboard:" + activityId;
    Double score = redisTemplate.opsForZSet().score(key, userId.toString());
    Long rank = redisTemplate.opsForZSet().reverseRank(key, userId.toString());
    if (score == null) return new RankEntry(userId, 0.0, -1); // 未上榜
    return new RankEntry(userId, score, rank + 1); // 转 1-based
}
```

## 定时快照

@Scheduled 每 5min 执行一次，将 Top 100 落库：

```java
@Scheduled(cron = "0 */5 * * * ?")
public void snapshot() {
    List<Long> activeActivities = getActiveActivities(); // 查询正在进行的活动
    for (Long activityId : activeActivities) {
        List<RankEntry> top100 = getTopN(activityId, 100);
        // 批量 INSERT
        jdbcTemplate.batchUpdate(
            "INSERT INTO t_leaderboard_snapshot (activity_id, user_id, score, rank, snapshot_time) VALUES (?, ?, ?, ?, NOW())",
            top100.stream().map(e -> new Object[]{activityId, e.getUserId(), e.getScore(), e.getRank()}).toList()
        );
    }
}
```

面试追问：快照数据量大了怎么办？
答：按月分表 `t_leaderboard_snapshot_202601`，活动结束后清除 Redis ZSet，历史查询走 MySQL 快照表。

## 历史排行

```sql
SELECT user_id, score, rank, snapshot_time
FROM t_leaderboard_snapshot
WHERE activity_id = ? AND snapshot_time BETWEEN ? AND ?
ORDER BY snapshot_time ASC, rank ASC
LIMIT 100;
```

查询最近一次快照的时间戳 + N 条，返回用户在该活动的排行变化趋势。

可以通过 `GROUP BY snapshot_time` 获取所有快照时间点，前端画折线图。

## 冷热分离

| 数据 | 存储 | 访问频率 | 说明 |
|------|------|---------|------|
| 实时排行 | Redis ZSet | 极高 | 用户/主播实时刷新 |
| 最近 5min 快照 | Caffeine 本地 | 高 | 历史趋势查询 |
| 历史快照数据 | MySQL | 低 | 活动结束后查询 |

## 面试追问要点

- ZSet 底层数据结构（跳表 + 哈希表，O(log N)）
- 跳表为什么层高 O(log N) 概率均衡（P = 0.25 层高升级概率）
- ZINCRBY 是原子的吗（是，Redis 单线程执行）
- 百万用户同时加分会瓶颈吗（单个 ZSet key 可能热点，分片方案）
- 为什么不用 DB 排序（MySQL ORDER BY score DESC 全表扫描，100w 行就慢了）
- 快照 5min 的间隔依据（活动通常 > 1h，5min 粒度足够）
