# 性能目标与 SLO

> 将 "10w QPS" 总目标拆解到各服务、各链路段，定义延迟预算和可观测指标。

---

## 一、总目标与适用范围

| 指标 | 数值 | 说明 |
|------|------|------|
| 全站目标 QPS | 10w | HTTP + WebSocket 合计，非单接口 |
| 秒杀峰值 QPS | 5w | 单活动秒杀瞬时流量 |
| 日常 QPS | 500~2000 | 非秒杀场景：浏览、排行等 |
| 目标可用性 | 99.9%（月停机 ≤ 43min） | |
| 错误率 SLO | < 0.1%（成功率 > 99.9%） | 秒杀正常售罄不计入错误 |

---

## 二、各服务 QPS 拆解

| 服务 | 目标 QPS | 说明 |
|------|---------|------|
| Gateway | 10w（总入口） | 路由转发 + JWT 验签，纯 CPU 无 IO |
| Seckill | 5w | 秒杀抢购接口（瓶颈在 Redis Lua） |
| User | 1w | 登录注册，峰值不高 |
| Leaderboard | 5000 | TopN 查询 1s Caffeine 缓存，击穿部分 |
| WebSocket | 5w 连接 + 10w msg/s | 按消息条数统计 |

---

## 三、秒杀链路延迟预算

从 Gateway 入口到返回结果，单次请求的目标 P99 延迟：

```
总预算：200ms（P99）
├── Gateway 验签 + 鉴权       ≤ 5ms（含 JWT HMAC-SHA256 验签 ~0.1ms + Sentinel ~0.05ms）
├── Gateway → Seckill 路由     ≤ 2ms
├── Seckill 业务逻辑           ≤ 3ms
│   ├── Caffeine 活动校验      ≤ 0.1ms
│   └── Redis Lua 库存扣减     ≤ 2ms（单实例、同机房）
├── Kafka 异步下单            不阻塞主流程（异步 50ms 内）
└── Dubbo → WS 推送结果       不在请求-响应路径中
```

| 环节 | P50 | P99 | 瓶颈 |
|------|-----|-----|------|
| Gateway → Seckill | 1ms | 3ms | Dubbo 网络 + 序列化 |
| Redis Lua | 0.5ms | 2ms | 单实例 CPU 主线程 |
| Kafka 写入 | 0.5ms | 5ms | 页缓存写入，异步刷盘 |
| Kafka 消费（端到端） | 10ms | 50ms | 消费者拉取间隔 |
| 订单 INSERT | 2ms | 10ms | MySQL 写入 |

### 安全组件 CPU 开销

10w QPS 全流量经过安全组件，需计入 CPU 时间预算：

| 组件 | 单次耗时 | 10w QPS 累计 CPU 时间/秒 | 影响 |
|------|---------|------------------------|------|
| JWT HMAC-SHA256 验签 | ~0.1ms | 10s | 占满约 2~3 个核 |
| 接口签名 HMAC 重算 | ~0.1ms（仅签名接口） | < 1s（非全量） | 可忽略 |
| DFA 敏感词遍历 | ~0.05ms（仅弹幕） | < 0.5s（弹幕非 10w） | 可忽略 |
| BCrypt 密码验证 | ~10ms（仅登录） | < 1s（登录非高频） | 可忽略 |

> JWT 验签是纯 CPU 运算，10w QPS 全量验签约消耗 2~3 个核心。双实例 Gateway 各扛 5w QPS，每个节点约 1~2 个核用于验签，在 4 vCPU VM 上可控。瓶颈仍在 Redis，不在 CPU。

---

## 四、各组件容量上限

| 组件 | 单节点理论上限 | 本项目配比 | 瓶颈 |
|------|-------------|-----------|------|
| Gateway（WebFlux） | ~15w QPS | 10w（双实例各 5w） | EventLoop 线程数 = CPU 核数 |
| Redis 单实例 | ~10w OPS | Lua 5w + ZSet 1w + 其他 2w | 单线程 CPU |
| Kafka 单分区写入 | ~10w msg/s | 5w（2 分区） | 磁盘顺序写 |
| MySQL 写入 | ~5000 TPS | 500（Kafka 削峰后） | 磁盘 IO |
| Dubbo RPC | ~10w TPS | 5w（秒杀调 WS） | 序列化 |

### 瓶颈分析

第一瓶颈是 **Redis**（单线程，所有 Lua 脚本串行）。秒杀峰值 5w QPS 时，加上 TopN、排行加分等其他 Redis 操作，总 OPS 约 7~8w，接近单实例上限。扩容策略：

1. 库存分片：4 片分散单 key 热点
2. 认证 Redis 独立实例（后续优化）
3. 排行榜 ZSet 独立实例（后续优化）

第二瓶颈是 **Gateway**。WebFlux + 纯 CPU 验签，单实例理论上限 15w QPS，双实例 30w，10w 目标有余量。但 Sentinel 限流会增加开销。

## 五、可观测指标

| 指标 | 采集方式 | 告警阈值 |
|------|---------|---------|
| Gateway P99 延迟 | `/actuator/metrics` | > 10ms |
| Redis Lua P99 延迟 | 自定义 Micrometer Timer | > 5ms |
| Kafka 消费 lag | `kafka-consumer-groups` | > 1000 条 |
| 秒杀错误率 | 自定义 Counter | > 0.5% |
| JVM GC 停顿 | `/actuator/metrics` | > 50ms |
| Redis 连接池耗尽 | Lettuce 指标 | 可用连接 < 20% |
| Dubbo 线程池队列 | Dubbo 内置指标 | > 100 |
