## 1. 消息队列：Kafka

### 为什么选 Kafka 不选别的

| 维度 | Kafka | RocketMQ | RabbitMQ |
|------|-------|----------|----------|
| 吞吐量 | **最高**（顺序写 + 零拷贝 + 页缓存） | 高 | 中 |
| 面试频率 | **最高**（大厂必问） | 中 | 中 |
| 部署复杂度 | 单节点 KRaft 模式，轻量 | 中等 | 简单 |
| 延时消息 | ❌ 不支持（需要定时任务配合） | ✅ 支持 18 级延时 | ✅ 支持 TTL + 死信 |
| 消息顺序 | ✅ 分区内有序 | ✅ 队列内有序 | ❌ 不保证 |
| 持久化 | 磁盘刷写，依赖页缓存 | 磁盘刷写 | 内存/磁盘 |
| 运维成本 | 中等 | 中等 | 简单 |

### 核心理由

Kafka 的吞吐量是三家里最强的，**顺序写磁盘 + 零拷贝（sendfile） + 页缓存**这套组合拳面试官一定会问。而且大厂面试高频，选它等于给面试官递话头，让他往 Kafka 原理上深挖。

**下单链路用 Kafka 逻辑**：秒杀场景下，Redis 扣库存后发 Kafka 消息异步创建订单。Kafka 的吞吐量能扛住秒杀峰值削峰，消费者用虚拟线程处理，不阻塞主流程。部署用 3.x KRaft 模式（不依赖 ZK），更轻量。唯一缺陷是不支持延时消息——订单超时取消需要定时任务配合，但这也是个面试扩展点（"为什么不用 RocketMQ 延时？"）。

### 不选 RocketMQ

RocketMQ 延时消息确实香，但它部署要有 NameServer + Broker + Console，比 Kafka 还重一套。而且对于中厂面试，面试官更熟悉 Kafka，选 RocketMQ 反而可能被问住——"你们公司用 RocketMQ？我用得不多，你讲讲"——你讲不过他。

### 不选 RabbitMQ

RabbitMQ 的吞吐量和 Kafka 不在一个量级，秒杀场景下高并发写入容易积压。而且面试官看到 RabbitMQ 会先入为主觉得你项目量级不大。

## 2. RPC：Dubbo

### 为什么选 Dubbo 不选 Feign / gRPC

| 维度 | Dubbo | Feign | gRPC |
|------|-------|-------|------|
| 协议 | 自定义 TCP（Header 16 字节） | HTTP/1.1 | HTTP/2 |
| 序列化 | Hessian2（二进制） | JSON（文本） | Protobuf（二进制） |
| 长连接 | ✅ 单一长连接 | ❌ 每次请求新建连接 | ✅ HTTP/2 多路复用 |
| 服务治理 | ✅ 负载均衡/重试/降级/路由 **内置** | ❌ 需配合 Spring Cloud 全家桶 | ❌ 无内置 |
| SPI 扩展 | ✅ 完善 | ❌ | ❌ |
| 面试深度 | **高**（SPI/自适应/协议栈） | 低（只是 HTTP 调用） | 中（Protobuf） |

### 核心理由

Dubbo 的技术纵深是最够的：SPI 扩展机制、自适应扩展、服务治理（5 种负载均衡、多种容错策略）、自定义协议栈。Feign 只是 Spring Cloud 的一个 HTTP 客户端，面试官问两句就没了。gRPC 性能最强，但面试官不熟、生态不如 Dubbo。

**选 Dubbo 不是因为它比 Feign 快多少，是面试需要 Dubbo。**

### SPI 扩展机制（面试必问）

Java SPI：`ServiceLoader` 加载所有实现，无 IoC / AOP。
Dubbo SPI：`@SPI` + `@Adaptive`，按需加载，支持 IoC（自动注入）、AOP（Wrapper 包装）。

### 负载均衡

5 种：加权随机（默认）、最少活跃、一致性哈希、最短响应、加权轮询。
本项目：秒杀用最少活跃（请求耗时差异大）、用户用加权随机、排行榜用一致性哈希（带缓存）。

### 容错策略

秒杀下单用 **Failfast**——失败立即报错，不做重试，防止重复扣库存。
查询用 **Failover**——失败自动切到其他节点。

### 线程模型

Dubbo 默认：IO 线程（Netty EventLoop）+ Biz 线程池（200 个平台线程）。
本项目：Biz 线程池改为虚拟线程 Executor，IO 线程保持不变。200 → 无上限（由内存决定）。

## 3. 网关：Spring Cloud Gateway (WebFlux)

### 为什么选 WebFlux

| 维度 | SCG WebFlux | Zuul |
|------|-------------|------|
| 线程模型 | 响应式（EventLoop） | 同步（阻塞） |
| 性能 | 非阻塞，线程数 = CPU 核数 | 每个请求占一个线程 |
| 社区 | Spring Cloud 官方，活跃 | 已停更 |
| 限流集成 | ✅ Sentinel 原生支持 | ❌ |

### 内核心理由

Gateway 是 IO 密集中的 IO 密集——只做路由转发和鉴权，没有业务逻辑。WebFlux 的少量 EventLoop 线程就能处理大量并发连接，不会成为瓶颈。

### WebFlux + ScopedValue 的注意事项

> ⚠️ 不推荐在 WebFlux Filter 中直接用 `ScopedValue.where().call()` 传用户上下文。WebFlux 的响应式链路中线程可能切换，ScopedValue 绑定在当前 Thread 上，切换后丢失。正确做法：存入 `exchange.getAttributes()` → 转发前写入 Header → 下游 MVC 服务提取后赋值 ScopedValue。

### 和虚拟线程的矛盾

本项目 Gateway 用 WebFlux（响应式），业务服务用虚拟线程（同步阻塞），两套哲学共存。Gateway 无业务逻辑，WebFlux 天生适合；业务服务有加锁/事务/状态机，VT 更适合。作为技术展示是合理的。

## 4. 用户上下文：ScopedValue

### 为什么选 ScopedValue 不选 ThreadLocal

| 维度 | ThreadLocal | ScopedValue |
|------|------------|-------------|
| 内存 | 每个 Thread 有 Map，未 set 也占 16 slot | 没 bound 不占内存 |
| VT 池化 | 残留 → 内存泄漏 | 作用域结束自动清理 |
| pinning | synchronized 会导致 VT pinned | 不相关 |
| 可变性 | 可随意修改 | 不可变，bind 后不能改 |

### 面试必答

> ThreadLocal 即使不 set，Map 数组也会占用内存。N 个 VT 就有 N 个 16-slot 数组。ScopedValue 没有 bound 的 VT 不占任何内存。

代码实现详见 `2.1-公共模块.md`。

## 5. 缓存：Caffeine + Redis

### 三级缓存架构

| 层级 | 实现 | 速度 | 容量 | 一致性问题 |
|------|------|------|------|-----------|
| L1 | Caffeine（堆内） | 纳秒级 | 10000 条 | 各节点不一致 |
| L2 | Redis（远程） | 毫秒级 | 大量 | 一致性强 |
| L3 | MySQL（兜底） | 10ms 级 | 全量 | 强一致 |

### 为什么不是 Guava 或 Ehcache

Guava Cache 功能弱，不支持 refreshAfterWrite 的异步刷新。Ehcache 太重，有持久化和集群功能，单项目不需要。

Caffeine 的 `refreshAfterWrite` 是异步的——读请求不阻塞，后台线程刷新，适合高并发秒杀场景。

### 三大问题 + 解决方案

| 问题 | 场景 | 方案 |
|------|------|------|
| 穿透 | 攻击者查不存在的 key | 布隆过滤器 + 缓存空值 + 接口签名 |
| 击穿 | 热点 key 过期瞬间大量请求 | 本地缓存不过期 + 互斥锁重建 |
| 雪崩 | 大量 key 同时过期 | TTL 随机化（60~300s）|

### 秒杀专用策略

本地缓存存"是否有库存"标记（boolean），1s 刷新。请求先查本地——显示无库存直接返回售罄，过滤掉大部分请求，防止 Redis 被打爆。

### 缓存一致性方案

多级缓存（Caffeine + Redis + MySQL）在写操作时的一致性问题：

| 方案 | 步骤 | 风险 | 本项目 |
|------|------|------|--------|
| Cache Aside | 读 miss 回填；写 DB 前删缓存 | 删缓存→写 DB 之间有并发读到旧数据 | 不适用 |
| 延迟双删 | 写 DB → 删缓存 → sleep → 再删缓存 | sleep 不优雅，高并发下 sleep 长 | 不适用 |
| **最终一致性（本项目）** | 写 DB → 发 Kafka → 消费者删/刷新缓存 | 短暂不一致（秒级），自动纠正 | ✅ 适用 |

秒杀场景接受秒级不一致——库存扣减走 Redis Lua（实时精确），订单状态变更走最终一致（Kafka 消费后刷新缓存）。面试必答：为什么能接受最终一致？因为秒杀结果通过 WebSocket 实时推送，用户已知道结果；缓存中的订单列表差一秒不影响体验。

## 6. 限流：Sentinel

### 为什么选 Sentinel

| 维度 | Sentinel | Hystrix | Resilience4j |
|------|----------|---------|--------------|
| 状态 | 活跃 | 已停更 | 维护中 |
| 限流算法 | 滑动窗口（LeapArray） | 信号量/线程池 | 令牌桶 |
| 热点限流 | ✅ 支持按参数限流 | ❌ | ❌ |
| Dashboard | ✅ 动态调参 | ❌ | ❌ |
| 熔断降级 | ✅ | ✅ | ✅ |

### 本项目用嵌入模式

Sentinel 集成在应用内部，规则通过启动配置加载。省去一个 Dashboard 部署。但要能说出"生产环境用 Dashboard 动态调参"。

### 滑动窗口原理

将 1 秒切为 2 个 500ms 窗口，每个窗口独立计数。当前时间落在哪个窗口就累加到哪个窗口，过期窗口自动废弃。比 `AtomicInteger` 固定窗口精度高一倍。

### 热点参数限流

秒杀接口限制：每个用户每个活动 100 QPS。用 Sentinel 的 ParamFlow 按 `activityId + userId` 分别限流。

## 7. 链路追踪：Micrometer Tracing + Zipkin

### 为什么选这个

Spring Boot 3 原生集成，零配置即可工作。底层用 Brave（Zipkin 的 Java 客户端），自动收集 Dubbo/Kafka/DB 的 trace 信息。

### 不选 Skywalking

Skywalking 功能更强（拓扑图、告警、采样策略），但要安装 Agent 和 OAP 服务，太重。项目选轻量的 Zipkin——一个容器 + 三行配置。

### 面试必答

- `traceId`：全链路唯一（UUID），一次请求一个
- `spanId`：每跳不同，每次 RPC/DB/消息产生新 span
- `parentId`：父 span ID，串联成树
- Zipkin 异步上报，不影响主流程

## 8. 分布式 ID：Snowflake

### 为什么选 Snowflake 不选 UUID

| 维度 | Snowflake | UUID |
|------|-----------|------|
| 长度 | 64bit long（8 字节） | 128bit（36 字节字符串） |
| 有序性 | 时间戳高位，单调递增 | 完全无序 |
| 索引性能 | 好（B+Tree 顺序插入） | 差（页分裂） |
| 可反解 | ✅ 反解时间戳和机器 | ❌ |

MySQL InnoDB 主键是聚簇索引，UUID 的随机顺序会导致频繁的页分裂和索引重建。Snowflake 的时间戳高位天然有序。

结构（64bit：0 + 41bit 时间戳 + 10bit workerId + 12bit 序列号）和时钟回拨处理详见 `2.1-公共模块.md`。

## 10. 注册中心：Nacos

### 为什么选 Nacos 不选 Zookeeper / Consul

| 维度 | Nacos | Zookeeper | Consul |
|------|-------|-----------|--------|
| CAP | CP + AP 可切换 | CP 强一致 | CP 强一致 |
| 健康检查 | 客户端心跳 + 服务端探测 | Session 超时（被动） | 客户端心跳 + TCP/HTTP 探测 |
| 配置中心 | ✅ 原生支持 | ❌ 需额外搭建 | ✅ 原生 KV |
| 与 Dubbo 集成 | ✅ 原生支持 | ✅ | ❌ 需适配 |
| 动态路由 | ✅ 支持 | ❌ | ✅ 支持 DNS |
| 运维复杂度 | 中（一个进程搞定注册+配置） | 中 | 中 |
| 社区活跃度 | 阿里维护，活跃 | 成熟但慢 | 中 |

### 核心理由

Nacos = 注册中心 + 配置中心，一个中间件同时解决两个问题。Dubbo 对 Nacos 的支持是第一优先级（Dubbo 3.x 官方推荐），不需要额外适配。

### 不选 Zookeeper

ZK 的 CP 强一致性在主节点故障时会导致短暂不可用（Leader 选举期间拒绝写请求），这对秒杀场景不友好。而且 ZK 只能做注册中心，配置管理还得再搭一套。

### 不选 Consul

Consul 和 Dubbo 的集成不如 Nacos 丝滑，需要额外写适配。而且国内大厂面试更熟悉 Nacos（阿里系），选它等于递话头。

### Nacos 配置中心

本项目默认用本地 yml（简单，docker compose 无额外依赖），但通过 Nacos Config 支持热更新（Sentinel 规则、排行榜权重配置）。面试时可说"生产环境全部走 Nacos Config"。

### 面试追问

- 🔹 CAP 模式下 Nacos 怎么选：注册中心用 AP（优先可用性），配置中心用 CP（优先一致性）
- 🔹 Nacos vs Eureka：Eureka 已停更，Nacos 功能更全
- 🔹 Nacos 挂了怎么办：Dubbo 有本地缓存，已注册的服务不受影响，新服务无法注册但已有调用链路不断

## 11. 认证：双 Token

### 对比表

| 维度 | Session | 纯 JWT | 双 Token |
|------|---------|--------|----------|
| 状态 | 有状态（每次查 Redis） | 无状态（零 IO） | Access 无状态 + Refresh 有状态 |
| 可撤销 | ✅ 删 Redis 即可 | ❌ 不可撤销 | ✅ 删 Refresh 即可 |
| 移动端 | Cookie 不好用 | Header 完美 | Header + 本地存储 |
| 高并发性能 | ❌ 10w QPS = 10w 次 Redis IO | ✅ 仅验签 | ✅ 99% 请求仅验签 |
| 面试深度 | 低 | 中 | **高** |

### 核心权衡

Session 每次请求查 Redis，10w QPS 就是 10w 次 IO，和秒杀 Lua 抢同一事件循环。纯 JWT 无 IO，但泄露后不可撤销。

双 Token 是黄金分割点：Access Token 用 JWT（无状态、快），Refresh Token 存 Redis（有状态、可撤销）。Access 15min 内泄露影响有限，Refresh 可随时踢下线。

### 性能量化

```
Session：10,000 QPS × 1 次 Redis GET = 10,000 次 IO
双 Token：10,000 QPS × 0 次 IO（仅 JWT 验签）
          + 10,000 用户 ÷ 900s ≈ 11 次 Redis 刷新/秒
差 900 倍。
```

## 12. 数据库：MySQL 8.x

### 为什么选 MySQL 不选 PostgreSQL

| 维度 | MySQL 8.x | PostgreSQL 16 |
|------|-----------|---------------|
| 面试频率 | **高**（国内大厂首选） | 中（外企/新兴公司） |
| 并发控制 | MVCC（UNDO 日志） | MVCC（元组版本链） |
| 连接模型 | 线程池（每连接一线程） | 进程模型（每连接一进程） |
| 索引 | 聚簇索引（InnoDB） | 堆表 + 非聚簇索引 |
| 运维生态 | 极成熟，资料丰富 | 社区活跃但人数少 |

MySQL InnoDB 聚簇索引 + Snowflake 有序主键 = B+Tree 顺序插入，页利用率高。面试官对 MySQL 的 MVCC / 锁机制 / 执行计划普遍更熟，能接住追问。PostgreSQL 功能更先进但面试切入点少。
