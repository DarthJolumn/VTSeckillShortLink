## 二、RPC 与通信

### 4. RPC：Dubbo ✅

| 维度 | Dubbo | Feign | gRPC |
|------|-------|-------|------|
| 协议 | 自定义 TCP（Header 16 字节） | HTTP/1.1 | HTTP/2 |
| 序列化 | Hessian2（二进制） | JSON（文本） | Protobuf（二进制） |
| 长连接 | ✅ 单一长连接 | ❌ 每次新建 | ✅ HTTP/2 多路复用 |
| 服务治理 | 内置 5 种 LB + 多种容错 | ❌ 需配合全家桶 | ❌ 无内置 |
| SPI | ✅ 完善 | ❌ | ❌ |
| 面试深度 | **高**（SPI/自适应/协议栈） | 低 | 中 |

| 项目 | 内容 |
|------|------|
| 决策 | Dubbo 作为唯一 RPC |
| 不选 Feign | HTTP 每次建连，无服务治理，面试问两句就没了 |
| 不选 gRPC | 性能最强，但面试官不熟、生态不如 Dubbo |
| 线程模型 | IO 线程 Netty EventLoop + Biz 线程池改为 VT |
| 负载均衡 | 秒杀用最少活跃、用户用加权随机、排行榜用一致性哈希 |
| 容错 | 秒杀用 Failfast（防重复扣库存），查询用 Failover |

> **选 Dubbo 不是因为它比 Feign 快多少，是面试需要 Dubbo。**

面试追问：SPI vs Java SPI、一致性哈希的虚拟节点、Dubbo 线程模型与 VT 结合的坑。

🔄 关联待实现：`6.1-待决策事项.md` §一 RPC 三协议对比压测。

### 7. 缓存多级策略 ✅

| 层级 | 实现 | 速度 | 容量 | 场景 |
|------|------|------|------|------|
| L1 | Caffeine（堆内） | 纳秒 | 10000 条 | 秒杀库存标记、热点活动信息 |
| L2 | Redis（远程） | 毫秒 | 大量 | 分布式数据：库存、排行榜、会话 |
| L3 | MySQL（兜底） | 10ms | 全量 | 最终数据源 |

**Caffeine 选 refreshAfterWrite 不选 expireAfterWrite 的原因：**

| 策略 | 行为 | 高并发表现 |
|------|------|----------|
| expireAfterWrite | 过期后下次读同步阻塞重建 | 击穿 |
| refreshAfterWrite | 过期后异步刷新，返回旧值 | 不阻塞 |

秒杀专用：Caffeine 存"是否有库存" boolean 标记，1s 刷新，过滤无库存请求 → 减少 90% Redis 压力。

### 9. 分布式 ID：Snowflake ✅

| 段 | 位数 | 说明 |
|----|------|------|
| 符号位 | 1 | 始终 0 |
| 时间戳 | 41 | epoch `1735689600000L`（2025-01-01），与 2.1 一致，可用 69 年 |
| workerId | 10 | 0~1023，环境变量注入 |
| 序列号 | 12 | 0~4095，同一毫秒递增 |

时钟回拨处理（与 2.1 一致）：
- ≤30ms：先 unlock → sleep → 重新 lock → `Math.max(lastTimestamp + 1, currentTimeMillis)` 保证单调
- >30ms：抛异常，人工介入（NTP 校时通常 10~50ms，30ms 覆盖 95% 场景）

面试追问：Snowflake vs UUID vs Leaf（美团）。

## 六、认证与安全

### 14. 双 Token 认证 ✅

| 维度 | Session | 纯 JWT | 双 Token |
|------|---------|--------|----------|
| 状态 | 有状态（每次查 Redis） | 无状态（零 IO） | Access 无状态 + Refresh 有状态 |
| 可撤销 | ✅ 删 Redis | ❌ | ✅ 删 Refresh |
| 高并发 | ❌ 10w 次 IO | ✅ 仅验签 | ✅ 11 次刷新/秒 |
| 面试深度 | 低 | 中 | **高** |

| Token | 有效期 | 存储 | 用途 |
|-------|--------|------|------|
| Access JWT | 15min | 无状态（JWT payload）| 99% 业务请求 |
| Refresh | 7 天 | Redis（可撤销） | 换 Access |

设计细节（已定案，代码见 `2.2-用户服务与认证.md`）：
- **Rotation**：刷新时生成新 Refresh Token，旧 Token 作废——泄露检测
- **并发刷新**：SETNX 分布式锁 + CompletableFuture 合并，TTL 3s 防死锁
- **WebSocket 认证**：连接 URL Query 带 Access Token，@OnOpen 中验签

🔄 待细化：
- Token App 端存储（SharedPreferences vs Keychain/Keystore）
- 登录保护异地检测（对比登录 IP 与历史 IP）

## 七、服务治理

### 16. 注册中心：Nacos ✅

| 维度 | Nacos | Zookeeper | Consul |
|------|-------|-----------|--------|
| CAP | CP + AP 可切换 | CP 强一致 | CP 强一致 |
| 健康检查 | 客户端心跳 + 服务端探测 | Session 超时 | 客户端心跳 +TCP/HTTP 探测 |
| 配置中心 | ✅ 原生支持 | ❌ 需额外搭建 | ✅ 原生 KV |
| 与 Dubbo 集成 | ✅ 原生支持 | ✅ | ❌ 需适配 |

| 项目 | 内容 |
|------|------|
| 决策 | Nacos 单实例，同时做注册中心和配置中心 |
| 不选 ZK | CP 强一致性 Leader 选举期间拒绝写请求，秒杀场景不友好 |
| 不选 Consul | Dubbo 集成不如 Nacos 丝滑，需额外适配 |
| 配置方式 | 默认用本地 yml，Nacos Config 支持热更新（Sentinel 规则、排行榜权重） |

面试追问：CAP 模式选择——注册中心用 AP（优先可用性），配置中心用 CP（优先一致性）。Nacos 挂了 Dubbo 有本地缓存，已注册服务不受影响。

### 17. 配置中心：Nacos Config ✅

| 项目 | 内容 |
|------|------|
| 决策 | Nacos Config，与注册中心共用同一实例 |
| 不选 Apollo | 功能强但太重，单人项目不需要灰度/回滚 |
| 当前策略 | 本地 yml 为主，动态配置（Sentinel 规则、排行榜权重）走 Nacos Config |

面试追问：生产环境建议全部走 Nacos Config，配合 `@RefreshScope` 热更新。
