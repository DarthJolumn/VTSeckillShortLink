## 🎯 Q1：ZGC vs G1

### 升级话术

> 根据我们压测监控，4GB 堆峰值下 G1 的 856ms STW 全部是 Evacuation Pause，并非 Full GC。根本原因是秒杀扣减库存时短生命周期对象分配速率极高，G1 在 Mixed GC 阶段需要复制大量存活对象到 Survivor/Old 区，当复制量超过预期阈值时，STW 时间随存活对象线性增长。
>
> 分代 ZGC 通过染色指针 + 读屏障将对象转移、重定位等 99% 的工作并发化；同时开启 Proactive 模式后，ZGC 会在堆使用率达到阈值前主动触发回收，避免了 G1 那种"等到空间不够才紧急同步复制"的被动局面，所以 STW 稳定在 3ms。

### 防御补丁

**Q：为什么不用 Shenandoah？**
> JDK 21 下分代 ZGC 是官方主推，且我们的压测数据已验证其满足 P99 要求，技术选型优先选择生态成熟度最高的方案。

### 支撑数据

| 指标 | G1 | 分代 ZGC |
|------|-----|-----------|
| GC 总耗时（90s 压测） | 0.856s | 0.003s |
| 耗时倍数 | 1× | 285× |
| 全部是 STW Evacuation Pause | ✅ | — |
| 全部是 Proactive 主动触发 | — | ✅ |
| Full GC | 0 | 0 |
| 堆峰值 | ~4GB | ~4GB |

## 🎯 Q2：瓶颈定位（异步改造后重新验证）

### 升级话术

> SkyWalking 链路追踪定位 Kafka Producer 同步发送等待，最长 **3342ms** 为瓶颈（Consumer 侧入库仅数 ms）。改为异步 `addCallback()` 削峰后全链路阶梯加压（10→600 并发）确认：
>
> | 线程 | TPS | Avg | P99 |
> |------|-----|-----|-----|
> | 200 | 1,278 | 9ms | 52ms |
> | **300** | **1,513** | **26ms** | **92ms** |
> | 400 | 1,661 | 35ms | 122ms |
> | 600-10（快斜坡） | **2,065** | 133ms | 268ms |
>
> 结论：**300 线程为甜点（TPS 1513 / P99 92ms），快斜坡峰值可达 2065 TPS**。单机限流阈值定为 **300 并发 / 1500 QPS**。

### 防御补丁

**Q：Kafka Producer 同步发送等待 3342ms 怎么发现的？**
> SkyWalking 链路追踪面板直接显示 `/seckill/order` 端点下有 Kafka/seckill-order/Producer span 耗时最长 3342ms，Consumer 侧入库仅几 ms，立即锁定 Producer 同步等待为瓶颈。

**Q：为什么不优化 Kafka 本身（如批量、压缩）？**
> `send().get(3s)` 是同步阻塞等待 Broker ack，瓶颈在网络往返而非吞吐。改为 `addCallback()` 异步化后 3s 超时消失，P99 降 65%，Kafka 侧未做任何调优。

## 🎯 Q3：背压与虚拟线程

### 升级话术

> 虚拟线程堆积的本质是消费速率 > DB 处理速率时，VT 在 DB IO 上阻塞后会 unmount 载体线程，但 Kafka poll 循环仍在载体线程上持续拉取新消息并创建新 VT，最终导致百万级 VT 耗尽 heap。
>
> 我们在载体线程层（而非 VT 内部）前置 Semaphore，上限对齐 HikariCP 池大小（30）。当信号量耗尽时，直接阻塞 poll 循环本身，迫使 Kafka Consumer 停止拉取，Broker 端自然触发背压降速。这比在 VT 内做限流更彻底——因为连消息都不会被拉进内存。
>
> 对吞吐量的影响是可控的：引入背压后 P99 延迟从波动剧烈变为平稳，且彻底杜绝了 OOM 风险。这是用极小的吞吐代价换取系统确定性。

### 防御补丁

**Q：为什么不用 Kafka 自带的 `max.poll.records` 限流？**
> `max.poll.records` 是静态配置，无法动态感知下游 DB 的实际处理能力。当 DB 变慢时，即使每次只拉 10 条，VT 仍会堆积。Semaphore 是动态自适应的——下游快就多消费，下游慢就自动阻塞，才是真正的端到端背压。

**Q：信号量耗尽时阻塞 poll，会不会导致 Consumer 心跳超时触发 Rebalance？**
> 不会。`max.poll.interval.ms` 默认 5min，我们的 `SEM.acquire()` 阻塞是等待 VT 完成 DB 写操作释放信号量，平均等待时间在 VT 正常处理时间量级（毫秒级），远低于心跳超时阈值。实测从未因背压触发 Rebalance。

## 🛡️ 数据一致性五道防线（升级版）

> 以下五个防线按"执行顺序"排列，面试时从前往后讲，形成"层层递进"的叙事线。

### 第 1 道：扣减原子性 — Redis Lua 查重-扣减-标记

**一句话**：一条 Lua 脚本内完成「查重 → DECR 扣减 → SETEX 标记」三个操作，保证原子性。

**为什么需要**：Web 层可能并发到达同一 userId 的请求（重复点击、重试），如果不做查重标记，同一用户在同一场活动里多次扣减。MySQL 层面虽有唯一索引，但先减后回补浪费性能且可能超卖。

**实现细节**：
```lua
-- KEYS[1] = stock:{activityId}  KEYS[2] = ordered:{activityId}:{userId}
-- ARGV[1] = "1" 启用去重 / "0" 跳过去重（压测开关）

local dedup = ARGV[1] ~= "0"
if dedup then
    local ordered = redis.call("GET", KEYS[2])
    if ordered then return -1 end   -- 已参与，返回重复
end

local stock = redis.call("DECR", KEYS[1])
if stock >= 0 then
    if dedup then redis.call("SETEX", KEYS[2], 86400, "1") end
    return 200
end
redis.call("INCR", KEYS[1])  -- 扣超了回滚
return -2
```

**Hash Tag 同槽**：库存 key 和去重 key 都包含 `{activityId}` 作为 Redis Cluster Hash Tag，保证两条 key 落在同一 slot、同一节点，Lua 执行时无需跨节点转发。

**追问：为什么不用 MULTI/EXEC 事务？**
> Redis 事务不支持条件回滚——无法做到"DECR 后如果 < 0 就取消扣减"。Lua 脚本是原子执行的，且支持 if/else 逻辑，天然解决这个问题。

### 第 2 道：超时取消 — 定时扫描兜底（当前实现）

**一句话**：`@Scheduled` 每 15s 扫描超时未支付订单，逐条 refund 回补库存。

**代码结构**：
```java
@Scheduled(fixedDelayString = "${seckill.timeout-scan-ms:15000}")
public void cancelTimeoutOrders() {
    if (!timeoutCancelEnabled) return;            // 压测时关闭
    List<SeckillOrder> timeoutOrders =
        orderRepo.findByStatusAndCreatedAtBefore(0, deadline);
    for (SeckillOrder order : timeoutOrders) {
        Thread.startVirtualThread(() -> {
            stockService.refund(...);              // Lua EXISTS 校验幂等
            cacheService.markInStock(...);         // 刷新 Caffeine 售罄状态
            order.setStatus(2);                    // DB 更新
            orderRepo.save(order);
        });
    }
}
```

**防重入**：`refund_stock.lua` 先 `EXISTS` 检查 ordered key，只有存在才 `INCR + DEL`，不存在直接跳过，保证幂等。

**追问：为什么不加 Kafka 延迟消息做精确触发？**
> 当前定时扫描 15s 间隔已覆盖超时场景（超时阈值为 15min），15s 的延迟相对于 15min 可忽略。加入 Kafka 延迟消息架构复杂度上升，实际收益有限。这是优先级取舍，不是技术不能。

> ⚠️ 面试注意：如果你的简历写了"Kafka 延迟消息精确触发"，面试官追问实现细节就穿帮了。要么删掉，要么确实实现后再写。

### 第 3 道：DB 最终兜底 — 双重唯一键幂等

**一句话**：DB 层面两重唯一约束兜住任何漏网的重复订单，捕获 `DuplicateKeyException` 直接 ACK 跳过。

**实现**：

| 约束 | 作用 |
|------|------|
| `order_no` 唯一索引 | 同一订单号不会入库两次 |
| `(activity_id, user_id)` 联合唯一 | 同一用户同一活动只能有一条记录 |

**消费端处理**：
```java
} catch (DuplicateKeyException e) {
    log.warn("重复订单（幂等兜底）: orderNo={}", e.getMessage());
    ack.acknowledge();
}
```
无论 Redis 去重是否漏过（极端情况），DB 唯一键是最终的不可绕过的防线。

**追问：为什么不用 select-before-insert？**
> select-before-insert 不是原子操作，并发下可能两条线程同时 select 返回空、同时 insert，唯一索引直接抛异常天然保证原子性——`try-insert-catch-DuplicateKeyException` 是秒杀场景的标准模式。

---

### 第 4 道：Redis 故障安全 — 强制走 Master

**一句话**：Redis Cluster 下所有库存操作（Lua 脚本含写命令）天然路由到 slot 所在 Master 节点，禁掉读写分离避免主从异步复制导致超卖。

**为什么安全**：
- Lua 脚本内的 `DECR`、`SETEX`、`INCR` 都是写命令，Cluster 自动转发到 Master
- `StringRedisTemplate` 默认 `ReadFrom.MASTER`，读也走 Master
- 没有额外配置 `readFrom.REPLICA_PREFERRED`，杜绝主从复制延迟导致的"已售罄但从库还显示有库存"

**追问：Master 挂了怎么办？**
> Redis Cluster 自动故障转移（failover），从节点晋升 Master，期间秒杀请求短暂不可用。这在秒杀场景是可接受的——宁可短暂拒绝，也不能超卖。这正是"一致性优于可用性"的 trade-off。

### 第 5 道：退款幂等 — Lua EXISTS 前置校验 + 原子回补

**一句话**：`refund_stock.lua` 先 `EXISTS` 验证 ordered key，存在才 `INCR` 回补 + `DEL` 标记，不存在直接跳过，天然幂等。

**源码**（9 行，完整可读）：
```lua
-- KEYS[1] = stock:{activityId}   KEYS[2] = ordered:{activityId}:{userId}
if redis.call("EXISTS", KEYS[2]) == 1 then
    redis.call("INCR", KEYS[1])
    redis.call("DEL", KEYS[2])
end
return 1
```

**防重入场景**：
1. 用户主动取消 → timeout 扫描又触达 → lua EXISTS 为 0 → 跳过，不多退
2. 退款接口幂等 → 连续调用两次 → 第一次已 DEL，第二次 EXISTS=0 → 跳过
3. Kafka 不可用 Fail Fast 回补 → refund + 异常上抛 → 重启后重试 → EXISTS=0 跳过

**追问：业务退款不入账怎么办？**
> 退款分两步：① Redis 回补库存 ② DB 更新订单状态为已取消。① 由 Lua 脚本保证原子幂等，② 由 `@Transactional` + `@Version` 乐观锁保证。Redis 失败时抛异常回滚整个事务，DB 不会更新——不会出现"库存已补但订单状态仍为待支付"的不一致状态。

### 五道防线协作关系（面试必讲）

面试时画一条从请求到入库的路径线：

```
用户点击 "抢购"
       ↓
     Web 层（Bloom + Caffeine + 限流）
       ↓
┌ 1. Redis Lua 【查重→扣减→标记】 ← Hash Tag 保证同 slot
│  (扣减失败 → 直接返回 库存不足 / 重复下单)
│
├ 2. 异步投递 Kafka → Consumer
│       ↓
│   Consumer 处理
│       ↓
├ 3. DB 兜底 【order_no 唯一 + activity_user 联合唯一】
│   DuplicateKeyException → 幂等 ACK
│       ↓
│   成功 → 手动 ACK → 完成
│   超时未支付
│       ↓
├ 4. 定时扫描（每 15s）→ refund（Lua EXISTS 幂等）
│   + Fail Fast 回补（Kafka 不可用时）
│       ↓
├ 5. 退款幂等 → Lua EXISTS 前置校验 → 原子 INCR
```

每一道防线都是上一道的兜底：
- Redis 没拦住 → DB unique key 拦住
- DB 数据产生了（超时未支付）→ 定时扫描回收
- 人回来了要取消 → refund Lua 保证幂等不超退
