## 一、登录弹窗一体化（登录 + 注册）

### 1.1 设计目标

v1 的登录弹窗只有一个登录表单。v2 的弹窗支持登录/注册双 Tab 切换，让新用户在一次交互中完成注册+登录，无缝回到之前的操作。

### 1.2 组件结构

```
LoginModal.vue
├── Tab: 登录 | 注册
├── LoginForm
│   ├── username + password
│   ├── "忘记密码"链接（v2 暂不实现）
│   └── 提交 → userStore.login() → onSuccess callback
└── RegisterForm
    ├── username + password + confirmPassword + phone(可选)
    ├── 提交 → userStore.register() → 自动登录 → onSuccess callback
    └── 注册成功提示："注册成功，已自动登录"
```

### 1.3 状态机

```
弹窗状态：IDLE → LOGIN_FORM | REGISTER_FORM
         → LOADING → SUCCESS → CLOSE
         → ERROR（show error, stay in form）
```

### 1.4 关键交互

```
用户点击秒杀
  → 未登录 → 弹出 LoginModal（默认登录 Tab）
  → 新用户切换到注册 Tab
  → 填写信息 → 提交注册
  → userStore.register() 成功
  → userStore.login() 自动登录（用刚注册的凭据）
  → onSuccess callback → 继续秒杀流程
  → 弹窗关闭
```

### 1.5 实现要点

```js
// composables/useLoginModal.js
export function useLoginModal() {
  const visible = ref(false)
  const activeTab = ref('login')  // 'login' | 'register'
  let resolveCallback = null      // Promise resolve for awaiting login

  function show(options = {}) {
    activeTab.value = options.tab || 'login'
    visible.value = true
    return new Promise((resolve) => {
      resolveCallback = (user) => {
        visible.value = false
        resolve(user)
      }
    })
  }

  async function handleLogin(credentials) {
    try {
      await userStore.login(credentials)
      resolveCallback?.(userStore.userInfo)
    } catch (e) {
      throw e  // 表单展示错误
    }
  }

  async function handleRegister(form) {
    await userStore.register(form)
    // 注册成功自动登录
    await userStore.login({
      username: form.username,
      password: form.password,
    })
    resolveCallback?.(userStore.userInfo)
  }

  return { visible, activeTab, show, handleLogin, handleRegister }
}
```

### 1.6 设计模式

- **Promise 化弹窗**：`show()` 返回 Promise，调用方 `await` 等待用户操作完成，避免回调嵌套
- **状态机**：弹窗状态（表单 / loading / success / error）用状态机管理，清晰可测试

## 二、差异化限流

### 2.1 问题

v1 中所有用户共享同一限流策略。实际直播平台中：

- 匿名用户发弹幕频率应远低于登录用户（防刷屏机器人）
- 低信誉用户应比高信誉用户限流更严
- 秒杀接口对匿名用户应直接拒绝（不弹登录窗，直接提示）

### 2.2 分级限流策略

| 接口 | 匿名 | 观众（已登录） | 主播 | 管理员 |
|------|------|-------------|------|--------|
| 弹幕发送 | 拒绝 | 1 条/2s | 无限制 | 无限制 |
| 礼物发送 | 拒绝 | 1 次/3s | 无限制 | 无限制 |
| 秒杀下单 | 拒绝 | 1 次/活动（业务层一人一单） | 同左 | 同左 |
| 直播间信息查询 | 100 QPS/IP | 100 QPS/user | 同左 | 同左 |
| 排行榜查询 | 100 QPS/IP | 100 QPS/user | 同左 | 同左 |

### 2.3 实现方案

#### 方案 A：Sentinel 热点参数 + 用户等级（推荐）

```java
// Sentinel 规则：按 userId 热点限流，userId=null 时走 IP 限流
@PostMapping("/live/barrage")
@RequireAuth
@SentinelResource(
    value = "sendBarrage",
    paramIndex = 0,  // userId
    fallback = "barrageRateLimitFallback"
)
public Result<Void> sendBarrage(@RequestHeader("X-User-Id") Long userId, ...) {
    // 业务逻辑
}

// Sentinel 控制台规则
// 资源: sendBarrage
// 热点参数索引: 0 (userId)
// 阈值: 1 QPS/user（已登录），100 QPS/IP（匿名）
```

#### 方案 B：`@RateLimit` 自定义注解（更灵活）

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    /** 时间窗口，秒 */
    int window() default 1;

    /** 窗口内最大请求数 */
    int maxRequests() default 10;

    /** 限流维度：IP / USER / GLOBAL */
    Dimension dimension() default Dimension.USER;

    /** 匿名用户的限流维度（覆盖 dimension） */
    Dimension anonymousDimension() default Dimension.IP;

    /** 匿名用户的最大请求数（覆盖 maxRequests） */
    int anonymousMaxRequests() default 2;

    enum Dimension { IP, USER, GLOBAL }
}
```

```java
// 使用
@PostMapping("/live/barrage")
@RequireAuth
@RateLimit(window = 2, maxRequests = 1, anonymousMaxRequests = 0)
//                                                       ↑ 0 = 匿名用户直接拒绝
public Result<Void> sendBarrage(...) { ... }

@GetMapping("/live/room/{roomId}")
@PublicApi
@RateLimit(window = 1, maxRequests = 100, anonymousDimension = IP, anonymousMaxRequests = 100)
public Result<RoomInfoVO> getRoomInfo(...) { ... }
```

### 2.4 拦截器实现

```java
@Component
public class RateLimitInterceptor implements HandlerInterceptor {

    private final ReactiveStringRedisTemplate redis;  // 或 Lettuce

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        if (!(handler instanceof HandlerMethod hm)) return true;
        RateLimit rl = hm.getMethodAnnotation(RateLimit.class);
        if (rl == null) return true;

        Long userId = UserContext.currentUserId();
        boolean isAnonymous = userId == null;

        String key;
        int maxRequests;
        if (isAnonymous) {
            String ip = getClientIp(request);
            key = "rl:" + hm.getMethod().getName() + ":ip:" + ip;
            maxRequests = rl.anonymousMaxRequests();
        } else {
            key = "rl:" + hm.getMethod().getName() + ":user:" + userId;
            maxRequests = rl.maxRequests();
        }

        // Redis INCR + TTL
        Long count = redis.opsForValue().increment(key);
        if (count == 1) {
            redis.expire(key, Duration.ofSeconds(rl.window()));
        }
        if (count > maxRequests) {
            sendRateLimited(response, "操作太频繁，请稍后再试");
            return false;
        }
        return true;
    }
}
```

### 2.5 设计模式

- **注解驱动策略**：`@RateLimit` 的不同参数组合 = 不同限流策略，不改拦截器代码
- **拦截器链**：`AuthInterceptor → RateLimitInterceptor → Controller`，各司其职

## 三、设备指纹 + 匿名用户行为追踪

### 3.1 设计目标

匿名观看模式下，需要识别"同一个匿名用户"以支持：

- 匿名用户行为统计（停留时长、观看直播间数、点击率）
- 后续推荐系统的基础数据
- 防刷量（同一设备频繁注册多个账号）

### 3.2 设备指纹生成

当前已经有 `X-Device-Id`（UUID v4 存 localStorage），但可以增强：

```js
// 前端 infra/device.js
// 增强版设备指纹：多维度合成
function generateFingerprint() {
  const components = {
    userAgent: navigator.userAgent,
    language: navigator.language,
    screenRes: `${screen.width}x${screen.height}`,
    timezone: Intl.DateTimeFormat().resolvedOptions().timeZone,
    canvas: getCanvasFingerprint(),       // Canvas 指纹（可选，有隐私顾虑）
    webgl: getWebGLFingerprint(),         // WebGL 指纹（可选）
  }
  const raw = JSON.stringify(components)
  return simpleHash(raw)  // SHA-256 前 16 位
}
```

**折中方案**：v2 先用 UUID + UserAgent + Screen 三个低隐私维度的组合哈希。Canvas/WebGL 指纹有隐私争议，v2 不做，面试时可提"后续可加"。

### 3.3 匿名用户追踪数据模型

```java
// 匿名用户在 Redis 中的行为记录
// Key: anonymous:{fingerprint}
// Type: Hash
// Fields:
//   first_seen: timestamp（首次出现）
//   last_seen: timestamp（最后活跃）
//   total_views: int（总观看次数）
//   viewed_rooms: set（看过的直播间 ID）
//   total_duration: long（累计观看时长，秒）
// TTL: 7 天（匿名用户数据定期清理）
```

```java
// 记录匿名用户行为（在 WebSocket @OnOpen / @OnClose 中触发）
public void trackAnonymousBehavior(String fingerprint, String event, Long roomId) {
    String key = "anonymous:" + fingerprint;
    redis.hset(key, "last_seen", String.valueOf(System.currentTimeMillis()));
    redis.hincrBy(key, "total_views", 1);
    redis.sadd(key + ":rooms", roomId.toString());
    redis.expire(key, Duration.ofDays(7));
}
```

### 3.4 登录后合并

用户登录时，将匿名行为数据合并到登录用户：

```
用户登录成功
  → 读取 X-Device-Id 的设备指纹
  → Redis 查 anonymous:{fingerprint}
  → 如果有数据：
      → 合并到 user:{userId}:behavior（Hash）
      → 删除 anonymous:{fingerprint}（或保留做设备关联分析）
      → 记录设备-用户关联：device:{fingerprint} → userId Set
```

**面试价值**：这是推荐系统冷启动问题的经典解法——"匿名阶段积累行为数据，登录后合并，解决新用户无历史数据的问题"。

## 四、游客身份展示

### 4.1 问题

匿名用户进直播间，弹幕区、在线列表里如何显示？需要一个"游客身份"。

### 4.2 方案一：随机游客昵称（推荐 v2）

```
匿名用户在线列表展示：
  "游客_AB3F"     （随机后缀，每个设备指纹稳定）
  "路人_7X2K"
  "观众_K9P1"

生成规则：
  guestName = 词库数组[fingerprint.hashCode() % 词库.length]
            + "_"
            + fingerprint 的前 4 位大写
```

```java
public class GuestNameGenerator {
    private static final String[] PREFIXES = {
        "游客", "路人", "观众", "访客", "吃瓜", "围观"
    };

    public static String generate(String fingerprint) {
        int prefixIdx = Math.abs(fingerprint.hashCode()) % PREFIXES.length;
        String suffix = fingerprint.substring(0, 4).toUpperCase();
        return PREFIXES[prefixIdx] + "_" + suffix;
    }
}
```

### 4.3 方案二：设备名（v3 可考虑）

让用户自定义一个"游客名称"，存 localStorage，类似 B站 的"游客xxx"但可自定义。v2 不做——涉及敏感词过滤 + 额外的并发验证。

### 4.4 游客标识传递

匿名 WebSocket 连接的上行消息（PING、AUTH）中附加 `guestName` 字段，用于在线列表的显示。

## 五、SSO 单点登录

### 5.1 设计目标

降低注册门槛——第三方账号一键登录。

### 5.2 OAuth2 流程（以 GitHub 为例）

```
1. 前端点击 "GitHub 登录"
2. 跳转 GitHub OAuth authorize 页面
   GET https://github.com/login/oauth/authorize?client_id=xxx&redirect_uri=...
3. 用户授权
4. GitHub 回调 redirect_uri → Gateway → /auth/oauth/github/callback?code=xxx
5. 后端用 code 换 access_token → GitHub API 获取用户信息
6. 查找或创建本地用户：
   - 已有关联：直接登录，签发 JWT + Refresh Token
   - 无关联：创建新用户（username = github_username + 后缀）
   - 用户名冲突：加随机后缀，允许后续修改
7. 返回 JWT + Refresh Token → 前端存储 → 关闭弹窗
```

### 5.3 数据模型扩展

```sql
-- t_user 加字段（可空）
ALTER TABLE t_user ADD COLUMN oauth_provider VARCHAR(20);  -- 'github', 'wechat'
ALTER TABLE t_user ADD COLUMN oauth_open_id VARCHAR(100);  -- 第三方用户 ID
ALTER TABLE t_user ADD UNIQUE INDEX idx_oauth (oauth_provider, oauth_open_id);
```

### 5.4 后端接口

```java
// /auth/oauth/github/callback
@GetMapping("/auth/oauth/github/callback")
@PublicApi
public Result<LoginResponse> githubCallback(
    @RequestParam String code,
    @RequestHeader("X-Device-Id") String deviceId) {

    // 1. code → access_token
    String accessToken = oauthService.exchangeCode(code);

    // 2. access_token → GitHub user info
    OAuthUserInfo ghUser = oauthService.getUserInfo(accessToken);

    // 3. 查找或创建本地用户
    User user = userService.findOrCreateByOAuth("github", ghUser.getId(), ghUser.getUsername());

    // 4. 签发 Token
    return Result.ok(userService.issueTokens(user, deviceId));
}
```

### 5.5 v2 的范围

仅实现 GitHub OAuth（只需注册 OAuth App，无需国内审核）。微信登录需要企业资质 + 认证费（300/年），v2 不做但面试时可提"流程相同，接入微信开放平台即可"。

### 5.6 安全考量

| 问题 | 解法 |
|------|------|
| CSRF（state 参数） | OAuth 请求时生成随机 state，存在 Redis，回调时校验 |
| code 重放 | 一次 code 只能换一次 token（GitHub 服务端保证） |
| 本地用户关联 | open_id 唯一索引防重复绑定 |
| 首次注册需绑定手机 | 可选步骤——OAuth 登录后引导绑定手机号（v2 不做强制） |

## 六、敏感接口二次验证（Step-Up Auth）

### 6.1 场景

| 操作 | 风险 | 是否需要二次验证 |
|------|------|----------------|
| 修改密码 | 账号被盗 | 需要（旧密码本身就是验证） |
| 高价值秒杀（如 > 1000 元） | 盗刷 | 推荐 |
| 开播 | 冒名开播 | v2 暂不需要 |
| 删除直播活动 | 误操作 | v2 暂不需要 |

### 6.2 实现方案

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface StepUpAuth {
    /** 二次验证方式：PASSWORD / SMS / TOTP */
    AuthMethod method() default AuthMethod.PASSWORD;

    /** 验证窗口（秒），窗口内重复操作不重复验证 */
    int window() default 300;  // 5min

    enum AuthMethod { PASSWORD, SMS, TOTP }
}
```

```java
// 使用
@PutMapping("/seckill/order/{orderNo}/high-value-action")
@RequireAuth
@StepUpAuth(method = PASSWORD, window = 300)
public Result<Void> highValueAction(@PathVariable String orderNo) {
    // 通过二次验证后才能执行
}
```

### 6.3 拦截器逻辑

```
StepUpAuthInterceptor.preHandle()
  → 检查注解 @StepUpAuth
  → 从 Header 提取 X-StepUp-Token（一次性验证令牌）
  → 无 Token？→ 需要验证
      → 前端弹出二次验证弹窗
      → 用户输入密码 → POST /auth/step-up/verify { password }
      → 后端验证密码 → 签发 StepUp Token（Redis SET, 5min TTL）
      → 前端重发原请求（带 X-StepUp-Token）
  → 有 Token？→ Redis 查 step-up:{userId}:{method}
      → 存在且有效 → 放行，续期 TTL
      → 不存在/过期 → 返回 401 Step-Up Required
```

### 6.4 StepUp Token 设计

```
Key: step-up:{userId}:PASSWORD
Value: nonce（随机字符串）
TTL: 300s（可配置）
验证逻辑：前端 Header X-StepUp-Token = nonce，后端 EXISTS + GET 比对
```

## 七、操作审计日志

### 7.1 设计目标

记录所有敏感操作，用于：

- 安全审计（谁在什么时候做了什么）
- 异常排查（订单为何被取消）
- 面试展示（"我们有完整的审计体系"）

### 7.2 数据模型

```sql
CREATE TABLE t_audit_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT,               -- 操作人（NULL = 系统/匿名）

    role TINYINT,                 -- 操作时的角色

    error_msg VARCHAR(500),       -- 失败原因
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_action (user_id, action, created_at),
    INDEX idx_target (target_type, target_id),
    INDEX idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='操作审计日志';
```

### 7.3 Action 枚举

```java

    // 秒杀
```

### 7.4 实现：AOP + 异步写入

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditLog {
    AuditAction action();
    String targetType() default "";   // SpEL 支持，如 "#roomId"
    String targetId() default "";
    String detail() default "";
}
```

```java
@Aspect
@Component
public class AuditLogAspect {

    private final KafkaTemplate kafka;  // 异步写入，不阻塞主流程

    @Around("@annotation(auditLog)")
    public Object audit(ProceedingJoinPoint pjp, AuditLog auditLog) {
        AuditEntry entry = buildEntry(pjp, auditLog);
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            entry.setResult(1);
            entry.setCostMs(System.currentTimeMillis() - start);
            return result;
        } catch (Exception e) {
            entry.setResult(0);
            entry.setErrorMsg(e.getMessage());
            throw e;
        } finally {
            // 异步发 Kafka，不阻塞主流程
            kafka.send("audit-log", JsonUtil.toJson(entry));
        }
    }
}
```

### 7.5 设计决策：Kafka 异步 vs 直接写 MySQL

| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接写 MySQL | 简单，事务内保证一致性 | 拖慢主流程，审计日志表成为热点 |
| Kafka 异步（推荐） | 不阻塞主流程，削峰填谷 | 极端情况下丢日志（Kafka 挂了） |
| 本地队列 + 批量写 | 无外部依赖 | 进程重启丢日志 |

v2 选 Kafka 异步。面试时可说："审计日志对实时一致性无要求，Kafka 异步写入保证主流程性能。Kafka 挂了的极端情况下，降级为本地日志文件。"

## 八、`@RateLimit` 注解（完整设计）

### 8.1 注解定义

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    /** 时间窗口（秒） */
    int window() default 1;

    /** 窗口内最大请求数 */
    int maxRequests() default 10;

    /** 限流 key 的维度 */
    KeyType keyType() default KeyType.USER;

    /** 超出限制后的等待时间（秒），0 = 直接拒绝 */
    int waitSeconds() default 0;

    /** 限流提示消息 */
    String message() default "操作太频繁，请稍后再试";

    /** 匿名用户的特殊配置 */
    Anonymous anonymous() default @Anonymous;

    @interface Anonymous {
        /** 匿名用户的 maxRequests（覆盖外层），-1 = 使用外层值 */
        int maxRequests() default -1;

        /** 匿名用户的 keyType（覆盖外层） */
        KeyType keyType() default KeyType.IP;
    }

    enum KeyType {
        IP,      // 按客户端 IP
        USER,    // 按 userId
        DEVICE,  // 按设备指纹
        GLOBAL   // 全局（所有用户共享）
    }
}
```

### 8.2 与 Sentinel 的关系

`@RateLimit` 不替代 Sentinel，而是互补：

| 层次 | 工具 | 用途 |
|------|------|------|
| Gateway 层 | Sentinel | 防 DDoS，IP 级熔断，粗粒度 |
| 业务层 | `@RateLimit` | 接口级，用户/设备维度，细粒度 |

`@RateLimit` 拦截器的 Redis 操作走 Lettuce 异步（VT 友好），不阻塞线程。

### 8.3 实现要点

```java
@Component
public class RateLimitInterceptor implements HandlerInterceptor, Ordered {

    // 本地缓存减少 Redis IO（Caffeine）
    private final Cache<String, AtomicLong> localCounter = Caffeine.newBuilder()
        .expireAfterWrite(2, TimeUnit.SECONDS)
        .maximumSize(10_000)
        .build();

    @Override
    public boolean preHandle(...) {
        // 1. 本地计数先挡一道（内存级，避免频繁 Redis IO）
        // 2. 本地超阈值 → Redis 精确计数
        // 3. Redis INCR + 首次 SET TTL（Lua 保证原子性）
        // 4. 超限 → 返回 429
    }

    @Override
    public int getOrder() {
        return 1;  // 在 AuthInterceptor(order=0) 之后
    }
}
```

**面试亮点**：两级计数（Caffeine 本地 + Redis 精确），减少 90% 的 Redis IO。本地计数器用 `AtomicLong`，无需分布式锁。

## 九、拦截器链设计回顾

v1 + v2 全部拦截器形成一条清晰的链：

```
请求进入 MVC 服务
  │
  ├─ [Order 0]  AuthInterceptor          ← v1
  │    ├─ 提取 X-User-Id, X-User-Role → ScopedValue
  │    ├─ @PublicApi    → 放行
  │    ├─ @RequireAuth  → 验 JWT
  │    └─ @RequireRole  → 验 JWT + 角色
  │
  ├─ [Order 1]  RateLimitInterceptor     ← v2
  │    └─ @RateLimit → Caffeine 本地计数 → Redis 精确计数 → 429
  │
  ├─ [Order 2]  StepUpAuthInterceptor    ← v2
  │    └─ @StepUpAuth → 验 X-StepUp-Token → Redis 查有效期
  │
  ├─ [Order 99] Controller
  │
  └─ [AOP]       AuditLogAspect           ← v2
       └─ @AuditLog → Kafka 异步写审计日志
```

**设计模式**：Chain of Responsibility（拦截器链） + Strategy（注解选择策略） + Observer（Kafka 异步审计事件）。
