# 面试准备

> 针对 LiveMall 项目的面试官拷打问题与回答策略。按"项目介绍→架构→技术选型→模块→场景→故障→开放题"层层深入。

---

## 一、项目介绍（30s 电梯演讲）

> 面试开场第一个问题。目标是让面试官 30s 内知道：做什么、技术栈、难点、亮点。

**模板：**

```
我做了一个高并发直播电商秒杀系统，叫 LiveMall。
5 个微服务 + Gateway 统一入口，Java 21 虚拟线程 + Dubbo RPC + Kafka + Redis + MySQL。
核心链路是秒杀抢购：Gateway 限流验签 → 用户服务鉴权 → Redis Lua 原子扣库存 → Kafka 异步
创建订单。难点是库存分片热点、弹幕百万连接推送、实时排行榜。亮点是双 Token 无状态鉴
权、ScopedValue 替代 ThreadLocal、Caffeine+Redis 多级缓存过滤无库存请求。
```

## 二、架构设计追问

### Q1：为什么 5 个微服务？不是应该更多？

**答：** 宁深勿广。5 个服务刚好覆盖面试技术纵深——每个都能挖出面试官想要的东西：
- 用户服务 → 双 Token + BCrypt + 设备管理
- 秒杀服务 → Lua + Kafka + 状态机 + 雪崩防护
- WebSocket → 百万连接 + 跨节点路由 + 踢人 + 心跳
- 排行榜 → ZSet 跳表 + 热冷分离 + 快照
- 网关 → WebFlux + Sentinel + 签名 + 链路追踪

如果拆 15 个服务，每个都浅尝辄止，面试官问两句就没了。

### Q2：Dubbo / Feign / gRPC 为什么选 Dubbo？

**答：** 三个原因：
1. 面试纵深——Dubbo 有 SPI、自适应扩展、5 种负载均衡、多种容错策略，面试官能连问 5 轮
2. 长连接+二进制协议性能好，秒杀场景下请求量大，HTTP 每次建连开销不可忽略
3. 服务治理内置，不用额外搭全家桶

反过来不选 gRPC 是因为：面试官不熟，你讲 Protobuf 他接不住话。不选 Feign 是因为：Spring Cloud 里只是一个 HTTP 客户端，面试问两句就没了。

> 说完补一句：我们也计划做三协议对比压测，到时拿数据说话。

### Q3：虚拟线程和 WebFlux 混用不矛盾吗？

**答：** Gateway 用 WebFlux（响应式），业务服务用 MVC + VT（同步），确实两套哲学。

回答策略：**刻意的技术多样性展示。** Gateway 没有业务逻辑，只有路由转发和鉴权，WebFlux 的少量 EventLoop 就能扛住。业务服务有事务、加锁、状态机，VT 更适合。

生产环境不会混用，但作为技术展示，这恰恰说明我对两种模型都有理解。

### Q4：10w QPS 怎么论证你们扛得住？

**答：** 
- **网关**：WebFlux EventLoop，单机扛 5w QPS 没问题，双实例 10w
- **限流**：Sentinel 热点限流，每个用户每活动 100 QPS，打满 Limit 的请求直接 429
- **库存**：Redis Lua 单机 8w QPS，4 分片 → 32w QPS，瓶颈在 Redis 不在应用
- **下单**：Lua 扣完库存发 Kafka，Kafka 单分区写入 10w+ QPS，消费端 VT 逐条处理
- **数据库**：唯一索引 `uk_activity_user` 兜底防重复，超时取消批量扫描

**瓶颈在哪？** Redis 单机。4 分片后 Redis 依然单线程处理 Lua，实测 8w QPS。10w QPS 需要 2 个 Redis 分片集群，我们用了 4 片余量。

### Q5：SecurityManager 或者权限怎么设计的？

**答：** 三种角色：观众、主播、管理员。用 `@RequireRole` 注解 + ScopedValue 传角色。Gateway 验 JWT 时提取 role，注入 ScopedValue，下游方法级拦截。

## 三、技术选型追问

### 3.1 Java 21 虚拟线程

| 追问 | 回答 |
|------|------|
| VT 和平台线程的区别 | VT 是 JVM 管理的纤程，M:N 调度。平台线程是 1:1 内核线程。VT 创建/切换成本低 2 个数量级 |
| VT 什么场景不适合 | CPU 密集型不适合，pinning 场景（synchronized / JNI）会卡住 Carrier 线程 |
| VT 的 pinning 怎么解决 | 用 ReentrantLock 替代 synchronized，或者把 synchronized 块缩小到极致 |
| 有没有遇到 VT 的坑 | Spring Boot 3.2 集成 VT 时 Tomcat 的线程池需要显式开启。Dubbo 的 Biz 线程池也需要换成 VT Executor |
| 为什么不选 Kotlin 协程 | 协程需要挂起函数染色，侵入性太大。VT 对现有代码零侵入，改一行配置就生效 |

### 3.2 ScopedValue vs ThreadLocal

| 追问 | 回答 |
|------|------|
| ThreadLocal 在 VT 下什么问题 | 每个 VT 有一个 ThreadLocalMap，10w VT = 10w 个 16-slot 数组 = 1.6M 条目。即使没 set 也占内存 |
| ScopedValue 怎么解决 | ScopedValue 没 bound 的 VT 不占内存，bound 后超出作用域自动清理 |
| ScopedValue 不可变怎么传值 | `ScopedValue.where(K, v).run(() -> ...)`，在 run 的作用域内通过 `K.get()` 获取。不可变意味着子线程不能改 |
| WebFlux 下 ScopedValue 好使吗 | 不好使。WebFlux 的链式调用可能在不同的 EventLoop 线程执行，ScopedValue 跨不过去。我们 Gateway 用 `exchange.getAttributes()` 存 |

### 3.3 Caffeine refreshAfterWrite vs expireAfterWrite

| 追问 | 回答 |
|------|------|
| 有什么区别 | expireAfterWrite：过期后第一个读线程同步阻塞重建 → 击穿。refreshAfterWrite：过期后返回旧值，异步刷新 |
| 秒杀场景怎么用的 | 本地缓存存"是否有库存" boolean，1s refreshAfterWrite。无库存请求直接返回售罄，不查 Redis。压测可减少 90% Redis 压力 |
| 一致性问题呢 | 秒杀场景下，缓存"无库存"可能有延迟（最多 1s），但不影响正确性——最终 Redis Lua 确保不超卖。延迟只是多放进来几个请求被 Redis 拒绝 |

### 3.4 Sentinel 限流

| 追问 | 回答 |
|------|------|
| 滑动窗口怎么实现的 | LeapArray 将 1s 切为 2 个 500ms 的桶，时间落在哪个桶就累加哪个，过期桶自动废弃。比 AtomicInteger 固定窗口精度高一倍 |
| 热点参数限流底层 | `ParamFlowRule` 按参数值建立 Map<Object, AtomicLong>，每个参数独立计数 |
| 嵌入模式的限制 | 各实例独立计数。如果每实例限 100 QPS，3 节点总限流 300 QPS。需要 Dashboard 推全局规则 |
| Sentinel 挂了怎么办 | 限流降级为本地 RateLimiter（Guava/自研），请求量回归应用自身处理能力 |

### 3.5 Kafka 零拷贝

| 追问 | 回答 |
|------|------|
| 什么是零拷贝 | 数据从磁盘到网卡不经过用户态。传统：磁盘→内核→用户→内核→网卡（4 次拷贝）。sendfile：磁盘→内核→网卡（2 次） |
| Kafka 怎么用的 | 日志段文件通过 FileChannel.transferTo 直接发送到 SocketChannel |
| 页缓存是什么 | 操作系统缓存磁盘页面，Kafka 写数据先写页缓存，刷盘异步。读消息命中页缓存就直接返回，不读磁盘 |

### 3.6 双 Token 性能量化

| 追问 | 回答 |
|------|------|
| 性能差多少 | Session 每次请求查 Redis：10w QPS = 10w 次 IO。双 Token：99% 请求仅 JWT 验签，约 111 QPS 刷新（10w 用户 ÷ 900s ≈ 111）。差约 900 倍 |
| Refresh 并发刷新怎么处理 | 分布式锁 + CompletableFuture 合并。同一 Refresh 的并发请求只有一个去查 Redis，其他等待 |
| Access Token 泄露了怎么办 | 15min 内泄露影响有限。攻击者拿到 Access 只能在这段时间内冒充用户。泄露后刷新 Refresh 即可让旧 Access 失效（短 TTL） |

## 四、模块深度追问

### 4.1 秒杀模块

| 追问 | 回答 |
|------|------|
| Lua 脚本为什么原子 | Redis 单线程执行 Lua，整个脚本执行期间不会被其他命令插入。不需要事务 |
| 为什么 `userId % shardCount` 不分遍 | 遍历 4 个分片在最坏情况下要 DECR 4 次（前 3 片被抢完），多了一次不可控。哈希路由直接定位分片，1 次 DECR 搞定 |
| 分片数为什么 4 片 | 经验值。太少 → 热点集中。太多 → Redis 内存碎片 + key 管理成本。4~8 在多数场景下均衡 |
| DECR 到负数怎么办 | 不会。DECR 返回 ≥0 才扣成功；返回负数说明库存不足，不设置 ordered 标记 |
| 一人一单怎么保证 | `uk_activity_user` 唯一索引兜底。Redis 预判（SETNX ordered）减少 DB 写入 |
| 超时取消和用户取消并发 | 乐观锁 CAS：`UPDATE t_seckill_order SET status=2, version=version+1 WHERE order_no=? AND version=?` |
| 为什么不直接 RocketMQ | RocketMQ 延时消息确实香，但部署更重。而且面试官更熟 Kafka，选 Kafka 面试能深挖 |

### 4.2 WebSocket 模块

| 追问 | 回答 |
|------|------|
| 百万连接内存多大 | 每个 WebSocket Session 约 1-2KB，百万连接 ~1-2GB。主要在 TCP 缓冲区，不是堆内存 |
| 心跳怎么实现的 | 客户端 30s PING，服务端 PONG。60s 无消息自动 close。@Scheduled 每 10s 扫描存活 |
| 踢人逻辑 | @OnOpen 查 Redis `ws:route:{userId}`，旧连接发 KICK 消息，3s 后强制 close |
| 跨节点转发延迟 | 一次 Dubbo RPC < 5ms，用户在 UI 上完全无感 |
| 为什么不直接用 Netty | Spring WebSocket + @ServerEndpoint 封装好了，VT 屏蔽了 IO 模型差异。用 Netty 也差不多 |

### 4.3 排行榜模块

| 追问 | 回答 |
|------|------|
| ZSet 底层什么结构 | 跳表（skiplist）+ 哈希表（Dict）。增删改查 O(log N) |
| 跳表为什么 O(log N) | 层高概率升级（P=0.25），每层元素减半。查找时从上往下，期望高度 log N |
| 为什么不用 MySQL order by | 100w 行 ORDER BY score 全表扫描+文件排序，响应时间 > 500ms。Redis ZSet O(log N) < 1ms |
| 快照 5min 间隔的依据 | 活动一般持续 1h+，5min 粒度足够。太频繁浪费 MySQL 写入，太少丢失趋势 |
| 大活动热点怎么处理 | ZSet 分片（activityId % shardCount），查询时合并排序。本项目初期不分片，面试可提 |

### 4.4 网关模块

| 追问 | 回答 |
|------|------|
| 为什么不把签名验签放业务服务 | 所有请求必经 Gateway，在网关层统一验签，减少业务服务的重复代码。不符合签名规则的请求根本进不了内网 |
| JWT 验签性能 | HMAC-SHA256 纯 CPU 运算，1 核可验 5w+ TPS，不是瓶颈 |
| Nonce 的 Redis SETNX 如果 Redis 超时 | 降级：跳过 Nonce 检查，只验 timestamp + sign。幂等设计兜底 |
| Gateway 的 tracing 怎么传到下游 | 通过 Dubbo 的 RpcContext 透传 traceId，或者通过 HTTP Header 传递 traceId/spanId |

## 五、场景题

### 场景 1：秒杀开始时一瞬间流量打崩了

**问题：** 10w 人同时抢 1000 件商品，你怎么扛？

**回答步骤：**

```
① 网关层：Sentinel 热点限流，每用户 100 QPS。恶意刷请求的直接 429
② 本地缓存：Caffeine 1s 刷新，无库存标记直接返回售罄，过滤掉绝大部分请求
③ Redis Lua：4 分片 DECR。分片把请求散列到 4 个 key，单分片瓶颈 8w QPS → 4 片 32w QPS
④ Kafka：异步削峰。Lua 扣成功后发 Kafka，订单在消费者侧创建。Kafka 可以扛住瞬时 10w+ 写入
⑤ 数据库唯一索引：uk_activity_user 兜底，确保一人一单
⑥ 超时取消：15min 未支付回补库存
```

### 场景 2：Redis 挂了

**问题：** 库存 Redis 节点宕机了，秒杀能用吗？

**回答：** 熔断降级。Redis 不可用 → 限流的降级策略：
- **Sentinel 降级**：限流阈值从 100 QPS 降到 10 QPS，减少直接打到 DB
- **缓存降级**：Caffeine 本地缓存（秒级过期）还能挡一阵
- **库存降级**：直接查 MySQL 库存（不走 Redis），用数据库锁控制扣减。能力降级到 1/100
- **最终**：如果 DB 也扛不住，直接返回"活动太火爆" + 限流熔断

面试官想要的不是"Redis 挂了就挂了"，是**降级链路**。

### 场景 3：Kafka 消息堆积

**问题：** 秒杀时 Kafka 消费不过来，订单积压了怎么办？

**回答：** 
- **扩容消费者**：Kafka 支持增加消费者组中的消费者数量，增加并行消费能力
- **VT 消费**：虚拟线程不受平台线程池限制，内存够就能同时消费更多
- **监控告警**：`lag` 指标超过阈值发告警
- **补偿**：用户在 App 上看到订单"处理中"，刷新后从 DB 查到最终状态

## 六、故障排查题

### Q：用户反馈秒杀成功了但没看到订单

**排查链路：**

```
用户请求 → Gateway（看日志有没有到达）
  → SeckillController（看日志入参 activityId + userId）
  → Redis Lua（看 Redis 慢日志、Lua 返回值）
  → Kafka Producer（看消息有没有发出去）
  → Kafka Consumer（看消费日志有没有异常）
  → MySQL INSERT（看唯一索引冲突、看数据落没落库）
```

大概率是 Kafka 消费侧异常或 DB 唯一索引冲突。

### Q：WebSocket 连接断了不重连

**排查：**
- 心跳日志有没有 PING/PONG
- 服务端是否 60s 断开了连接
- 客户端指数退避是否限制了重试次数
- `ws:route:{userId}` 的 TTL 是否续期（心跳更新）

## 七、开放题

### Q：还有什么你做了但没写在简历上的？

**答：**
- 三协议对比压测（Dubbo vs Feign vs gRPC）的 benchmark 模块，还在调研
- DFA 敏感词热更新机制（AtomicReference 无锁替换词库）
- 时钟回拨处理（≤100ms 自旋等待，>100ms 抛异常）
- 接口签名降级方案（Redis 挂了跳过 Nonce，只验 timestamp + sign）

### Q：项目有什么改进空间？

**答：**
- 认证 Redis 独立实例，避免和业务 Redis 抢事件循环
- 主从复制 + 读写分离提升 MySQL 读能力
- 排行榜 ZSet 分片解决热点 key
- CI/CD 流水线 + 自动化测试 + Docker 镜像构建
- Prometheus + Grafana 监控面板
