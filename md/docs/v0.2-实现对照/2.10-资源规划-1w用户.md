# 资源配置规划（1w 并发用户场景）

> 假设：1w 用户同时在线，1000 人同时抢购 100 件商品

## 各服务资源配置

| 服务 | 内存 | CPU | 端口 | 瓶颈 |
|---|---|---|---|---|
| MySQL | 512MB | 1 vCPU | 3306 | Kafka 削峰后 < 100 TPS |
| Redis | 256MB | 1 vCPU | 6379 | Lua 1w QPS ≈ 12.5% 单核 |
| Nacos | 256MB | 0.5 vCPU | 8848 | 注册中心, 轻量 |
| Gateway | 256MB | 1 vCPU | 8080 | WebFlux EventLoop |
| User | 256MB | 1 vCPU | 8081 | 低频 (登录注册) |
| Seckill | 512MB | 2 vCPU | 8082 | Lua+Kafka+gRPC, CPU 相对高 |
| WebSocket | 512MB | 1 vCPU | 8083 | 1w 连接 ≈ 20MB 堆 + VT |
| Leaderboard | 256MB | 1 vCPU | 8084 | Redis ZSet 为主, 自身轻量 |
| **合计** | **~3GB** | **~8.5 vCPU** | — | — |

## 数据库规划

### 垂直分库（设计, 不落地）

```
livemall_user_db   — t_user (MyBatis-Plus, 单表 100w 行 ≈ 500MB)
livemall_live_db   — t_live_room, t_barrage, t_gift_log
livemall_trade_db  — t_seckill_activity, t_seckill_order, t_leaderboard_snapshot
```

### 水平分表（面试方案）

| 表 | 分片键 | 路由 | 预估行数 |
|---|---|---|---|
| t_seckill_order | user_id | user_id % N | 5000w |
| t_barrage | room_id | room_id % N | 1 亿 |
| t_gift_log | room_id | room_id % N | 5000w |

**不落地原因：** 1w 用户量级，单表完全够。

### MySQL 主从（面试方案）

1 主 2 从 + MGR 半同步复制。写走主库，读（订单查询、活动列表）走从库分担。

**不落地原因：** Kafka 削峰后写入压力 < 100 TPS，单实例绰绰有余。

## Redis 实例拆分（面试方案）

```
Redis-A: 秒杀库存 (256MB, 核心, 不淘汰)
Redis-B: 认证 session (128MB, 7 天 TTL)
Redis-C: 排行榜 + WS 路由 (128MB)
```

**不落地原因：** 当前单实例 100MB 用量，256MB 配置充裕。
