> `@DubboService` 方法默认运行在 Dubbo Biz 线程池上。本项目 `application.yml` 中已配置 `dubbo.provider.threads` 使用虚拟线程 Executor（详见 `1.2-技术选型分析.md` §2 Dubbo）。因此加 `@DubboService` 的方法也跑在 VT 上。

## 输入输出

**Dubbo 接口**

```java
boolean addScore(Long activityId, Long userId, String eventType, Double extraScore);
```

| 参数 | 类型 | 说明 |
|------|------|------|
| activityId | Long | 活动 ID |
| userId | Long | 用户 ID |
| eventType | String | WATCH/LIKE/COMMENT/SHARE/GIFT |
| extraScore | Double | 额外分数（礼物金额），非礼物传 null |

## 权重配置

| 事件 | 权重 | 说明 |
|------|------|------|
| WATCH | +0.3 | 每分钟 |
| LIKE | +0.5 | 每次 |
| COMMENT | +1.0 | 每次 |
| SHARE | +2.0 | 每次 |
| GIFT | 金额 × 1.0 | 按礼物价值 |

## 核心流程

```
addScore(activityId, userId, eventType, extraScore)
  → 查权重表获取 weight
  → eventType == "GIFT" → weight = extraScore * 1.0
  → ZINCRBY "leaderboard:{activityId}" userId weight
  → 返回 true
```

```java
@DubboService
public class LeaderboardServiceImpl implements LeaderboardService {
    private static final Map<String, Double> WEIGHT = Map.of(
            "WATCH", 0.3, "LIKE", 0.5, "COMMENT", 1.0, "SHARE", 2.0, "GIFT", 0.0);

    public boolean addScore(Long activityId, Long userId, String eventType, Double extraScore) {
        double weight = WEIGHT.get(eventType);
        if ("GIFT".equals(eventType) && extraScore != null) weight = extraScore;
        redisTemplate.opsForZSet().incrementScore("leaderboard:" + activityId,
                userId.toString(), weight);
        return true;
    }
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 不支持的 eventType | 忽略，返回 false |
| 权重为 0 | ZINCRBY 0 不改变分数 |
| userId 不存在于 ZSet | ZINCRBY 自动创建 |
| 网络重传重复加分 | 参见 3.3.2 送礼幂等——礼物层 `messageId` 已做去重，非送礼事件（点赞/评论等）前端用 `X-Idempotency-Key` 去重 |

🤔 **面试扩展**：ZINCRBY 是原子的吗？是，Redis 单线程执行，不存在并发加分错的可能。为什么权重可配置？Nacos 动态下发，运营可调整活动期间的互动激励策略。
