| 涉及类 | `SnapshotTask` |
| 关联功能 | 3.5.5 历史排行（快照是历史数据来源）|
| 关联文档 | `2.5-排行榜服务.md` §定时快照、`1.4-项目约束清单.md` |

> `@Scheduled` 运行在平台线程上。快照是定时任务，每分钟执行一次，平台线程执行无问题。

## 核心流程

```
@Scheduled(cron = "0 */5 * * * ?") // 每 5min
  → 查询正在进行的活动列表
  → FOR EACH activity:
       ZREVRANGE "leaderboard:{activityId}" 0 99 WITHSCORES → Top100
       INSERT INTO t_leaderboard_snapshot
         (activity_id, user_id, score, rank, snapshot_time)
       VALUES (?, ?, ?, ?, NOW())
  → 删除旧的快照数据（按时间分区或 TRUNCATE）
```

```sql
INSERT INTO t_leaderboard_snapshot (activity_id, user_id, score, rank, snapshot_time)
VALUES (?, ?, ?, ?, NOW());
-- 索引: idx_activity_time (activity_id, snapshot_time)
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 无活跃活动 | 跳过 |
| ZSet 为空 | 跳过该活动 |
| 快照大量数据 | 批量 INSERT，每批 500 条 |
| 活动结束 | 停止快照，设置 Redis ZSet TTL 7 天后自动清理 |

🤔 **面试扩展**：为什么 5min 一次？活动通常 > 1h，5min 粒度足够看到排名变化趋势。频率过高 MySQL 写入压力增大。按月分表 `t_leaderboard_snapshot_202601`，活动结束后清除 Redis ZSet。
