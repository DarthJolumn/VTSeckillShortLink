## 边界处理

| 场景 | 行为 |
|------|------|
| 时钟回拨 ≤ 30ms | 等待回拨长度后恢复 |
| 时钟回拨 > 30ms | 抛异常，人工介入 |
| 序列号耗尽 | 等待下一毫秒 |
| 重新加锁后时间戳仍小于 lastTimestamp | `Math.max(lastTimestamp + 1, currentTimeMillis)` 保证单调 |

🤔 **面试扩展**：
- **追问：VT 下为什么用 ReentrantLock 而不是 synchronized？** → `synchronized` 是 JVM 内置锁，持有锁的 VT 无法 unmount（pinning），carrier 线程被占住直到锁释放。`ReentrantLock` 是 `java.util.concurrent` 锁，VT 持有时 JVM 可以在 park 点 unmount。虽然 `nextId()` 的临界区只有几行整数运算（< 1μs），但时钟回拨时 `Thread.sleep` 在锁内 → pin 整个 sleep 期间。所以：先 `unlock` → sleep → 重新 `lock`
- **追问：回拨阈值为什么是 30ms 而不是 100ms？** → NTP 校时通常一次性回拨 10~50ms。设 30ms 覆盖 95% 的 NTP 回拨场景，超过 30ms 的异常回拨（如手动改时钟、NTP 配置错误）应当人工介入而非静默等待——等待 100ms 在高并发下会阻塞 400+ 个 ID 生成请求
- **追问：unlock→sleep→lock 之后时间戳仍小于 lastTimestamp 怎么办？** → `Math.max(lastTimestamp + 1, System.currentTimeMillis())` 保证单调性——宁可未来时间戳也不回退。`lastTimestamp + 1` 推进到上一时间戳之后 1ms，保证后续 ID 严格递增
