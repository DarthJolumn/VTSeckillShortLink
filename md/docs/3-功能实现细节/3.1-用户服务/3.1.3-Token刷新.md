# Token 刷新 (3.1.3)

| 属性 | 值 |
|------|-----|
| 功能编号 | 3.1.3 (原#3) |
| 所属模块 | 3.1 用户服务 |
| 涉及类 | `AuthController`、`RefreshRequest`、`RefreshResponse`、`UserService` |
| 关联功能 | 3.1.2 登录（签发 refreshToken 的前置）、3.1.4 退出登录（销毁 refreshToken）|
| 关联文档 | `2.2-用户服务与认证.md` §Token 刷新、§并发刷新防护、§Rotation vs Reuse |

> 项目启用 VT，Spring `spring.threads.virtual.enabled=true`。所有 HTTP 请求和 Service 方法默认运行在 VT 上，IO 阻塞不占平台线程。

## 输入输出

**请求** `POST /auth/refresh`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| refreshToken | String | ✅ | 登录时下发的不透明字符串 |

**响应**

| 场景 | code | message | data |
|------|------|---------|------|
| 成功 | 200 | — | `RefreshResponse`（同 LoginResponse 结构）|
| token 无效/过期 | 1013 | "登录已过期，请重新登录" | null |

## 核心流程

```
POST /auth/refresh { refreshToken }
  → Redis GETDEL refresh:{token} → 不存在 → 1013
  → 解析 value = "userId:role:deviceId"
  → JwtUtil.generate(userId, role, 900s) → 新 accessToken
  → 新 UUID refreshToken → SET key 7d（Rotation：旧 key 已在 GETDEL 删除）
  → 返回 RefreshResponse
```

### 并发刷新防护（关键难点）

Access 过期瞬间，前端多个请求同时触发的场景：

```
请求 A                 请求 B                 请求 C
  │                     │                     │
  ▼                     ▼                     ▼
GET refresh             GET refresh           GET refresh
(miss, to refresh)      (miss, to refresh)    (miss, to refresh)
  │
  ├── pendingRefreshes.putIfAbsent → 成功
  │   └── Redis SETNX lock 3s → 成功 → 执行刷新
  │       └── 写入新 Token → future.complete → unlock
  │
  ├── pendingRefreshes.get → 命中 → future.get(5s)
  │   └── 等 A 完成 → 复用结果
  │
  └── pendingRefreshes.get → 命中 → future.get(5s)
      └── 等 A 完成 → 复用结果
```

## 关键代码

```java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import static java.util.concurrent.TimeUnit.SECONDS;

// 请求合并缓存——同一 refreshToken 的并发刷新只执行一次
private final ConcurrentHashMap<String, CompletableFuture<RefreshResponse>>
        pendingRefreshes = new ConcurrentHashMap<>();

public RefreshResponse refresh(String refreshToken) {

    // ── 请求合并：同一个 token 的并发请求只执行一次 ──
    CompletableFuture<RefreshResponse> existing = pendingRefreshes.get(refreshToken);
    if (existing != null) {
        try {
            return existing.get(5, SECONDS);
        } catch (TimeoutException e) {
            // 极端情况：第一个请求卡住超过 5s，当前请求降级为重新执行
            log.warn("等待刷新超时, refreshToken={}", maskToken(refreshToken));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BizException(500, "系统繁忙");
        } catch (ExecutionException e) {
            // 第一个请求抛异常，向上传播
            throw new BizException(1013, "登录已过期");
        }
    }

    CompletableFuture<RefreshResponse> future = new CompletableFuture<>();
    CompletableFuture<RefreshResponse> old = pendingRefreshes.putIfAbsent(refreshToken, future);
    if (old != null) {
        // 刚好另一个线程在 putIfAbsent 之前插入了
        try { return old.get(5, SECONDS); }
        catch (Exception e) { throw new BizException(1013, "登录已过期"); }
    }

    try {
        // ── 分布式锁：防止同一 token 被两个节点同时刷新 ──
        String lockKey = "refresh:lock:" + refreshToken;
        Boolean locked = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, "1", 3, SECONDS);

        if (!Boolean.TRUE.equals(locked)) {
            // 另一个节点持有锁 → Rotation 下旧 key 已被 GETDEL 删除，无法恢复
            throw new BizException(1013, "登录已过期");
        }

        // ── 核心刷新（Rotation：GETDEL 返回旧值并删除） ──
        String value = redisTemplate.opsForValue().getAndDelete("refresh:" + refreshToken);
        if (value == null) throw new BizException(1013, "登录已过期");

        // value 格式：userId:role:deviceId（由 3.1.2 登录签发）
        String[] parts = value.split(":", 3);
        if (parts.length < 3) throw new BizException(500, "token 数据异常");

        Long userId = Long.valueOf(parts[0]);
        Integer role = Integer.valueOf(parts[1]);
        String deviceId = parts[2];

        // 签发新 Access Token（带上正确的 role，不再硬编码 1）
        String newAccessToken = JwtUtil.generate(userId, role, 900);

        // 新 Refresh Token（Rotation：旧 key 已删，写入新 key）
        String newRefreshToken = "rft_" + UUID.randomUUID().toString().replace("-", "");
        redisTemplate.opsForValue().set(
                "refresh:" + newRefreshToken,
                userId + ":" + role + ":" + deviceId,
                7, TimeUnit.DAYS);

        RefreshResponse resp = new RefreshResponse(
                newAccessToken, newRefreshToken, 900, "Bearer");
        future.complete(resp);
        return resp;

    } catch (BizException e) {
        future.completeExceptionally(e);
        throw e;
    } finally {
        pendingRefreshes.remove(refreshToken);
        redisTemplate.delete("refresh:lock:" + refreshToken);
    }
}

private String maskToken(String token) {
    return token != null && token.length() > 10
            ? token.substring(0, 10) + "***" : "***";
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| token 过期 | 1013 重登录 |
| token 被伪造 | GETDEL return null → 1013 |
| 并发刷新同 token | `CompletableFuture` 请求合并 |  
| 刷新后旧 token 被使用 | Rotation 已 GETDEL 删除旧 key → 1013 |
| 7 天未活跃 | key EXPIRE → 自然过期 → 1013 |
| 分布式多节点并发 | Redis SETNX 锁，抢锁失败直接 1013（Rotation 下旧 key 已被另一节点 GETDEL）|
| 同一个 VT 被中断 | 捕获 InterruptedException 并标记中断状态 |
| token value 格式异常 | 500 "token数据异常"（不暴露详情）|

🤔 **面试扩展**：Rotation vs Reuse？Rotation 更安全——刷新即换新 token，泄露后可检测。请求合并用 `CompletableFuture` + `ConcurrentHashMap`，避免同时多次操作 Redis。为什么 value 存 `userId:role:deviceId`？刷新签发新 JWT 时需要 role，纯客户端传 role 不可信。SCAN 不用于刷新路径（只用于封禁的大规模清理），刷新路径用精确 key GET/DEL。
