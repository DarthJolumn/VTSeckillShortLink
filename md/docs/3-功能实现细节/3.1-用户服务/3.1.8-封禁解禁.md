## 输入输出

**请求** `PUT /user/ban/{userId}`（需管理员 JWT）

| 字段 | 位置 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| userId | Path | Long | ✅ | 目标用户 |
| action | Body | String | ✅ | `"ban"` / `"unban"` |

**响应**

| 场景 | code (§2.1) | message |
|------|-------------|---------|
| 成功 | 200 | "账号已封禁" / "账号已解禁" |
| 非管理员 | 403 | "仅管理员可操作" |
| 用户不存在 | 404 | "用户不存在" |

## 核心流程

```
PUT /user/ban/{userId} { action: "ban" }
  → [Gateway] JWT → role ≠ ADMIN → 403
  → UPDATE t_user SET status=0 WHERE id=? AND status=1
     ├── 0 行影响 → 幂等或用户不存在
  → DEL device_sessions:{userId}  ← 清理所有会话
  → [Dubbo] WebSocket 推送 BANNED 到该用户所有连接
```

> ⚠️ 不在此处 SCAN 遍历清理 refreshToken——SCAN 在大规模 token 时不可靠。accessToken 15min 后自动过期。详见面试扩展。

## 关键代码

> 封禁不涉及 DB 写入后的后续复杂逻辑（Dubbo RPC 不放在事务内）。

```java
// ⚠️ 不加 @Transactional——DB 操作只有一条 UPDATE（单条 DML 自带事务），
// Dubbo RPC 和 Redis 清理不应放在事务中
public void banUser(Long targetUserId) {
    int updated = userRepository.updateStatus(targetUserId, 0); // 单条 DML
    if (updated == 0) {
        throw new BizException(404, "用户不存在或已是封禁状态");
    }

    // Redis 清理（非关键路径：即使失败也只影响 15min 内的 accessToken）
    try {
        redisTemplate.delete("device_sessions:" + targetUserId);
    } catch (Exception e) {
        log.warn("封禁时清理缓存失败, userId={}", targetUserId, e);
    }

    // Dubbo RPC 通知 WebSocket 踢所有连接（非关键路径）
    try {
        wsPushService.kickUser(targetUserId, "BANNED");
    } catch (Exception e) {
        log.warn("封禁时 WS 推送失败, userId={}", targetUserId, e);
    }
}

public void unbanUser(Long targetUserId) {
    int updated = userRepository.updateStatus(targetUserId, 1);
    if (updated == 0) {
        throw new BizException(404, "用户不存在");
    }
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 封禁已封禁的人 | 幂等 -> 404 |
| 解禁已正常的人 | 幂等 -> 404 |
| 封禁后用户正在登录 | 下次登录被 status=0 拦截 → 1006 |
| 封禁后用户已登录 | accessToken 能用 15min，但 WS 推送 BANNED 实时踢 |
| 管理员封禁自己 | 允许（防止管理员账号泄露后的自救操作）|
| Redis 清理失败 | 打印 WARN 日志，不抛异常——不影响核心操作 |
| WS 推送失败 | 同上——用户下次请求会被 Gateway 拦截 |
| DB 查到了但 device_sessions key 已过期 | DEL 返回 0，无影响 |

🤔 **面试扩展**：

- **accessToken 还能用 15min 怎么办？** 加黑名单 Set（`blacklist:userId`）则每次请求多一次 Redis 查询——对 10w QPS 项目来说不可接受。本项目接受 15min 延迟吊销，因为：a) 秒杀场景每次请求验证黑名单的额外延迟不可接受；b) 15min 后自动过期，最坏情况少 15min。大厂做法是 Token 版本号——JWT 中带 `tokenVersion`，查 Redis 或 DB 校验，但成本是每次请求多一次 Redis GET。

- **SCAN 为什么不在这里用？** `SCAN 0 MATCH refresh:*` 遍历所有 Refresh Token 去匹配 userId 的复杂度是 O(N)。假设 100 万次登录，SCAN 需要遍历 100 万个 key 去匹配，不可靠且延迟不可控。生产方案：额外维护 `user_tokens:{userId}` 反向索引，登录时 `SADD`，踢/封禁时 `SMEMBERS` 拿所有 refreshToken 逐个 `DEL`。本项目当前不做反向索引，升级路径明确。
