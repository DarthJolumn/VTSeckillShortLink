## 输入输出

**请求** `POST /auth/login`

| 字段 | 位置 | 类型 | 必填 | 验证/说明 |
|------|------|------|------|----------|
| username | Body | String | ✅ | 1~50 字符，trim 后入库 |
| password | Body | String | ✅ | 1~255 |
| X-Device-Id | Header | String | ✅ | UUID 格式，客户端持久化 |
| X-Idempotency-Key | Header | String | ❌ | UUID，防网络重传重复登录，Redis SETNX 5min |

**响应**

| 场景 | code | message | data |
|------|------|---------|------|
| 成功 | 200 | "登录成功" | `LoginResponse` |
| 重复提交 | 200 | 返回已有 LoginResponse（幂等键命中） | `LoginResponse` |
| 用户名或密码错误 | 1011 | "用户名或密码错误" | null |
| 账号已封禁 | 1006 | "账号已被封禁" | null |

### LoginResponse 结构

| 字段 | 类型 | 示例 | 说明 |
|------|------|------|------|
| accessToken | String | `eyJhbGciOiJIUzI1NiJ9...` | JWT，15min |
| refreshToken | String | `rft_a1b2c3d4e5f6...` | 不透明，Redis 存 7d |
| expiresIn | long | `900` | 过期秒数 |
| tokenType | String | `Bearer` | 固定值 |

## 核心流程

```
POST /auth/login + X-Device-Id + X-Idempotency-Key(可选)
  → [Gateway] 签名验签 + Sentinel 限流 10 QPS/IP
  → X-Idempotency-Key 存在 → Redis SETNX idempotency:{key} 1 EX 300
      → 抢到 → 继续
      → 未抢到 → 查已有登录结果缓存直接返回（幂等）
  → username.trim() 查 t_user → 不存在 → 1011
  → 检查 status → 0 → 1006
  → BCrypt.checkpw → 不匹配 → 1011
  → JwtUtil.generate(userId, role, 900s) → accessToken
  → UUID → refreshToken → Redis SET refresh:{token} userId:role:deviceId EX 7d
  → Redis SADD device_sessions:{userId} deviceId + EXPIRE 7d
  → 缓存 LoginResponse（key=幂等键，TTL=5min）→ 返回
```

## 关键代码

> 项目启用 Java 21 虚拟线程（VT），`spring.threads.virtual.enabled=true`。以下代码运行在 VT 上，注意不把 VT 和 `@Transactional` 混用——VT 应避免在非 DB 操作期间持有 DB 连接。

```xml
<!-- pom.xml 依赖 -->
<dependency>
    <groupId>org.mindrot</groupId>
    <artifactId>jbcrypt</artifactId>
    <version>0.4</version>
</dependency>
```

```java
import org.mindrot.jbcrypt.BCrypt;

// 注意：登录方法只有 SELECT 查询 + Redis 写入，不涉及 DB 写操作
// 不加 @Transactional —— 否则 VT 会在调用 BCrypt / Redis SET 期间
// 一直占着一个 DB 连接，高并发登录时可能耗尽连接池
public LoginResponse login(LoginRequest request, String deviceId, String idempotencyKey) {
    // 0. 幂等检查（可选，有 idempotencyKey 时防网络重传）
    if (idempotencyKey != null && !idempotencyKey.isBlank()) {
        LoginResponse cached = idempotencyService.get(idempotencyKey);
        if (cached != null) return cached;
    }

    // 1. 查用户（纯 SELECT，JPA 自身原子的）
    User user = userRepository.findByUsername(request.getUsername().trim())
            .orElseThrow(() -> new BizException(1011, "用户名或密码错误"));

    // 2. 封禁检查
    if (user.getStatus() == 0) {
        throw new BizException(1006, "账号已被封禁");
    }

    // 3. BCrypt 校验（CPU 密集，VT 不阻塞平台线程）
    if (!BCrypt.checkpw(request.getPassword(), user.getPassword())) {
        throw new BizException(1011, "用户名或密码错误");
    }

    // 4. 签发双 Token
    String accessToken = JwtUtil.generate(user.getId(), user.getRole(), 900);
    String refreshToken = "rft_" + UUID.randomUUID().toString().replace("-", "");

    // 5. Redis 写入（VT IO 密集，不占用平台线程）
    String refreshKey = "refresh:" + refreshToken;
    String deviceSessionKey = "device_sessions:" + user.getId();

    try {
        redisTemplate.opsForValue().set(refreshKey,
                user.getId() + ":" + user.getRole() + ":" + deviceId, 7, TimeUnit.DAYS);
        redisTemplate.opsForSet().add(deviceSessionKey, deviceId);
        // ⚠️ 设 TTL，否则废弃设备 ID 在 Redis 永不过期
        redisTemplate.expire(deviceSessionKey, 7, TimeUnit.DAYS);
    } catch (Exception e) {
        // Redis 挂了：accessToken 已签发但 refreshToken 不可用
        // 15min 后用户尝试刷新会失败，需重新登录
        log.error("登录时 Redis 写入失败, userId={}", user.getId(), e);
        throw new BizException(500, "系统繁忙，请稍后重试");
    }

    // P0-2 fixed：设备会话只在 Redis 中维护（device_sessions Set + Refresh Token String），无需写 MySQL t_device_session
    LoginResponse response = LoginResponse.of(accessToken, refreshToken);
    // 6. 缓存登录结果（幂等键 5min TTL）
    idempotencyService.set(idempotencyKey, response, 5, TimeUnit.MINUTES);
    return response;
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 用户不存在 | 1011（同密码错误，防枚举） |
| 密码错误 | 1011（不暴露哪个字段错） |
| 封禁用户 | 1006 |
| 请求带幂等键重复提交 | 返回已有登录结果，不重复签发 token |
| 请求不带幂等键（旧客户端） | 降级：正常登录，同设备并发各自生成独立 token |
| Redis 写超时/挂 | 500 回滚，accessToken 作废 |
| 多次输错密码 | Sentinel 10 QPS/IP 防爆破 |
| deviceId 不传 | 400 |
| device_sessions 永不过期 | ❌ 显式 EXPIRE 7 天防泄漏 |

🤔 **面试扩展**：
- 为什么不用 Session？→ Session 10w QPS = 10w Redis GET，JWT 0 IO
- BCrypt 慢？→ 10~50ms 校验，登录 QPS 远小于总 QPS，VT 下不阻塞平台线程
- 为什么去 @Transactional？→ 纯 SELECT + Redis I/O，VT 不能长时间占 DB 连接
- Redis 写失败为什么抛 500 不降级？→ 登录是写入操作，refreshToken 不可用等于功能半残，宁可拒绝让用户重试
- 多设备登录为什么不自动踢旧设备？→ 业务上没有限制，PC + 手机同时在线合理
- **追问：为什么用 X-Idempotency-Key 而不是 DB 设备会话冲突检测？** → 登录的幂等需求是"同一请求重复提交返回相同结果"，和设备管理是两个不同场景。deviceId 去重适用于"新设备登录踢旧设备"的会话控制，幂等键适用于网络重传防重。两者解决不同问题——deviceId 保证一个设备只有一个有效 session，幂等键保证一次操作不会被执行两次
