> 本项目所有业务服务运行在 VT 上（`spring.threads.virtual.enabled=true`）。以下 Service 方法跑在 VT 上——Dubbo RPC 调用阻塞 VT 但不阻塞平台线程，不加 `@Transactional`。

## 输入输出

**请求** `DELETE /user/devices/{deviceId}`（需 JWT）

| 场景 | code | message |
|------|------|---------|
| 成功 | 200 | "已踢下线" |
| 设备不存在 | 404 | "设备不在线" |
| 无权限 | 403 | "只能操作自己的设备" |

## 核心流程

```
DELETE /user/devices/{deviceId}
  → [Gateway] JWT → userId（ScopedValue）
  → SREM device_sessions:{userId} {deviceId}
     ├── 0 → 404 设备不存在
  → [Dubbo] wsPushService.kickUser(userId, "KICK")  ← VT 阻塞，不占平台线程
  → 返回成功
```

> ⚠️ 这里不用清理 refreshToken。被踢的设备下次登录时发现 token 过期或设备 ID 不被信任即可。**反向索引问题**：当前 `refresh:{refreshToken}` value 里存了 `userId:role:deviceId`，但不知道具体是哪个 key 对应被踢的 deviceId。暴力 SCAN 在生产环境不可行。详见面试扩展。

## 关键代码

```java
// 运行在 VT 上。Redis SREM + Dubbo RPC 都是 IO 操作，VT 阻塞但不占平台线程。
// 不加 @Transactional——没有 DB 写入。
public void kickDevice(Long targetUserId, String deviceId, Long currentUserId) {
    if (!targetUserId.equals(currentUserId)) {
        throw new BizException(403, "只能操作自己的设备");
    }

    Long removed = redisTemplate.opsForSet()
            .remove("device_sessions:" + targetUserId, deviceId);
    if (removed == 0) {
        throw new BizException(404, "设备不在线");
    }

    // Dubbo RPC 调用——VT 下阻塞，平台线程切换给其他 VT 使用
    wsPushService.kickDevice(targetUserId, deviceId);
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 踢不存在的设备 | 404 |
| 踢自己当前设备 | 允许，自踢（可用于"在其他设备登录，当前设备被提示"）|
| WS 推送失败（该设备离线）| Dubbo 返回 false → 已清理 Redis，下次不会收到消息 |
| WS 推送失败（网络问题）| 不影响 Redis 清理，下次请求被拦截 |
| 同时多端操作 | SREM 不存在并发问题，Redis 单线程 |

🤔 **面试扩展**：踢设备时怎么找到 deviceId 对应的所有 refreshToken？两个方案——

1. **SCAN 方案**（当前）: `SCAN 0 MATCH refresh:*` 遍历所有 key，解析 value 匹配 deviceId。O(N) 不可用于生产，百万 token 时延迟秒级。
2. **反向索引方案**（推荐生产）: 额外维护 `device_tokens:{userId}:{deviceId}` Set，存该设备所有 refreshToken。踢设备时 `SMEMBERS` 取出来一个个 DEL。牺牲写入放大（每次登录额外 SADD），换取踢设备的 O(1) 查询。本项目当前用 SCAN，升级方向为反向索引。
