| 属性 | 值 |
|------|-----|
| 功能编号 | 3.4.7 (原#25) |
| 所属模块 | 3.4 秒杀服务 |
| 涉及类 | `SeckillOrderTimeoutTask`、`StockService` |
| 关联功能 | 3.4.8 用户取消订单（回补逻辑一致）|
| 关联文档 | `2.3-秒杀服务.md` §超时取消、`1.4-项目约束清单.md` |

> `@Scheduled` 默认运行在平台线程上。`session.close()` 异步 VT 规则（见 3.2.6）在此不适用——这里是 @Scheduled 定时扫描订单，不是 WebSocket。ORDER BY created_at LIMIT 500 是 DB 操作，平台线程上执行 SELECT + UDPATE 是合理的（非 IO 阻塞）。如需 VT，在 `@Async` 方法中手动 `Thread.startVirtualThread`。

## 核心流程

```
@Scheduled(fixedRate = 15000) // 每 15s
  → SELECT id, activity_id, user_id, version
    FROM t_seckill_order
    WHERE status = 0 AND created_at < NOW() - INTERVAL 15 MINUTE
    LIMIT 500
  → FOR EACH order:
      乐观锁：UPDATE t_seckill_order
              SET status = 2, cancelled_at = NOW(), version = version + 1
              WHERE id = ? AND status = 0 AND version = ?
      影响行数 = 1 → 回补库存（Redis Lua 回补脚本）
      影响行数 = 0 → 已被取消/支付，跳过
```

### 回补库存 Lua

```lua
-- KEYS[1] = stockShardKey
-- KEYS[2] = orderedKey
-- KEYS[3] = orderLockKey (防重复回补)
local locked = redis.call("SETNX", KEYS[3], "1")
if locked == 0 then return {code = -1} end
redis.call("EXPIRE", KEYS[3], 10)

redis.call("INCR", KEYS[1])
redis.call("DEL", KEYS[2])
return {code = 200}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 订单已支付 | status ≠ 0，乐观锁跳过 |
| 订单已被用户取消 | 乐观锁竞争，先到先得 |
| 回补库存时 Redis 挂了 | 回补失败，记录日志，人工对账 |
| 扫描限流 | 每次 LIMIT 500，避免一次加载太多 |

🤔 **面试扩展**：为什么用乐观锁 CAS？悲观锁 `SELECT FOR UPDATE` 在秒杀高频下死锁风险高。version 字段 + WHERE status=0 保证只有 PENDING 状态的订单能被取消。为什么 15min？秒杀场景下用户支付意愿最强的时间段，通常 5min 内完成支付。
