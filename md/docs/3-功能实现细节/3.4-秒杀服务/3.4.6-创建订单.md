> 🔴 `@KafkaListener` 默认运行在平台线程上（Kafka 容器线程池）。消费方法内 INSERT + Dubbo push 是 IO 密集——优化方向见 3.4.5 的 VT 说明。`@Transactional` 在此是合理的：INSERT 一条订单，事务范围可控。**commit 时机**：`AckMode.MANUAL`（手动提交），INSERT 成功后才 `ack.acknowledge()`，失败不提交以触发重试。

## 核心流程

```
Kafka topic: seckill-order (partition key = userId)
  → SeckillOrderConsumer 消费
  → 校验活动是否有效
  → INSERT t_seckill_order
     ├── uk_activity_user 唯一索引兜底防重
     ├── 冲突 → 回滚（已存在订单）
  → 订单状态机初始化：PENDING(0)
  → [Dubbo] WsPushService.push 推送结果
```

```sql
INSERT INTO t_seckill_order (order_no, activity_id, user_id, product_id, seckill_price, status, created_at)
VALUES (?, ?, ?, ?, ?, 0, NOW());
-- UNIQUE INDEX uk_activity_user (activity_id, user_id) 防重复下单
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 重复消息（Kafka 重投）| uk_activity_user 唯一索引报错，catch 后幂等跳过 |
| 消费失败 | 重试 3 次，仍失败进死信队列 |
| 活动已下架 | 订单依然创建（用户已扣库存），通过退款流程处理 |

🤔 **面试扩展**：为什么 Kafka 分区 key 用 userId？保证同一用户的消息顺序消费。唯一索引 `uk_activity_user` 作为最后一道防重防线——Redis ordered key 可能因宕机丢失，DB 唯一索引不会。
