# 上架/下架活动 (3.4.2)

| 属性 | 值 |
|------|-----|
| 功能编号 | 3.4.2 (原#20) |
| 所属模块 | 3.4 秒杀服务 |
| 涉及类 | `SeckillAdminController`、`SeckillActivityService` |
| 关联功能 | 3.4.1 创建活动（前置）、3.4.3 用户抢购（上架后才能抢）|
| 关联文档 | `2.3-秒杀服务.md` §核心流程、`2.7-数据库设计.md` §秒杀域、`1.4-项目约束清单.md` |

> 运行在 VT 上。上架时涉及 MySQL UPDATE + Redis 初始化（多次 SET），VT 下 Redis I/O 不占平台线程。不加 `@Transactional`——Redis 操作不能在事务内。

## 输入输出

**请求** `PUT /seckill/activity/{id}/status`（需管理员 JWT）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| status | Integer | ✅ | 1=上架, 2=下架, 4=取消 |

**响应**

| 场景 | code | message |
|------|------|---------|
| 成功 | 200 | "上架成功" / "已下架" |
| 活动不存在 | 404 | "活动不存在" |
| 状态转换非法 | 400 | "当前状态不允许此操作" |

## 核心流程

### 上架

```
PUT status=1
  → 校验 status 转换（0→1 允许）
  → 幂等检查：Redis SETNX activity:online:{activityId} 1 EX 86400
      → 未抢到 → 活动已上架过，直接返回成功（防网络重传重置库存）
  → 初始化 Redis 库存 shard
     for i in 0..shardCount-1:
       SETNX stock:shard:{activityId}:{i} {totalStock / shardCount}
  → 初始化用户购买记录集合（空）
  → UPDATE t_seckill_activity SET status=1
```

> ⚠️ 关键：库存初始化用 `SETNX` 而非 `SET`——如果活动已上架且库存已部分扣减，网络重传再次上架不会覆盖 Redis 库存，防止超卖。

### 下架

```
PUT status=2
  → 校验允许转换（1→2 允许）
  → DEL stock:shard:{activityId}:*
  → UPDATE t_seckill_activity SET status=2
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 下架后重新上架 | 不清除已下单记录，但库存重置 |
| 活动中直接下架 | 强行停止，正在抢购的用户返回失败 |
| 活动已结束才上架 | status 校验拒绝 |
| 网络重传重复上架 | 幂等返回成功，Redis 库存不会被覆盖（SETNX 保护） |
| 上架时 Redis 不可用 | 500 失败，不执行 MySQL UPDATE（保持 status=0 待上架） |

🤔 **面试扩展**：上架时初始化 Redis 库存，为什么分片？`userId % shardCount` 哈希路由，4 片基线，公式见 `2.3-秒杀服务.md` §分片数计算。库存分配取整，超出部分加到最后一片。为什么用 SETNX 而非 SET？防止网络重传导致库存被重置为满库存——如果活动已上架且库存部分扣减，SETNX 发现 key 已存在则跳过，不会覆盖。这是幂等性和库存安全的双重保障。
