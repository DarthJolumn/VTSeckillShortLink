# 用户取消订单 (3.4.8)

| 属性 | 值 |
|------|-----|
| 功能编号 | 3.4.8 (原#26) |
| 所属模块 | 3.4 秒杀服务 |
| 涉及类 | `SeckillOrderController`、`SeckillOrderService` |
| 关联功能 | 3.4.6 创建订单（前置）、3.4.7 超时取消（共享回补逻辑）|
| 关联文档 | `2.3-秒杀服务.md` §订单状态机、`1.4-项目约束清单.md` |

> 运行在 VT 上。HTTP Controller 请求是 VT。@Transactional 包裹 SELECT→UPDATE→Redis Lua：SELECT 在事务内是合理的（读当前订单）。但 Redis Lua 在事务内（非 DB 资源）——这是一个妥协。优化：先开事务 UPDATE（CAS 乐观锁），提交事务后 Redis Lua 回补。面试持"先提交后回补"方案。

## 输入输出

**请求** `PUT /seckill/order/{orderNo}/cancel`（需 JWT）

| 场景 | code | message |
|------|------|---------|
| 成功 | 200 | "订单已取消" |
| 订单不存在 | 404 | "订单不存在" |
| 订单状态不可取消 | 400 | "当前订单状态不允许取消" |

## 核心流程

```
PUT /seckill/order/{orderNo}/cancel
  → JWT → userId
  → SELECT * FROM t_seckill_order WHERE order_no = ? AND user_id = ?
     ├── 不存在 → 404
     ├── status ≠ 0 → 400（已支付/已取消/已退款）
  → 乐观锁 UPDATE t_seckill_order SET status=2, cancelled_at=NOW(), version=version+1
      WHERE order_no = ? AND status = 0 AND version = ?
     ├── 影响行数 = 0 → 并发取消，返回成功（幂等）
  → Redis Lua 回补库存（同 3.4.7 超时取消的回补脚本）
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 取消已取消的订单 | 幂等返回成功 |
| 取消已支付的订单 | 400，需走退款流程（3.4.9）|
| 回补库存 Redis 出错 | 记录日志，人工对账补偿 |

🤔 **面试扩展**：用户取消和超时取消并发执行怎么办？乐观锁双保险——谁先执行 CAS 成功谁生效，另一个发现 version 不匹配或 status 已变，跳过。
