> 本项目所有业务服务运行在 VT 上（`spring.threads.virtual.enabled=true`）。以下代码跑在 VT 上，管理员操作只有 INSERT 一条 DML，不加 `@Transactional`。

## 输入输出

**请求** `POST /seckill/activity`（需管理员 JWT）

| 字段 | 位置 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| title | Body | String | ✅ | 活动标题 |
| productId | Body | Long | ✅ | 商品 ID |
| seckillPrice | Body | BigDecimal | ✅ | 秒杀价 |
| originalPrice | Body | BigDecimal | ✅ | 原价 |
| totalStock | Body | Integer | ✅ | 总库存 |
| startTime | Body | LocalDateTime | ✅ | 开始时间 |
| endTime | Body | LocalDateTime | ✅ | 结束时间 |
| X-Idempotency-Key | Header | String | ✅ | UUID，防重复提交，服务端 Redis SETNX 5min |

**响应**

| 场景 | code | message |
|------|------|---------|
| 成功 | 200 | 返回 ActivityVO |
| 重复提交 | 200 | 返回已有 ActivityVO（幂等键命中）|
| 时间不合法 | 400 | "开始时间必须在当前时间之后" |
| 非管理员 | 403 | "仅管理员可操作" |
| 缺幂等键 | 400 | "缺少幂等键" |

## 核心流程

```
POST /seckill/activity + X-Idempotency-Key
  → JWT → role ≠ ADMIN → 403
  → 缺 X-Idempotency-Key → 400
  → Redis SETNX idempotency:{key} 1 EX 300 → 未抢到 → 查已有结果直接返回（幂等）
  → 参数校验（endTime > startTime > now）
  → INSERT t_seckill_activity (status=0 待上架)
  → 返回 ActivityVO
```

## 边界处理

| 场景 | 行为 |
|------|------|
| startTime 在过去 | 400 拒绝 |
| endTime < startTime | 400 拒绝 |
| stock ≤ 0 | 400 拒绝 |
| 创建后自动初始化库存 | 不初始化，上架时才写 Redis |
| 重复提交同幂等键 | 返回已有结果，不重复插入 |
| Redis 不可用 | 降级：跳过幂等检查，直接 INSERT（依赖 DB unique 约束兜底，后续加 title+product_id 唯一索引） |

🤔 **面试扩展**：为什么创建时不初始化 Redis 库存？活动创建到上架可能有一段时间，redis 预热应延迟到上架时，避免占用内存。
- **追问：为什么用 Redis SETNX 做幂等而不是 DB 唯一约束？** → DB 唯一约束需要建联合索引（title+product_id 等业务字段），字段变更成本高。Redis 幂等键 5min TTL，覆盖网络重传窗口，过期后自动清理，不占存储。
- **追问：Redis 挂了怎么办？** → 降级跳过幂等检查，直接 INSERT。t_seckill_activity 表后续加 `uk_title_product (title, product_id)` 兜底唯一约束。
