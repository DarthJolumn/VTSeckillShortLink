# 用户抢购 (3.4.3)

| 属性 | 值 |
|------|-----|
| 功能编号 | 3.4.3 (原#21) |
| 所属模块 | 3.4 秒杀服务 |
| 涉及类 | `SeckillController`、`SeckillOrderService`、`StockService`、`SeckillOrderConsumer` |
| 关联功能 | 3.4.4 库存分片、3.4.6 创建订单、3.4.5 秒杀结果推送 |
| 关联文档 | `2.3-秒杀服务.md` §核心流程、`1.4-项目约束清单.md` |

> 运行在 VT 上。核心路径：Caffeine 本地缓存（无 IO）→ Redis Lua（IO，VT park）→ Kafka send（IO，VT park）。全程不加 `@Transactional`。

## 输入输出

**请求** `POST /seckill/order`（需 JWT）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| activityId | Long | ✅ | 秒杀活动 ID |

**响应**

| 场景 | code | message |
|------|------|---------|
| 排队中 | 200 | "抢购请求已提交" + orderNo |
| 活动未开始/已结束 | 400 | 具体原因 |
| 重复下单 | 400 | "您已参与过本次活动" |
| 库存不足 | 400 | "库存不足" |

## 核心流程

```
POST /seckill/order {activityId}
  → [Gateway] Sentinel 限流（每用户每活动 100 QPS）
  → Caffeine 活动缓存 checkActivityValid(activityId)
     ├── 未开始/已结束 → 400
  → checkUserLimit（Redis 预判 + DB 唯一索引兜底）
     ├── 已下单 → 400
  → StockService.deduct（Redis Lua 原子扣库存）
     ├── 库存不足 → 400
     ├── 重复下单（ordered key 存在）→ 400
  → 发 Kafka 消息（activityId, userId, orderNo）
  → 返回 "抢购请求已提交" + orderNo
```

## 关键代码

```java
// ★ 此方法运行在 VT 上。全程 IO 操作（Redis Lua + Kafka send），VT park 等待不占平台线程。
// 不加 @Transactional——方法内容全是非 DB 操作。
@PostMapping("/order")
public Result<OrderVO> createOrder(@Valid @RequestBody CreateOrderRequest request) {
    // Caffeine 活动缓存——本地内存读取，VT 无阻塞
    SeckillActivity activity = activityCache.get(request.getActivityId());
    if (activity == null || activity.getStatus() != 1)
        return Result.error(400, "活动未开始或已结束");

    Long userId = UserContext.getUserId();

    // Redis 预判——VT park 等 Redis 响应
    Boolean ordered = redisTemplate.hasKey("ordered:" + request.getActivityId() + ":" + userId);
    if (Boolean.TRUE.equals(ordered))
        return Result.error(400, "您已参与过本次活动");

    // Lua 扣库存——VT park 等 Redis EVAL 返回
    StockResult result = stockService.deduct(request.getActivityId(), userId);
    if (result.getCode() != 200)
        return Result.error(400, result.getMsg());

    // Kafka send——VT park 等 Broker ACK
    String orderNo = snowflake.nextIdStr();
    kafkaTemplate.send("seckill-order", new SeckillOrderMsg(request.getActivityId(), userId, orderNo));

    return Result.ok(new OrderVO(orderNo, "PENDING"));
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 活动未开始 | Caffeine 活动状态缓存拦截 |
| 活动已结束 | 同上 |
| 重复抢购 | Lua 中 SETNX ordered key 防重 |
| 库存扣完 | Lua DECR 返回负数 → 库存不足 |
| Sentinel 限流 | 返回 429 |

🤔 **面试扩展**：
- **追问：VT 下这条链路的资源占用？** → 一次抢购请求约 3 次 Redis（hasKey + EVAL）+ 1 次 Kafka send，每次 IO VT park 释放平台线程。10w QPS 下同时只有很少的平台线程被占用，VT 的 park/unpark 开销约 1μs，远小于 IO 时间
- **追问：为什么 Caffeine 缓存不用加锁？** → Caffeine 是线程安全的本地缓存。多个 VT 同时 get 同一个 key 不会冲突。过期后第一个 get 触发 load，后续 VT 等待 load 完成——这个等待是 Caffeine 内部阻塞，在 VT 上不占平台线程
- **追问：如果 VT 在 Caffeine.get 时发生 pinning？** → Caffeine 的 load 方法内部可能使用 synchronized（LoadingCache），这会导致 VT pinned 到平台线程。但 short synchronized 块的 pinning 开销很小（微秒级），且平台线程很快释放——接受。@Transactional 内的长持有才是真正的性能杀手
