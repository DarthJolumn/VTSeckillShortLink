## 消息协议

```json
客户端 → 服务端: {"type": "PING"}
服务端 → 客户端: {"type": "PONG"}
```

## 核心流程

### 服务端接收 PING（跑在消息对应的 VT 上）

```java
@OnMessage
public void onMessage(Session session, String message) {
    WsMessage msg = JsonUtil.parse(message, WsMessage.class);
    if ("PING".equals(msg.getType())) {
        updateLastHeartbeat(session.getId());
        // PONG 回复，AsyncRemote 保证线程安全
        session.getAsyncRemote().sendText("{\"type\":\"PONG\"}");
    }
}
```

### 服务端检测超时（@Scheduled 扫描，异步 close）

```java
@Scheduled(fixedRate = 10000) // 10s
public void checkHeartbeat() {
    long now = System.currentTimeMillis();
    // 拿到快照，避免迭代中 concurrent modification
    Map<String, Session> allSessions = WsSessionManager.getSnapshot();

    for (Map.Entry<String, Session> entry : allSessions.entrySet()) {
        Long lastBeat = lastHeartbeatMap.get(entry.getKey());
        if (lastBeat != null && (now - lastBeat) > 60000) {
            Session stale = entry.getValue();
            // ★ 异步 VT 执行 close，不阻塞 @Scheduled 线程
            Thread.startVirtualThread(() -> {
                try {
                    stale.close();
                } catch (Exception e) {
                    log.warn("Heartbeat close session failed: {}", e.getMessage());
                }
            });
        }
    }
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 客户端 30s PING | 正常，lastHeartbeat 定期更新 |
| 客户端不发 PING 但连接正常（网络单向）| 60s 超时后断开，客户端发现断连后重连 |
| @Scheduled 扫描 10w 连接 | 遍历 O(N)，close 操作异步 VT 不阻塞 |
| PONG 发送失败（session 已断开）| IOException 捕获后忽略，等待 @OnClose 清理 |
| lastHeartbeatMap 内存占用 | 100w 连接 × 8 字节 ≈ 8MB，可接受 |

## 安全点

| 措施 | 说明 |
|------|------|
| 异步 close | 防止 @Scheduled 线程被 @OnClose 中的 Redis 操作拖慢 |
| 快照迭代 | 防止迭代时 WsSessionManager 被其他 VT 修改导致 CMExxx |

🤔 **面试扩展**：
- **追问：为什么取快照而不直接迭代 WsSessionManager？** → `WsSessionManager.getAll()` 返回的是 ConcurrentHashMap 的 entrySet，迭代期间其他 VT 增删 session 不会抛 `ConcurrentModificationException`（CHM 的弱一致性），但可能读到不一致的状态。取快照 `new HashMap<>(liveSessions)` 保证一次扫描基于固定视角
- **追问：100w 连接每 10s 遍历一次，性能如何？** → 遍历 100w 条 Map entry 约 50-100ms（纯内存），筛选出超时连接后每个 close 开一个 VT。性能瓶颈不在遍历，在 Redis SREM（@OnClose 中）。异步 VT 解决
- **追问：为什么超时阈值是 60s？** → 客户端 PING 间隔 30s，允许丢一个 PING（30s + 容忍 30s = 60s）。太短（45s）网络抖动误踢，太长（120s）幽灵连接残留太久。60s = 2 倍间隔是行业惯例
