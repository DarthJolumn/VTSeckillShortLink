## 核心流程

```
@OnClose 或 @OnError
  → 从 RoomManager 移除 sessionId
  → Redis SREM "room:members:{roomId}" userId
  → Redis DEL "ws:route:{userId}"（或留 TTL 自然过期）
  → 通知房间用户 online_count 更新
```

## 被动断开检测

```
@Scheduled(fixedRate = 10000) // 10s
  → 检查 session.isOpen()
  → 检查最后活跃时间（心跳更新）> 60s
  → 过期 → 提交到 VT 异步执行 close:
     Thread.startVirtualThread(() -> {
        session.close();  // @OnClose 在这条 VT 上触发
        cleanup(session); // Redis SREM + DEL 不阻塞调度线程
     });
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 正常断开 | @OnClose 触发，同步清理 |
| 网络断连（未触发 OnClose）| 心跳超时 60s 后 VT 异步 close |
| RoomManager 满 | 强制踢最旧连接（FIFO 淘汰）|
| OnClose 中 Redis 操作失败 | 记录日志，session 已销毁不影响下次连接 |
| 容器 shutdown | `@PreDestroy` 优雅关闭：广播 KICK 全部连接 → sleep 5s → WsSessionManager.closeAll()。application.yml `spring.lifecycle.timeout-per-shutdown-phase: 30s` |

🤔 **面试扩展**：
- **追问：为什么 session.close() 要异步 VT？** → @Scheduled 运行在定时任务线程上，如果同步 close 触发 @OnClose（含 Redis SREM + DEL），10w 连接的超时扫描可能拖垮调度线程。每个 close 开一个 VT，相互独立
- **追问：RoomManager 容量上限设多少？** → 一个 session 约 1-2KB（TCP 缓冲区主体在 OS 层），100w 连接 × 2KB ≈ 2GB。RoomManager 本身 `ConcurrentHashMap<sessionId>` 约 100 字节/条，100w ≈ 100MB。设 20w 是安全余量
- **追问：Scheduled 扫描间隔为什么是 10s？** → 心跳间隔 30s，超时阈值 60s。10s 扫描意味着最多 10s 发现断开 + 10s 清理 = 20s 内清理幽灵连接。精度足够
