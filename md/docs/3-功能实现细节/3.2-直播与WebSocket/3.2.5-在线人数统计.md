## 实时计数

```java
// Redis SCARD O(1)，全局准确
Long globalOnline = redisTemplate.opsForSet().size("room:members:" + roomId);

// RoomManager 本地计数（用于实时展示，允许轻微不一致）
int localOnline = roomManager.getOnlineCount(roomId);
```

## 定时落库（单节点写）

```java
// 多节点同时写 MySQL 是冗余的，Redis SCARD 返回的是全局值
// 用分布式锁控制仅 leader 节点写入：
@Scheduled(fixedRate = 30000)
public void syncOnlineCount() {
    Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent("lock:online_sync", "1", 5, TimeUnit.SECONDS);
    if (!Boolean.TRUE.equals(locked)) return; // 非 leader 跳过

    try {
        for (Long roomId : activeRooms) {
            Long count = redisTemplate.opsForSet().size("room:members:" + roomId);
            jdbcTemplate.update(
                "UPDATE t_live_room SET online_count = ? WHERE id = ? AND status = 1",
                count, roomId);
        }
    } finally {
        redisTemplate.delete("lock:online_sync");
    }
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| Redis 挂了 | 降级为本地 RoomManager 计数（重启丢失，但运行时精确）|
| Redis 恢复 | 从 MySQL 重新初始化（但 MySQL 也滞后，最终一致性）|
| SCARD 返回 0（key 不存在）| 视为 0，不抛异常 |
| 锁超时 | 5s TTL 自动释放，下一周期正常执行 |

🤔 **面试扩展**：
- **追问：为什么用分布式锁控制单节点写 MySQL，各节点写同样的值不行吗？** → 可以，但浪费。写入量 = 节点数 × 活动数。N=3、活动数=100 时每 30s 写 300 次 SQL，99% 是重复值。分布式锁让写入量降为 1/N
- **追问：Redis SCARD 比本地计数慢？** → SCARD O(1)，本地计数 O(1) 但可能不准确（节点间进/出事件只更新本 RoomManager、本 Redis）。以 Redis 为准
- **追问：在线人数同步 30s 够实时吗？** → 前端每 30s 可以通过 WS 推送 ONLINE_COUNT 更新，用户不会感知到明显延迟。面试官追问"怎么提高实时性"——减少到 5s 但 MySQL 写入更频繁，10w QPS 下要权衡
