## 输入输出

**请求** `PUT /live/room/{roomId}/start`（需主播 JWT）

| 场景 | code | message |
|------|------|---------|
| 成功 | 200 | "开播成功" |
| 非主播 | 403 | "仅主播可操作" |
| 房间不存在 | 404 | "房间不存在" |

## 核心流程

```
PUT /live/room/{roomId}/start
  → JWT → userId, role
  → role ≠ 主播 → 403
  → 校验该主播持有该房间
  → UPDATE t_live_room SET status=1, start_time=NOW() WHERE id=? AND status=0
  → Redis SADD "room:members:{roomId}" 空集合（初始化，仅预留 key）
  → 返回成功
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 已开播再次开播 | 幂等，status=1 不再重复修改 |
| 非主播调用 | 403 |
| Redis 写入失败 | 不影响 MySQL，房间可用但在线人数降级 |
| 房间已被其他主播占用（多人直播房）| 校验 room.anchor_id = user_id |

## 安全点

| 措施 | 说明 |
|------|------|
| 主播身份双校验 | JWT role 校验 + room.anchor_id 归属校验 |

🤔 **面试扩展**：
- **追问：开播写入 MySQL 的同时 Redis 失败怎么办？** → 以 MySQL 为准，Redis key 缺失时在线人数功能降级。恢复时可主动重新初始化 Redis。一致性暂不考虑事务，因为 Redis 宕机是小概率，且 MySQL + Redis 双写无法用本地事务覆盖
- **追问：为什么需要 SADD 空集合？** → 预占位，防止关播/进房间时 key 不存在导致的 Redis 异常判断。实际 SADD 空元素会创建空 Set，后续 SCARD 返回 0
