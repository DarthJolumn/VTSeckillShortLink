## 核心流程

```
PUT /live/room/{roomId}/stop
  → JWT → 验证主播身份
  → 广播 KICK 消息 (type=ROOM_CLOSED) 给房间所有人
  → 异步：Thread.startVirtualThread(() -> {
       Thread.sleep(5000); // 给客户端 5s 优雅退出
       强制关闭 RoomManager 中该房间所有剩余 session
     })
  → UPDATE t_live_room SET status=0, end_time=NOW()
  → DEL room:members:{roomId}
  → 接口立即返回 "关播成功"
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 关播时广播 KICK 部分失败 | 不阻塞关播，客户端下次心跳发现房间已关 |
| 关播后仍有 session 残留 | 异步 5s 后强制 close 兜底 |
| 已关播再次关播 | 幂等，status=0 不重复执行 |

## 安全点

| 措施 | 说明 |
|------|------|
| 异步关 Old Session | 关播接口不阻塞，VT 后台清理不拖慢主流程 |
| 优雅关闭 `@PreDestroy` | 容器 shutdown 时广播 ROOM_CLOSED + 等待 5s + closeAll，防止 10w session 泄漏 |

### 优雅关闭配置

```yaml
# application.yml
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

```java
@PreDestroy
public void gracefulShutdown() {
    // 广播 KICK → 等待 5s → closeAll
    WsSessionManager.closeAll();
}
```

🤔 **面试扩展**：
- **追问：为什么要异步等 5s 而不是同步 sleep？** → 关播接口是 HTTP 调用，同步 sleep 5s 会长时间占用一个 VT，虽然不阻塞平台线程但使接口 RT 飙升到 5s+，上游 Nginx 可能超时断开。异步 VT 让接口 200ms 内返回，5s 后后台清理
- **追问：异步 VT 内 session.close() 异常如何捕获？** → 用 `CompletableFuture` 或 try-catch 兜底，异常只记日志不重试
- **追问：关播后 room:members Redis key 已删，异步清理还有意义？** → 有意义。RoomManager 本地 Map 中还持有 session 引用，不关闭会导致内存泄漏。Redis key 已删保障新连接进不来
