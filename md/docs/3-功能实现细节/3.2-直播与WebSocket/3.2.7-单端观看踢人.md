## 核心流程

```
@OnOpen
  → 查 Redis "ws:route:{userId}"
  → 如果已有 sessionId && 不是当前 session：
    ① 新 session 立即注册（先注册后踢，保证连接不卡）
    ② 异步 VT：发 KICK 给旧 session
    ③ 异步 VT：等 3s 后强制 close 旧 session
  → 更新 Redis "ws:route:{userId}" = "{nodeId}:{newSessionId}"
```

## 关键代码

```java
@OnOpen
public void onOpen(Session session, @PathParam("roomId") Long roomId,
                   @QueryParam("token") String token) {
    Long userId = JwtUtil.verify(token);
    String nodeId = getNodeId();
    String sessionId = session.getId();

    // 先注册新连接，@OnOpen 立即返回
    WsSessionManager.add(sessionId, session);
    redisTemplate.opsForValue()
        .set("ws:route:" + userId, nodeId + ":" + sessionId, 30, TimeUnit.MINUTES);

    // 异步踢旧连接（不阻塞 onOpen）
    String oldRoute = (String) redisTemplate.opsForValue().get("ws:route:" + userId);
    if (oldRoute != null) {
        String[] parts = oldRoute.split(":", 2);
        String oldNodeId = parts[0];
        String oldSessionId = parts[1];

        if (oldNodeId.equals(nodeId)) {
            // 同节点踢人
            Thread.startVirtualThread(() -> {
                Session oldSession = WsSessionManager.get(oldSessionId);
                if (oldSession != null && oldSession.isOpen()) {
                    try {
                        oldSession.getAsyncRemote()
                            .sendText("{\"type\":\"KICK\",\"data\":{\"reason\":\"NEW_LOGIN\"}}");
                        Thread.sleep(3000);
                        if (oldSession.isOpen()) oldSession.close();
                    } catch (Exception e) {
                        log.warn("Kick old session failed: {}", e.getMessage());
                    }
                }
            });
        } else {
            // 跨节点踢人 → Dubbo RPC
            wsPushService.kickDevice(userId, oldSessionId);
        }
    }
}
```

## 跨节点路由

```
ws:route:{userId} = "{nodeId}:{sessionId}"
  例: ws:route:1001 = "node-1:abc123"

同节点（相同 nodeId）→ 直接发
跨节点 → 查节点信息 → Dubbo 调用 WsPushService.push
```

## 广播并发安全

广播场景下多个 VT 可能同时写同一个 session。**VT 下必须用 AsyncRemote**，禁止 `synchronized` + `getBasicRemote`：

```java
// ✅ AsyncRemote：无锁，VT 不 pin
session.getAsyncRemote().sendText(message);
```

> ⚠️ `synchronized (session) { session.getBasicRemote().sendText(msg); }` 在 VT 下是反模式——`synchronized` 导致 VT pinning，`sendText` 是 IO 操作，pinning 期间 carrier 线程被占住。

## 边界处理

| 场景 | 行为 |
|------|------|
| 旧连接已断开（ws:route 残留）| TTL 30min 自然过期，异步 KICK 发到已关闭 session 抛异常 → catch 忽略 |
| 跨节点踢人时目标节点宕机 | Dubbo 调用失败 → 日志告警，ws:route 等 TTL 自动清理 |
| 同节点踢人时旧 session 刚好自己断开 | sendText 抛 IOException → catch 后跳过 close |
| 异步 VT 内 sleep 被中断 | InterruptedException 捕获，直接 close 旧 session |

## 安全点

| 措施 | 说明 |
|------|------|
| 异步踢人不阻塞 @OnOpen | 新连接握手 < 10ms，用户体验好 |
| 3s 强制 close 兜底 | 防止旧连接一直残留 |
| try-catch 兜底 | 防止异步 VT 抛出未捕获异常导致 JVM 打印到 System.err |

🤔 **面试扩展**：
- **追问：为什么先注册新连接再踢旧的，顺序反了有问题吗？** → 如果先踢旧连接（sleep 3s）再注册新连接，新用户看到的是"连接中..."转了 3 秒。先注册新连接，旧用户收到 KICK 的 3s 内两条连接并存，但同一时间只有一个活跃
- **追问：跨节点踢人为什么用 Dubbo 不用 Kafka？** → Kafka 延迟几百 ms，Dubbo < 5ms。踢人要立即生效（旧用户可能还在发弹幕、操作），延迟不可接受
- **追问：`Thread.startVirtualThread` 和 `CompletableFuture.runAsync` 区别？** → 后者默认用 `ForkJoinPool.commonPool()`，在 VT 环境下应显式传入 `Executors.newVirtualThreadPerTaskExecutor()`。直接 `Thread.startVirtualThread` 更简洁
