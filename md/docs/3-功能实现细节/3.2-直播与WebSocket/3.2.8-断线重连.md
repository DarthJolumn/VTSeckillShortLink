## 客户端策略

指数退避：1s → 2s → 4s → 8s → 16s → max 30s，重试 10 次后停止。

## 服务端离线消息

```java
// 推送前判断
if (session != null && session.isOpen()) {
    // VT 下用 AsyncRemote，无锁且不 pin
    session.getAsyncRemote().sendText(message);
} else {
    // 追加到离线消息列表，LTRIM 限制长度防 OOM
    String key = "offline:" + userId;
    redisTemplate.opsForList().rightPush(key, message);
    redisTemplate.opsForList().trim(key, -100, -1); // 只保留最近 100 条
    redisTemplate.expire(key, 5, TimeUnit.MINUTES);
}
```

> ⚠️ 原用 `synchronized (session) { session.getBasicRemote().sendText(msg); }` — 在 VT 下是反模式。`synchronized` pin VT 到 carrier 线程，`sendText` 是 IO 操作，pinning 期间整个 carrier 线程被占住无法调度其他 VT。

### 重连后拉取

```java
@OnOpen
public void onOpen(Session session, Long roomId, Long userId) {
    // ... 注册新连接 ...

    // 拉取离线消息
    List<String> offlineMsgs = redisTemplate.opsForList()
            .range("offline:" + userId, 0, -1);
    if (offlineMsgs != null && !offlineMsgs.isEmpty()) {
        for (String msg : offlineMsgs) {
            session.getAsyncRemote().sendText(msg); // AsyncRemote 免锁
        }
        redisTemplate.delete("offline:" + userId);
    }
}
```

## 重连时序图

```
客户端断连
  │  ws:route:{userId} 残留（30min TTL）
  │  消息 → offline:{userId} (TTL 5min, max 100条)
  │
  ├── 5min 内重连成功 → 拉取离线消息，恢复直播
  │
  └── >5min 重连 → 离线消息已过期，只能看到当前状态
          └── 重连时 @OnOpen 中的踢人检测清理旧 ws:route
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 5min 内重连 | 收到离线消息，直播状态无缝恢复 |
| 超过 5min 重连 | 离线消息 TTL 到期，用户看到当前直播状态 |
| 重连到不同节点 | @OnOpen 中踢人检测清理旧节点 ws:route |
| 离线消息积累 >100 条 | LTRIM 自动淘汰最早消息，防止 Redis List 无限增长 |
| 用户一直重连超过 10 次 | 客户端停止重连，用户手动刷新页面 |
| 重连时房间已关播 | @OnOpen 房间校验 4004 关闭，客户端展示"直播已结束" |
| 重连后客户端重发未确认弹幕 | 服务端 messageId 去重（`barrage:{messageId}` SETNX 5min），不会重复广播/入库 |

## 安全点

| 措施 | 说明 |
|------|------|
| LTRIM 限长 | 防止 5min 内大量弹幕撑爆 Redis 内存 |
| AsyncRemote 拉取离线消息 | 多个消息逐个发，无需同步锁 |
| 离线消息 TTL | 5min 后自动清理，不手动也安全 |

🤔 **面试扩展**：
- **追问：为什么离线消息限制 100 条而不是所有？** → 5min 内 100 条弹幕已经很多了（平均 1 条/3s），再多用户也刷不过来。假设一个弹幕 200 字节，100 条 = 20KB，Redis List 内存可接受。无限条数可能被恶意刷爆
- **追问：`LTRIM key -100 -1` 不原子？** → 不在 Lua 中，rightPush + LTRIM 不是原子操作。但 Redis List 的淘汰是近似的——多出来的几条会被淘汰掉，不影响业务。如需精确控制，用 Lua 脚本包装
- **追问：断线后用户去另一个直播间再回来？** → 离线消息按 userId 隔离，不同直播间消息分别推送。重连时拉取所有离线消息（包含其他房间的），前端根据 roomId 过滤
- **追问：重连后客户端重发未确认弹幕怎么办？** → 弹幕本身已有 messageId 去重（`barrage:{messageId}` SETNX 5min）。离线消息是服务端推给客户端的（如 SEC_KILL_RESULT、GIFT 等），弹幕是客户端发给服务端的——两个方向，消息 ID 去重解决弹幕方向，离线消息解决推送方向，互不冲突
