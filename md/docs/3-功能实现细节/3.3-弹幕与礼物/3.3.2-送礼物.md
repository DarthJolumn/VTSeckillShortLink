> `@OnMessage` 运行在 VT 上（vt Executor 配置见 3.2.3）。Dubbo RPC 调用在 VT 上阻塞但不占平台线程。异步入库用 `Thread.startVirtualThread`。

## 输入输出

**客户端 → 服务端**

```json
{"type": "GIFT", "data": {"messageId": "uuid", "giftId": 101, "quantity": 1}}
```

> `messageId` 由客户端生成 UUID，用于服务端去重。断网重连时防止同一礼物消息被重复处理。

**服务端 → 房间所有人**

```json
{"type": "GIFT", "data": {"messageId": "uuid", "userId": 1001, "nickname": "张三", "giftName": "火箭", "quantity": 1, "timestamp": 1719360000000}}
```

## 核心流程

```
客户端 → WS: GIFT {messageId, giftId, quantity}
  → @OnMessage VT 解析
  → 幂等去重：Redis SETNX gift:{messageId} 1 EX 300（防断网重连重发）
  → 查本地缓存礼物配置
  → 房间广播（AsyncRemote 无锁）
  → [Dubbo] LeaderboardService.addScore() ← VT 阻塞等 Dubbo 响应
  → 异步入库 t_gift_record（Thread.startVirtualThread）
```

## 关键代码

```java
@OnMessage
public void onMessage(Session session, String message, @PathParam("roomId") Long roomId) {
    // ★ 此方法运行在 VT 上

    WsMessage wsMsg = JsonUtil.parse(message, WsMessage.class);
    if ("GIFT".equals(wsMsg.getType())) {
        String messageId = wsMsg.getData().get("messageId").asText();
        Long giftId = wsMsg.getData().get("giftId").asLong();
        int quantity = wsMsg.getData().get("quantity").asInt();
        Long userId = getUserId(session);

        // 幂等去重：同一 messageId 只处理一次（防断网重连重复送礼）
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent("gift:" + messageId, "1", 5, TimeUnit.MINUTES);
        if (!Boolean.TRUE.equals(firstTime)) {
            return; // 已处理过，静默丢弃
        }

        GiftConfig gift = giftConfigCache.get(giftId);
        double totalAmount = gift.getPrice() * quantity * 1.0;

        // 房间广播（AsyncRemote 无锁，VT 友好）
        WsMessage broadcast = new WsMessage("GIFT", Map.of(
            "messageId", messageId,
            "userId", userId,
            "giftName", gift.getName(),
            "quantity", quantity,
            "timestamp", System.currentTimeMillis()
        ));
        roomBroadcast(roomId, broadcast);

        // Dubbo RPC 调用排行榜加分——VT 阻塞等待响应，平台线程可服务其他 VT
        leaderboardService.addScore(getActivityId(roomId), userId, "GIFT", totalAmount);

        // 异步入库——显式 VT 而非 ForkJoinPool
        Thread.startVirtualThread(() ->
            giftRecordRepository.save(
                new GiftRecord(roomId, userId, giftId, quantity, totalAmount)));
    }
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 礼物 ID 不存在（配置缓存中无）| 丢弃消息，记录 WARN 日志 |
| 数量为 0 或负数 | 丢弃 |
| 重复 messageId（网络重发） | 静默丢弃，不重复广播/加分/入库 |
| 缺 messageId（旧客户端） | 降级：正常处理，不做去重 |
| Dubbo 排行榜超时 | 不影响广播，加分丢失——可降级为 Kafka 异步加分（在 TS-2 约束下，Dubbo 是唯一 RPC，超时降级用 try-catch 记录日志）|
| Dubbo 服务不可用 | try-catch 包裹，记录日志。排行榜不加分但礼物广播正常 |
| 异步入库失败 | 不影响主流程——用户看到特效但流水丢失。降级：记录失败日志，对账补偿 |
| 连续快速送多个 | 逐个广播，不加锁 |

🤔 **面试扩展**：
- **追问：VT 下 Dubbo RPC 调用的线程模型？** → 根据 `1.2-技术选型分析.md` §2 Dubbo，Dubbo 的 Biz 线程池改为 VT。当前 VT 发出的 Dubbo 调用走 Dubbo 的 IO 线程（Netty EventLoop）发送请求，然后 VT park 等待响应。响应回来后恢复 VT。全程不占平台线程
- **追问：为什么不用 Kafka 解耦？** → 排行榜需要实时性——送礼后排名应秒变。Kafka 有 100~500ms 延迟，Dubbo < 5ms。如果 Dubbo 挂了，降级为记录日志后 Kafka 异步补偿（但不作为主要路径——违反 TS-3 "Kafka为主"约束吗？不，Dubbo 是主路径，Kafka 是降级路径，仍以 Dubbo 为主）
- **追问：礼物和弹幕的 messageId 去重逻辑一样吗？** → 原理一样（Redis SETNX 5min TTL），key 前缀不同（`gift:{msgId}` vs `barrage:{msgId}`）。礼物涉及扣费，去重更重要——弹幕重复只是刷屏，礼物重复是真金白银。详见 `3.3.1-发送弹幕.md` §核心流程
- **追问：synchronized 在 VT 下的 pinning？** → 当前送礼逻辑没有 synchronized（广播用 AsyncRemote、Dubbo 不涉及共享资源、入库异步 VT）。不存在 pinning 问题
