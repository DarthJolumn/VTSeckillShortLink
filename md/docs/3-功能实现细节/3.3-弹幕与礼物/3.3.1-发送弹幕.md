> WebSocket 模块的 `@OnMessage` 运行在 VT 上（通过 `ServletServerContainerFactoryBean.setExecutor(Executors.newVirtualThreadPerTaskExecutor())` 配置）。详见 `3.2.3-进直播间.md` §VT 配置。异步入库确保用 VT 而非 ForkJoinPool。

## 输入输出

**客户端 → 服务端**

```json
{"type": "BARRAGE", "data": {"messageId": "uuid", "content": "666"}, "timestamp": 1719360000000}
```

> `messageId` 由客户端生成 UUID，用于服务端去重。断网重连时客户端可能重发同一条弹幕，服务端通过 Redis SETNX 保证同一条消息不被重复广播 + 入库。

**服务端 → 房间所有人**

```json
{"type": "BARRAGE", "data": {"messageId": "uuid", "userId": 1001, "nickname": "张三", "content": "666", "timestamp": 1719360000000}}
```

> 广播出去的消息也带 `messageId`，客户端收到后用于判断是否是自己发的消息（避免重复显示）。

## 核心流程

```
客户端 → WS: BARRAGE {messageId, content}
  → @OnMessage VT 解析消息
  → Redis SETNX barrage:{messageId} 1 EX 300 → 已存在 → 跳过（幂等）
  → DFA 敏感词过滤（纯 CPU，VT 不阻塞平台线程）
  → 房间广播（遍历 session + AsyncRemote 异步发送）
  → 异步入库（Thread.startVirtualThread 保证跑在 VT 上）
```

## 关键代码

```java
@OnMessage
public void onMessage(Session session, String message, @PathParam("roomId") Long roomId) {
    // ★ 此方法运行在 VT 上。WebSocket VT 配置见 3.2.3

    WsMessage wsMsg = JsonUtil.parse(message, WsMessage.class);

    if ("BARRAGE".equals(wsMsg.getType())) {
        String messageId = wsMsg.getData().get("messageId").asText();
        String content = wsMsg.getData().get("content").asText();

        // 幂等去重：同一 messageId 只处理一次（防断网重连重发）
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent("barrage:" + messageId, "1", 5, TimeUnit.MINUTES);
        if (!Boolean.TRUE.equals(firstTime)) {
            return; // 已处理过，静默丢弃
        }

        // DFA 过滤（纯 CPU 计算，VT 下不阻塞平台线程）
        String filtered = dfaFilter.replaceSensitiveWords(content);

        // 房间广播（AsyncRemote 无锁广播，VT 友好）
        WsMessage broadcast = new WsMessage("BARRAGE", Map.of(
            "messageId", messageId,
            "userId", getUserId(session),
            "content", filtered,
            "timestamp", System.currentTimeMillis()
        ));
        roomBroadcast(roomId, broadcast);

        // ★ 异步入库：显式用 VT 而非 ForkJoinPool.default
        Thread.startVirtualThread(() ->
            barrageRepository.save(new Barrage(roomId, getUserId(session), filtered)));
    }
}
```

## 边界处理

| 场景 | 行为 |
|------|------|
| 空内容 | 丢弃 |
| 纯空格 | 丢弃 |
| 超长内容 | 截断（200 字符上限）|
| 命中敏感词 | 替换为 *** |
| 重复 messageId（网络重发） | 静默丢弃，不广播不重复入库 |
| 缺 messageId（旧客户端） | 降级：正常处理，不做去重 |
| 房间已关播 | session 已断开，不可能收到消息 |
| 异步入库失败 | 异步入库失败不影响广播——用户看到弹幕但历史回放可能丢。降级：重试 1 次或写日志 |

## 安全点

| 措施 | 说明 |
|------|------|
| 服务端 DFA 过滤 | 客户端可篡改，服务器过滤是底线 |
| 内容不直接入库 | 过滤后才写入 MySQL |
| 内容限长 | 200 字符上限，防恶意超长文本 |

🤔 **面试扩展**：
- **追问：VT 下 DFA 过滤的 CPU 密集问题？** → DFA 时间复杂度 O(N)，N 为内容长度（通常 ≤ 200），纯 CPU 计算约微秒级。VT 执行 CPU 短操作不会引发显著的 pinning 问题。如果词库极大（10w+），首次加载构建 Trie 树是 CPU 密集，放 `@PostConstruct` 中单次执行
- **追问：为什么 `Thread.startVirtualThread` 而不是 `CompletableFuture.runAsync`？** → `CompletableFuture.runAsync()` 默认用 `ForkJoinPool.commonPool()`（平台线程池），在 VT 环境下应用显式传 VT Executor。`Thread.startVirtualThread()` 直接创建 VT，更简洁
- **追问：弹幕广播的并发问题？** → 广播时多个 VT 可能同时写同一个 session。**VT 下必须用 `session.getAsyncRemote().sendText()`**——内部线程安全 + 无锁 + VT 不 pin。禁止 `synchronized(session)`——pin 住 carrier 线程，在 IO 操作中持有锁尤其致命。详见 3.2.3
- **追问：messageId 去重用 Redis SETNX 而不是本地 Set 的原因？** → WS 连接断开后重连可能连到不同节点，本地 Set 无法跨节点共享。Redis 5min TTL 覆盖重连窗口，过期后自动清理，不占内存
- **追问：Redis 不可用时 messageId 去重失效怎么办？** → 降级跳过去重，弹幕可能重复显示（用户看到重复弹幕但不会丢消息）。t_barrage 表不设唯一约束（1 亿条量级，索引成本高），接受少量重复入库
