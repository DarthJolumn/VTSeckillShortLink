## P0 — 必须修（4/4 已修复）

### P0-1：WebFlux 中阻塞 Redis 调用 ✅

- **根因**: `SignVerifyGlobalFilter` 在 WebFlux EventLoop 上调用同步 `RedisTemplate.setIfAbsent()` 做 Nonce 检查
- **影响**: 10w QPS 下 EventLoop 线程被阻塞 → 请求排队 → 网关成为瓶颈
- **修复**: 
  - `2.6-网关与可观测性.md` §签名验签：替换为 `ReactiveRedisTemplate` + `Mono.flatMap()` 链式调用
  - `3.6.3-接口签名验签.md`：同步替换，增加 P0-1 fixed 标注
- **文件**:
  - `docs/2-模块详细设计/2.6-网关与可观测性.md`
  - `docs/3-功能实现细节/3.6-网关与公共/3.6.3-接口签名验签.md`

### P0-2：`t_device_session` 死表 ✅

- **根因**: DDL 建了表（7 字段 2 索引）但整个项目无任何代码路径读写它；设备会话只用 Redis
- **影响**: 无效设计——建了不用的表造成运维困扰和面试追问风险
- **修复**:
  - `2.2-用户服务与认证.md`：移除 `t_device_session` DDL，增加说明设备会话仅存 Redis
  - `2.7-数据库设计.md`：移除 §1.2 `t_device_session` 整个小节
  - `3.1.2-登录.md`：代码注释标注 P0-2 fixed
- **文件**:
  - `docs/2-模块详细设计/2.2-用户服务与认证.md`
  - `docs/2-模块详细设计/2.7-数据库设计.md`
  - `docs/3-功能实现细节/3.1-用户服务/3.1.2-登录.md`

### P0-3：Snowflake epoch 不一致 ✅

- **根因**: `2.1` epoch=`1735689600000L` (2025-01-01)，`3.6.5` epoch=`1700000000000L` (2023-11-15)，差 356 天
- **影响**: 同一毫秒生成的 ID 高位不同，订单号冲突
- **修复**:
  - `3.6.5-SnowflakeID.md`：epoch 统一为 `1735689600000L`（以 2.1 为权威源），删除重复代码改为引用 2.1
  - `3.1-技术决策清单.md`：clock rollback 阈值 100ms → 30ms，epoch 显式标注 `1735689600000L`，与 2.1 一致
- **文件**:
  - `docs/3-功能实现细节/3.6-网关与公共/3.6.5-SnowflakeID.md`
  - `docs/1-架构设计/3.1-技术决策清单.md`

### P0-4：BARRAGE 消息体不一致 ✅

- **根因**: `2.8-接口文档.md` BARRAGE 客户端消息为 `{content}`，缺 `messageId`；但 `2.4` 的幂等去重依赖此字段
- **影响**: 接口文档描述的消息无法去重
- **修复**: `2.8-接口文档.md` §三 BARRAGE 客户端消息改为 `{messageId, content}`
- **文件**: `docs/2-模块详细设计/2.8-接口文档.md`

## 审计小结

此次审计从 5 个维度（架构 × 测试 × VT 纪律 × 高并发 × 设计完整性）扫描了 40+ 份文档，发现的核心问题是：

1. **Gateway 线程模型冲突**（P0-1）：WebFlux + 同步 Redis = 高并发下退化为阻塞模型，是最严重的架构级问题
2. **设计留存偏差**（P0-2/4）：表建了不用、字段有了但接口文档没写——设计层和实现层脱节
3. **多文档一致性**（P0-3/P1-6）：同一 epoch 在 2 份文档写了 2 个不同值——"单一源"规则未严格执行
4. **面试质量瑕疵**（P1-4/P2-3）：决策缺依据、算术不精确——面试中会被追问

修复后文档质量：架构一致性 ✅、接口文档完备性 ✅、VT 纪律 ✅、面试防御性 ✅
