# 行业专家设计原则总结

> 综合阿里云、腾讯云、慕课网、牛客网等多方资料提炼的秒杀/高并发系统设计原则

---

## 一、四大核心原则

```
1. 能缓存不数据库
   - 90% 的读请求走缓存（Caffeine + Redis）
   - 数据库只做最终落盘

2. 能异步不同步
   - 核心链路：扣库存同步 → 下单异步
   - 非核心流程全部异步化

3. 能降级不崩溃
   - 每一层都有 Plan B
   - 拒绝请求比返回错误数据安全

4. 能简单不复杂
   - 用 20% 的复杂度解决 80% 的问题
   - 不要为不存在的量级过度设计
```

---

## 二、流量漏斗模型

```
100% 请求
   ↓
CDN 过滤静态资源           → 过滤 30% 请求
   ↓
Nginx 限流 + WAF          → 过滤 20% 恶意请求
   ↓
Gateway 限流 + 鉴权       → 过滤 10% 无效请求
   ↓
本地缓存过滤无库存         → 过滤 30% 请求
   ↓
Redis 原子扣减             → 99.9% 请求在此返回失败
   ↓
Kafka 异步下单
   ↓
MySQL 持久化
```

**最终效果：** 100 万请求 → 实际到 MySQL 的只有几百个真实下单

## 三、面试回答的标准结构

```
第一步：场景分析
  "秒杀的特点是瞬时高并发 + 有限库存 + 一致性要求高"

第二步：架构分层
  "我把它分为四层：接入层（Nginx）、应用层（Gateway + Service）、缓存层（Redis）、数据层（MySQL）"

第三步：核心难点
  "三个最核心的问题：
   1. 怎么防超卖 —— Redis Lua 原子脚本
   2. 怎么扛流量 —— 多级缓存 + 限流 + 异步
   3. 怎么保数据 —— 最终一致性 + 定时补偿"

第四步：量化结果
  "压测数据：单机 5,000 QPS，P99 延迟 50ms，0 超卖"

第五步：如果是大厂你会怎么做
  "如果 QPS 再上 10 倍，需要做的：
   1. 库存分片（热点打散）
   2. Dubbo/gRPC 替换 Feign（减少序列化开销）
   3. Redis 集群 + 本地缓存兜底
   4. 异地多活部署"
```

## 四、"降级"的具体方案

| 故障场景 | 降级动作 | 用户感知 |
|---------|---------|---------|
| Redis 挂了 | 跳过 Redis，直接读 MySQL + 拒绝写 | 秒杀不可用，浏览正常 |
| Kafka 挂了 | 切为同步下单（Redis → 直接 INSERT DB） | 下单变慢但可用 |
| MySQL 挂了 | Redis 缓存读正常 + 写操作记录到 Redis 草稿 | 查数据正常，下单稍后再试 |
| 本地缓存过期 | 重新从 Redis 加载 | 无感知 |
| 网关超负荷 | Nginx 返回 503 | 页面无法访问 |

---

## 五、任何高并发项目必须回答的 5 个问题

1. **QPS 是多少？怎么测的？** —— 必须有自己的压测数据
2. **怎么防超卖？** —— Redis Lua 原子脚本 + DB 唯一索引双重保障
3. **某个中间件挂了怎么办？** —— 每一层都要有兜底方案
4. **为什么选这个技术不选那个？** —— 要有对比、有 trade-off 分析
5. **如果再给你一个月你会优化什么？** —— 说出 2~3 个可优化点且有理有据
