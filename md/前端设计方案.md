# LiveMall 前端设计方案

> 本文档基于 `md/docs/` 下后端架构设计（1.1～3.6）与 `livemall-ui-vue` 现有 Vue3 脚手架，输出前端整体设计方案。
> 范围：视觉风格、技术架构、全量页面线框、核心交互流程、网络层与 WebSocket 客户端、组件库、动效清单、后端对接要点。
> 不包含：可直接运行的完整代码（本文为设计文档，代码实现按章节逐步落地）。

---

## 一、设计总纲

### 1.1 项目定位与前端目标

LiveMall 是高并发直播电商秒杀系统，前端需对接 5 个后端微服务（user / seckill / websocket / leaderboard / gateway），承载四条核心链路：

| 链路 | 前端职责 | 关键体验 |
|------|---------|---------|
| 直播 | 进入房间、长连接保活、弹幕收发、在线人数 | 实时感、低延迟 |
| 秒杀 | 倒计时、抢购点击、结果推送、订单流转 | 紧张感、防误触、即时反馈 |
| 排行榜 | 实时 TopN、个人排名、历史趋势 | 顺位变化可视 |
| 弹幕礼物 | 发送、过滤无感、礼物特效、加分联动 | 沉浸、炫酷 |

前端目标：**用一个直播间页把后端所有技术纵深串成可演示的闭环**，同时给观众/主播/管理员三套角色各自的操作界面。

### 1.2 设计原则

1. **实时优先**：在线人数、弹幕、秒杀结果、排行榜全部走 WebSocket 推送，UI 用最小变更粒度局部刷新，避免整页重渲染。
2. **秒杀紧张感**：倒计时、库存条、按钮蓄力按压、抢购结果 toast 全程强反馈。
3. **角色分明**：观众重沉浸观看，主播重管控，管理员重数据全局观，三套界面布局语言区分。
4. **性能优先**：长列表虚拟滚动、弹幕轨道限量、礼物特效用 CSS/Canvas 而非重 DOM、大屏图表节流刷新。
5. **AI 可生成**：每个页面线框 + 组件契约足够明确，后续可直接交给 AI 产出代码。

### 1.3 视觉风格方向：暗夜电竞霓虹风

**定位**：深色底 + 霓虹紫青/金色高亮 + 强光晕流光，贴合直播 + 秒杀紧张氛围，大屏效果炸裂。

| 维度 | 规范 |
|------|------|
| 主背景 | `#0A0B1A`（近黑深紫）→ `#12132A` 渐变 |
| 卡片底 | `rgba(20, 22, 48, 0.7)` + 1px `rgba(138, 99, 255, 0.2)` 描边 + 背景模糊 |
| 主强调色 | 霓虹紫 `#8A63FF` / 电青 `#00E5FF` |
| 秒杀色 | 烈焰橙红 `#FF4D4F` → `#FF8A00` 渐变 |
| 排行榜色 | 金 `#FFD666` / 银 `#C9CDD4` / 铜 `#FFA572` |
| 文字 | 主 `#E5E6F0` / 次 `#8A8FB5` / 弱 `#56587A` |
| 圆角 | 卡片 12px / 按钮 8px / 头像圆形 |
| 字体 | 标题 `Oswald/思源黑体 Heavy` / 正文 `Inter/思源黑体` / 数字 `DIN Alternate` |
| 光晕 | 关键 CTA 按钮外发光 `box-shadow: 0 0 20px var(--neon-purple)` |
| 动效曲线 | `cubic-bezier(0.16, 1, 0.3, 1)`（弹性感出场）|

**动效总原则**：微交互（hover/按压/数字滚动）全局统一；场景级动效（秒杀成功烟花、礼物全屏飘落、大屏翻牌）仅在关键节点触发，避免性能过载。所有动效尊重 `prefers-reduced-motion`。

## 二、技术架构

### 2.1 技术栈选型

| 分类 | 选型 | 理由 |
|------|------|------|
| 框架 | Vue 3（`<script setup>` + Composition API） | 现有脚手架已 Vue3.2.13，沿用 |
| 构建 | **Vite 5**（替换 Vue CLI） | 冷启动 <1s，HMR 快，Vue CLI 已不再主推 |
| 语言 | JavaScript（可选 TS） | 脚手架现状为 JS，先 JS 落地，TS 作为可选演进 |
| 路由 | Vue Router 4 | 标配 |
| 状态 | **Pinia** | Vue3 官方推荐，TS 友好，替代 Vuex |
| UI 库 | **Naive UI**（推荐） | 暗色主题原生支持、按需引入、不依赖全局 CSS，契合霓虹风自定义 | 
| 图表 | ECharts 5 | 大屏实时图表能力强，支持增量数据 |
| 动效 | GSAP + `@vueuse/motion` + CSS3 | GSAP 做编排，Vueuse 做声明式，CSS 做轻量 |
| 特效 | Canvas 2D + CSS 粒子 | 礼物飘落/烟花用 Canvas，避免重 DOM |
| HTTP | Axios | 拦截器机制成熟，便于签名/刷新注入 |
| WS | 原生 WebSocket + 自研客户端 | 后端用 `@ServerEndpoint`，原生兼容；自研心跳/重连/分发 |
| 工具 | VueUse / dayjs / crypto-js | VueUse hooks、dayjs 时间、crypto-js 做 HMAC 签名 |
| 代码规范 | ESLint + Prettier + Stylelint | 统一风格 |

> UI 库备选：若偏好组件最全可用 Element Plus（暗色主题需额外配置）；本方案以 Naive UI 为基准设计。

### 2.2 前端分层架构

```

│  视图层 (views / pages)                            │
│  路由页面 + 角色布局外壳                            │
├───────────────────────────────────────────────────┤

├───────────────────────────────────────────────────┤
│  服务层 (services)                                 │
│  api 模块(user/seckill/leaderboard) + ws 客户端    │
├───────────────────────────────────────────────────┤
```

依赖方向自上而下，基础设施层不依赖任何上层。

```

VITE_WS_BASE  = ws://localhost:8083
VITE_APP_KEY  = demo-web      # 签名 AppKey（见 §10.4 安全对策）
```

## 三、角色与权限体系

### 3.1 三角色

| 角色 | role 码 | 入口 | 核心界面 |
|------|--------|------|---------|
| 观众 | 1 | 首页直播间广场 | 直播间页、个人中心、订单 |
| 主播 | 2 | 主播控制台 | 开播、活动管理、直播数据 |
| 管理员 | 3 | 管理后台 | 用户管理、活动总览、数据大屏 |

### 3.2 权限控制三层

1. **路由级**：`meta.roles` + 全局前置守卫，无权访问跳 403 页。
2. **菜单级**：按 `user.role` 动态渲染侧栏/顶栏菜单。
3. **按钮级**：`v-permission="['admin']"` 指令，无权节点点不渲染或禁用。

### 3.3 JWT 双 Token 前端策略

- Access Token（15min）存内存（Pinia）+ `sessionStorage` 兜底刷新页保活。
- Refresh Token（7天）存 `localStorage`，用于无感刷新。
- 请求拦截器自动注入 `Authorization: Bearer <access>`。
- 响应拦截器遇 401 → 触发刷新 → 重发原请求；刷新失败 → 清 storage → 跳登录。
- 并发 401 合并：用 Promise 队列保证同一时刻只发一个 `/auth/refresh`，其余请求挂起等结果（对应后端 §2.2 并发刷新防护）。
- WS 连接用 Access Token 作 query 参数；Access 过期时 WS 层主动重连换 token。

**区域职责与数据源：**

| 区域 | 数据源 | 更新方式 |
|------|--------|---------|
| 视频区 | 推流占位 / 本地摄像头（主播端） | 静态/预览 |
| 秒杀卡 | `GET /seckill/activity/{id}` + WS 库存推送 | 倒计时本地 + 结果 WS |
| 排行榜 | `GET /leaderboard/top` 轮询 3s + 送礼后立即刷新 | WS GIFT 触发刷新 |
| 在线人数 | WS `ONLINE_COUNT` | WS 推送局部更新 |
| 弹幕 | WS `BARRAGE` 下行 + `POST BARRAGE` 上行 | WS 推送入队 |
| 礼物 | WS `GIFT` 下行 + 上行送礼 | 触发特效 + 刷新榜 |
| 秒杀结果 | WS `SEC_KILL_RESULT` | Toast + 订单跳转 |
| 踢人/封禁 | WS `KICK` / `BAN` / `ROOM_CLOSED` | 强制弹窗 + 跳回首页 |

**关键动效：**
- 弹幕从右向左飘入，3 条轨道不重叠，超 50 条出列旧消息。
- 礼物弹幕带金边高亮 + 礼物图标。
- 秒杀倒计时最后 10s 数字变红 + 放大跳动。
- 抢购按钮：未到点灰色蓄力进度条；到点变橙红 + 外发光脉冲；点击有按压震动反馈；售罄灰化。
- 抢中：烟花 Canvas 全屏 1.5s + 顶部 toast「抢购成功，去支付」。
- 排行榜顺位变化：FLIP 动画上下交换。
- 送礼：礼物图标从底部飞向视频区 + 全屏飘落 2s。

## 六、核心交互流程设计

### 6.1 登录鉴权全流程

```
用户输入 → 前端生成 timestamp/nonce/sign(§10.4) 
  → POST /api/auth/login (X-Timestamp/X-Nonce/X-Sign/X-AppKey)
  → 200: 存 access(sessionStorage)+refresh(localStorage) + user store
  → 跳首页 (按 role 跳不同默认页)

后续请求:
  请求拦截器注入 Authorization: Bearer <access>
  响应 401 → auth.refresh() (并发合并) → 重发
  refresh 失败 → 清 storage → 跳 /login
```

### 6.2 直播间实时交互流程

```
进入 /live/:roomId
  → 校验 access token → 建 WS: ws://.../ws/live/{roomId}?token=<access>
  → onOpen: 启动 30s 心跳 PING; 订阅消息
  → 并行拉取: 活动详情 / 排行榜Top / 在线人数(首屏)

消息分发 (ws-client → live store → 组件):
  PONG         → 续心跳计时
  BARRAGE      → push 弹幕队列 (限量)
  GIFT         → 触发礼物特效 + 刷新排行榜
  ONLINE_COUNT → 更新顶栏数字 (数字滚动)
  SEC_KILL_RESULT → toast + 订单状态更新
  KICK         → 弹窗「同一账号在别处登录」→ 跳首页
  BAN          → 弹窗「账号已封禁」→ 跳登录
  ROOM_CLOSED  → 弹窗「主播已下播」→ 跳首页

断线:
  指数退避 1s→2s→4s...→30s, 重试 10 次
  重连成功后拉离线消息 (后端 offline:{userId} 已补发)
  连接状态徽标: 已连接(绿)/重连中(黄呼吸)/已断开(红)

发弹幕:
  输入 → 生成 messageId(uuid) → send BARRAGE {messageId, content}
  → 服务端去重+DFA过滤 → 广播回来自己也能看到
  → 防连发: 前端 500ms 节流

送礼:
  选礼物 → send GIFT {giftId, quantity}
  → 服务端加分(Dubbo→leaderboard) + 广播 GIFT
  → 自己端立即播特效(乐观更新), 收到广播后刷新榜
```

### 6.3 秒杀抢购全链路

```
活动未开始:
  倒计时本地跑 (基于 startTime 与服务器时间差)
  按钮显示「即将开始」+ 蓄力进度

到点:
  按钮变「立即抢购」橙红脉冲
  POST /api/seckill/order {activityId}
  → 按钮立即置 loading + 防重复点击 (500ms 锁)
  → 后端: 验签+JWT+限流+Lua扣库存+Kafka

结果路径 (双通道):
  1) HTTP 响应: 预确认 (抢到/售罄/重复)
  2) WS SEC_KILL_RESULT: 最终订单号 (异步落库后)

抢中:
  烟花特效 + toast「抢购成功」
  → 跳订单详情 (待支付, 15min 倒计时)
售罄: 按钮灰化「已售罄」
重复: toast「您已抢购过」
```

### 6.4 排行榜实时刷新

```
首屏: GET /leaderboard/top?activityId&top=100
轮询: 每 3s 拉一次 (兜底)
事件触发即时刷新: 收到 WS GIFT 后 300ms 防抖拉一次 TopN
个人排名: GET /leaderboard/rank/{userId}?activityId
历史: GET /leaderboard/history?activityId&time → 折线图
渲染: 顺位变化用 FLIP 动画, 头像光环 Top1/2/3 特殊样式
```

## 七、基础设施层设计

### 7.1 网络层 `infra/request.js`

- axios 实例，baseURL = `/api`
- 请求拦截器：注入 `Authorization`；登录/注册接口注入签名头。
- 响应拦截器：
  - 解析 `Result<T>`：`code===200` 返回 `data`；否则走错误码映射 `error-code.js`。
  - `401` → 调 `auth.refresh()` 并发合并 → 重发原请求。
  - `429` → toast「操作太频繁，请稍后」+ 按钮冷却。
  - 网络/超时 → 统一异常兜底页。
- 超时 10s，秒杀接口单独 15s。
- 取消重复请求（同一 url+method+params 在飞行中复用）。

### 7.2 鉴权 `infra/auth.js` + 签名 `infra/sign.js`

- `auth.js`：get/set/clear access & refresh；`refresh()` 用 Promise 锁合并并发；过期前 1min 主动刷新（可选）。
- `sign.js`：`genSignHeaders()` 生成 `X-Timestamp`(ms) / `X-Nonce`(uuid) / `X-Sign` = `HMAC-SHA256(timestamp+nonce+secret)`，用 `crypto-js`。Secret 由 AppKey 映射（见 §10.4）。

### 7.3 WebSocket 客户端 `infra/ws-client.js`

自研轻量客户端，职责：

| 能力 | 实现 |
|------|------|
| 建连 | `new WebSocket(url?token=)`；onOpen 启心跳 |
| 心跳 | 每 30s 发 `{type:'PING'}`；收 PONG 续命；60s 无 PONG 判定超时重连 |
| 重连 | 指数退避 1→2→4→8→16→30s，最多 10 次；重连成功重置 |
| 离线消息 | onOpen 后服务端自动补发 `offline:{userId}`（后端已实现） |
| 发送 | `send(type, data)` 自动包 messageId + timestamp + JSON |
| 分发 | 内部 EventEmitter，按 `type` 订阅；组件/store `ws.on('BARRAGE', fn)` |
| 状态 | `status` ref: connecting / open / reconnecting / closed，驱动顶栏徽标 |
| 销毁 | `destroy()` 关连接 + 清定时器 + 移除监听 |

单例：每个直播间页一个实例，离开页面 `destroy`。

### 7.4 状态管理（Pinia stores）

| store | 关键 state | 关键 action |
|-------|-----------|-------------|
| user | userInfo, role, access, refresh | login/register/logout/refresh/profile |
| live | roomId, online, status, barrage[], giftQueue[] | connect/sendBarrage/sendGift/onMessage |
| seckill | activities[], current, countdown, stockPct | fetchList/fetchDetail/placeOrder/applyResult |
| leaderboard | top[], myRank, history[] | fetchTop/fetchRank/fetchHistory/refreshOnGift |
| order | list[], detail, filter | fetchList/fetchDetail/cancel/refund |
| ui | theme, sidebarCollapsed, globalLoading | toggle* |

弹幕队列用环形缓冲（限量 50×3 轨道），避免无限增长。

|---------|---------|------|

### 10.2 鉴权三态

| 接口类型 | 鉴权 | 前端处理 |
|---------|------|---------|
| 登录/注册 | 签名（X-Timestamp/X-Nonce/X-Sign/X-AppKey） | sign.js 注入 |
| 业务接口 | JWT（Authorization: Bearer） | request.js 注入 |
| WebSocket | Query `?token=<access>` | ws-client.js 注入 |

### 10.3 WebSocket 消息协议映射

| 方向 | type | data | 前端处理 |
|------|------|------|---------|
| 上行 | PING | {} | 心跳 |
| 上行 | BARRAGE | {messageId, content} | 发弹幕 |
| 上行 | GIFT | {giftId, quantity} | 送礼 |
| 下行 | PONG | {} | 续心跳 |
| 下行 | BARRAGE | {userId, content, timestamp} | 入弹幕队列 |
| 下行 | GIFT | {userId, giftName, quantity} | 特效 + 刷榜 |
| 下行 | SEC_KILL_RESULT | {orderNo, success, msg} | toast + 订单 |
| 下行 | KICK | {reason} | 弹窗 + 跳首页 |
| 下行 | ONLINE_COUNT | {count} | 数字滚动 |
| 下行 | BAN | {} | 弹窗 + 跳登录 |
| 下行 | ROOM_CLOSED | (推断) | 弹窗 + 跳首页 |

> `ROOM_CLOSED` 未在 2.8 表中显式列出，但 2.4 §开播关播 提到关播广播 `type=ROOM_CLOSED`，前端按此处理，需与后端确认 type 字符串。

### 10.4 浏览器端签名安全困境与对策

**问题**：后端 `SignVerifyGlobalFilter` 要求 `X-Sign = HMAC-SHA256(timestamp+nonce+secret)`，secret 由 AppKey 映射。浏览器是公开客户端，secret 一旦打包进前端 JS 就会暴露，任何人可伪造签名。

**对策（分场景）**：

| 方案 | 适用 | 说明 |
|------|------|------|
| Demo 内置 AppKey/Secret（本项目） | 面试/演示 | 前端内置一对 demo key，网关白名单仅放行 `/auth/login` `/auth/register`；演示用，文档显式标注「不用于生产」|
| BFF 中间层 | 生产 | 前端不签名，由轻量 BFF（Node）持有 secret 代签；前端只跟 BFF 通信 |
| 网关豁免浏览器来源 | 生产可选 | 浏览器请求走单独域名，网关对该来源跳过签名、仅 JWT；签名仅留给移动端/第三方 |

**本项目采用 Demo 方案**：在 `.env` 配 `VITE_APP_KEY=demo-web`、`VITE_APP_SECRET=<demo>`，登录/注册带签名；其余接口走 JWT。文档与大屏均标注此为演示用配置。

### 10.5 CORS 与跨域

后端 `CorsWebFilter` 已允许 `http://localhost:8080`。前端 dev server 端口需固定为 8080，或后端 `addAllowedOrigin` 增加前端 dev 端口。建议：前端 dev 走 8080，或用 Vite 代理避免 CORS（推荐，§2.4 已走 `/api` 代理）。

### 10.6 错误码映射（摘要，源见后端 2.1）

| code | 含义 | 前端表现 |
|------|------|---------|
| 200 | 成功 | 正常 |
| 400 | 参数错误 | 表单项红字 |
| 401 | 未登录/过期 | 触发刷新或跳登录 |
| 403 | 无权限 | toast + 跳 403 |
| 429 | 限流 | toast「太频繁」+ 按钮冷却 |
| 1001 | 库存不足 | 按钮售罄 |
| 1011 | 用户名或密码错误 | 表单提示 |
| 1012 | 用户名已注册 | 表单提示 |
| 1013 | 登录已过期 | 触发刷新 |
| 1014 | 手机号已使用 | 表单提示 |
