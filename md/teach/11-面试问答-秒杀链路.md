# 11 — 面试问答：秒杀链路

> 按面试官提问方向组织的秒杀专题。树形结构，逐层深入。

---

## 秒杀链路
│
├── 一、缓存
│   ├── 1.1 穿透
│   │   ├── Q: 如果用户传一个不存在的 activityId 会怎么样
│   │   │   -> Caffeine.get() 返回 null，不缓存，抛 404
│   │   │   -> 每次都查 DB？Caffeine 不缓存 null，确实每次都穿透
│   │   │   -> 但秒杀场景 activityId 是后端生成的合法 ID，攻击成本高
│   │   ├── Q: 怎么防穿透
│   │   │   -> 布隆过滤器：活动上线时 bloom add，请求时 bloom check，不存在直接返回
│   │   │   -> 空值缓存：null 也缓存 5s，但占用内存
│   │   │   -> 项目没做，因为风险低收益小
│   │   └──
│   ├── 1.2 击穿
│   │   ├── Q: 热点 key 过期时大量请求同时打到 DB 怎么办
│   │   │   -> Caffeine.get(key, loader) 自带 single-flight
│   │   │   -> 同一时刻只有一个线程去加载，其他线程等结果
│   │   │   -> 天然防击穿
│   │   └──
│   ├── 1.3 雪崩
│   │   ├── Q: 大量 key 同时过期怎么办
│   │   │   -> 项目只有少量 activity key，不存在批量过期
│   │   │   -> 真要防：TTL 加随机偏移，或错开过期时间
│   │   └──
│   ├── 1.4 预热
│   │   ├── Q: 缓存什么时候加载的
│   │   │   -> 不是启动时全部加载
│   │   │   -> 上架时 cacheService.refresh() 清空旧缓存
│   │   │   -> 第一个用户请求触发 Caffeine 回填（5s TTL）
│   │   └──
│   └──
│
├── 二、Redis 库存扣减
│   ├── 2.1 Lua 原子性
│   │   ├── Q: Redis Lua 为什么能保证不超卖
│   │   │   -> Redis 单线程串行执行整个脚本
│   │   │   -> DECR 扣库存 → SETEX 写防重标记：中间不被其他命令插入
│   │   │   -> 不需要事务，不需要锁
│   │   └── Q: 如果 DECR 到负数怎么办
│   │   │   -> 项目刚修了：DECR < 0 时 INCR 回补
│   │   │   -> 不改的话库存永久损失 1
│   │   └──
│   ├── 2.2 库存分片
│   │   ├── Q: 为什么分片，不分行不行
│   │   │   -> 单 key DECR 上限 8w QPS
│   │   │   -> 4 片 hash 散列 = 理论 32w QPS
│   │   └── Q: 为什么 userId % shardCount 而不是遍历
│   │   │   -> 直接定位分片，一次 DECR 搞定
│   │   │   -> 遍历需要多次 DECR，不可控
│   │   └── Q: 分片数怎么确定的
│   │       -> 4 片是经验值，太少热点集中，太多碎片浪费
│   │       -> 10w QPS / 8w 单分片 ≈ 2 片，留余量取 4
│   │   └── Q: 分片 key 不在 KEYS 参数里，Cluster 下会报错吗
│   │       -> 会。stock:shard 在 Lua 运行时才拼出来
│   │       -> cluster 模式报 CROSSSLOT
│   │       -> 解决方案：用 hash tag 对齐 slot，或不用 cluster
│   │   └──
│   ├── 2.3 防重
│   │   ├── Q: 一人一单怎么保证
│   │   │   -> 三层防护
│   │   │   ├── Lua 内 GET ordered:{actId}:{userId} → 已存在返回 -1
│   │   │   ├── DB uk_activity_user 唯一索引 → DuplicateKeyException
│   │   │   └── Kafka 消费幂等 → catch 后直接 ACK
│   │   └── Q: Redis 防重 key 丢了怎么办
│   │       -> 还有 DB 唯一索引兜底，不会产生重复订单
│   │   └──
│   ├── 2.4 Redis 挂了
│   │   ├── Q: 库存 Redis 节点宕机了
│   │   │   -> Sentinel 降级限流 100→10 QPS
│   │   │   -> Caffeine 本地缓存还能挡一阵
│   │   │   -> 直查 MySQL 库存，能力降到 1/100
│   │   └──
│   └──
│
├── 三、异步下单
│   ├── 3.1 Kafka 削峰
│   │   ├── Q: 为什么扣完库存不直接 INSERT DB
│   │   │   -> 10w 并发 INSERT 会打崩 MySQL 连接池
│   │   │   -> Lua 扣完库存回 200，Kafka 异步写
│   │   │   -> Kafka 充当缓冲区，瞬时写入 10w+ 无压力
│   │   └──
│   └── 3.2 降级兜底
│       ├── Q: Kafka 挂了怎么办
│       │   ├── 正常降级：同步调用 createOrder INSERT DB
│       │   ├── DB 也挂了：stockService.refund() 回补库存
│       │   └── cacheService.markInStock() 清本地售罄标记
│       └── Q: 降级路径查 DB 还是查缓存
│           -> 已改：getActivityCached() 走 Caffeine，不穿透 DB
│       └──
│
├── 四、数据一致性
│   ├── 4.1 订单状态机
│   │   ├── Q: 订单状态怎么流转
│   │   │   -> 0:PENDING → 1:PAID / 2:CANCELLED / 3:REFUNDED
│   │   │   -> @Version 乐观锁 CAS 防止并发更新
│   │   └──
│   ├── 4.2 超时取消
│   │   ├── Q: 超时取消怎么实现的
│   │   │   -> @Scheduled 每 15s 扫描 PENDING 超过 15min 的订单
│   │   │   -> CAS UPDATE status=CANCELLED WHERE version=?
│   │   │   -> 成功后才 Redis INCR 回补库存
│   │   └── Q: 超时取消和用户同时取消冲突怎么办
│   │       -> 乐观锁：version 不匹配则 UPDATE 影响行数为 0
│   │       -> 谁先 UPDATE 成功谁生效，另一个失败
│   │   └──
│   ├── 4.3 取消订单
│   │   ├── Q: cancelOrder 哪个先执行，Redis 还是 DB
│   │   │   -> 项目当前 Redis 先于 DB（有 bug）
│   │   │   -> DB save 失败时 Redis 已 refund，事务回滚不了
│   │   │   -> 正确顺序：DB 先改状态 → Redis 后回补
│   │   └──
│   └──
│
├── 五、MySQL & 连接池
│   ├── Q: 连接池配多大
│   │   -> maximum-pool-size=30
│   │   -> 基于核数*2+磁盘数经验，秒杀路径根本不走 DB
│   └── Q: 30 连接够用吗
│       -> 抢购只走 Caffeine + Redis
│       -> 只有最终 INSERT 订单用 DB（Kafka 异步写）
│       -> 30 连接绰绰有余
│   └──
│
└── 六、场景故障题
    ├── Q: 秒杀开始一瞬间流量打崩怎么办
    │   ├── 网关：Sentinel 热点限流每用户 100 QPS
    │   ├── 本地缓存：Caffeine 售罄标记挡住 90% 无效请求
    │   ├── Redis Lua：4 分片 DECR 散列热点
    │   ├── Kafka：异步削峰，不直接写 DB
    │   └── DB：唯一索引 uk_activity_user 兜底
    └── Q: 用户秒杀成功但没看到订单怎么排查
        ├── Gateway 日志 → SeckillController 日志 → Lua 返回值
        ├── Kafka Producer 有没有发出消息
        ├── Consumer 有没有消费 + 有没有 INSERT 成功
        └── 大概率 Kafka 消费异常或 DB 唯一索引冲突
