## 版本 A：精简版（适合海投，~120 字）

**LiveMall — 高并发直播电商秒杀系统** | 全栈独立开发

- 基于 **Java 21 虚拟线程 + Spring Boot 3 + Dubbo + Kafka + Redis** 构建 5 个微服务，目标 **10w QPS**
- 设计**双 Token 认证**（Access JWT + Refresh Redis），99% 请求零 IO 验签，性能优于 Session 方案约 **900 倍**
- 秒杀核心链路：**Redis Lua 原子扣库存**（4 分片 DECR，上限 32w QPS）+ **Kafka 异步削峰**下单 + **Caffeine 多级缓存**过滤无效请求
- **WebSocket 长连接**实时推送弹幕/秒杀结果/送礼特效，支持**匿名观看与按需登录升级**，指数退避断线重连
- 网关层 **Sentinel 热点参数限流** + **HMAC-SHA256 签名验签**防重放，统一异常处理与幂等设计

## 版本 B：标准版（适合主投，~200 字）

**LiveMall — 高并发直播电商秒杀系统** | 2024.xx — 至今

> 技术栈：Java 21 (Virtual Threads) · Spring Boot 3.2 · Spring Cloud Gateway (WebFlux) · Dubbo 3.3 · Kafka 3.6 · Redis · MySQL 8.x · Vue 3 + Vite

- **架构设计**：5 个微服务（用户/秒杀/WebSocket/排行榜/网关），Dubbo RPC 服务间通信，Nacos 注册中心，Docker Compose 一键部署中间件
- **秒杀链路**（目标 10w QPS）：Gateway Sentinel 热点限流 → **Redis Lua 原子扣库存**（`userId % 4` 分片 DECR，单分片 8w QPS）→ Kafka 异步下单 → 虚拟线程消费写入 MySQL → WebSocket 实时推送结果
- **双 Token 认证**：Access Token（JWT HS256，15min）无状态验签 + Refresh Token（Redis，7d）可撤销。前端并发刷新请求合并（全局 Promise），性能较 Session 方案 IO 减少约 900 倍
- **WebSocket 长连接**：`@ServerEndpoint` + 虚拟线程，支持匿名连接与 AUTH 消息按需升级。心跳保活（30s PING / 60s 超时）、跨节点 Dubbo 路由转发、断线指数退避重连（1s→30s）与离线消息补发
- **多级缓存**：Caffeine（refreshAfterWrite 1s）+ Redis + MySQL 三级，防穿透/击穿/雪崩。排行榜 ZSet 跳表 O(log N) 实时排序 + 5min 定时快照存 MySQL
- **安全与降级**：接口签名验签（HMAC-SHA256 + Timestamp + Nonce 防重放）、DFA 敏感词过滤（Trie 树 + AtomicReference 热更新词库）、Snowflake 分布式 ID（时钟回拨 ≤100ms 自旋等待）。Redis/Kafka/MySQL 均有分层降级方案

## 版本 C：详细版（适合简历项目单独一页，~350 字）

**LiveMall — 高并发直播电商秒杀系统** | 2024.xx — 至今 | 全栈独立开发

> 技术栈：Java 21 (Virtual Threads) · Spring Boot 3.2 · Spring Cloud Gateway (WebFlux) · Dubbo 3.3 (Hessian2) · Kafka 3.6 (KRaft) · Redis (Lettuce + Lua) · MySQL 8.x (MyBatis-Plus) · Sentinel 1.8 · Nacos · Zipkin · Vue 3 (Pinia + Axios + WebSocket) · Docker Compose

**项目背景**：面向秋招展示高并发系统设计能力，模拟直播间秒杀抢购场景，覆盖用户认证、直播弹幕互动、秒杀下单、实时排行榜等完整业务链路。

**核心工作：**

**1. 架构与微服务拆分**
- 5 个微服务（Gateway/User/Seckill/WebSocket/Leaderboard）按业务边界拆分，每个模块有独立技术纵深
- Gateway 用 WebFlux 响应式处理路由/鉴权/限流，业务服务用 MVC + Virtual Threads 应对有状态业务
- 服务间 Dubbo RPC 通信（TCP 长连接 + Hessian2 序列化），Nacos 注册中心 + 配置中心

**2. 秒杀核心链路（10w QPS 目标）**
- Gateway 层 **Sentinel 热点参数限流**（按 userId+activityId 分别限 100 QPS）+ JWT 鉴权 + HMAC-SHA256 签名验签
- **Caffeine 本地缓存**（refreshAfterWrite 1s）存储"有无库存"标记，过滤约 90% 无库存请求
- **Redis Lua 脚本**原子扣减库存：先 EXISTS 查重复 → DECR 库存分片（`userId%4` 哈希路由，4 片共 32w QPS 上限）→ 负数 INCR 回补 → SETEX 防重标记
- **Kafka 异步削峰**：Lua 扣减成功后发消息即返回响应，Consumer 端虚拟线程消费写入 MySQL，事务内手动提交 Offset 保障不丢消息
- **订单状态机**：PENDING→PAID→REFUNDED / CANCELLED，超时取消用 @Scheduled 15s 扫描 + 乐观锁 CAS（version 字段）+ Redis Lua 回补库存

**3. 双 Token 认证与安全**
- Access Token（JWT HS256，15min）无状态验签，Refresh Token（UUID，存 Redis，7d）可撤销可踢人
- 前端并发刷新合并（单 Promise 全局共享），性能对比 Session 方案 IO 减少约 900 倍
- 用户上下文用 **ScopedValue** 替代 ThreadLocal（VT 池化下自动清理、零内存残留）
- 接口签名防篡改/防重放（timestamp±5min + Nonce Redis SETNX + HMAC-SHA256），DFA Trie 树敏感词过滤热更新

**4. WebSocket 实时通信**
- `@ServerEndpoint` + 虚拟线程（每连接一个 VT），支持**匿名连接与运行时 AUTH 消息升级**
- 心跳保活（客户端 30s PING / 服务端 60s 超时断开）、跨节点 Dubbo 路由转发、断线指数退避重连（1s-30s，最多 10 次）+ Redis List 离线消息补发
- 弹幕广播 + DFA 过滤 + 消息幂等去重（Redis SETNX messageId），送礼联动排行榜实时加分

**5. 排行榜与缓存策略**
- Redis **ZSet 跳表** O(log N) 实时 TopN + 个人排名，@Scheduled 每 5min 快照存 MySQL 支持历史查询
- Caffeine + Redis + MySQL 三级缓存，防穿透（布隆过滤器+缓存空值）、防击穿（refreshAfterWrite 异步刷新）、防雪崩（TTL 随机化）
- 缓存一致性：库存走 Redis Lua 实时精确，订单状态走 Kafka 最终一致

**6. 工程化与故障降级**
- 自研 **Snowflake 分布式 ID**（时钟回拨 ≤100ms 自旋等待且不持锁，ReentrantLock 替代 synchronized）
- 全局异常处理 `@RestControllerAdvice`、幂等性（Redis SETNX + 唯一索引兜底）
- 分层降级方案：Redis 挂 → Sentinel 收紧限流 + Caffeine 顶 + MySQL 兜底 + 熔断；Kafka 挂 → 切同步下单；MySQL 挂 → 读写分离 + Redis 草稿暂存

- ❌ "LiveMall 商城项目" → 太普通
- ✅ "LiveMall — 高并发直播电商秒杀系统" → 关键词全在：高并发、直播、电商、秒杀

- ❌ `Java、Spring Boot、Redis、MySQL` → 太笼统
- ✅ `Java 21 (Virtual Threads) · Dubbo 3.3 · Kafka 3.6 · Redis Lua` → 版本号 + 亮点技术

### 怎么加数字
技术简历第一原则：**能用数字就用数字，不能用数字就用对比**。

| 抽象描述 | 量化描述 |
|---------|---------|
| 性能提升很大 | IO 减少约 **900 倍** |
| 支持高并发 | 目标 **10w QPS** |
| 库存分片 | **4 片** DECR，单分片 **8w QPS** |
| 缓存很快 | Caffeine **纳秒级**，refreshAfterWrite **1s** |
| 心跳保活 | **30s** PING，**60s** 超时 |
| Token 有效期 | Access **15min**，Refresh **7d** |
| 异步下单 | Kafka 消费侧 **虚拟线程**（10w 连接 ~1GB 内存） |

### 对比：网上"秒杀系统"典型写法 vs 我们的写法

**网上常见写法（二流）：**
> "使用 Redis + Lua 脚本实现秒杀资格预检，解决超卖问题；基于 RocketMQ 实现异步下单削峰填谷；引入 Redisson 分布式锁保证一人一单。"

**我们的写法（当前）：**
> "Redis Lua 原子扣库存（4 分片 DECR，上限 32w QPS）+ Kafka 异步削峰下单 + Caffeine 多级缓存过滤约 90% 无效请求"

**升级版（一流方向）：**
> "为解决高并发下库存超卖，对比 MySQL 行锁 / 乐观锁 / Redis Lua 三种方案后选择 Lua 脚本——单线程原子执行，性能远优于 DB 锁。进一步通过 `userId % 4` 分片将单 key 瓶颈从 8w 提升至 32w QPS。经 JMeter 压测，单机 5000 并发下 QPS 达 4200+，超卖率 0%。"

## 升级版：STAR 法则重构

> 按照网上大厂面试官推荐的结构，用"情境→任务→行动→结果"重写每条 bullet。

### 秒杀链路（升级版）

```
【难点】10w 用户同时抢购 1000 件商品，存在库存超卖、热点 key 瓶颈、数据库写入压力三重挑战

【方案对比】
• 库存扣减：MySQL 行锁 → 性能差（< 1000 QPS）→ 乐观锁 → 冲突率高 → ✅ Redis Lua
• 削峰策略：同步写 DB → 响应慢 → ✅ Kafka 异步下单，扣库存成功后立即返回
• 库存分片：单 key 8w QPS 瓶颈 → ✅ userId % 4 哈希分片，理论上限 32w QPS

【落地成果】
• Redis Lua 原子扣减（EXISTS 防重 → DECR 扣库存 → <0 回补 → SETEX 防重标记）
• Caffeine 本地缓存"有无库存"标记（refreshAfterWrite 1s），过滤约 90% 无效请求
• Kafka 异步下单 + VT 消费写入 MySQL，事务内手动提交 Offset
• 订单状态机 PENDING→PAID→REFUNDED/CANCELLED，超时取消 @Scheduled + 乐观锁 CAS
• 一人一单：Redis 防重 key + DB 唯一索引 uk_activity_user 双保险
```

### 双 Token 认证（升级版）

```
【难点】Session 方案 10w QPS = 10w 次 Redis IO，与秒杀 Lua 抢同一事件循环

【方案对比】
• Session：每次查 Redis → 10w IO/s
• 纯 JWT：无状态快但泄露后不可撤销
• ✅ 双 Token：Access JWT（15min，无状态验签）+ Refresh Redis（7d，可撤销）

【落地成果】
• 99% 请求仅 JWT 验签（纯 CPU，零 IO），约 111 次/s 刷新才查 Redis，IO 减少约 900 倍
• 前端并发刷新合并（全局 Promise），多请求同时 401 只发一次 Refresh
• ScopedValue 替代 ThreadLocal 传递用户上下文（VT 池化下自动清理，零内存残留）
• 设备管理：Redis Set 存储在线设备，支持查看/踢下线，WS 推送 BAN 消息
```

### 技术选型的"为什么"速查（面试防追问）

> 这是简历上每个技术点背后必须准备好的"对比故事"。

| 简历写到的 | 面试官会问 | 你要回答的对比 |
|-----------|-----------|-------------|
| Dubbo RPC | 为什么不用 Feign？ | Dubbo TCP 长连接 + Hessian2 二进制 vs Feign HTTP/JSON；面试纵深更深（SPI/自适应/5 种 LB） |
| Kafka | 为什么不用 RocketMQ？ | Kafka 零拷贝吞吐最高 + 面试高频；RocketMQ 有延时消息但部署更重 |
| Redis Lua | 为什么不用分布式锁？ | Lua 单线程原子执行，零锁开销；分布式锁有加锁/解锁/续期开销，适合复杂业务 |
| ScopedValue | 和 ThreadLocal 区别？ | TL 在 VT 池化下有内存泄漏；SV 作用域结束自动清理，不可变线程安全 |
| Sentinel | 和令牌桶的区别？ | Sentinel 滑动窗口精度更高，支持热点参数限流（按 userId 分别限） |
| Caffeine | 和 Redis 缓存什么关系？ | Caffeine L1 本地纳秒级过滤无效请求，Redis L2 精确扣库存，MySQL L3 兜底 |
| Snowflake | 为什么不用 UUID？ | Snowflake 时间戳高位天然有序，B+Tree 顺序插入；UUID 无序导致页分裂 |

## 网上搜到的一条"满分简历"长什么样

> 以下是从多个大厂面试官分享中提炼的**理想简历项目描述结构**：

```
项目名称：XXX系统 | 核心开发者 | 2024.10 – 2024.12

【业务背景】一句话说清楚解决什么问题、面向什么用户、多大量级
【技术选型与决策】每种关键技术的对比与选择理由（至少 2 组对比）
【核心难点突破】2-3 个最有深度的技术难点 + 解决方案 + 演进过程
【量化成果】QPS / 响应时间 / 成功率 / 可用性的具体数字
```

**关键原则：**
1. **每一条都能被追问** — 如果某条描述写出来你自己都解释不了 → 删掉
2. **问题驱动不要功能驱动** — 不是"我做了 X"，是"遇到 Y 问题，对比了 A/B/C 方案，选了 C 因为…"
3. **压测报告是硬通货** — 截一张 JMeter 压测结果图放 GitHub README + 简历上放二维码，可信度碾压 90% 的候选人
