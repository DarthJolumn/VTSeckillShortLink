# 04 — 秒杀链路详解

> **目标：** 这是面试必问的核心链路。从网关到数据库，每一层都清楚为什么、怎么做、有什么坑。

---

## 全链路一览（面试时画这个）

```
用户点击抢购
    │
    ▼
① Gateway: Sentinel 热点限流（每用户 100 QPS）
    │   ↓ 超过限制 → 429 Too Many Requests
    ▼
② Gateway: JWT 鉴权（验签提取 userId）
    │   ↓ Token 无效 → 401
    ▼
③ Gateway: 签名验签（timestamp + nonce + HMAC-SHA256）
    │   ↓ 签名不匹配 → 401
    ▼
④ SeckillController: 活动状态校验
    │   ├─ Caffeine 本地缓存（1s 刷新）
    │   └─ Redis 兜底校验
    │   ↓ 活动未开始/已结束 → 返回错误
    ▼
⑤ Redis Lua 原子扣库存
    │   ├─ EXISTS ordered:{activityId}:{userId} → 重复下单？
    │   ├─ DECR stock:shard:{activityId}:{userId%4}
    │   └─ SETEX ordered key（24h TTL）
    │   ↓ remain < 0 → INCR 回补 → 库存不足
    │   ↓ 重复下单 → 返回 -1
    ▼
⑥ 返回预确认给用户："抢购成功，订单处理中"
    │
    ▼
⑦ Kafka 异步下单（Producer）
    │
    ▼
⑧ SeckillOrderConsumer（VT 消费）
    ├─ INSERT t_seckill_order（PENDING 状态）
    └─ Dubbo → WebSocket 推送结果给用户
    │
    ▼
⑨ 超时取消（@Scheduled 每 15s）
    ├─ 扫描 status=PENDING 且 created_at < now-15min
    ├─ CAS UPDATE SET status=CANCELLED WHERE version=?
    └─ Redis Lua INCR 回补库存
```

## 逐层详解

### ① Gateway Sentinel 限流

**为什么在网关层限流：** 恶意请求根本进不了内网，保护下游服务。

**为什么用热点参数限流：** 普通 QPS 限流对所有用户一视同仁，热点参数可以**按 userId 分别限流**。

```
规则：resource=seckill:create, paramIdx=0, count=100
效果：每用户每活动 100 QPS。正常用户 100 QPS 够用，脚本刷子被限。
```

**Sentinel 嵌入模式 vs Dashboard 模式：**
- 当前用嵌入模式（规则写死在启动配置），各实例独立计数
- 面试时要说：生产环境用 Dashboard 动态调参 + 全局限流

### ② JWT 鉴权

**鉴权链路：**
```
Gateway JwtAuthGlobalFilter:
  1. 路径匹配：/auth/login, /auth/register → 公开，跳过
  2. GET 公开路径：/seckill/activity/** → 浏览不需要登录
  3. 签名通过 → 跳过（签名本身就是更强的认证）
  4. 其他 → 验证 Authorization: Bearer <token>
  5. 验签通过 → userId, role 写入 exchange.getAttributes()
  6. 转发前 → 注入 Header X-User-Id, X-User-Role
```

**性能：** HMAC-SHA256 纯 CPU 运算，1 核可验 5w+ TPS，不是瓶颈。

### ③ 接口签名验签

```
算法: HMAC-SHA256(method + uri + timestamp + nonce + body, secretKey)

验签步骤：
  1. 检查 timestamp 是否在 ±5min 内（防重放）
  2. Nonce 是否已使用 → Redis SETNX nonce:{nonce}（防重放，60s TTL）
  3. 用相同参数重新计算 sign，比对

Redis 挂了怎么办：降级 → 跳过 Nonce 检查，只验 timestamp + sign。
  幂等设计兜底（下单有 Redis 防重 key）。
```

### ④ 活动状态校验

**多级缓存策略：**
```
L1: Caffeine 本地缓存（1s refreshAfterWrite）
  - 存 "活动状态 + 是否有库存"
  - 无库存请求直接返回售罄 → 过滤 90% 请求
  - 1s 后异步刷新 → 短暂不一致（最多 1s），但最终安全

L2: Redis 查活动状态（毫秒级）
L3: MySQL 兜底
```

### ⑤ Redis Lua 原子扣库存（★ 核心）

**为什么用 Lua：**
```
Redis 单线程执行 Lua 脚本，整个脚本执行期间不会被其他命令插入。
MULTI/EXEC 事务不支持条件判断（不能 "如果 stock≥0 则..."），
Lua 可以。
```

**Lua 脚本源码（`seckill_deduct.lua`）：**
```lua
-- KEYS[1] = ordered:{activityId}:{userId}    防重 key
-- KEYS[2] = stock:shard:{activityId}:{shard} 库存分片
-- ARGV[1] = ordered TTL（秒）

-- 1. 防重预判
if redis.call('EXISTS', KEYS[1]) == 1 then
    return -1  -- 重复下单
end

-- 2. 库存扣减
local remain = redis.call('DECR', KEYS[2])
if remain < 0 then
    redis.call('INCR', KEYS[2])  -- 回补
    return -2  -- 库存不足
end

-- 3. 设置防重 key
redis.call('SETEX', KEYS[1], ARGV[1], '1')
return 200  -- 成功
```

**关键设计点：**

1. **DECR 原子性**：单 key DECR 是原子的，不需要额外加锁
2. **负数回补**：`remain < 0` 时 `INCR` 回补，确保不超卖
3. **防重 key 的设计**：`SETEX ordered:{activityId}:{userId} 86400 1`
   - 24h TTL：活动期间不允许重复下单
   - 和 DB 唯一索引 `uk_activity_user` 形成双保险
4. **为什么先 EXISTS 再 DECR**：先快速过滤重复下单（O(1) EXISTS），避免无效 DECR

**库存分片计算逻辑：**
```java
// 分片数计算
int shard = userId % shardCount;  // 0, 1, 2, 3
String stockKey = "stock:shard:" + activityId + ":" + shard;

// 为什么是 % 而不是遍历：
// 遍历 4 个分片需要 4 次 DECR（最坏情况）
// 哈希路由只需 1 次 DECR
```

**分片数为什么是 4：**
```
单 key DECR 上限 ~8w QPS（Redis 单线程 benchmark）
4 片 × 8w = 32w QPS，覆盖 10w 目标有余量
8 片 × 8w = 64w QPS，但库存碎片化严重

过度分片的代价：
  - 某分片卖完但总分片还有库存 → 需要回收碎片库存
  - key 管理成本和内存碎片增加
```

**一人一单怎么保证：**
```
1. Redis 预判：ordered:{activityId}:{userId} SETNX → 重复时直接拒绝
2. DB 唯一索引：uk_activity_user (activity_id, user_id) → 兜底
3. 极端情况：Redis 挂了，DB 唯一索引是最后防线
```

### ⑥ 返回预确认

**为什么不等 Kafka 消费完就返回：**
```
用户只需要知道"抢到了"还是"没抢到"。
订单创建是异步的，不影响用户体验。

如果等 Kafka → DB → 返回，延迟会增加 50-200ms，
  用户体验差，而且需要同步等待 Kafka。
```

### ⑦⑧ Kafka 异步下单

**Producer 侧：**
```java
// Redis Lua 扣成功后
kafkaTemplate.send("seckill-order", orderMessage);
// 立即返回结果给用户
return Result.ok("抢购成功，订单处理中");
```

**Consumer 侧：**
```java
@KafkaListener(topics = "seckill-order")
public void onOrder(OrderMessage msg) {
    Thread.startVirtualThread(() -> {
        // VT 执行，不阻塞 Kafka 消费线程池
        doCreateOrder(msg);
    });
}

@Transactional
void doCreateOrder(OrderMessage msg) {
    // INSERT INTO t_seckill_order ...
    // Dubbo WsPushService.push(userId, result)
}
```

**为什么 VT 执行：** Kafka 消费者线程池有限，如果每条消息都用消费者线程处理，慢消息会阻塞后续消费。VT 委托后消费者线程快速返回，继续拉取下一条。

### ⑨ 超时取消

```java
@Scheduled(fixedDelay = 15000) // 每 15s
public void cancelTimeoutOrders() {
    List<Order> timeoutOrders = orderRepo.findByStatusAndCreatedBefore(
        PENDING, now.minusMinutes(15));

    for (Order order : timeoutOrders) {
        // CAS 乐观锁
        int updated = orderRepo.updateStatus(
            order.getOrderNo(), order.getVersion(),
            PENDING, CANCELLED);
        if (updated > 0) {
            // Redis Lua 回补库存
            restock(order);
        }
    }
}
```

**为什么用乐观锁 CAS：** 防止超时取消和用户主动取消并发冲突。

## 面试必答题

### Q: 为什么 Lua 是原子的？
```
Redis 单线程执行命令。Lua 脚本作为一个整体提交给 Redis，执行期间不会被其他
客户端的命令插入。相当于天然的事务隔离。

和 MULTI/EXEC 的区别：MULTI/EXEC 不支持条件判断（不能 "if GET key == 1"），
Lua 可以。
```

### Q: 怎么保证不超卖？
```
三层防护：
1. DECR 原子操作：返回值 ≥0 才成功，<0 回补
2. 防重 key：同一用户同一活动只允许一次扣减
3. DB 唯一索引 uk_activity_user：兜底
```

### Q: Redis 挂了怎么办？
```
降级链路（面试官要的就是这个）：
1. Sentinel 降级：限流阈值从 100 降到 10 QPS
2. Caffeine 本地缓存还能挡一阵
3. 库存直接查 MySQL，用 SELECT FOR UPDATE 锁行扣减
4. 如果 DB 也扛不住 → 熔断返回"活动太火爆"
```

### Q: DECR 返回负数怎么办？
```
不会到业务层。Lua 脚本里 remain < 0 时立即 INCR 回补，然后返回 -2。
业务层收到 -2 就是"库存不足"，底层已经纠正了。
```

### Q: 库存分片后某片卖完但总库存还有怎么办？
```
这就是库存碎片化。当前 4 片暂不处理碎片回收（复杂度太高）。
面试时承认这一点并表示：
- 4 片下碎片化概率低
- 如需要，可用定时任务扫描碎片库存并回收
- 电商真实场景中，库存碎片化是行业难题，有专门的重分配策略
```
