# 13 — 分布式秒杀服务设计文档

> `livemall-seckill` 模块从单节点升级为 Redis Cluster 分布式架构的设计文档。

## 一、设计目标

| 维度 | 单节点版 (livemall-seckill-single) | 分布式版 (livemall-seckill) |
|------|-----------------------------------|----------------------------|
| Redis | 单实例，4 分片热点分散 | 3 主 3 从 Cluster，Hash Tag 聚合同 Slot |
| 扩展性 | 单机上限 ~8w QPS | 水平扩展，理论无上限 |
| 高可用 | 无故障转移 | Cluster 内置 failover <10s |
| 持久化 | 开发阶段关闭 | 全内存运行（dev） |

## 四、Key 设计与 Hash Tag

### 4.1 核心原则

**所有写链路 Key 必须统一使用 `{itemId}` 前缀**，确保 Lua 原子操作不报 CROSSSLOT。

| Key 类型 | 格式 | Hash Tag | 说明 |
|----------|------|----------|------|
| 库存 | `stock:{itemId}` | `{itemId}` | 单 key，集群自动分布 |
| 防重 | `ordered:{itemId}:{userId}` | `{itemId}` | 与 stock 同 Slot |
| 售罄标记 | `soldOut:{itemId}` | `{itemId}` | 售罄状态 |
| 活动缓存 | `activity:{itemId}` | `{itemId}` | 活动信息 |

> **注**：`itemId` 在本项目中即 `activityId`（秒杀活动 ID）。

### 4.2 为什么用 Hash Tag

```
stock:{123}        → CRC16("123") % 16384 = Slot A
ordered:{123}:42   → CRC16("123") % 16384 = Slot A  ← 同 Slot

Lua 脚本操作两个 key，都在 Slot A → 不报 CROSSSLOT ✓
```

### 4.3 读写分离策略

| 操作 | 路径 | 说明 |
|------|------|------|
| 写（扣库存） | Master | Lua 脚本保证原子性 |
| 读（活动信息） | Caffeine L1 → Master | 禁用 Slave 高频读 |

## 五、Lua 脚本（集群兼容版）

### 5.1 扣库存 `deduct_stock.lua`

> **🔴 关键**：Redis Cluster 模式下，**所有 Key 必须通过 KEYS 数组传入**，脚本内拼接的 key 会被视为非法访问，报 MOVED 错误。

```lua
-- 🔴 正确写法：所有 key 从 KEYS 数组传入
-- KEYS[1] = stock:{itemId}
-- KEYS[2] = ordered:{itemId}:{userId}
-- ARGV[1] = userId (仅用于日志，非必需)
-- 返回: 200=成功, -1=重复, -2=售罄, -3=活动未初始化

-- 前置检查：库存 key 不存在说明活动未上架
if redis.call("EXISTS", KEYS[1]) == 0 then
    return -3
end

local ordered = redis.call("GET", KEYS[2])
if ordered then return -1 end

local stock = redis.call("DECR", KEYS[1])
if stock >= 0 then
    redis.call("SETEX", KEYS[2], 86400, "1")
    return 200
end
redis.call("INCR", KEYS[1])   -- 回补，避免永久扣减
return -2
```

```java
// Java 调用端
public int deduct(Long activityId, Long userId) {
    String stockKey = "stock:{" + activityId + "}";
    String orderedKey = "ordered:{" + activityId + "}:" + userId;
    Long result = redisTemplate.execute(deductScript, List.of(stockKey, orderedKey),
            userId.toString());
    return result != null ? result.intValue() : -2;
}
```

### 5.2 回补库存 `refund_stock.lua`

```lua
-- KEYS[1] = stock:{itemId}
-- KEYS[2] = ordered:{itemId}:{userId}

if redis.call("EXISTS", KEYS[2]) == 1 then
    redis.call("INCR", KEYS[1])
    redis.call("DEL", KEYS[2])
end
return 1
```

### 5.3 关键变更（vs 单节点版）

| 项目 | 单节点版 | 集群版 |
|------|----------|--------|
| 库存 key | `stock:shard:{itemId}:{shard}` | `stock:{itemId}` |
| Key 传参 | 脚本内拼接 stockKey | **全部通过 KEYS 数组传入** |
| 分片逻辑 | `userId % 4` 客户端分片 | 无分片，单 key |
| Hash Tag | 无 | `{itemId}` 统一 Slot |
| CROSSSLOT/MOVED | 会报错 | 已规避 |

## 六、启动预热（防首抖）

### 6.1 Lua 脚本预加载

```java
@Component
public class RedisScriptWarmup implements ApplicationRunner {

    private final StringRedisTemplate redisTemplate;
    
    @Value("classpath:lua/deduct_stock.lua")
    private Resource deductScriptResource;
    
    @Value("classpath:lua/refund_stock.lua")
    private Resource refundScriptResource;

    @Override
    public void run(ApplicationArguments args) throws IOException {
        // SCRIPT LOAD 预热，传入脚本内容（非 SHA）
        // 使用 RedisCallback 避免裸 getConnection() 泄漏
        String deductScript = new String(deductScriptResource.getInputStream().readAllBytes());
        String refundScript = new String(refundScriptResource.getInputStream().readAllBytes());
        
        String deductSha = redisTemplate.execute((RedisCallback<String>) conn -> 
            conn.scriptLoad(deductScript.getBytes()));
        String refundSha = redisTemplate.execute((RedisCallback<String>) conn -> 
            conn.scriptLoad(refundScript.getBytes()));
        
        log.info("Lua 脚本预热完成: deduct={}, refund={}", deductSha, refundSha);
    }
}
```

### 6.2 数据预热

```java
@Component
public class SeckillDataWarmup implements ApplicationRunner {

    private final ActivityCacheService cacheService;
    private final ActivityBloomFilter bloomFilter;
    private final SeckillActivityRepository activityRepo;
    
    @Override
    public void run(ApplicationArguments args) {
        // 1. 重建布隆过滤器
        bloomFilter.rebuild();
        
        // 2. 预加载进行中的活动到 Caffeine
        List<SeckillActivity> activeActivities = activityRepo.findByStatus(1);
        for (SeckillActivity activity : activeActivities) {
            cacheService.refresh(activity.getId());
            cacheService.markInStock(activity.getId());
        }
        log.info("数据预热完成: {} 个活动", activeActivities.size());
    }
}
```

## 七、完整写链路

```
POST /seckill/order {activityId=1, userId=42}
  │
  ├─ ① Bloom Filter（本地 AtomicReference）
  │     itemId 不存在？→ 404 "活动不存在"
  │
  ├─ ② Caffeine L1（refreshAfterWrite + executor 避免阻塞请求线程）
  │     isSoldOut(itemId)?  → 1009 "库存不足"
  │     getActivity(itemId) → 404 / 400 状态检查
  │
  ├─ ③ Redis Lua 扣库存（Master）
  │     KEYS[1]=stock:{itemId}, KEYS[2]=ordered:{itemId}:{userId}
  │     → 200=成功 / -1=重复 / -2=售罄 / -3=活动未初始化（返回 500）
  │
  ├─ ④ Kafka 异步下单
  │     send("seckill-order", "userId:itemId:orderNo")
  │     └─ Kafka 不可用 → Fail Fast 返回 503 + 回补库存
  │
  └─ ⑤ Consumer 消费
        INSERT t_seckill_order
        └─ 唯一索引 uk_activity_user 兜底防重
```

## 八、多节点缓存一致性

### 8.1 Caffeine 配置（避免阻塞请求线程）

```java
// refreshAfterWrite 默认使用 ForkJoinPool.commonPool() 异步刷新
// ❌ 错误写法：Runnable::run = 在请求线程同步执行，比不配还差
// .executor(Runnable::run)  // 同步执行，阻塞请求线程

// ✅ 正确写法：删掉 executor() 行（默认就是 ForkJoinPool.commonPool()）
// 或显式指定独立池，避免与业务线程争抢
Cache<Long, SeckillActivity> activityCache = Caffeine.newBuilder()
    .maximumSize(1000)
    .refreshAfterWrite(5, TimeUnit.SECONDS)
    // 不配 executor，默认 ForkJoinPool.commonPool()
    .expireAfterWrite(30, TimeUnit.SECONDS)
    .build(id -> activityRepo.findById(id).orElse(null));

// 或显式指定虚拟线程执行器（推荐，I/O 刷新不占平台线程）
// .executor(Executors.newVirtualThreadPerTaskExecutor())
```

### 8.2 售罄标记传播

```
节点 A: 扣减成功，库存归零 → markSoldOut(itemId)
节点 B: 1s 内请求 → Caffeine 无标记 → 放行到 Redis → Lua 拒绝 -2
                 → 然后 Caffeine 加载后也标记售罄

容忍 1s 窗口期，正确性由 Redis Lua 保证
```

### 8.3 布隆过滤器多节点同步

```
方案 1：各节点独立定时重建（60s）
  - 简单，新建活动最多等 60s 生效
  - 适合活动数量少（<1000）的场景

方案 2：Redis PubSub 广播
  - 活动上架时发布 seckill:bloom:add itemId
  - 各节点订阅并本地 add
  - 实时性更好，但需处理消息丢失

方案 3：MQ 广播（Kafka/RocketMQ）
  - 与订单消息共用 MQ，更可靠
  - 需单独 topic: seckill-bloom-sync
```

## 九、故障场景与应对

| 场景 | 影响 | 应对 |
|------|------|------|
| 单 Master 宕机 | 该 Slot 不可用 | **Cluster 内置 failover** 自动切主 <10s |
| Redis 重启 | 库存丢失 | 重新 `initStock` 恢复 |
| 网络分区 | 部分请求失败 | Cluster 自动路由到可用节点 |
| Kafka 不可用 | 异步下单失败 | **Fail Fast 返回 503** + 回补库存 |
| DB 不可用 | 订单写不进去 | 回补库存 refund，等恢复 |

### 9.1 Cluster 故障切换流程

```
1. Master 6381 宕机
2. 其他节点 cluster-node-timeout (5s) 内未收到心跳
3. 标记 6381 为 PFAIL (Possibly Failed)
4. 多数 Master 确认 → 标记为 FAIL
5. Slave 6386 发起选举，获得多数票
6. 6386 晋升为 Master，接管 Slot 0-5460
7. 客户端收到 MOVED，重连 6386
```

> **⚠️ 注意**：Cluster 故障切换期间，对应 Slot 的请求会短暂失败（~5-10s）。应用层需捕获 `RedisClusterException` 并快速失败，不要阻塞等待。

## 十二、面试要点

**Q: 为什么不用客户端分片，而用 Redis Cluster？**
> 客户端分片复杂度高，路由逻辑在应用层，扩容麻烦。Redis Cluster 自动管理 Slot 分布，应用只需连接任意节点。

**Q: Hash Tag 会不会导致热点？**
> `{itemId}` 让同一活动的所有 key 落在同 Slot。不同活动分布在不同 Slot。单活动热点可接受，因为库存本就是单 key。

**Q: 主从切换时数据会丢吗？**
> dev 关闭持久化，会丢。生产可开 AOF everysec，最多丢 1s。库存数据可从 DB 重新 initStock 恢复。

**Q: 多节点售罄标记不一致怎么办？**
> Caffeine 1s TTL 短窗口，容忍短暂不一致。正确性由 Redis Lua 保证，Lua 拒绝的不会超卖。

**Q: Redis Cluster 和 Sentinel 什么区别？**
> Sentinel 是单主多从的高可用方案，负责故障检测和自动切换。Cluster 是分片方案，多主多从，数据按 Slot 分布。两者不能混用——Cluster 内置故障切换，不需要 Sentinel。

**Q: 为什么 Lua 脚本的 Key 必须从 KEYS 数组传入？**
> Redis Cluster 根据 KEYS 数组计算目标 Slot，脚本内拼接的 key 不在 KEYS 里，Cluster 无法路由，会报 MOVED 错误。这是 Cluster 模式的强制约束。
