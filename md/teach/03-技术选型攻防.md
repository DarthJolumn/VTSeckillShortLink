# 03 — 技术选型攻防

> **目标：** 每个技术选型都能说出"为什么选 A 不选 B"，面试官追问 3 轮不崩。

## 每个选型的详细攻防

### 1. Dubbo（RPC 框架）

**面试官会问：** "为什么选 Dubbo？Feign 不行吗？"

**回答结构：**

```
第一层（技术）：Dubbo 自定义 TCP 协议头部仅 16 字节，单一长连接复用，
  HTTP/1.1 每次请求建连。秒杀场景请求量大，建连开销不可忽略。

第二层（服务治理）：Dubbo 有 SPI 扩展、自适应扩展、5 种负载均衡（加权随机/
  最少活跃/一致性哈希/最短响应/加权轮询）、多种容错策略。Feign 只是 HTTP 客户端。

第三层（面试策略）：实话实说——选 Dubbo 不是因为它比 Feign 快多少，
  是面试需要 Dubbo。SPI、自适应、线程模型，面试官能连问 5 轮。Feign 问两句就没了。
```

**追问 → Dubbo SPI 机制：**
```
Java SPI: ServiceLoader 加载所有实现，无 IoC/AOP
Dubbo SPI: @SPI + @Adaptive，按需加载，支持 IoC 注入、Wrapper AOP

面试时举例：Dubbo 的 LoadBalance 接口有 @SPI("random")，
  5 种实现类通过 SPI 按需加载，@Adaptive 自动选择合适的实现。
```

**追问 → 负载均衡怎么选：**
```
秒杀 → 最少活跃（请求耗时差异大，避开慢节点）
用户 → 加权随机（请求耗时均匀）
排行榜 → 一致性哈希（带缓存，同用户路由到同节点）
```

**追问 → 容错策略：**
```
秒杀下单 → Failfast（失败立即报错，防重复扣库存）
查询 → Failover（失败自动切其他节点）
```

### 2. 双 Token（认证方案）

**面试官会问：** "Session + Cookie 不够吗？为什么搞双 Token？"

**回答结构：**

```
数据对比（必背）：
  Session：10w QPS = 10w 次 Redis GET ≈ 10w IO/s
  双 Token：99% 请求仅 JWT 验签 = 0 IO，约 111 次刷新/s
  相差约 900 倍。

为什么中间态最好：
  - Session（有状态）：每次 IO，高并发瓶颈
  - 纯 JWT（无状态）：泄露后不可撤销，安全风险
  - 双 Token（折中）：Access JWT（快）+ Refresh Redis（可撤销）

Access Token 15min 内泄露的影响：
  - 攻击者只能冒充 15 分钟
  - Refresh Token 一直在服务端手里，随时可删
```

**追问 → 并发刷新怎么处理：**
```
前端：同一时刻只发一个 Refresh 请求，其他请求排队等结果
后端：Refresh Token 存在 Redis，查一次就知道还有没有效，
  不需要分布式锁（Redis 本身就是单线程的）
```

### 3. Kafka（消息队列）

**面试官会问：** "为什么 Kafka？RocketMQ 有延时消息不用？"

**回答结构：**

```
第一层（吞吐量）：顺序写磁盘 + 零拷贝（sendfile）+ 页缓存，
  三家里吞吐最高。秒杀峰值写入 10w+ 条/s，只有 Kafka 轻松扛。

第二层（面试高频）：零拷贝和页缓存是面试必问。

第三层（诚实说缺陷）：Kafka 不支持延时消息，订单超时取消用定时任务实现。
  这反而是扩展点——"为什么不直接用 RocketMQ 延时？因为部署更重，
  而且面试官更熟悉 Kafka。"
```

**追问 → 零拷贝原理：**
```
传统路径：磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区 → 网卡（4 次拷贝）
sendfile：磁盘 → 内核缓冲区 → 网卡（2 次拷贝，不经过用户态）
Kafka 用 FileChannel.transferTo 实现
```

**追问 → 页缓存：**
```
操作系统内核缓存磁盘页面。Kafka 写数据先写页缓存（内存），异步刷盘。
读消息命中页缓存直接返回，不读磁盘——等于内存速度。
```

**追问 → 消息不丢失怎么保证：**
```
Producer: acks=all（等所有副本确认）
Broker: min.insync.replicas=2（至少写入 2 个副本）
Consumer: 手动提交 offset（处理完再提交）
本项目: Consumer 用 @Transactional + MANUAL ACK，DB 和 offset 同步提交
```

### 4. Sentinel（限流）

**面试官会问：** "Sentinel 和 Resilience4j 有什么区别？"

```
Sentinel 亮点：
- 滑动窗口（LeapArray）：1 秒切 2 个 500ms 窗口，精度优于固定窗口
- 热点参数限流：按参数值（activityId + userId）独立限流，
  秒杀场景每用户 100 QPS
- 阿里系面试官更熟悉，递话头

Hystrix 已停更，Resilience4j 功能弱于 Sentinel
```

**追问 → 滑动窗口实现：**
```
固定窗口：0~1s 一个计数器 → 边界问题（前 0.5s 和后 0.5s 各 60 个 → 超限）
滑动窗口：1s 切为 N 个细粒度桶，时间滑动时淘汰旧桶 → 精度高 N 倍
```

### 5. Java 21 虚拟线程

**面试官会问：** "虚拟线程和平台线程的区别？"

```
平台线程：1:1 内核线程，创建成本 ~1ms + ~2MB 栈空间
虚拟线程：M:N JVM 调度，创建成本 ~1μs + 按需分配栈（初始 ~1KB）
创建成本低 2-3 个数量级，内存占用低 3-4 个数量级

WebSocket 场景：100w 连接 = 100w VT → 约 1-2GB 堆外内存
如果用平台线程：100w × 2MB = 2TB 栈空间，不可能
```

**追问 → VT 的坑：**
```
1. Pinning：synchronized 块/JNI 调用会 pin 住 Carrier 线程（平台线程），
   导致该 VT 不释放，其他 VT 等待。解决：用 ReentrantLock 替代 synchronized
2. ThreadLocal 泄漏：VT 池化后 ThreadLocal 不清除 → 内存泄漏。
   解决：用 ScopedValue（作用域结束自动清理）
```

### 6. ScopedValue vs ThreadLocal

**面试官会问：** "ScopedValue 和 ThreadLocal 什么区别？"

```
ThreadLocal 问题：
  - 即使不 set，每个 Thread 也有 16-slot Entry 数组（ThreadLocalMap）
  - 10w VT = 10w × 16 × 8 字节 ≈ 12.8MB 浪费
  - VT 池化后不清除 → 内存泄漏

ScopedValue 优势：
  - 没 bound 的线程不占任何内存
  - 不可变：bind 后不能改（线程安全）
  - 作用域结束自动清理（ScopedValue.where().run() 结束后清理）

代价：不可变。如果需要子线程修改上下文 → 不适合。
```

### 7. Caffeine（本地缓存）

**面试官会问：** "Caffeine 比 Guava Cache 好在哪？"

```
Caffeine 的 refreshAfterWrite：
  - 过期后返回旧值，异步后台刷新 → 不会击穿
  - Guava 的 expireAfterWrite：过期后第一个读线程同步重建 → 击穿

秒杀场景：本地缓存存"是否有库存" boolean，1s refreshAfterWrite。
  无库存请求直接返回售罄，不查 Redis → 压测减少 90% Redis 压力。

一致性：最多 1s 延迟返回"还有库存"（实际已无），
  但最终 Redis Lua 确保不超卖 → 多放几个请求进来被 Redis 拒绝 → 安全
```

## 面试万能公式

当被问"为什么选 X 不选 Y"时，按这个顺序回答：

1. **技术维度**：X 在哪些技术指标上优于 Y（性能/可靠性/扩展性）
2. **场景适配**：我们的场景为什么需要这些指标（秒杀高并发/长连接...）
3. **面试策略**（可选）：X 在面试时能聊更多深度
4. **诚实说 X 的不足**：展示你有全面认识
