## 第一轮：项目介绍

### Q1: 介绍一下你做的这个项目

**标准回答（30 秒）：**
> 我做了一个高并发直播电商秒杀系统 LiveMall。5 个微服务加一个 Gateway，Java 21 虚拟线程 + Dubbo RPC + Kafka + Redis + MySQL。核心链路是秒杀抢购：Gateway 限流验签 → Redis Lua 原子扣库存（4 分片）→ Kafka 异步下单 → WebSocket 推送结果。目标是 10w QPS，难点在库存热点分片和弹幕实时推送。

**进阶（如果面试官看起来感兴趣）：**
> 这个项目是为秋招准备的，亮点在于每个模块都有独立的技术纵深。比如 Dubbo 的 SPI 扩展、ScopedValue 替代 ThreadLocal、Kafka 零拷贝、Redis ZSet 跳表——面试官可以往任何一个方向深挖。

### Q2: 你在项目里负责什么？

> 这是个人项目，全栈独立开发。从架构设计、技术选型、数据库设计到后端 5 个服务的核心代码、前端 Vue 3 SPA 页面都自己写的。中间件用 Docker Compose 部署。

## 第二轮：架构设计

### Q3: 为什么拆成 5 个微服务？不觉得少吗？

> 宁深勿广。这是刻意为之的——5 个服务每个都有独立的技术纵深。用户服务有双 Token、秒杀有 Lua+Kafka、WebSocket 有百万连接管理、排行榜有 ZSet 跳表、网关有 Sentinel+WebFlux。如果拆成 15 个服务，每个都浅尝辄止，面试官问两句就没了。

### Q5: 服务间通信怎么做的？Dubbo 和 HTTP 各用在哪？

> Gateway 到业务服务走 HTTP（Spring Cloud Gateway 路由）。服务之间走 Dubbo RPC——自定义 TCP 协议，单一长连接复用，Hessian2 序列化。WebSocket 是直接 TCP 长连接，不经过 Gateway。选 Dubbo 不选 Feign 主要是因为面试纵深——Dubbo 的 SPI、负载均衡、容错策略每个点都能聊。

### Q6: 虚拟线程和 WebFlux 混用不矛盾吗？

> 是刻意为之的技术多样性展示。Gateway 用 WebFlux 因为纯 IO 转发，少量 EventLoop 就够。业务服务用 MVC + VT 因为有事务、加锁、状态机——VT 的 `Thread.startVirtualThread` 对这些零侵入。生产环境不会混用，但这恰恰说明我对两种模型都有理解。

## 第三轮：秒杀核心技术

### Q7: 秒杀全链路怎么做的？

> （见 `04-秒杀链路详解.md` 的全链路图，从网关到数据库每个环节解释）

### Q8: Redis Lua 为什么是原子的？

> Redis 是单线程执行命令的。Lua 脚本作为一个整体提交给 Redis，执行期间不会被其他客户端的命令插入。相当于天然的事务隔离，但比 MULTI/EXEC 更强——MULTI/EXEC 不支持条件判断，Lua 可以。所以我们在 Lua 里做"查重复 → 扣库存 → 设置防重标记"三步，这三步对外部来说是原子的。

### Q9: 库存分片怎么设计的？

> 单 Redis 实例单 key DECR 的上限约 8w QPS。我们用 `userId % 4` 做哈希路由，把库存分散到 4 个 key：`stock:shard:{activityId}:{0|1|2|3}`。每个分片独立 DECR，4 片加起来理论 32w QPS，覆盖 10w 目标有余。分片数不是越多越好——过度分片会导致库存碎片化：某分片卖完但总库存还有余。

### Q10: 怎么保证不超卖？

> 三层防护。第一层：Redis Lua 中 DECR 返回 ≥0 才成功，<0 立即 INCR 回补。第二层：防重 Key（`ordered:{activityId}:{userId}`）确保同一用户同一活动只能下一次单。第三层：MySQL 唯一索引 `uk_activity_user` 做最终兜底。

### Q11: 怎么保证一人一单？

> Redis 预判 + DB 唯一索引双保险。Lua 脚本中先 EXISTS 查 `ordered:{activityId}:{userId}`，存在就直接返回 -1。DB 有 `uk_activity_user (activity_id, user_id)` 唯一索引，即使 Redis 挂了也不会重复下单。

### Q12: Kafka 在秒杀链路里起什么作用？

> 异步削峰。Redis Lua 扣库存是同步的必须快，扣成功后发 Kafka 消息就立即返回给用户了。订单创建在 Consumer 侧异步执行，这样用户体感延迟极低。而且 Kafka 可以扛住瞬时 10w+ 写入，下游 Consumer 用虚拟线程慢慢消费，不会积压。

### Q13: Kafka 消息丢了怎么办？

> 三层保障。Producer 端 acks=all 等所有副本确认。Broker 端 min.insync.replicas=2 至少写入两个副本。Consumer 端手动提交 offset，先处理消息再提交。我们的 Consumer 用 @Transactional 包裹 DB 操作，offset 和 DB 事务同步——如果 DB 写失败，offset 不提交，消息会被重新消费。

## 第四轮：认证与安全

### Q14: 为什么用双 Token 而不是 Session？

> 性能差距太大。Session 方案每次请求都要查 Redis：10w QPS = 10w IO/s。双 Token 方案 99% 的请求仅做 JWT 验签（纯 CPU，零 IO），只有约 111 次/秒的刷新请求才查 Redis。差约 900 倍。而且双 Token 兼顾了安全——Refresh Token 在服务端手里，随时可以删除踢人，纯 JWT 做不到这点。

### Q15: JWT 的三个部分是什么？

> Header（声明算法 HS256 + 类型 JWT）、Payload（放 sub=userId, role, iat, exp 等 claims）、Signature（用密钥对前两部分签名，防篡改）。Payload 只是 Base64 编码不是加密，任何人解码就能看到内容，所以不能放敏感信息。

### Q16: Access Token 泄露了怎么办？

> 影响窗口是 15 分钟。15 分钟后 Token 过期，攻击者无法继续使用。而且用户发现异常后可以立即登出，服务端删除 Refresh Token，旧 Access Token 虽然还能用但最多 15 分钟。相比纯 JWT 方案（无撤销机制），这个风险可控得多。

### Q17: 并发刷新 Token 怎么处理？

> 前端用一个全局 Promise 做请求合并。同一时刻只发出一个 Refresh 请求，其他需要刷新的请求都等待这个 Promise 的结果。这样即使 10 个请求同时 401，也只触发一次 Refresh。

## 第五轮：缓存与性能

### Q18: 缓存怎么设计的？

> 多级缓存。L1 是 Caffeine 本地缓存（堆内，纳秒级），存活动状态和有无库存标记，1s 异步刷新。L2 是 Redis（毫秒级），存库存和排行榜。L3 是 MySQL（10ms 级），存持久化数据。秒杀场景下 L1 过滤掉 90% 的无库存请求，大幅减轻 Redis 压力。

### Q19: 缓存穿透/击穿/雪崩怎么解决？

> 穿透（查不存在的 key）：布隆过滤器 + 缓存空值 + 接口签名防恶意请求。击穿（热点 key 过期）：Caffeine refreshAfterWrite 不过期，后台异步刷新，不会击穿。雪崩（大量 key 同时过期）：TTL 随机化 60~300s，避免同时过期。

### Q20: Caffeine refreshAfterWrite 和 expireAfterWrite 的区别？

> expireAfterWrite 过期后第一个读请求同步阻塞重建 → 击穿。refreshAfterWrite 过期后返回旧值，异步后台刷新 → 不阻塞读请求。秒杀场景用 refreshAfterWrite，即使缓存延迟 1s 也不影响正确性——最终 Redis Lua 确保不超卖。

## 第六轮：WebSocket

### Q21: WebSocket 和 HTTP 长轮询的区别？

> HTTP 长轮询是半双工——客户端发请求，服务端挂起直到有数据才返回，然后客户端再发下一个。WebSocket 是全双工——一次握手后双方随时发送。WebSocket 头部只有 2-6 字节，HTTP 头部动辄几百字节。弹幕场景下服务端需要主动推消息给所有观众，长轮询做不到高效的广播。

### Q22: 100 万连接需要多少内存？

> 每个 WebSocket Session 约 1-2KB（主要是 TCP 缓冲区），百万连接约 1-2GB。虚拟线程每个初始栈约 1KB，百万 VT 约 1GB。总计约 2-3GB 内存。

### Q23: 心跳怎么设计的？

> 客户端每 30s 发 PING，服务端回 PONG。服务端有一个 @Scheduled 任务每 10s 扫描所有 session，最后活跃时间超过 60s 的主动 close。这样防止客户端异常断开导致"幽灵连接"占用资源。

## 第七轮：数据库

### Q24: 为什么用 Snowflake 不选 UUID？

> MySQL InnoDB 主键是聚簇索引，B+Tree 按主键顺序存储。Snowflake 时间戳在高位，生成的 ID 天然单调递增，插入时顺序写入，页利用率高。UUID 完全无序，会导致频繁的页分裂和索引重建，写入性能差。而且 Snowflake 64bit long 只占 8 字节，UUID 字符串 36 字节。

### Q25: Snowflake 时钟回拨怎么处理？

> 分两种情况。回拨 ≤100ms：自旋等待，等时钟追上。回拨 >100ms：抛异常，拒绝生成 ID。用 ReentrantLock 而不是 synchronized——因为在 VT 环境下 synchronized 会导致 VT pinning。等待时先释放锁再 sleep，避免持锁阻塞其他请求。

### Q26: 订单状态机怎么设计的？

> PENDING（待支付）→ PAID（已支付）→ REFUNDED（已退款）。PENDING → CANCELLED（超时取消/用户取消）。超时取消用 @Scheduled 每 15s 扫描过期订单，乐观锁 CAS 更新状态+版本号，防止超时取消和用户取消并发冲突。取消或退款后通过 Redis Lua 回补库存。

## 第八轮：开放题

### Q27: 你觉得你们系统最大的瓶颈在哪？

> Redis 单机。虽然有 4 片分库存，但 Redis 依然是单线程处理。如果秒杀活动特别火爆（超过 32w QPS），Redis 会成为瓶颈。解决方案是 Redis Cluster 分片集群，把不同活动分布到不同 Redis 节点上。

### Q28: 如果让你重新做，你会改什么？

> 第一，加 CI/CD 流水线和自动化测试。第二，认证 Redis 独立实例，不和业务 Redis 抢事件循环。第三，排行榜 ZSet 分片解决热点 key。第四，Prometheus + Grafana 搭建监控面板。

### Q29: 有什么你做了但没写在简历上的？

> DFA 敏感词热更新（AtomicReference 无锁替换词库）、Snowflake 时钟回拨的完整处理、接口签名降级方案（Redis 挂了跳过 Nonce）、前端秒杀按钮的蓄力动画和库存进度条——这些都是加分项。

### Q30: 说一个你解决的最难的技术问题

> ScopedValue 在 WebFlux 中的失效问题。Gateway 是 WebFlux 响应式模型，线程可能在链式调用中切换，ScopedValue 绑定在当前 Thread 上会丢失。解决方案是 WebFlux Filter 中将用户信息存入 ServerWebExchange.getAttributes()，转发前通过另一个 Filter 写入 Header，下游 MVC 服务从 Header 提取后再绑定 ScopedValue。这让我深入理解了响应式模型和同步模型在线程模型上的根本差异。

## 面试策略

1. **开头 30 秒定基调**：电梯演讲要让面试官知道"这个项目有东西可挖"
2. **主动递话头**：在回答中故意提到面试官可能追问的点（"我们用 Dubbo 而不是 Feign，主要是因为 SPI..." → 面试官大概率会追问 SPI）
3. **诚实说不足**：不要假装完美，诚实说哪里做得不够好反而显得你有判断力
4. **画图**：能画的就画——架构图、秒杀流程图、状态机图
5. **带数据**：每个结论尽量带数字（900 倍、8w QPS、4 分片）——数字比形容词有说服力
