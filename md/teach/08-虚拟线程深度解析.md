# 08 — 虚拟线程深度解析

> **目标：** 完整理解虚拟线程原理、优势、坑、与 WebFlux 的对比。这是 Java 21 最亮眼的特性，面试官一定会问。

---

## 1. 平台线程 vs 虚拟线程

### 1.1 平台线程（Platform Thread）

```
Java 线程 = 1:1 操作系统内核线程

创建成本：
  - 栈空间：~2MB（可配置 -Xss）
  - 创建时间：~1ms（系统调用，分配栈 + 内核数据结构）
  - 上下文切换：~10μs（用户态 ↔ 内核态切换 + 寄存器保存/恢复）

问题：
  - 100w 连接 = 100w 平台线程 = 2TB 栈空间 → 不可能
  - Tomcat 默认 200 线程池 → 201 个请求就要排队
  - 大部分线程在等 IO（阻塞），CPU 利用率极低
```

### 1.2 虚拟线程（Virtual Thread）

```
Java 虚拟线程 = M:N 调度（JVM 管理）

JVM 把 N 个 VT 映射到 M 个 Carrier 线程（平台线程）上。
当一个 VT 阻塞（等 IO），JVM 自动把它从 Carrier 上"卸下来"，
Carrier 去执行另一个 VT。等 IO 完成后，VT 被重新"挂上去"。

创建成本：
  - 栈空间：按需分配（初始 ~1KB）→ 堆内存，非栈内存
  - 创建时间：~1μs（纯 Java 对象创建，无系统调用）
  - 上下文切换：~0.1μs（纯 Java 操作，无内核态切换）

100w 连接 → 100w VT → ~1GB 堆内存（按需分配的栈）→ 可行
```

### 1.3 核心对比表

| 维度 | 平台线程 | 虚拟线程 |
|------|---------|---------|
| 创建成本 | ~1ms（syscall） | ~1μs（new 对象） |
| 栈内存 | ~2MB 固定 | ~1KB 起，按需增长 |
| 调度 | OS 内核调度 | JVM 用户态调度 |
| 上下文切换 | ~10μs（内核态） | ~0.1μs（用户态） |
| 数量上限 | ~1000 | ~10w~100w |
| 适合场景 | CPU 密集型 | IO 密集型 |
| 不适合 | — | CPU 密集 / Pinning 场景 |

## 2. VT 的实现原理

### 2.1 Continuation（续体）

```
VT 的核心是 Continuation——一个可暂停、可恢复的执行单元。

当 VT 遇到阻塞 IO：
  1. JVM 把当前栈帧保存到堆上的 Continuation 对象
  2. VT 从 Carrier 线程上"卸载"（unmount）
  3. Carrier 线程去执行另一个 VT
  4. IO 完成后，JVM 把 Continuation 恢复到某个 Carrier 上
  5. VT "挂载"（mount）继续执行

对代码来说，看起来就是普通的同步阻塞——但底层是非阻塞的。
这是 VT 最大的魅力：同步代码，异步执行。
```

### 2.2 Carrier 线程池

```
默认 Carrier 线程数 = CPU 核数

JVM 用 ForkJoinPool 管理 Carrier 线程。
一个 Carrier 同时只能运行一个 VT。
VT 阻塞 → 卸下 → Carrier 执行下一个 → VT 恢复 → 挂到任意空闲 Carrier。

这就是为什么 VT 不能在 synchronized 中阻塞：
  synchronized 锁住的是对象监视器，与 Carrier 线程关联。
  VT 从 Carrier 卸下时，监视器不会释放 → 其他 VT 无法获取锁 → Pinning。
```

## 3. Pinning（粘滞）问题

### 3.1 什么是 Pinning

```
当 VT 在执行以下操作时阻塞，它无法从 Carrier 上卸载：
  1. synchronized 块/方法
  2. JNI（Native 方法调用）
  3. 某些 JDK 内部 synchronized（如 Object.wait() 的某些路径）

导致：Carrier 线程被 VT 占用，无法执行其他 VT。
一个 Pinning 可能拖慢整个 VT 调度。
```

### 3.2 如何避免 Pinning

```
① 用 ReentrantLock 替代 synchronized：
   // ❌ VT 下
   synchronized (lock) { doIO(); }

   // ✅ VT 下
   lock.lock();
   try { doIO(); } finally { lock.unlock(); }

② 缩小 synchronized 块：
   // ✅ 只在必要的临界区用 synchronized，不放 IO 操作

③ JDK 在持续改进：
   Java 21 已修复 Object.wait() 的 Pinning
   Java 24 计划修复所有 synchronized 的 Pinning
```

### 3.3 本项目怎么处理的

```java
// Snowflake ID 生成器 —— 用 ReentrantLock 而非 synchronized
public class DistributedIdGenerator {
    private final Lock lock = new ReentrantLock();

    public long nextId() {
        lock.lock();
        try {
            // ... 获取时间戳、处理时钟回拨、生成 ID
        } finally {
            lock.unlock();
        }
    }
}

// Kafka Consumer —— 委托 VT 而非用消费者线程
@KafkaListener(topics = "seckill-order")
public void onOrder(OrderMessage msg) {
    Thread.startVirtualThread(() -> {
        doCreateOrder(msg);  // 这里面可能有 @Transactional → synchronized
    });
}
```

## 4. ScopedValue 替代 ThreadLocal

### 4.1 ThreadLocal 在 VT 下的问题

```
问题 1 — 内存浪费：
  每个 Thread 的 ThreadLocalMap 有 16 个 Entry 槽位。
  10w VT = 10w × 16 × 8 字节 ≈ 12.8MB（仅空槽位）。

问题 2 — 内存泄漏：
  VT 池化后，ThreadLocal 的值不清除。
  VT 用完归还池 → 下次被复用 → 读到上一个请求的残留数据。

问题 3 — 无法继承：
  父 VT 创建子 VT 时，ThreadLocal 不会自动继承。
  需要手动 InheritableThreadLocal（又引入新问题）。
```

### 4.2 ScopedValue 如何解决

```java
// 定义
private static final ScopedValue<User> USER = ScopedValue.newInstance();

// 绑定（在作用域内有效）
ScopedValue.where(USER, currentUser).run(() -> {
    // 整个调用链中都可以通过 USER.get() 获取
    doSomething();
    doSomethingElse();
});
// 离开 run() 后，USER 自动解绑

// 获取
User user = USER.get();  // 当前 VT 绑定的值，无则抛异常

// 子线程继承
ScopedValue.where(USER, currentUser).run(() -> {
    Thread.startVirtualThread(() -> {
        User u = USER.get();  // ✅ 自动继承
    });
});
```

### 4.3 本项目怎么用的

```
Gateway Filter:
  exchange.getAttributes().put("userId", userId);
  → 转发前写入 Header X-User-Id

业务服务 Interceptor:
  String userId = request.getHeader("X-User-Id");
  → ScopedValue.where().run() 绑定 → Controller/Service 获取

不能直接在 Gateway 用 ScopedValue:
  WebFlux 事件循环线程切换时 ScopedValue 会丢失，
  所以走 exchange attributes → Header → Interceptor 的链路。
```

## 5. VT vs WebFlux（响应式编程）

### 5.1 对比

| 维度 | 虚拟线程 | WebFlux |
|------|---------|---------|
| 编程模型 | 同步阻塞（写起来简单） | 响应式链式（Mono/Flux） |
| 学习曲线 | 低（和普通 Java 一样） | 高（需要理解响应式范式） |
| 调试 | 简单（完整堆栈跟踪） | 困难（堆栈是拼接的） |
| 适合场景 | 有事务/加锁/状态机的业务 | 纯 IO 转发/流处理 |
| 性能 | 高（用户态调度） | 高（少量线程处理大量连接） |
| 生态兼容 | 好（零侵入） | 需要全链路响应式 |

### 5.2 本项目为什么两者混用

```
Gateway → WebFlux：
  纯路由转发 + 鉴权 + 限流。没有业务逻辑。
  少量 EventLoop 线程就够了。WebFlux 天生适合。

业务服务 → MVC + VT：
  有事务（@Transactional）、加锁（ReentrantLock）、状态机。
  同步代码写起来自然，VT 提供高并发能力。

这是刻意的技术多样性展示。
生产环境不会混用，但能说明我对两种模型都有理解。
```

## 6. 面试追问速答

| 追问 | 回答 |
|------|------|
| VT 的调度器是什么 | ForkJoinPool，默认 Carrier 数 = CPU 核数 |
| VT 栈内存在哪 | 堆上（Java 对象），非 OS 栈内存。按需分配，初始 ~1KB |
| VT 创建成本为什么低 | 纯 Java 对象创建，无系统调用 |
| synchronized 什么时候可以不改 | 如果 synchronized 块内没有 IO 操作，只是 CPU 计算 → 没问题 |
| VT 和 Kotlin 协程的区别 | VT 零侵入，普通 Java 代码即可。协程需要 suspend 函数染色 |
| VT 和 Go goroutine 的区别 | 理念相似，实现不同。Go 是语言级，Java 是 JVM 级 |
| VT 适合所有场景吗 | 不适合 CPU 密集型（没有调度收益），不适合 Pinning 代码 |
