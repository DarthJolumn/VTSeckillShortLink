## v1 增强版：引入布隆过滤器

### 链路变化

```
  │     activityId 不存在？ → 抛 404，不碰缓存和 DB
  │     activityId 存在？   → 放行
  │
  ├─ ② Caffeine: isSoldOut? + getActivity?   (已有)
  │
  ├─ ③ Redis Lua: deduct                      (已有)
  │
  └─ ④ Kafka / 降级兜底                        (已有)
```

### ActivityBloomFilter 设计

```java
@Component
public class ActivityBloomFilter {

    private final AtomicReference<BloomFilter<Long>> filterRef = new AtomicReference<>();
    private final SeckillActivityRepository activityRepo;

    @PostConstruct
    public void init() {
        rebuild();
    }

    // 定期从 DB 加载所有 activityId 重建布隆过滤器
    @Scheduled(fixedDelay = 60_000)
    public void rebuild() {
        List<Long> ids = activityRepo.findAllIds();  // 所有活动 ID，不限状态
        BloomFilter<Long> newFilter = BloomFilter.create(
                Funnels.longFunnel(), Math.max(ids.size(), 100), 0.01);
        ids.forEach(newFilter::put);
        filterRef.set(newFilter);
    }

    public boolean mightContain(Long activityId) {
        BloomFilter<Long> f = filterRef.get();
        return f != null && f.mightContain(activityId);
    }
}
```

**为什么不用处理删除**：布隆过滤器只回答"ID 是否存在"，不回答"状态是否正确"。下架/取消的活动 ID 仍在 Bloom 中，放行后会由 Caffeine 根据 status 拦截。

**误判率**：0.01（1%），误判的请求放行后进入 Caffeine → DB，数量极低可接受。

## v2 多节点分布式高可用架构

### 总体拓扑

```
                         ┌──────────────┐
                         │   Gateway    │ Sentinel + JWT + Bloom(可选集中)
                         └──────┬───────┘
                                │
                    ┌───────────┴───────────┐
                    │                       │
             ┌──────▼──────┐        ┌──────▼──────┐
             │ Seckill 节点1 │        │ Seckill 节点2 │
             │ (VT + Caffeine)       │ (VT + Caffeine)
             └──────┬───────┘        └──────┬───────┘
                    │                       │
                    └──────────┬────────────┘
                               │
                    ┌──────────▼──────────┐
                    │    Redis Cluster    │
                    │                     │
                    │  ┌──────┐ ┌──────┐  │
                    │  │节点A  │ │节点B  │  │  写节点 (库存桶)
                    │  │shard0│ │shard2│  │  持久化: RDB 60s / 关闭
                    │  │shard1│ │shard3│  │
                    │  └──────┘ └──────┘  │
                    │  ┌──────┐ ┌──────┐  │
                    │  │节点C  │ │节点D  │  │  读节点 (token/活动信息)
                    │  │ 副本  │ │ 副本  │  │  持久化: AOF everysec
                    │  └──────┘ └──────┘  │
                    └─────────────────────┘
                               │
                    ┌──────────▼──────────┐
                    │   Kafka (3分区)      │  异步削峰，分区 key = userId
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │   MySQL + 读写分离   │
                    │  (主: INSERT订单)    │  乐观锁 @Version + 唯一索引
                    │  (从: 活动查询)      │
                    └─────────────────────┘
```

### 关键设计点

#### 1. Redis Cluster + 库存路由

```java
// 根据 userId 决定请求走哪个 Redis 节点
// 保证 ordered 和 stock:shard 在同一节点
int nodeIdx = (userId / shardCount) % nodeCount;
RedisNode node = clusterNodes[nodeIdx];

// 在选定的节点上执行 Lua 脚本
// 分片计算仍在 Lua 内部：userId % shardCount
```

**路由粒度**：`user_id` → `node` → `shard`，保证同一用户的操作始终落在同一节点。

#### 2. 持久化策略

| 节点角色 | 策略 | 理由 |
|---------|------|------|
| 写节点 (库存桶) | RDB 60s / 关闭持久化 | 库存数据可从上架时重新 initStock，重启即恢复 |
| 读节点 (用户/Token) | AOF everysec | Token 和会话数据不能丢 |

**面试考点**：写节点关闭持久化，Redis 重启后库存丢失怎么办？

```
① 秒杀进行中 → Redis 重启 → 库存全丢
② 用户继续请求 → Caffeine 无售罄标记 → 放行
③ Redis Lua 对不存在的 key DECR → DECR 不存在 key 返回 -1
④ 订单写入 DB，但实际库存为 0 → 可能超卖
```

最终防线：`uk_activity_user` 唯一索引 + `@Version` 乐观锁兜底。Redis 重启后需重新 `initStock` 恢复。

#### 3. 库存分桶碎片化

```
库存 1000，shardCount=4，2 个写节点

节点 A: shard 0~1 (各 250)
节点 B: shard 2~3 (各 250)

用户均匀分布 → 理论同时扣完
但实际 userId 分布不均 → 某片先空，其他片还剩
```

**回答**：碎片化是 trade-off。**均匀度足够的场景（大量用户随机分布）碎片率 < 5%**。不均匀场景可接受，因为分片目的是扛 QPS 而非完全利用库存。

#### 4. 布隆过滤器在 v2 的位置

| 方案 | 部署位置 | 优点 | 缺点 |
|------|---------|------|------|
| 集中式 | Gateway + Redis BF | 全局统一，实时更新 | 多一次 Redis 调用 |
| 本地式 | 每个 Seckill 节点 | 无额外网络开销 | 60s 重建延迟，新建活动需等 |

v2 推荐**本地式**，误判 60s 窗口可接受。

#### 5. Caffeine 多节点缓存

`soldOutFlags` 在 v2 中改为**短 TTL 的 Caffeine 缓存**：

```
节点 A: markSoldOut(1) → Caffeine 1s
节点 B: 1s 内请求 → 缓存无标记 → 放行到 Redis → Lua 拒绝（不超卖）
         1s 后请求 → 如果 Redis 还无库存 → Caffeine 加载后也标记售罄
```

正确性由 Redis Lua 保障，Caffeine 只做性能优化。

#### 6. 完整 v2 链路

```
请求 POST /seckill/order {activityId=1, userId=42}
  │
  ├─ ① 布隆过滤器 (本地 AtomicReference)
  │     → activityId 不存在? 抛 404
  │
  ├─ ② Caffeine: isSoldOut? + getActivity? (1s TTL)
  │     → 售罄抛 1009、不存在抛 404、非进行中抛 400
  │
  ├─ ③ 路由: userId=42 → nodeIdx = (42/4) % 2 = 5 % 2 = 1 → 节点 B
  │
  ├─ ④ 节点 B Redis Lua: deduct_stock.lua
  │     → GET ordered:1:42 → 已存在? -1
  │     → shard = 42 % 4 = 2 → DECR stock:shard:1:2
  │     → ≥0? SETEX ordered + 200 | <0? INCR + -2
  │
  ├─ ⑤ Kafka send("seckill-order", "42:1:orderNo")
  │     → 分区 key = userId → 同一用户消息顺序消费
  │
  └─ ⑥ Consumer: INSERT DB → gRPC 推 WS
        → 唯一索引 + 乐观锁最终防线
```

### v1 → v2 改动清单

| 组件 | v1 | v2 |
|------|----|----|
| Redis | 单机 4 分片 | Cluster 2+ 写节点 (各管部分桶) + 读副本 |
| 路由 | 固定地址 | userId 计算 node 路由 |
| 持久化 | 未显式配置 | 写 RDB/关闭、读 AOF |
| 布隆过滤器 | ❌ | ✅ 本地 AtomicReference 60s 重建 |
| 售罄标记 | ConcurrentHashMap | Caffeine 1s TTL |
| DB | 单库 | 主从读写分离 |
| 多节点 | 不感知 | Caffeine 短 TTL + Lua 最终把关 |
