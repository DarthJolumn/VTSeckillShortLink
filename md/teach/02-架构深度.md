## 2. 为什么是 5 个服务（不是 3 个也不是 15 个）

面试官爱问"为什么拆成 N 个微服务"。回答策略：

**拆少了的代价（单体/3 个服务）：**
- 秒杀的 Redis 热点 Key 和 WebSocket 的百万连接混在一个进程 → GC 互相影响
- 排行榜的 ZSet 操作和用户登录的 BCrypt 混用 CPU → 资源竞争

**拆多了的代价（15 个服务）：**
- 每个服务浅尝辄止，面试官问两句就没了
- 分布式事务、网络开销暴增，不出活

**5 个刚好——每个都有独立技术纵深：**

| 服务 | 核心技术纵深 |
|------|-------------|
| gateway | WebFlux 响应式、Sentinel 滑动窗口、签名验签 |
| user | 双 Token、BCrypt、ScopedValue、设备管理 |
| seckill | Redis Lua 原子扣减、库存分片、Kafka 削峰、状态机 |
| websocket | @ServerEndpoint + VT、心跳、跨节点路由、DFA 过滤 |
| leaderboard | ZSet 跳表、热冷分离、定时快照 |

## 3. 服务间通信方式

```
Gateway → 业务服务: HTTP（Spring Cloud Gateway 路由）
业务服务之间:     Dubbo RPC（TCP 长连接 + Hessian2 序列化）
WebSocket:        直接 TCP 长连接（不经过 Gateway）
```

**为什么不全部走 HTTP？**
- Dubbo 自定义协议头部仅 16 字节，HTTP/1.1 头部动辄几百字节
- Dubbo 单一长连接复用，HTTP 每次建连开销大
- Dubbo 内置负载均衡/容错/服务治理

**WebSocket 为什么不走 Gateway？**
- WebSocket 握手后是长连接，Gateway 只做初始路由
- 后续消息直接在客户端和 WS 服务之间传输

## 4. 数据存储策略

| 数据类型 | 存储 | 原因 |
|---------|------|------|
| 用户信息 | MySQL | 持久化，需要事务 |
| Token（Refresh） | Redis | 需要 TTL 和快速查找 |
| 库存（秒杀中） | Redis | 需要原子操作 + 超高并发 |
| 库存（活动结束） | MySQL | 持久化最终状态 |
| 订单 | MySQL | 持久化，需要事务和查询 |
| 在线人数 | Redis Set + MySQL 同步 | 实时性（Redis）+ 历史（MySQL） |
| 排行榜 | Redis ZSet | O(log N) 实时排序 |
| 排行榜快照 | MySQL | 历史数据持久化 |
| 离线消息 | Redis List（5min TTL） | 临时缓存 |
| 设备会话 | Redis Set | TTL 管理 |

## 5. 关键设计模式

### 5.1 双 Token 认证

```
Access Token（JWT, 15min）→ 每次请求仅验签 → 0 IO
Refresh Token（存 Redis, 7d）→ 过期后用 Refresh 换新的 → 少量 IO

为什么不用 Session：每次查 Redis（10w QPS = 10w IO）
为什么不用纯 JWT：泄露后不可撤销
```

### 5.2 多级缓存

```
L1 Caffeine（堆内，纳秒级）→ "有库存吗？" boolean，1s 刷新
L2 Redis（远程，毫秒级）  → 库存精确扣减
L3 MySQL（兜底，10ms 级） → 最终数据
```

### 5.3 异步削峰

```
Redis Lua 扣库存（同步，必须快）
  → 扣成功 → 发 Kafka（异步，不阻塞返回）
    → Consumer VT 消费 → INSERT 订单（异步）
      → WebSocket 推送结果（异步）
```

### 5.4 库存分片

```
单 key DECR 上限 ~8w QPS（Redis 单线程）
分片: userId % 4 → stock:shard:{activityId}:{0|1|2|3}
4 片 × 8w = 32w QPS 上限，覆盖 10w 目标有余量
```

## 7. 面试常见追问

**Q: 为什么用 Nacos 不用 Eureka？**
A: Nacos = 注册中心 + 配置中心，一个中间件干两件事。Eureka 已停更。Dubbo 3.x 官方推荐 Nacos。

**Q: Nacos 挂了怎么办？**
A: Dubbo 有本地缓存，已注册的服务不受影响，新服务无法注册但现有链路不断。

**Q: 为什么不拆出独立的认证服务？**
A: 认证逻辑和用户服务紧耦合（查用户表），拆出去反而多一跳 RPC 延迟。双 Token 的 Access Token 是无状态的，对用户服务无额外压力。

**Q: WebSocket 服务为什么单节点？**
A: 设计支持多节点——通过 Redis `ws:route:{userId}` 路由表 + Dubbo 跨节点转发。单节点是当前开发阶段。
