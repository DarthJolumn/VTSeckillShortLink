# 07 — 排行榜与缓存策略

> **目标：** 理解 Redis ZSet 跳表原理、多级缓存设计、缓存三大问题及解决方案。

---

## 1. 排行榜为什么用 Redis ZSet

### 1.1 不用 MySQL 的原因

```sql
-- 如果 100w 行数据，这个查询就是灾难
SELECT user_id, score FROM leaderboard
ORDER BY score DESC LIMIT 100;

-- MySQL: 全表扫描 + 文件排序（Using filesort），>500ms
-- Redis ZSet: ZRevRange O(log N + M)，<1ms
```

### 1.2 ZSet 底层结构

```
ZSet = 跳表（skiplist）+ 哈希表（Dict）

跳表：多层有序链表，查找/插入/删除 O(log N)
哈希表：member → score 映射，查分数 O(1)

跳表原理：
  - 最底层是完整有序链表
  - 每层以概率 P=0.25 升级元素到上层
  - 每层元素约为下层的 1/4
  - 查找时从上往下：顶层快速跨越，底层精确定位
  - 期望高度 log₁/ₚ(N) ≈ log₄(N)，每层比较次数常数 → O(log N)
```

### 1.3 为什么不用 Sorted Set 的其他实现

| 实现 | 复杂度 | 问题 |
|------|--------|------|
| 平衡树（AVL/红黑树） | O(log N) | 需要频繁旋转，实现复杂 |
| 跳表 | O(log N) | 概率平衡，实现简单，Redis 采用 |
| B+Tree | O(log N) | 适合磁盘，内存场景不如跳表 |

## 2. 排行榜功能实现

### 2.1 数据结构

```
Redis Key: leaderboard:{activityId}
类型: ZSet
Member: userId
Score: 互动积分

操作：
  ZIncrBy leaderboard:{activityId} <score> <userId>    # 加分
  ZRevRange leaderboard:{activityId} 0 99 WITHSCORES    # Top 100
  ZRevRank leaderboard:{activityId} <userId>            # 用户排名
  ZScore leaderboard:{activityId} <userId>              # 用户分数
```

### 2.2 互动加分规则

```
观看直播  +1
点赞      +2
评论      +3
分享      +5
送礼      +10~100（按礼物价值）
秒杀成功  +20
```

### 2.3 定时快照

```
@Scheduled(cron = "0 */5 * * * *")  // 每 5 分钟
void snapshot() {
    Set<ZSetOperations.TypedTuple<String>> top100 =
        redisTemplate.opsForZSet()
            .reverseRangeWithScores("leaderboard:" + activityId, 0, 99);

    // INSERT INTO t_leaderboard_snapshot
    // (activity_id, user_id, score, rank, snapshot_time)
}
```

**为什么 5 分钟：**
- 活动一般 1h+，5min 粒度足够
- 太频繁浪费 MySQL 写入
- 太久丢失变化趋势

### 2.4 历史排行查询

```
查 MySQL 快照表：
SELECT user_id, score, rank, snapshot_time
FROM t_leaderboard_snapshot
WHERE activity_id = ? AND snapshot_time BETWEEN ? AND ?
ORDER BY snapshot_time, rank
```

## 3. 多级缓存设计

### 3.1 三级架构

```
┌─────────────────────────────────────────┐
│ L1: Caffeine（堆内，纳秒级）              │
│ - 活动状态 + 有无库存标记（boolean）        │
│ - refreshAfterWrite: 1s                  │
│ - 容量: 10000 条                         │
├─────────────────────────────────────────┤
│ L2: Redis（远程，毫秒级）                  │
│ - 库存精确值                              │
│ - 活动详情                               │
│ - TTL: 活动结束 + 1h                      │
├─────────────────────────────────────────┤
│ L3: MySQL（兜底，10ms 级）                │
│ - 全量数据                               │
│ - 持久化保证                              │
└─────────────────────────────────────────┘
```

### 3.2 Caffeine vs Guava Cache vs Ehcache

| 维度 | Caffeine | Guava Cache | Ehcache |
|------|----------|-------------|---------|
| 性能 | 最高（W-TinyLFU） | 中（LRU） | 中 |
| 异步刷新 | ✅ refreshAfterWrite | ❌ | ✅ |
| 持久化 | ❌ | ❌ | ✅（磁盘/集群） |
| 适合场景 | 本地高速缓存 | 已过时 | 需要持久化 |

**本项目选 Caffeine 的理由：**
- `refreshAfterWrite` 异步刷新，不会阻塞读请求
- 秒杀场景下，缓存"无库存"标记 1s 刷新，过滤 90% 无效请求
- 不需要持久化（Redis 是真正的缓存层）

## 4. 缓存三大问题及解决方案

### 4.1 缓存穿透

**场景：** 攻击者用不存在的 userId 疯狂查排行榜 → 缓存 miss → 全打 DB。

**方案：**
```
① 布隆过滤器：所有存在的 userId 预先加入布隆过滤器，
   查询前先过布隆 → 不存在直接返回

② 缓存空值：key 不存在 → 缓存一个 null，TTL 1min

③ 接口签名 + 限流：不签名的请求根本进不来
```

### 4.2 缓存击穿

**场景：** 热点活动缓存刚好过期 → 瞬间大量请求打到 DB。

**方案：**
```
① Caffeine refreshAfterWrite：永不过期，异步刷新，
   读请求永远不会因为缓存过期而阻塞

② 互斥锁重建：如果缓存真的 miss，用 Redis SETNX 抢锁，
   只有一个线程去查 DB 重建缓存，其他等待

// 伪代码
String cache = redis.get(key);
if (cache == null) {
    if (redis.setnx("lock:" + key, "1")) {  // 抢到锁
        cache = db.query();
        redis.setex(key, 300, cache);
        redis.del("lock:" + key);
    } else {
        Thread.sleep(50);  // 没抢到，等重建
        cache = redis.get(key);
    }
}
```

### 4.3 缓存雪崩

**场景：** 大量 key 在同一时刻过期 → 大量请求打到 DB。

**方案：**
```
TTL 随机化：基础 TTL 300s + random(0, 300)
  不同 key 在不同时间过期，避免同时失效

多级缓存：本地 Caffeine 还有一层，即使 Redis 全挂也能挡
```

## 5. 缓存一致性策略

### 5.1 本项目用最终一致性

```
秒杀场景为什么能接受最终一致：
  - 库存扣减走 Redis Lua（实时精确）→ 不会超卖
  - 订单状态变更 → 发 Kafka → Consumer 刷新缓存
  - 用户通过 WebSocket 实时知道结果
  - 缓存中的订单列表差 1-2 秒不影响体验
```

### 5.2 其他一致性方案对比

| 方案 | 流程 | 适用场景 |
|------|------|---------|
| Cache Aside | 读 miss 回填；写 DB → 删缓存 | 读多写少 |
| 延迟双删 | 写 DB → 删缓存 → sleep → 再删缓存 | 需要强一致 |
| Write Through | 写缓存 → 缓存同步写 DB | 写少 |
| 最终一致（本项目） | 写 DB → 发 MQ → Consumer 刷新缓存 | 高并发，接受秒级不一致 |

## 6. 面试追问速答

| 追问 | 回答 |
|------|------|
| 跳表为什么是 O(log N) | 层高概率升级（P=0.25），每层元素减半，期望高度 log₄(N) |
| 为什么不用平衡树 | 跳表实现更简单，概率平衡避免旋转，Redis 选了跳表 |
| ZSet 热点问题 | 大活动 ZSet 分片（activityId % shardCount），查询时合并排序 |
| 缓存一致性怎么选 | 秒杀场景库存精确即可，订单状态允许秒级延迟，用最终一致 |
| 布隆过滤器的问题 | 不能删除元素，有误判率（约 1%）。用 Counting Bloom Filter 可删除 |
