## 三、关键组件详解

### 3.1 BloomFilter（`ActivityBloomFilter.java`）

```
功能：快速判断 activityId 是否有效（活跃活动集合）
实现：Guava BloomFilter<Long>（AtomicReference 线程安全）
误判率：1%（FPP=0.01）
重建：60s 定时 + @PostConstruct 启动时重建
即时插入：活动上架时 add() 绕过 60s 窗口
作用：拒绝无效活动 ID 请求，减少后续 Redis 查询

代码位置：line 37 → BloomFilter.create(Funnels.longFunnel(), size, 0.01)
           line 34 → @Scheduled(fixedDelay = 60_000)
           line 52 → mightContain() → 返回 false 时抛 404
```

### 3.2 Caffeine 缓存（`ActivityCacheService.java`）

```
活动信息缓存（activityCache）：
  - LoadingCache，refreshAfterWrite=5s，expireAfterAccess=30s
  - 过期返回旧值 + 后台异步刷新（永不阻塞）
  - 最大 1000 条

售罄标记缓存（soldOutCache）：
  - expireAfterWrite=1s，自动过期（弱一致）
  - markSoldOut() → 存入 TRUE
  - markInStock() → invalidate() 清除
  - isSoldOut() → 返回 true 时直接拒绝

注意：售罄标记最多 1s 延迟，Redis Lua 最终防超卖

代码位置：line 30-38 → Caffeine 初始化
           line 47 → markSoldOut()
           line 57 → isSoldOut()
```

### 3.3 Redis Lua 扣库存（`deduct_stock.lua`）

```
输入：
  KEYS[1] = stock:{activityId}
  KEYS[2] = ordered:{activityId}:{userId}
  ARGV[1] = "1" 启用去重 / "0" 跳过去重

流程：
  ① EXISTS KEYS[1] → 不存在返回 -3（活动未初始化）
  ② ARGV[1]!="0" 时 GET KEYS[2] → 存在返回 -1（重复下单）
  ③ DECR KEYS[1] → 结果 >= 0 则 SETEX ordered key (86400s) + 返回 200
  ④ DECR < 0 → INCR 回滚 + 返回 -2（库存不足）

Cluster 兼容：{activityId} hash tag 保证所有 key 同 slot
启动预热：RedisScriptWarmup 启动时 SCRIPT LOAD
```

### 3.4 Redis Lua 回补库存（`refund_stock.lua`）

```
输入：
  KEYS[1] = stock:{activityId}
  KEYS[2] = ordered:{activityId}:{userId}

流程：
  EXISTS KEYS[2] == 1 → INCR KEYS[1] + DEL KEYS[2]
  幂等：ordered key 不存在时不执行任何操作
```

### 3.5 Controller 下单入口（`SeckillController.placeOrder()` line 70-100）

```
输入：
  Header: X-User-Id = {userId}
  Body: {"activityId": {activityId}}

流程：
  ① idGenerator.nextOrderNo() → 雪花算法生成订单号
  ② seckillService.placeOrder() → Bloom → Caffeine → Redis Lua
  ③ 返回 "ok" → Kafka send 异步写订单
     - 正常：发消息到 "seckill-order" topic
     - Kafka 不可用：Fail Fast → refund 回补库存 → 返回 503
  ④ 返回前端 {result, orderNo}

Fail Fast 设计（line 86-89）：
  如果 Kafka 不可用，不回滚 Redis 扣减而是 refund 回补，
  避免"库存扣了但订单没建"的不一致状态。
```

### 3.6 Kafka Consumer（`SeckillOrderConsumer.onMessage()` line 40-99）

```
输入格式："userId:activityId:orderNo"

流程：
  ① Semaphore.acquire() → 限流（默认 30，匹配 HikariCP）
  ② Thread.startVirtualThread() → VT 处理
     a) 解析消息 → userId, activityId, orderNo
     b) Caffeine 查活动信息
     c) seckillService.createOrder() → INSERT 订单 (status=0)
     d) gRPC push 秒杀结果到 WebSocket 服务
     e) ack.acknowledge()
     f) Semaphore.release()（finally）
   
异常处理：
  DuplicateKeyException → ack（命中唯一索引，幂等跳过）
  TransactionException   → 不 ack（DB 故障，Kafka 重投）
  Exception              → ack（未知异常，跳过防止死信堆积）
```

### 3.7 超时取消 Scheduler（`TimeoutCancelScheduler.cancelTimeoutOrders()` line 40-64）

```
配置：
  timeout-cancel-enabled: true   （压测时置 false）
  order-timeout-minutes: 15      （15 分钟超时）
  timeout-scan-ms: 15000         （每 15 秒扫描一次）
  timeout-scan-batch: 500        （每次最多处理 500 条）

流程：
  ① 查 status=0 && createdAt < now - 15min 的订单
  ② 每条订单：
     a) stockService.refund() → Redis INCR stock + DEL ordered
     b) cacheService.markInStock() → 清除售罄标记
     c) order.setStatus(2) + orderRepo.save()
     d) @Version 乐观锁 CAS 防并发

异常处理：
  OptimisticLockException → 用户已手动取消，跳过
  Exception → log 但不影响其他订单
```

### 3.8 gRPC 配置（`GrpcClientConfig.java`）

```
seckill 服务：
  ManagedChannelBuilder.forAddress(wsHost, wsPort)
  .usePlaintext()
  → SeckillPushGrpc.newBlockingStub(channel)

WebSocket 服务端：
  @GrpcService（Spring Boot 4.1 自动配置）
  → SeckillPushGrpc.SeckillPushImplBase

protobuf 定义：livemall-common/src/main/proto/seckill-push.proto
```

## 四、配置清单（`application.yml`）

```yaml
# 秒杀业务配置
seckill:
  ordered-ttl-seconds: 86400              # ordered key TTL (24h)
  timeout-cancel-enabled: true            # 超时取消开关
  timeout-scan-ms: 15000                  # 扫描间隔 (15s)
  order-timeout-minutes: 15               # 订单超时阈值 (15min)
  timeout-scan-batch: 500                 # 每批处理数
  dedup-enabled: true                     # Redis 去重开关
  consumer-max-concurrency: 30             # 消费者并发数
  grpc:
    websocket-host: localhost             # gRPC WebSocket 地址
    websocket-port: 9090                  # gRPC WebSocket 端口
  activity-cache:
    ttl-seconds: 5                        # Caffeine TTL
    max-size: 1000                        # 最大缓存数

# HikariCP
spring.datasource.hikari:
  maximum-pool-size: 30                   # 连接池大小
  minimum-idle: 5

# 基础配置
server.port: 8090
spring.threads.virtual.enabled: true       # VT 开启
```

### 5.3 瓶颈定位

- 300 线程是这台 VM 的峰值（1312 TPS）
- 60/60 配置（HikariCP 60 + Semaphore 60）反而更差（928 TPS, P99 666ms）
- 瓶颈：MySQL 写入（DB 端点在 SW 中 P99 370-390ms）
- 突破瓶颈需：分库分表 / MySQL 升级 SSD / 迁移物理机
