## 一、核心变更点摘要

| 变更 | 旧认知 | 新认知 | 影响模块 |
|------|--------|--------|---------|
| **鉴权** | Bearer Token 即可 | 必须同时携带 `X-Device-Id`（设备指纹）和 `X-Idempotency-Key`（幂等） | Axios 拦截器、登录/注册 |
| **WebSocket 升级** | 连接时决定身份 | 支持匿名连接 → 运行时 `AUTH` 消息升级 | 直播间组件 |
| **心跳** | 后端会保活 | **前端必须每 30s 主动发 `PING`**，60s 不发则后端断开 | WS composable |
| **秒杀异步化** | 下单即成功 | `result:"ok"` 只表示扣库存成功，订单在 Kafka 中，结果靠 WS `SEC_KILL_RESULT` 确认 | 秒杀下单/结果页 |
| **时间校准** | 信任 `new Date()` | 秒杀倒计时必须用服务端时间（计算 offset） | 倒计时组件 |

## 二、联调前基建重构

在发起第一个请求前，必须完成以下基础设施。

### 2.1 设备指纹生成器

`X-Device-Id` 是登录接口**必填项**，也是设备管理、踢下线的核心标识。

```javascript
// utils/device.js
export const getDeviceId = () => {
  let id = localStorage.getItem('device_id')
  if (!id) {
    id = crypto.randomUUID()
    localStorage.setItem('device_id', id)
  }
  return id
}
```

**联调验证**: 打开 DevTools → Network，检查每个请求的 Request Headers 是否包含 `X-Device-Id`。

### 2.2 Axios 拦截器重构

```javascript
// utils/http.js
import { getDeviceId } from './device'

const http = axios.create({ baseURL: '/api' })

// ----- 请求拦截器 -----
http.interceptors.request.use(config => {
  // 1. 设备指纹（所有请求）
  config.headers['X-Device-Id'] = getDeviceId()

  // 2. 幂等键（仅写操作）
  if (['POST', 'PUT', 'DELETE'].includes(config.method?.toUpperCase())) {
    config.headers['X-Idempotency-Key'] = crypto.randomUUID()
  }

  // 3. 认证 Token
  const token = localStorage.getItem('accessToken')
  if (token) config.headers.Authorization = `Bearer ${token}`

  return config
})

// ----- 响应拦截器（双 Token 自动刷新）-----
let isRefreshing = false
let pendingQueue = []

http.interceptors.response.use(
  res => res.data,
  async error => {
    const { config, response } = error
    // 非 401 或已是重试请求 → 直接拒绝
    if (!response || response.status !== 401 || config._retry) {
      return Promise.reject(error)
    }

    // 刷新接口本身失败 → 跳登录（防死循环）
    if (config.url === '/auth/refresh') {
      redirectToLogin()
      return Promise.reject(error)
    }

    if (isRefreshing) {
      // 排队等待刷新完成
      return new Promise(resolve => pendingQueue.push(resolve))
    }

    config._retry = true
    isRefreshing = true

    try {
      const { data } = await http.post('/auth/refresh', {
        refreshToken: localStorage.getItem('refreshToken')
      })
      localStorage.setItem('accessToken', data.accessToken)
      localStorage.setItem('refreshToken', data.refreshToken)
      // 唤醒排队请求
      pendingQueue.forEach(cb => cb())
      pendingQueue = []
      config.headers.Authorization = `Bearer ${data.accessToken}`
      return http(config)
    } catch {
      redirectToLogin()
    } finally {
      isRefreshing = false
    }
  }
)
```

**联调验证**:

| 场景 | 预期 |
|------|------|
| accessToken 过期 | 自动调 POST /auth/refresh，拿到新 Token 重放原请求 |
| refreshToken 也过期 | 清 Token 跳转 /login |
| 并发 3 个请求同时 401 | 只调一次 refresh，3 个都重放成功 |

### 2.3 全局时间同步

秒杀倒计时**不能信任 `new Date()`**，因为签名验签有 ±5min 窗口，同时 `startTime`/`endTime` 是服务器 `LocalDateTime`。

```javascript
// utils/time.js
let offset = 0  // 服务端时间 - 本地时间

export const syncTime = async () => {
  // 方式一：从登录响应获取 Date header
  const start = Date.now()
  const res = await fetch('/auth/login', { method: 'HEAD' })
  const serverDate = new Date(res.headers.get('Date')).getTime()
  const end = Date.now()
  offset = serverDate - (start + end) / 2  // 减去 RTT 一半
}

export const serverNow = () => Date.now() + offset
```

**使用**: 所有倒计时组件中 `const now = serverNow()` 替代 `Date.now()`。

## 三、分阶段联调策略

### 第一阶段：地基与双 Token（最难攻克）

**目标**: 完成完整的认证闭环，解决 Token 刷新死循环和设备管理。

#### 联调场景 1 — 双 Token 刷新

```
前提: 已登录，localStorage 有 accessToken + refreshToken

操作:
  1. 手动修改 localStorage 的 accessToken 为 "invalid"
  2. 发起任意需要鉴权的请求（如 GET /user/profile）

预期结果:
  ├─ 请求 A → 401
  ├─ 自动调 POST /auth/refresh → 成功
  ├─ 用新 Token 重放请求 A → 200
  └─ 页面正常展示数据
```

**验证检查点**:

| 检查项 | 方法 |
|--------|------|
| `X-Device-Id` 随 refresh 请求发送 | Network tab 检查 |
| refresh 失败不触发二次刷新 | 模拟 refresh 失败 → 跳登录页 |
| Token 正确更新 | localStorage 中 accessToken 变新值 |

#### 联调场景 2 — 设备管理

```
操作:
  1. 登录（记录 deviceId = A）

预期结果:
  ├─ 返回 2 条设备记录

  └─ deviceId = A 的 current = false

操作:
  4. 调 DELETE /user/devices/{deviceId_A}

预期结果:
  ├─ 返回 200
```

### 第三阶段：秒杀异步逻辑闭环（核心难点）

**目标**: 正确处理"下单请求成功"与"抢购结果确认"的时差。

#### 核心时序

```
前端                               后端                 Kafka+WS
 │                                   │                    │
 ├─ 用户点击"立即抢购"                │                    │
 ├─ 按钮 → Loading + "排队中..."     │                    │
 ├─ POST /seckill/order ────────────▶│ Redis Lua 扣库存    │
 │◀── {"result":"ok","orderNo":N} ───│                    │
 │                                   ├─ send Kafka ──────▶│
 │                                   │                    ├─ INSERT order
 │                                   │                    ├─ gRPC → WS
 │◀── SEC_KILL_RESULT ────────────────────────────────────│
 │     {orderNo:N, ok:true}                                 │
 │                                   │                    │
 ├─ 按钮 → "抢购成功！"              │                    │
 └─ 跳转订单详情                     │                    │
```

#### 联调场景 — 完整抢购链路

```
前提: 已从 GET /seckill/activity/list 拿到活动列表，存在 PROCESSING 状态的活动

操作:
  1. 点击"立即抢购"
  2. 观察按钮 → 立即进入 Loading 态，文字变 "排队中..."

验证检查点:
  ├─ 按钮不可点击（pointer-events: none 或 disabled）
  └─ 请求 Header 包含 X-Idempotency-Key

操作:
  3. POST /seckill/order 返回 {"result":"ok","orderNo":"1234567890"}

验证检查点:
  ├─ 按钮保持 Loading，不变回"立即抢购"
  └─ 前端在 Map<orderNo, callback> 中记录此 orderNo

操作:
  4. 等待 WS SEC_KILL_RESULT

验证检查点（成功）:
  ├─ 收到 {orderNo:"1234567890", ok:true}
  ├─ 匹配到 Map 中的记录
  ├─ 按钮变 "抢购成功！" 绿色 + 跳跃动画
  └─ 3s 后跳转订单详情

验证检查点（失败）:
  ├─ 收到 {orderNo:"1234567890", ok:false, reason:"..."}
  ├─ 按钮变 "已售罄" 灰色
  └─ Toast 提示失败原因
```

#### 异常场景联调

| 场景 | 操作 | 预期 |
|------|------|------|
| 重复下单 | 快速双击抢购（前端未防抖） | 后端返回 `code:1010, message:"已参与过该活动"` |
| 库存刚耗尽 | 最后一个库存后发起 | `code:1009, message:"库存不足"` |
| 活动未开始 | 在 startTime 前下单 | `code:400, message:"不在活动时间范围内"` |
| WS 推送丢失 | 下单后前端未收到 SEC_KILL_RESULT | 前端设置超时（15s+），超时后调 `GET /seckill/order/{orderNo}` 查询状态 |

**关键代码**: 前端 orderNo 匹配器

```javascript
const orderCallbacks = new Map()  // orderNo → callback

const placeOrder = async (activityId) => {
  const res = await http.post('/seckill/order', { activityId })
  if (res.data.result !== 'ok') throw new Error(res.data.result)

  const orderNo = res.data.orderNo
  buttonStatus.value = 'QUEUING'

  // 注册 WS 回调
  await new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      orderCallbacks.delete(orderNo)
      reject(new Error('timeout'))
    }, 15000)

    orderCallbacks.set(orderNo, (msg) => {
      clearTimeout(timer)
      msg.ok ? resolve(msg) : reject(new Error(msg.reason))
    })
  })
}

// WS message handler
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data)
  if (msg.type === 'SEC_KILL_RESULT') {
    const cb = orderCallbacks.get(msg.data.orderNo)
    if (cb) {
      cb(msg.data)
      orderCallbacks.delete(msg.data.orderNo)
    }
  }
}
```

### 第五阶段：WebRTC 推流联调（新增）

**目标**: 完成浏览器摄像头采集 → WHEP 信令 → 媒体服务器 → 观众端播放的全链路。

#### 前置条件

| 依赖 | 说明 |
|------|------|
| STUN 服务器 | Google 公共 `stun:stun.l.google.com:19302` |
| TURN 服务器（可选） | 生产必配，开发环境同一内网可跳过 |
| 媒体服务器 | SRS / Janus / Mediasoup（开发环境本地部署） |
| HTTPS | `getUserMedia` 要求 HTTPS（`localhost` 除外） |

#### 联调场景 1 — 摄像头初始化

```
操作:
  1. 主播打开 StudioPage（B端 /streamer/panel）
  2. 浏览器弹出摄像头权限提示 → 点击"允许"

预期结果:
  ├─ 本地 video 预览画面出现
  ├─ pusherStore.status = 'READY'
  └─ 开发者工具 Console 无 getUserMedia 相关报错

异常场景:
  ├─ 用户拒绝权限 → 提示"请允许摄像头访问后重试"
  └─ 无摄像头设备 → 提示"未检测到摄像头"
```

#### 联调场景 2 — WHEP 信令握手

```
操作:
  1. 先调 POST /live/room/start 开播（获取 roomId）
  2. 点击"开始直播"按钮

预期结果（Network tab）:
  ├─ POST /live/webrtc/push (Content-Type: application/sdp)
  ├─ 请求体为 SDP Offer（v=0 开头...）

验证检查点:
  ├─ pusherStore.sessionId 有值
```

#### 联调场景 5 — 异常场景

| 场景 | 操作 | 预期 |
|------|------|------|
| 推流中断 | 断网 10s | `PC.onconnectionstatechange` → 'failed' → pusherStore.status = 'ERROR' → Toast "推流异常" |
| 权限被拒 | 第二次打开时浏览器已拒绝 | initCamera 抛 `NotAllowedError` → 提示引导用户开启权限 |
| 信令超时 | 媒体服务器无响应 | WHEP 请求 5s 超时 → Toast "连接媒体服务器失败" |
| 设备切换 | 摄像头从前置切后置 | `switchCamera()` 释放旧流 → 重新 `getUserMedia` → 预览更新 |

#### 避坑清单

| # | 坑 | 现象 | 解决 |
|---|-----|------|------|
| 1 | **镜像问题** | 主播预览是反的 | CSS `transform: scaleX(-1)` 仅本地预览，推流不变 |
| 2 | **回声啸叫** | 主播同时打开自己直播间 | 逻辑限制：主播 UI 不连接自己房间的 WS 播放流 |
| 3 | **HTTPS 缺失** | `getUserMedia` 返回 `undefined` | 开发环境用 `https://localhost` 或内网 HTTPS 证书 |
| 4 | **ICE 穿透失败** | `connectionState` 卡在 'connecting' | 部署 TURN 服务器或在同一内网测试 |
| 5 | **权限状态持久化** | 用户之前拒绝过，现在点了没反应 | `navigator.permissions.query({name:'camera'})` 检测权限状态，给出引导 |

## 四、接口字段对齐明细

### 4.1 注册 `POST /auth/register`

| 前端字段 | 后端字段 | 类型 | 校验 | 说明 |
|---------|---------|------|------|------|
| `username` | `username` | string | 4~50 位，必填 | 不能重复 |
| `password` | `password` | string | ≥8 位，必填 | 明文，后端 BCrypt |
| `phone` | `phone` | string | 手机号正则，非必填 | `^1[3-9]\d{9}$` |

```json
{"username":"test1234","password":"12345678","phone":"13800138000"}
```

**⚠️ 防重**: Header 带 `X-Idempotency-Key: uuid`，防止双击提交。

### 4.2 登录 `POST /auth/login`

| 前端字段 | 后端字段 | 类型 | 校验 |
|---------|---------|------|------|
| `username` | `username` | string | 1~50 位 |
| `password` | `password` | string | 1~255 位 |

```json
{"username":"test1234","password":"12345678"}
```

**⚠️ 必填 Header**: `X-Device-Id`（缺了返回 400）。

**响应**:

```json
{
  "accessToken": "eyJ...",    // 存 localStorage，15min
  "refreshToken": "rft_xxx",  // 存 localStorage，7天
  "expiresIn": 900,
  "tokenType": "Bearer"
}
```

### 4.3 Token 刷新 `POST /auth/refresh`

```json
{"refreshToken": "rft_xxx"}
```

**⚠️ Rotation**: 后端收到旧 token 后立即作废，发新的一对。同一个 token 并发刷新只有一次成功。

### 4.4 开播 `POST /live/room/start`

| 前端字段 | 后端字段 | 说明 |
|---------|---------|------|
| `title` | `title` | ≤80 字，必填 |
| `category` | `category` | ≤20 字 |
| `coverColor` | `coverColor` | 封面色值 |
| `sessionId` | `sessionId` | WebRTC 推流会话 ID（选填，先调 WHEP 再开播） |

```json
{"title":"今晚吃鸡","category":"游戏","coverColor":"#FF2C55"}
```

**⚠️ 幂等**: 同一主播已有直播中房间则复用，不新建。

**⚠️ 权限**: 需 `X-User-Role` ≥ 2（ANCHOR/ADMIN），否则 403。

**⚠️ 开播时序**: 前端流程为先调 `POST /live/webrtc/push` 完成 WHEP 握手，再调此接口绑定推流会话到直播间。`sessionId` 字段用于关联。

### 4.5 抢购下单 `POST /seckill/order` — ⚠️ **核心高并发接口**

```json
{"activityId": 1}
```

**响应**:

```json
{"result":"ok","orderNo":"9876543210"}
```

| result | 含义 | 前端行为 |
|--------|------|---------|
| `"ok"` | 库存扣减成功 | Loading → 等待 WS SEC_KILL_RESULT |
| 抛异常 | 失败 | 显示错误提示，恢复按钮 |

**⚠️ 前端防重**: 按钮点击后立即 `disabled + loading`，不可二次点击。
**⚠️ 代码防重**: 后端 Redis Lua `SETNX` + MySQL `UNIQUE(activity_id, user_id)`。
**⚠️ 异步确认**: `result:"ok"` ≠ 下单成功，靠 WS `SEC_KILL_RESULT` 确认。

### 4.6 订单列表 `GET /seckill/order/list`

```json
[{
  "orderNo": "9876543210",
  "activityId": 1,
  "seckillPrice": 0.01,
  "status": 0,          // 0待支付 1已支付 2已取消 3已退款
  "createdAt": "...",
  "paidAt": null,
  "cancelledAt": null

```

**⚠️ 待支付倒计时**: 基于 `createdAt + 15min - serverNow()`，超时后自动消失（后端超时取消扫描）。

## 五、WebSocket 消息协议

### 5.1 连接

```
ws://host:8080/ws/live/{roomId}?token={jwt}&deviceId={uuid}
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `roomId` | 是 | 路径参数 |
| `token` | 否 | 缺省为匿名连接 |
| `deviceId` | 否 | — |

### 5.2 服务端 → 客户端

#### CONNECTED — 连接成功

```json
{"type":"CONNECTED","data":{"anonymous":false,"displayName":"user_1","online":42}}
```

#### AUTH_OK / AUTH_FAILED — 认证升级结果

```json
{"type":"AUTH_OK","data":{"userId":1,"role":1,"displayName":"user_1"}}
{"type":"AUTH_FAILED","data":{"reason":"Token 无效或已过期"}}
```

#### NEED_AUTH — 匿名操作被拒

```json
{"type":"NEED_AUTH","data":{"reason":"请先登录后再操作"}}
```

#### PONG — 心跳回复

```json
{"type":"PONG","data":{}}
```

#### BARRAGE — 弹幕广播

```json
{"type":"BARRAGE","data":{"userId":1,"username":"user_1","content":"666","timestamp":1712345678000}}
```

**前端**: `transition-group` 滑入动画，新消息从底部进入。

#### GIFT — 礼物广播

```json
{"type":"GIFT","data":{"userId":1,"username":"user_1","giftId":1,"quantity":1,"timestamp":1712345678000}}
```

**前端**: 聊天面板送礼文字 + **全屏礼物特效** + **主动刷新排行榜**。

#### SEC_KILL_RESULT — 秒杀结果确认 ⚠️

```json
{"type":"SEC_KILL_RESULT","data":{"orderNo":"9876543210","ok":true,"reason":"success","message":"抢购成功","timestamp":1712345678000}}
```

**⚠️ 联调难点**: 前端需将 `orderNo` 与之前 `POST /seckill/order` 的返回值匹配。

#### ROOM_CLOSED — 直播结束

```json
{"type":"ROOM_CLOSED","data":{"roomId":1}}
```

**前端**: 弹出提示，3s 后连接被后端强制关闭。

#### KICK — 被踢下线 ⚠️

```json
{"type":"KICK","data":{"reason":"DEVICE_KICKED"}}
```

**⚠️ 前端**: 断开 WS → 全屏遮罩"您已在别处登录" → 跳转 `/login`。

### 5.3 客户端 → 服务端

| 消息 | 频率 | JSON |
|------|------|------|
| PING | 每 30s | `{"type":"PING"}` |
| AUTH | 运行时升级 | `{"type":"AUTH","data":{"token":"..."}}` |
| BARRAGE | 用户触发 | `{"type":"BARRAGE","data":{"content":"666"}}` |
| GIFT | 用户触发 | `{"type":"GIFT","data":{"giftId":1,"quantity":1}}` |
| SEC_KILL | 秒杀（预留） | `{"type":"SEC_KILL","data":{"activityId":1}}` |

### 5.4 心跳生命周期

```
连接建立 → 每 30s 发 PING → 收 PONG → 续命
                                   ↘ 60s 无 PONG → 后端关闭 → 前端触 onclose
```

### 5.5 WS 断线重连策略

```javascript
let reconnectTimer = null
let retryCount = 0
const MAX_RETRY = 5

function connect() {
  ws = new WebSocket(url)

  ws.onopen = () => { retryCount = 0 }

  ws.onclose = () => {
    if (retryCount < MAX_RETRY) {
      const delay = Math.min(1000 * 2 ** retryCount, 10000)
      reconnectTimer = setTimeout(connect, delay)
      retryCount++
    }
  }
}

onUnmounted(() => { clearTimeout(reconnectTimer); ws?.close() })
```

## 六、联调排雷清单

基于后端技术债务文档，联调时特别关注以下 6 个暗坑：

| # | 坑 | 现象 | 排查方向 |
|---|-----|------|---------|
| 1 | **JJWT + Gson Double** | 后端 `claims.get("role", Integer.class)` 抛异常，前端拿不到用户信息 | 后端已修复为 `((Number) claims.get("role")).intValue()`，联调时确认该代码已部署 |
| 2 | **Gateway 路由路径** | 路由配置在旧路径 `spring.cloud.gateway.routes` 时路由不生效 | 确认后端用新路径 `spring.cloud.gateway.server.webflux.routes` |
| 3 | **Jackson 包名** | 如果前端直接反序列化后端 JSON 报错 | Spring Boot 4.x 下包名 `com.fasterxml.jackson` → `tools.jackson`，前端不受影响 |
| 4 | **X-Idempotency-Key 遗漏** | 注册/登录被二次提交 | 前端必须生成 UUID 并传 Header |
| 5 | **X-Device-Id 遗漏** | 登录返回 400 | 确认 Axios 拦截器已注入 |
| 6 | **refresh catch 死循环** | 刷新失败后重复刷新 → 页面卡死 | 刷新接口收到 401 时不触发拦截器的刷新逻辑 |
| 7 | **WebRTC 推流 HTTPS** | `getUserMedia` 返回 `undefined` | 确保开发环境用 `https://localhost` |
| 8 | **WebRTC ICE 失败** | 推流状态卡在 CONNECTING | 联调环境使用同一内网或配置 TURN |
| 9 | **WebRTC 镜像** | 主播预览是反的，推流出去也是反的 | 前端 `scaleX(-1)` 仅作用于 preview video 标签，不修改 track |
