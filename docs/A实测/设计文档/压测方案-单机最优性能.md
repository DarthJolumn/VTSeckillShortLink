# LiveMall 单机压测方案 — 16GB RAM 最优性能

## 一、系统架构

| 服务 | 端口 | 特征 | 瓶颈类型 |
|---|---|---|---|
| Gateway | 8080 | WebFlux/Netty, JWT 解析, 路由转发 | CPU + 连接数 |
| User | 8081 | bcrypt (CPU 密集), JWT 签发 | CPU |
| Seckill | 8082 | Redis Lua 扣库存 + Caffeine L1 + DB | Redis + 网络 |
| Leaderboard | 8084 | Redis ZSet 操作 | Redis |
| WebSocket | 8083 | DB 查询 + WS 连接管理 | 连接数 + DB |

**公共依赖**：MySQL + Redis (192.168.147.132) + Nacos (192.168.147.132:8848)

---

## 二、流量模型（模拟线上）

### 比例设计

| 场景 | 占比 | 接口 | 说明 |
|---|---|---|---|
| 秒杀抢购 | **40%** | `POST /seckill/order` | Redis Lua + Caffeine, 核心压测目标 |
| 排行榜加分 | **20%** | `POST /leaderboard/score` (或 Dubbo addScore) | Redis ZSet, 高频写 |
| 排行榜查询 | **15%** | `GET /leaderboard/top?activityId=1` | Redis ZREVRANGE, 纯读 |
| 直播间列表 | **10%** | `GET /live/rooms` | DB 查询, 轻量读 |
| 登录 | **10%** | `POST /auth/login` | bcrypt, CPU 重 |
| 注册 | **5%** | `POST /auth/register` | bcrypt, 最重 |

### 为什么这个比例

线上真实场景：大量用户刷直播间/排行榜 + 秒杀开抢瞬间涌入。登录注册是低频操作，但 bcrypt 占 CPU，少量即可产生压力。

## 三、测试阶段

### Phase 0：数据准备

```sql
-- 1. 注册用户（已有 reg-users.csv: 1000 个）
-- 2. 创建秒杀活动（status=1, 进行中）
--    POST /seckill/activity  → 记录 activityId
-- 3. 初始化库存（上架时自动）
-- 4. 排行榜预热
--    循环调用 addScore 写入 1000 个用户的分数
-- 5. 创建直播间（至少 10 个 status=1）
```

### Phase 1：单接口摸底（找各服务上限）

目标：**每个服务独立压**，找到单机极限 QPS。

| # | 接口 | 起步线程 | 递增 | 持续时间 | 观察 |
|---|---|---|---|---|---|
| 1A | `GET /leaderboard/top` | 500 | +500 直到错误率 >5% | 60s | Redis 读上限 |
| 1B | `POST /seckill/order` | 500 | +500 | 60s | Redis Lua + Caffeine 上限 |
| 1C | `GET /live/rooms` | 500 | +500 | 60s | DB 读上限 |
| 1D | `POST /auth/login` | 200 | +200 | 60s | bcrypt CPU 上限 |

每个测试同时跑 `jstat -gcutil <PID> 2000` 记录 GC。

### Phase 2：混合流量（模拟线上）

按流量模型比例，**逐步加压**：

| 轮次 | 总线程 | 秒杀 | 排行榜写 | 排行榜读 | 直播间 | 登录 | 注册 |
|---|---|---|---|---|---|---|---|
| 2A | 1000 | 400 | 200 | 150 | 100 | 100 | 50 |
| 2B | 3000 | 1200 | 600 | 450 | 300 | 300 | 150 |
| 2C | 5000 | 2000 | 1000 | 750 | 500 | 500 | 250 |
| 2D | 8000 | 3200 | 1600 | 1200 | 800 | 800 | 400 |

每轮跑 **120s**（10s ramp-up + 110s 稳态），记录：
- JMeter 聚合报告（QPS / p99 / 错误率）
- 各服务 jstat（YGC 次数/时长、FGC、Old%）
- 任务管理器（CPU / 内存）

**停止条件**：错误率 >10% 或 p99 >2s

### Phase 3：调参后复测

用 Phase 2 中最优的线程组合，换 JVM 参数后重跑，对比 QPS 提升。

## 四、JVM 参数调优

### 4.1 内存分配（16GB 总量）

5 个 Java 服务 + MySQL + Redis + Nacos + JMeter + IDE，内存紧张。

| 服务 | G1 推荐堆 | ZGC 推荐堆 | 理由 |
|---|---|---|---|
| Gateway | `-Xms1g -Xmx1g` | `-Xms1g -Xmx1g` | 无状态转发，1G 足够 |
| User | `-Xms2g -Xmx2g` | `-Xms2g -Xmx2g` | bcrypt 对象分配大 |
| Seckill | `-Xms2g -Xmx2g` | `-Xms2g -Xmx2g` | Caffeine 缓存 + Redis 客户端 |
| Leaderboard | `-Xms1g -Xmx1g` | `-Xms1g -Xmx1g` | 纯 Redis 操作，内存占用小 |
| WebSocket | `-Xms2g -Xmx2g` | `-Xms2g -Xmx2g` | WS 连接 + DB 查询 |
| **合计** | **8GB** | **8GB** | 留 8GB 给 OS + MySQL + Redis + JMeter |

### 4.2 G1 调参

```
# 所有服务通用基础参数
-Xms{size} -Xmx{size}
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=4m           # 2G 堆推荐 4M region（默认 1M 太小）
-XX:InitiatingHeapOccupancyPercent=45  # 默认 45，触发并发标记的阈值
-XX:ConcGCThreads=2               # 16GB 机器通常 4~8 核，留 2 核给并发 GC
-XX:ParallelGCThreads=4           # STW 阶段并行线程数
-XX:+ParallelRefProcEnabled       # 并行处理引用，减少 STW
-XX:MetaspaceSize=256m            # 避免元空间频繁 GC
-XX:+UseStringDeduplication       # G1 专属，减少重复字符串
```

**调参思路**：
1. 先跑默认 G1，记录基线
2. 如果 YGC 频繁（>10次/min）→ 加大 Young 区 `-XX:G1NewSizePercent=30`
3. 如果 Mixed GC 不够快 → `-XX:G1MixedGCCountTarget=16`
4. 如果 FGC 出现 → 堆不够或内存泄漏，加堆

### 4.3 ZGC（分代）调参

```
# 所有服务通用基础参数
-Xms{size} -Xmx{size}
-XX:+UseZGC
-XX:+ZGenerational              # JDK 21+ 分代 ZGC
-XX:SoftMaxHeapSize={size}      # 软上限，ZGC 会尝试回收到此值以下
-XX:ConcGCThreads=2
-XX:ParallelGCThreads=4
-XX:MetaspaceSize=256m
```

**ZGC vs G1 关键差异**：
- ZGC 暂停时间 **<1ms**（G1 目标 200ms）
- ZGC 吞吐量略低（~5-10%），因为着色指针的开销
- ZGC 不需要调 `MaxGCPauseMillis`、`G1HeapRegionSize` 等
- ZGC 的 `SoftMaxHeapSize` ≈ G1 的堆大小目标

**调参思路**：
1. 先用默认 ZGC 跑 Phase 2
2. 如果 CPU 使用率高 → 减 `ConcGCThreads` 到 1
3. 如果 Old 区占用持续升高 → 减 `SoftMaxHeapSize` 到 80% 堆大小
4. 对比 G1：重点看 **p99 延迟** 和 **GC 暂停时间**

## 五、对比维度

| 指标 | 怎么看 | 工具 |
|---|---|---|
| **吞吐量** | JMeter Throughput (req/s) | JMeter 聚合报告 |

| **GC 频率** | YGC/min、FGC 次数 | `jstat -gcutil <PID> 2000` |

| **错误率** | HTTP 错误 / Connection refused | JMeter 聚合报告 |

## 六、执行顺序

```
1. Phase 0：造数据
2. Phase 1：单接口摸底（G1 默认参数）
3. Phase 2A→2D：混合流量逐步加压（G1 默认参数）→ 记录基线
4. Phase 3-G1：按 §4.2 调 G1 参数 → 重跑最优轮次
5. Phase 3-ZGC：切 ZGC（§4.3）→ 重跑最优轮次
6. 汇总对比：G1 默认 vs G1 调优 vs ZGC 调优
```

## 七、注意事项

1. **所有服务从 IntelliJ 启动**，VM options 里加 JVM 参数，重启生效
2. **jstat 同时跑**：每个服务一个终端 `jstat -gcutil <PID> 2000`
3. **JMeter 端口耗尽**：已设 `netsh dynamicport start=10000 num=55535`
4. **JMeter 连接复用**：`user.properties` 已配 `httpclient.reset_state_on_thread_group_iteration=true`
5. **Gateway Netty**：已配 `max-connections: 16384`
6. **压测时关掉非必要程序**（浏览器、其他 IDE 项目），释放 CPU 和内存
7. **Redis/MySQL 在远程机器 (132)**：网络延迟约 1-2ms，是天然瓶颈，本地调参无法消除
