# 前端对接后端注意事项

> 后端各模块中有一些前端必须了解的特性和约束，遗漏会导致联调失败或生产问题。

---

## 一、JWT 双 Token 机制

后端采用 **双 Token + Rotation 刷新** 模式：

| Token | TTL | 存储位置 | 说明 |
|-------|-----|---------|------|
| `accessToken` | 15min | 前端内存/LocalStorage | 请求时放 `Authorization: Bearer <token>` |
| `refreshToken` | 7天 | LocalStorage | 仅用于刷新，不由网关鉴权 |

### 前端必须做

```
axios 响应拦截器:

1. 所有请求在 request interceptor 注入 Authorization header
2. 收到 401 → 调 POST /auth/refresh 拿新 Token
3. 刷新成功 → 用新 Token 重放原请求
4. 刷新失败 → 清空 Token，跳转 /login

注意: 避免 401 + 刷新 死循环（refresh 接口本身不再触发刷新）
```

### 刷新接口

```http
POST /auth/refresh
Content-Type: application/json

{"refreshToken": "rft_xxx"}
```

### 请求头模板

```javascript
// axios request interceptor
config.headers.Authorization = `Bearer ${accessToken}`
config.headers['X-Device-Id'] = deviceId
```

## 二、X-Device-Id 设备标识

**所有登录、踢设备、设备管理功能依赖此字段**。

| 接口 | X-Device-Id 要求 |
|------|-----------------|
| `POST /auth/login` | **必填** — 后端记录设备 session |
| `POST /auth/refresh` | 自动继承 |
| `POST /auth/logout` | 从 refresh token 解析 |
| `GET /user/devices` | 可选 — 标记当前设备 |
| 其他需鉴权的请求 | 建议传，用于 AuthInterceptor 设备在线检查 |

### 前端实现

```javascript
// 设备指纹：首次访问生成 UUID，存 LocalStorage 持久化
const deviceId = localStorage.getItem('device_id')
  || crypto.randomUUID()
localStorage.setItem('device_id', deviceId)
```

## 三、WebSocket 双模式（匿名 + 认证）

`/ws/live/{roomId}` 支持**无 token 匿名连接**，连接后可通过 `AUTH` 消息升级。

### 连接参数

```
ws://host:8080/ws/live/{roomId}?token=xxx&deviceId=xxx
```

- `token`: 可选，缺省则为匿名连接
- `deviceId`: 可选

### 运行时升级（AUTH 消息）

```json
// 前端 → 后端
{"type":"AUTH","data":{"token":"eyJ..."}}

// 后端 → 前端（成功）
{"type":"AUTH_OK","data":{"userId":1,"role":1,"displayName":"user_1"}}

// 后端 → 前端（失败）
{"type":"AUTH_FAILED","data":{"reason":"Token 无效或已过期"}}
```

### 前端必须处理

- 匿名用户只能收 BARRAGE/CONNECTED，发消息需先 AUTH 升级
- token 过期 → 尝试 refresh → 用新 token 重新 AUTH
- `NEED_AUTH` 消息 → 提示用户登录

## 四、WebSocket 心跳保活

| 参数 | 值 |
|------|-----|
| 客户端 PING 间隔 | 30s |
| 服务端超时阈值 | 60s |
| 服务端扫描间隔 | 10s |

```javascript
// 终端超过 60s 无消息 → 服务端强制关闭连接

// 前端定时器
setInterval(() => {
  ws.send(JSON.stringify({type: "PING"}))
}, 30000)

// 收到回复
// {"type":"PONG","data":{}}
```

## 五、WebSocket KICK（设备被踢）

### 触发场景

1. 用户手动踢设备 `DELETE /user/devices/{deviceId}`
2. 同一账号新登录踢旧设备（待实现）

### 后端消息格式

```json
{"type":"KICK","data":{"reason":"DEVICE_KICKED"}}
```

### 前端收到 KICK 后的处理

1. 断开 WebSocket 连接
2. 弹出全屏遮罩 "您的账号在另一台设备登录，您已被迫下线"
3. 提供 "重新登录" 按钮 → 跳转 `/login`
4. 清空 JWT Token 和用户状态

## 六、秒杀下单防重（前端防抖 + 后端双重校验）

### 后端防重机制

| 层级 | 机制 | 说明 |
|------|------|------|
| Redis Lua | `SETNX ordered:{actId}:{userId}` 24h | 原子性防止重复扣库存 |
| MySQL | `UNIQUE(activity_id, user_id)` | 一人一单兜底 |

### 前端要求

- 点击"立即抢购"后按钮立即进入 **Loading 状态**，禁止二次点击
- 等待 `POST /seckill/order` 返回结果后再恢复按钮
- 结果映射:

```json
{"result":"ok","orderNo":"123456"}           → 抢购成功，等待 SEC_KILL_RESULT
{"code":1009,"message":"库存不足"}            → 售罄
{"code":1010,"message":"已参与过该活动"}       → 已抢过
```

### 秒杀结果异步推送

`POST /seckill/order` 返回 `"ok"` 只表示库存扣减成功，订单可能还在 Kafka 中。

最终结果需要通过 **WebSocket** `SEC_KILL_RESULT` 消息确认：

```json
{"type":"SEC_KILL_RESULT","data":{"orderNo":"123456","ok":true,"reason":"success"}}
```

前端需要将 `orderNo` 与 WS 推送的消息做 **匹配**。

## 七、X-Idempotency-Key 幂等键

部分接口支持幂等，前端需生成唯一 Key。

| 接口 | 幂等说明 |
|------|---------|
| `POST /auth/register` | 两次携带相同 key 只注册一次 |
| `POST /auth/login` | 5min 内返回相同结果 |

```javascript
// 生成幂等 key
const idempotencyKey = crypto.randomUUID()

// 请求头
headers['X-Idempotency-Key'] = idempotencyKey
```

## 八、时间同步问题

### 签名验签时间窗口

```
|前端时间 - 后端时间| > 5min → 签名验签失败 "Timestamp expired"
```

如果前端要调用需要签名的接口（如开放 API），需确保客户端时间与 NTP 同步，或从后端获取时间戳。

### 秒杀倒计时

- 倒计时应以**后端时间**为准，不要在 `new Date()` 上做
- 建议登录时获取 `Date` header 或通过 NTP 对齐
- 活动开始/结束时间使用后端返回的 `startTime`/`endTime`（LocalDateTime → epoch ms）

## 九、请求头速查表

| Header | 必填 | 说明 | 涉及接口 |
|--------|------|------|---------|
| `Authorization: Bearer <token>` | 鉴权接口 | JWT | 除 public 外所有 |
| `X-Device-Id` | 登录时 | 设备指纹 | `/auth/login`, `/user/devices` |
| `X-User-Id` | — | 网关注入，前端不应手动设置 | 响应式（后端读取） |
| `X-User-Role` | — | 网关注入 | 响应式 |
| `X-Idempotency-Key` | 可选 | 幂等 key | `/auth/register`, `/auth/login` |

## 十、角色与权限路由

角色码决定前端可访问的页面：

| 角色 | code | 页面 |
|------|------|------|
| `AUDIENCE`（观众） | 1 | C 端所有页面 |
| `ANCHOR`（主播） | 2 | C 端 + B 端工作台/秒杀管理 |
| `ADMIN`（管理员） | 3 | 全部 |

### 前端路由守卫

```javascript
router.beforeEach((to) => {
  if (to.meta.roles && !to.meta.roles.includes(user.role)) {
    return '/403' // 无权限
  }
})
```

B 端路由示例:

| 路由 | 权限 | 说明 |
|------|------|------|
| `/streamer/panel` | ANCHOR / ADMIN | 主播工作台 |
| `/streamer/seckill` | ANCHOR / ADMIN | 秒杀活动管理 |

## 十二、是否开播判断

主播 `/streamer/panel` 页面进入时需调用:

```http
GET /live/my-active-room
X-User-Id: {userId}
```

- 返回 `data != null` → 已在直播，显示"结束直播"按钮
- 返回 `data == null` → 未直播，显示"开始直播"按钮
